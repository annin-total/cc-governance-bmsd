# 調書テンプレート（大まかな型。厳格にしない）

統一感を持たせるための型であり、「何を書き、何を書かないか」の基準でもある。
結論を先頭に置き、冗長に書かない。見出しは足し引きしてよい。1〜2 ページに収まる量を目安にする。

## 書くこと
- 重そうな要因と、その確度（観測／推定／利用者談）
- 利用の全体像（モデルのファミリー比、effort の分布、トークン量は種別ごと、セッションの長さと頻度）
- 利用者から聞いた背景（抽象化したもの）
- 改善の候補（控えめに。断定しない）
- 制約（欠損、読めなかったもの、除外したもの、検証で残った注意）

## 書かないこと
- 本文・パス・コマンド・リポジトリ名・社内固有名詞
- 金額、単価、トークン種別の合算値
- 全件の一覧、検証や分析の過程
- 利用者を責める表現、断定

# Claude Code 利用ヒアリング調書

対象者: ＜氏名＞　／　作成日: ＜YYYY-MM-DD＞　／　期間: 直近＜N＞日（この端末の履歴のみ）
位置づけ: 履歴からの概算・推測。参考資料であり、数値は「だいたい」。

## 1. 結論
＜重そうな要因を大きい順に 2〜4 行。それぞれに確度を添える。例:「長いセッションの継続が主因と推定（観測）」＞

## 2. 利用の全体像
- 期間・セッション数・稼働日数: ＜＞
- モデルのファミリー比: ＜opus / sonnet / haiku / fable / 不明＞
- effort の分布: ＜読めた範囲で。読めなければ「不明」＞
- トークン量（種別ごと。合算しない）: 新規入力 ＜＞／出力 ＜＞／キャッシュ書き込み ＜＞／キャッシュ読み込み ＜＞
- スキル・拡張の使われ方: ＜よく使うもの、発火の傾向、導入数＞

## 3. 重さの要因
＜要因ごとに「観測 → 解釈 → 確度」を 2〜3 行。目安として全体の約 1 割以上を占めるものだけ構造まで掘る。同意を得て具体化した場合はその旨を書く＞

## 4. 利用者からの補足
＜聞いた業務背景・使い方を抽象化して数行＞

## 5. 改善の余地（候補）
＜観測に対応づけて数件。「〜かもしれない」の温度感。業務上必要な使い方ならそれ自体を所見にする＞

## 6. 制約・注意
＜保持期間による欠損／除外した自セッション／読めなかったデータ／検証で残った指摘＞
