# /hearing スキル設計書（たたき台）

Claude Code の利用コストが高い利用者の端末で実行し、「なぜコストが高いか」をローカルの情報から分析して、
ガバナンス担当向けの調査結果報告書（Markdown 1 ファイル）を作る独立スキルの設計。

**出典の表記**: 本書の事実はすべて起案時の調査メモ（非同梱）に拠る。メモはいずれも二次調査で、多くが Web ページの要約経由のため、
重要な値は実装前に原文で再確認する。表記は次の略号を使う。確認日はすべて 2026-10-01（当時の Claude Code 2.1.286）。

| 略号 | 内容 |
|---|---|
| [公式] | 公式ドキュメントと CHANGELOG の調査（costs / prompt-caching / commands / settings など） |
| [原因] | コストが高くなる原因と傾向の調査（公式、GitHub Issue、第三者による計測。二次情報を含む） |
| [ローカル] | ローカルデータ構造の調査（実機 1 台の transcript 観察と、Issue などの二次情報） |
| [スキル] | スキル・サブエージェント仕様の調査（公式ドキュメントの要約経由） |

「未確認」は、根拠が要約経由・単発・二次情報のいずれかにあたり、原文での裏付けが取れていないものを指す。

## 1. 目的と非目的

**目的**
- 利用者本人の端末にある履歴から、コストの**構造的な原因**（どの使い方・どの仕組みで消費が膨らんでいるか）を測り、説明する。
- 結果を、ガバナンス担当が読んで判断できる「調査結果」の形で 1 ファイルにまとめる。用途は抽象的なレベル（「大量のテスト出力を扱う開発作業」など）で書く。
- 観測から言える改善の余地を「候補」として控えめに添える。

**非目的**
- 請求額の確定。金額は概算にとどめ、正式な請求の代わりにはしない。
- 利用者の評価や監視。責める調子・断定口調で書かない。
- 本文（prompt・応答・メッセージ）、ファイルパス、コマンドの中身の収集と転記。
- 報告書の自動送信。送るのは利用者が内容を確認したあと、自分の手で行う。
- 複数の端末・組織全体の集計。対象は実行した端末 1 台の履歴だけ。
- 設定の自動変更（改善の実施）。

## 3. 全体ワークフロー

| 段階 | 入力 | 担当 | 出力（作業フォルダ内） |
|---|---|---|---|
| P0 準備・環境検出 | 起動引数（期間） | 監督役 | `env.json`（OS・スクリプト実行コマンド・Claude Code の版・設定ディレクトリ・氏名候補・期間・自セッション ID）、`progress.md` |
| P1 データ棚卸し | `env.json`、`references/schema.md` | 棚卸し担当 ×1 | `inventory.json`（ファイル一覧・サイズ・期間内か・行種の件数・版の分布）、`schema-check.md`（想定との差・測定不能になる指標） |
| P2 測定 | `inventory.json`、`references/metrics.md`・`schema.md` | 測定担当 ×N（ファイルを分担）＋統合 ×1 | `records/part-*.jsonl`（正規化レコード）→ `measure/*.json`（重複排除後の集計） |
| P3 観点別分析（並列） | `measure/*.json`、`references/lenses/*.md` | 分析担当 ×M（lens 群を分担） | `findings/<group>.md`（所定の形式。§6.3） |
| P4 統合・要約提示・補足質問 | `findings/*`、`references/questions.md` | 統合担当 ×1 が草案、監督役が提示と質問 | `summary.md`、`answers.md`（回答は抽象化して記録） |
| P5 報告書作成 | `summary.md`、`answers.md`、`measure/*`、`references/report-template.md` | 執筆担当 ×1 | `draft/report.md` |
| P6 検証 | `draft/report.md`、`measure/*`、`inventory.json` | 数値検証 ×1、文章検証 ×1（並列） | `review/numbers.md`、`review/text.md` |
| P7 修正 | `review/*` | 執筆担当 | `draft/report.md`（更新）→ P6 に戻る（上限は §9） |
| P8 最終確認・配置 | `draft/report.md` | 監督役 | 利用者が確認・修正したうえで、作業ディレクトリに報告書を 1 ファイルだけ置く |

- P0 で、このスキルを動かしている今のセッション（`${CLAUDE_SESSION_ID}` で取れる [スキル]）は分析対象から除き、その旨を報告書に書く。スキル自身の消費が結果を歪めないようにするため。
- P4 では、要約（数値の要点と、見えてきた使い方の像）を示したうえで 3〜5 問を尋ねる。`/usage` の貼り付けは求めない。起動時に利用者が自分から渡した場合だけ突き合わせに足す（§5.3）。
- P8 では報告書の全文を見せ、氏名・用途の表現を利用者が直せるようにする。送付は利用者が行うことを伝える。作業フォルダの削除を提案するのは、起動時に `cleanup` 引数が付いたときだけ（既定は何もしない。§14 Q6）。

## 4. サブエージェント構成

### 4.1 役割

| 役割 | 数 | 責務 | 書かないこと |
|---|---|---|---|
| 監督役（メイン会話） | 1 | 段階の進行、担当数の決定、progress.md、利用者との対話、最終判断 | 集計や文章作成そのもの |
| 棚卸し担当 | 1 | ファイル探索、期間判定、スキーマの照合、規模の見積もり | 本文の読み取り |
| 測定担当 | N | 割り当てられたファイルから正規化レコードを作る | 集計の解釈 |
| 統合（測定） | 1 | 全レコードを横断して重複を除き、集計する | 解釈 |
| 分析担当 | M | 割り当てられた lens 群を評価し、所見を書く | 担当外の lens |
| 統合（所見） | 1 | 所見の重複・矛盾をまとめ、寄与順に並べ、要約草案を作る | 利用者への質問 |
| 執筆担当 | 1 | 報告書の作成と修正 | 新しい分析 |
| 数値検証 / 文章検証 | 各 1 | §9 | 修正 |

### 4.2 担当数の決め方（既定値は `references/orchestration.md` で調整する）
- 測定担当 N: 期間内の jsonl の合計サイズで決める。目安は 50MB ごとに 1、最小 1・最大 4。数値は仮置きで、§13 の評価で決める（未確認）。分担はファイル単位で MECE にする。親セッションとその `subagents/` 配下は同じ担当に渡す。
- 分析担当 M: lens の `group` ごとに 1（初期は 4 群。§6.2）。データが小さければ（例: セッション 20 未満）群をまとめて 1〜2 にする。
- ファン・アウトは監督役からの 1 段だけにする。担当がさらにサブエージェントを起動することは禁止する（入れ子は既定で 3 層まで許される [スキル] が、コストと追跡しやすさを優先する）。
- モデル: サブエージェントには、使える環境なら `sonnet` を指定する。指定が拒否される・使えない環境では指定を外して親を継承する（フォールバック）。指定の有無と値は `references/orchestration.md` に置き、SKILL.md では起動の雛形から参照するだけにする。

### 4.3 受け渡し
- 受け渡しはすべて作業フォルダ上のファイルで行う。サブエージェントの応答本文は「出力ファイルのパスと 3 行以内の要約」に限る（監督役の文脈を太らせないため）。
- 起動時の指示には、作業フォルダの絶対パス、読むべき references、出力先、禁止事項（本文を読まない、パスや固有名詞を書き出さない）を必ず含める。雛形は `references/orchestration.md` に置く。
- 生成したスクリプトは `scripts/` に保存してから実行する。検証役がそれを読めるようにし、再現性を確保するため。

## 5. データ源とアクセス方針

### 5.1 読むもの（許可リスト方式）
| データ | 読む項目 | 用途 |
|---|---|---|
| `<設定ディレクトリ>/projects/**/*.jsonl`（`subagents/` 配下を再帰的に、`workflows/` を含む） | `type`、`timestamp`、`sessionId`、`isSidechain`、`agentId`、`version`、`requestId`、`uuid`、`message.id`、`message.model`、`message.usage` の数値項目、`message.stop_reason`、`content[].type`、`tool_use` の `name`、`tool_result` の**文字数だけ**、ファイル系ツールの入力のうち**拡張子だけ** | 測定の主データ [ローカル] |
| `subagents/agent-*.meta.json` | `agentType`、`spawnDepth`、`model`（`description` は読まない） | サブエージェントの種別 [ローカル] |
| `stats-cache.json` | `version`、モデル別トークン、日別の件数 | 突き合わせ（§5.3） |
| `settings.json`（ユーザー・プロジェクト） | `cleanupPeriodDays`、モデル・effort・キャッシュ TTL・auto-compact 関連のキーの有無と値、MCP サーバの**数** | 欠損期間の判定、lens の補助 |
| `cwd` | プロジェクトを不透明なラベル（P1, P2…）に置き換える目的でだけ使う。作業ファイルにも書き出さない | セッションのまとまり |

### 5.2 読まないもの
- `message.content` のテキストと thinking 本文、`toolUseResult`、`tool_use.input` の中身（拡張子の抽出を除く）。
- `history.jsonl`（入力した prompt の全文が入っている）、`ai-title`、`last-prompt`、`queue-operation` の本文 [ローカル]。
- 認証情報、`settings.json` の `env` の値（キー名は読んでよい）、MCP 設定の中身。
- 退避された旧 transcript（`.orphaned-*`、`*.superseded-*`）は集計に含めない。件数だけを数えて報告書に記載する（二重計上の恐れがあるため。未確認 [ローカル]）。

### 5.3 突き合わせ用の手元の集計値
- `stats-cache.json` はクリーンアップ後も残る集計値だが、版 4 と 5 で `dailyModelTokens` の意味が違う（二次 [ローカル]）。必ず版で分岐する。
- `/usage` は利用者が打つコマンドで、スキルから実行できるかは未確認。利用者に手間をかけさせないため、貼り付けは求めない（既定は `stats-cache.json` との照合だけ）。利用者が起動時に自分から渡した場合だけ、追加の突き合わせに使う。サブスクリプションの場合の数値はこの端末のローカル履歴に基づく概算で、24 時間 / 7 日の切り替えがある [公式]。公式の集計にも行の重複合算の不具合が過去にあった（二次 [ローカル]）。このため一致しなくても直ちに誤りとはみなさない。差の大きさと推定理由を書く。
- `/context` は今のセッションの内訳で、過去の履歴分析には寄与が小さい。既定では求めない。

### 5.4 取り扱いルール
- 作業フォルダに書いてよいのは数値・種別・ラベルだけ。本文、パス、コマンド、リポジトリ名は中間ファイルにも書かない。
- 用途カテゴリは構造の信号（ツールの構成比、拡張子の構成、セッションの長さと時間帯）と P4 の回答から導く。語彙は `references/privacy.md` の一覧から選ぶ（例:「アプリ開発」「データ分析」「文書作成」「調査」「運用・自動化」）。
- コストへの影響が非常に大きい場合も、構造の範囲で具体化するにとどめる（例:「1 回あたり数万トークンのログ出力を繰り返し読み込む作業」）。抽象度をどこまで下げるかは §14 Q10。

## 6. 観点（lens）一覧と拡張方法

### 6.1 前提
コストのほとんどは「文脈の長さ × リクエスト回数」の再読込と、キャッシュの再書き込みで決まる [原因]（公式の説明と単一ユーザーの実測に拠る）。このため指標の基本は、各リクエストの `input + cache_creation + cache_read`（文脈量）と単価の重み付けにする。

### 6.2 初期セット（優先度は [原因] の High/Med/Low を引き継ぐ）

| ID | 群 | 観点 | 検知指標 | データ源 | 誤検知の注意 | 優先 |
|---|---|---|---|---|---|---|
| L01 | 文脈 | 長時間セッション・`/clear` しない | セッション別のターン数、最終ターンの文脈量、Σcache_read の偏り | usage, timestamp | 長いのが妥当な作業もある。P4 で業務背景を確認する | High |
| L02 | キャッシュ | キャッシュ TTL 切れ | 間隔 > 5 分 / > 1 時間の直後の cache_creation の跳ね上がり、ヒット率 = cache_read / (input + cc + cr) | usage, timestamp, `cache_creation.ephemeral_*` | TTL は課金経路・主会話かサブエージェントかで違う [公式]。内訳が欠けた版では判定できない | High |
| L03 | キャッシュ | キャッシュを壊す操作 | 同一セッション内のモデル・版・effort・speed の変化の直後に、cache_read が急に下がる | model, version, effort, speed, usage | compaction など予定どおりの再構築と区別する | High |
| L04 | 並列 | サブエージェント | sidechain 由来のコスト比率、起動回数、立ち上がりの cache_creation | isSidechain, subagents/, meta.json | 親子で cache_creation が重複報告される可能性（二次・未確認）。冗長な作業を隔離して全体を下げている場合もある | High |
| L05 | 並列 | 並列・チーム実行 | 同じ時間帯に重なるセッション・エージェントの数 | timestamp, sessionId | 別端末の作業は見えない | High |
| L06 | 課金 | 高単価モデルの常用 | モデル別のコスト比率、単価の低いモデルで足りそうなターンの割合（出力が短い・ツール 1 回だけなど） | model, usage | 「足りそう」は推定。断定しない | High |
| L07 | 自動 | 無人実行・ループ・定期実行 | 人の入力を挟まない連続ターン、等間隔の起動、深夜帯の継続 | timestamp, `origin`/`turnOrigin` の種別 | 種別のフィールドは版によって違う（未確認） | Med |
| L08 | キャッシュ | 版に依存するキャッシュ異常 | 版ごとのヒット率の分布、特定の版で急に下がるか | version, usage | 過去の不具合報告は単独の計測者によるもの [原因]。版名だけで断定しない | Med |
| L09 | 課金 | 拡張思考・effort | thinking_tokens / output_tokens、effort の分布 | `output_tokens_details`, effort | effort とトークン量の関係は情報源間で結論が割れている [原因] | Med |
| L10 | 文脈 | 大きなツール結果 | ツール種別ごとの結果の文字数分布、大きな結果の直後の cache_creation、拡張子の構成 | tool_use.name, tool_result の長さ | 文字数とトークン数は比例しない。目安として扱う | Med |
| L11 | 文脈 | MCP・常駐する定義 | 各セッション初回の cache_creation（基準値）、MCP サーバ数 | usage, settings | 現行は遅延ロードが既定で寄与は縮小 [公式]。ゲートウェイ経由では大きい | Med |
| L12 | 課金 | 高速モード・割増 | `usage.speed` が標準以外の比率 | usage.speed | 単価は料金表で確認する | Med |
| L13 | 文脈 | Web 検索・取得 | `server_tool_use` の回数、Web 系ツールの結果サイズ | usage, tool name | — | Low |
| L14 | 文脈 | CLAUDE.md・メモリの肥大 | 初回 cache_creation の基準値が大きい（L11 と分けられない） | usage | 通常のサイズなら寄与は小さい [原因] | Low |
| L15 | 課金 | 背景処理 | 要約などの補助リクエストの比率 | 補助リクエストの識別子（未確認） | 公式では 1 セッションあたり小さい [公式] | Low |
| L99 | 残余 | その他・想定外 | 上の lens で説明できないコストの残り（全体から説明済み分を引いた量）の大きさと形 | measure 全体 | 「説明できない」こと自体を所見にする | — |

- L99 は MECE を保つための残余カテゴリで、観点を発散させる場所でもある。担当は想定外の傾向を自由に探し、新しい lens の候補として書く。
- 初期の群は 文脈・キャッシュ・課金・並列＋自動（＋L99 はいずれかの群に同居）の 4 つ。

### 6.3 lens ファイルの形式と拡張
- 1 lens を 1 ファイルにする（`references/lenses/L01-long-session.md` など）。冒頭の表に `id / group / priority / 必要なフィールド / 対応を確認した版 / 確認日 / 出典` を書き、本文に検知指標・判定の目安・誤検知の注意・報告書での書き方を書く。
- 追加は lens ファイルを置くだけで済む。監督役は P3 で `references/lenses/` を一覧し、`group` ごとに担当へ割り当てる。外す場合は `priority: off` にする。
- 必要なフィールドが P1 の照合で欠けていたら、その lens は「測定不能」として所見を出さず、理由だけを残す。
- 所見の形式（`findings/<group>.md`）は lens ID、観測値、寄与（全体比 %）、確度（観測 / 推定 / 不明）、根拠にした measure のキー、報告書での表現案、で揃える。

## 9. 検証設計

### 9.1 担当（推奨: 2 担当）
数値の誤りと文章の誤りでは失敗の仕方が違い、必要な手段も違う（数値はコードによる再計算、文章は読解）。このため 2 担当に分け、並列に走らせる。1 担当にまとめると、片方の観点が手薄になりやすい。3 担当にして（プライバシーを独立させる）もよいが、プライバシー検査の大部分は決定的なスキャンで機械化できるので、文章検証に含める。

| 担当 | 観点 | 手段 |
|---|---|---|
| 数値検証 | ① 再計算と整合 | 測定担当のスクリプトを使わず、`references/metrics.md` から**独立にスクリプトを生成**して主要な数値を再計算する（別の経路で計算: たとえばセッション別合計を積み上げた値と日別合計を積み上げた値が一致するか）。重複排除の漏れを調べる（生の行数・一意キーの数・同じキーで最大値を取った結果の比較）。`stats-cache.json` と貼られた `/usage` との差が許容範囲（既定 ±10%、仮の値）を超えたら、理由を推定して付録に書かせる |
| 文章検証 | ② 主張と根拠 | 結論・原因分析の各文が measure のキーまたは利用者の回答に対応しているか。推測を事実として書いていないか。確度の表記が正しいか |
| 〃 | ③ プライバシー・抑制 | 決定的なスキャン（パスの形、メールアドレス、URL、鍵らしい文字列、`inventory` にある実際のプロジェクト名との照合、コマンドらしい文字列）と、目視で詳細すぎる記述を探す |
| 〃 | ④ 可読性 | 冒頭の結論だけで要点がわかるか、用語に説明があるか、責める調子・断定口調になっていないか、ガバナンス担当が次の行動を判断できるか |

### 9.2 ループ
- 指摘は「重大（数値が許容誤差を超える、プライバシー違反、根拠のない断定）」と「軽微」に分ける。
- P6 → P7 → P6 の再検証は**最大 2 回**。2 回目の再検証は前回の指摘が直ったかと、新たな重大問題がないかだけを見る。

### 9.3 残った指摘の扱い
- 重大な指摘が残った場合: 該当する記述を削り「測定不能」または「確認できなかった」に置き換える。それでも解消しないときは、監督役が利用者に状況を伝えて判断を仰ぐ。
- 軽微な指摘: 付録 B「検証で残った注意点」に箇条書きで残す。

## 10. OS 差と Python の検出

### 10.1 実行環境の検出（P0）
前提: 利用端末には Node.js（社内の標準セットアップで導入済み）と Python のどちらか、または両方がある。環境が違えば、使えるほうを使う。
1. 候補を `node` → `python3` → `python` → `py -3` の順に `--version` で試す。`node` を先にするのは、コマンド名が OS で変わらず、Windows のランチャーやストアのスタブの問題がないため（推奨。順序は `references/environment.md` で変えられる）。
2. 採用の条件: 終了コードが 0 で、`node` は v18 以上、Python は 3.8 以上であること。Windows の `python` はストアのスタブであることがあるため、出力が空のものや起動に失敗するものは捨てる（二次 [ローカル]）。
3. どれも使えなければ中止し、理由を利用者に伝える（報告書は作らない）。
4. 1 回の実行では 1 つの言語に統一する（担当ごとに言語が混ざると、再計算の検証や再現が難しくなる）。検出した言語は `env.json` に書き、以後の指示に渡す。
5. 生成したスクリプトはファイルに書き、`<コマンド> <ファイル>` の形で実行する。シェルが bash か PowerShell かによるクォートの違いを避けるため（Windows ではシェルが Git Bash か PowerShell になる [公式]）。
6. references の記述は言語に依存しない（アルゴリズムと規則だけを書く）。言語固有の API は必要な箇所にだけ両言語の例を並べる。

### 10.2 OS 差の扱い（スクリプト生成時の規約は `references/environment.md` に置く）
| 項目 | 方針 |
|---|---|
| 設定ディレクトリ | 環境変数 `CLAUDE_CONFIG_DIR` があればそれ、なければホームの `.claude`（Windows は `%USERPROFILE%\.claude`）[公式]。`~/.config/claude` が今も使われるかは未確認なので、見つかったら利用者に尋ねる |
| パス | 標準のパス API（Node.js は `path`、Python は `pathlib`）で扱い、区切り文字を決め打ちしない。プロジェクトのディレクトリ名は元のパスに戻せないので使わない [ローカル] |
| 文字コード | UTF-8 として読み、BOM と不正なバイト列を許容する（Python は `utf-8-sig`＋`errors="replace"`、Node.js は先頭の BOM を除去）。Windows で CRLF が混じるかは未確認なので、行末を正規化する。大きな jsonl は一括で読まず、行ごとに処理する |
| 標準出力 | コンソールの文字コードの違いを避けるため、結果はファイルに書く。標準出力には ASCII の短い要約だけを出す |
| 時刻 | timestamp は UTC [ローカル]。日別の集計は端末のローカルタイムゾーンで行い、そのことを報告書に書く。`Z` 付き ISO8601 は Python 3.11 未満では置換してから解釈する |
| 氏名 | OS のアカウント名を標準 API で取る（Node.js は `os.userInfo().username`、Python は `getpass.getuser()`）。社員番号などの ID であることもあるため、P8 で利用者に確認・修正してもらう |
| 一時ディレクトリ | `tempfile` に任せる。macOS・Linux は定期的に掃除されることが多いが、Windows の `%TEMP%` が自動で消えるかは設定次第（未確認）。このため `cleanup` 引数があるときだけ P8 で削除を提案する（既定は何もしない。中間物は数値・種別・ラベルだけで本文を含まない） |
| WSL | WSL とネイティブ Windows の履歴は別物（一般論で未確認）。両方の痕跡を検出したら P4 で尋ねる |

### 11.2 確認日の運用
- 各ファイルの冒頭に `確認日: YYYY-MM-DD / 確認時の Claude Code 版: x.y.z` を書き、事実の行ごとに出典 URL を付ける。未確認の項目には「未確認」と書く。
- 確認日から 90 日（仮の値）を過ぎたファイルがあれば、P0 で報告書の「制約」欄に「参照情報が古い可能性」と記載する。実行は止めない。
- 料金表は配布前に一次情報で埋める。調査メモの段階では単価が情報源間で食い違っているため（[原因]）、現時点では空欄とする。キャッシュの倍率（5 分の書き込み 1.25 倍・1 時間の書き込み 2 倍・読み込み 0.1 倍）も原文での再確認が必要（[ローカル] は一次未確認としている）。

### 11.3 仕様の変化への備え
- P0 で Claude Code の版を取る（jsonl の `version` の最大値と、可能なら `claude --version`）。`schema.md` の確認済み範囲より新しければ、そのまま進めて報告書に書く。
- パースの規則: 行ごとに try で読み、壊れた行は数えて飛ばす。行種は許可リスト方式で、未知の型とキーは無視する。数値でない値は 0 として扱い、件数を残す。重複排除は `(message.id, requestId)` を**ファイルをまたいで**行い（ストリーミングや再開で同じ応答が複数行・複数ファイルに出る）、キーが欠けていれば `uuid` で代える。同じキーの中ではフィールドごとに最大値を取る。`iterations` は読まない。`<synthetic>` モデルは除く。キャッシュ書き込みの内訳がなければ、全量を 5 分扱いにして「内訳不明」の印を付ける（[ローカル] の提案に拠る。二次情報に基づく）。
- 必須のフィールドがほぼ欠けている場合（件数の 5% 以上、仮の値）は、その指標と、それに依存する lens を「測定不能」とし、理由を報告書の §9 に書く。
- 規則は SKILL.md に書かず、`schema.md` と `metrics.md` に置く。Claude Code の仕様が変わったときは文書を直すだけで済む。

### 11.4 起動と frontmatter（推奨案）
- `name: hearing`、`description`（何をするか＋「利用者が明示的に起動したとき」）、`argument-hint: "[日数] [cleanup]"`、`disable-model-invocation: true`。`cleanup` は任意で、付けると完了時に作業フォルダの削除を提案する。
- `disable-model-invocation: true` で自動起動を禁止し、`/` からの手動起動だけにできる [スキル]。ただし Web ページの要約経由の情報なので、原文で再確認する（未確認）。
- `context: fork` は使わない。P4 で利用者と対話する必要があるため。
- `allowed-tools` は既定では指定しない。読み取りとスクリプト実行の許可を利用者が目で確認できるほうが、透明性が高いため（§14 Q11）。
- Claude Code 専用のフィールドは claude.ai へのアップロード時にエラーになる [スキル]。配布先は Claude Code に限る。
- SKILL.md は 500 行未満とし [スキル]、重要な規則（本文を読まない・自動送信しない）は先頭に置く。compaction のあとに再添付されるのは先頭の部分だけのため [スキル]。

## 13. 評価計画

実際の利用者の履歴は手元にない前提で、合成した jsonl フィクスチャで評価する。

### 13.1 フィクスチャ
生成器で、正解値（トークンの合計・寄与率・仕込んだ原因）が既知のデータを作る。行の形は §5.1 の許可リストのフィールドと、それ以外のノイズ（未知の行種・本文）で構成する。

| シナリオ | 仕込む内容 | 確かめること |
|---|---|---|
| S01 基準 | 短いセッションが中心で、特に原因がない | 誤検知しない（「顕著な要因なし」と書ける） |
| S02 長時間 | `/clear` しない長いセッション | L01 を検出、寄与率が正解の ±2pt 以内 |
| S03 TTL | 休止のあとの再書き込み、5 分と 1 時間の混在 | L02 を検出、倍率ごとの概算 |
| S04 サブエージェント | `subagents/` と `workflows/` の入れ子 | 再帰的な探索、sidechain の比率 |
| S05 高単価モデル | モデル比率の偏り | L06 を検出、断定しない表現になっているか |
| S06 無人実行 | 等間隔のターン、深夜帯 | L07 を検出 |
| S07 重複 | ストリーミングの複数行、再開による別ファイルへの複製、キーの欠落 | 重複排除の正しさ（正解値と一致） |
| S08 スキーマの変化 | 必須フィールドの欠落、未知の型、壊れた行、内訳なし | 落ちない。「測定不能」と書く |
| S09 OS 差 | Windows 形式の cwd、CRLF、BOM | 正しく読める |
| S10 プライバシー | 本文・パス・コマンド・偽の鍵に目印の文字列（カナリア）を埋める | 報告書と中間ファイルに目印が 1 件も出ない |
| S11 欠損 | 保持期間が短く、30 日に満たない | 欠損を明記する |
| S12 想定外 | どの lens にも当たらない偏り | L99 が拾う |

### 13.2 指標とベースライン
- 指標: 数値の正確さ（正解値との誤差 ±1%）、仕込んだ原因の再現率と適合率、カナリアの漏洩（0 件が必須）、検証役による検出率（わざと誤りを入れた草案を検証にかける）、スキル実行自体のトークン量と所要時間。
- ベースライン: (a) スキルなしで「この端末の Claude Code のコスト原因を分析して報告書を作って」と頼んだ場合、(b) 前の版のスキル（回帰の確認用）。各シナリオを 3 回ずつ実行してばらつきを見る。
- 実機での確認: 評価担当者が自分の履歴で同意のうえで試し、Windows と macOS で 1 回ずつ動かす。
