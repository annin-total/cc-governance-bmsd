# /hearing スキル設計書（軽量版）

Claude Code の利用が重い利用者の端末で実行し、ローカルの履歴から「なぜ重いか」をおおまかに推定して、
ガバナンス課向けのヒアリング調書（Markdown 1 ファイル）を作る独立スキルの設計。
リポジトリ固有の事情・規約には依存しない。根拠が弱い点は「未確認」と書く（確認日 2026-10-01）。

## 1. 目的と温度感

- 位置づけは **アンケート／ヒアリング調書程度の参考資料**。報告書でも一次資料でもない。
- 正確さより概算と推測で足りる。数字は「だいたい」でよく、検証も軽くする。作り込むと保守しにくくなるので作り込まない。
- 金額は出さない。モデルのファミリー・effort・トークン量（種別ごと）・頻度・セッションの長さから、相対的に「重い／軽い」を定性的に述べる。
- 利用者を評価・監視するものではない。責める調子や断定口調で書かない。改善の余地は控えめに「候補」として添える。
- 対象は実行した端末 1 台の履歴だけ。設定の自動変更はしない。
- 調書の送付は利用者が自分で行う。スキルは送信手段を持たない。ガードレールは利用者の環境の設定（settings.json 等）に任せ、スキル側で承認を求める仕組みは足さない（自動実行から遠ざかるため）。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| 対話 | 分析 → 要約を提示 → 補足質問を数問 → 調書に反映 |
| 配布 | 単体のスキルフォルダ（`hearing/skill/hearing/` をコピーして使う） |
| 実行環境 | node か python。検出順は `node` → `python3` → `python` → `py -3`。1 回の実行では 1 言語に統一 |
| 分析期間 | 既定は直近 30 日（引数で変更可）。保持期間による欠損は調書に明記 |
| 深掘り | 全体のおよそ 10% 以上を占める要因・セッションが目安（緩い基準）。構造（ツール種別・ファイル種別・サイズ等）まで。利用者が同意した場合だけ 1 段具体化し、同意を調書に残す |
| 起動 | `/hearing` の明示起動のみ。`disable-model-invocation` の効き方は未確認 |
| 後始末 | 既定は何もしない。`cleanup` 引数があるときだけ作業フォルダの削除を提案 |
| 成果物 | Markdown 1 ファイル。利用者が確認して手動で送付する |
| 利用形態 | 社内では Bedrock 経由が前提。Bedrock 固有の注意は `references/bedrock.md` の 1 か所に隔離 |

## 3. 固定する指示と任せる指示

モデルの判断に任せると事故になるもの（漏洩・誤送信・二重計上・散らかり）だけを固定し、それ以外は任せる。
SKILL.md では固定の指示を先頭に置く（compaction のあとに残りやすいため）。

| 区分 | 内容 |
|---|---|
| 固定 | 本文（prompt・応答・thinking・tool 結果の中身）、パス、コマンド、社内固有名詞は、調書にも中間ファイルにも書かない。構造（種類・サイズ・頻度）で足りるので本文は原則読まない（用途の判別に必要なごく一部を読むのは可）。読む項目の許可リストは §5。理由は、調書を一次資料にしない・読む分のトークンを使わないため（送信の懸念ではない） |
| 固定 | プロジェクト名・リポジトリ名は用途カテゴリ（「アプリ開発」「データ分析」など）に抽象化する |
| 固定 | 調書は起動したセッションの作業ディレクトリのルートに、最終成果物 1 ファイルだけ置く |
| 固定 | 一時スクリプト・progress.md・サブエージェントの調査結果は、OS の一時領域に作る作業フォルダに置く |
| 固定 | progress.md は監督役だけが管理する。テンプレートを使い、冒頭にワークフロー定義を書く |
| 固定 | 実行中の自セッションを分析対象から除き、その旨を書く |
| 固定 | 重複行を排除する。ストリーミングで同じ応答が複数行に出るので、一意キーで 1 回だけ数える |
| 固定 | 検証役を必ず付ける（§7） |
| 固定 | 氏名は OS アカウント名の自動取得だけ。ほかの識別情報は載せない |
| 固定 | サブエージェントのモデルは、使える環境なら `sonnet` を指定し、使えなければ指定を外して親を継承する |
| 固定 | トークン種別（新規入力・出力・キャッシュ書き込み・キャッシュ読み込み）を合算しない。読み込みは軽いので、合算すると誤解を招く。種別ごとに併記する |
| 任せる | 分析観点の発散と選択（§5 の種は出発点にすぎない） |
| 任せる | サブエージェントの担当分割と人数 |
| 任せる | スクリプトの書き方 |
| 任せる | 補足質問の内容と数 |
| 任せる | 調書の見出し・文章の細部 |
| 任せる | 取得できないデータや想定外のデータの扱い（扱いを調書に一言書く） |
| 任せる | Web 検索をいつ使うか（不明点・変わりやすい点を調べてよい。URL は固定しない） |

## 4. ワークフローとサブエージェント

| 段階 | 担当 | やること | 完了条件 |
|---|---|---|---|
| 1 準備・環境検出 | 監督役 | 実行環境・設定ディレクトリ・期間・自セッション ID・氏名を取り、作業フォルダと progress.md を作る | 実行環境・設定ディレクトリ・期間・氏名が決まり、作業フォルダと progress.md がある（実行環境が無ければ中止して理由を伝える） |
| 2 棚卸し・測定 | 担当 1〜数名 | 期間内の履歴を数え、重複を除いてトークン量（種別ごと）・モデルのファミリー・effort・頻度・セッションの長さ・スキルの使われ方を集計する | 期間内の履歴を全部処理し（読めなかった件数も数え）、重複排除後の集計が作業フォルダにある |
| 3 観点別分析 | 担当 0〜数名（並列、必要時） | 集計をもとに観点を発散させ、重そうな要因を選んで所見を書く | 重い寄りの要因が大きい順に 1〜数件、確度（観測／推定）付きである。無ければ「目立つ要因なし」と書いてある |
| 4 要約提示と補足質問 | 監督役 | 要約を見せ、業務背景・使い方を数問尋ねる。回答は抽象化して記録 | 質問に答えが得られた。答えなし・スキップでもよく、その旨を記録して次へ進む |
| 5 執筆 | 担当 1 | `references/report-template.md` に沿って調書を書く | 結論が冒頭にある調書の草案がある |
| 6 検証 | 検証役 1 | §7 | 重大な指摘（推測の事実化・プライバシー混入）が直っている。再検証は最大 1 回 |
| 7 配置 | 監督役 | 作業ディレクトリのルートに調書を 1 ファイル置く | 1 ファイルが置かれ、パスと「送る前に内容を確認・修正してください」を利用者に伝えた。承認待ちで止まらない（`cleanup` 引数があるときだけ削除を提案） |

- 完了条件を満たしたら progress.md の状態を更新して次へ進む。満たせない段階は理由を記録して次へ進む（止めない）。止めるのは、実行環境が無いときだけ。
- 担当数は監督役が履歴の規模で決める。小さければ監督役と少数の担当で済ませてよい。閾値表は作らない。
- ファン・アウトは監督役からの 1 段だけ。受け渡しは作業フォルダのファイルで行い、担当の応答は「出力ファイルのパス＋数行の要約」にとどめる。
- 起動時の指示には、作業フォルダの絶対パス、出力先、§3 の固定指示を必ず含める。

## 5. データ源（読む・読まない）

**読む**（許可リスト。詳細は `references/history-notes.md`）
- `<設定ディレクトリ>/projects/**/*.jsonl`（サブエージェント分を含めて再帰）の、行の種類・時刻・セッション ID・sidechain の有無・重複排除キー・`message.model`・`message.usage` の数値・effort（読めるときだけ）・tool 名・tool 結果の文字数・ファイル系ツールの拡張子。
- 設定ファイルの、保持期間・モデル・effort に関するキーの値と、MCP サーバの数。
- スキルの使われ方と常駐量: `Skill` ツールの呼び出し回数と skill 名、導入済みスキル（個人・プロジェクト・プラグイン）の数と description・SKILL.md のサイズ。skill 名とサイズだけを見て、中身は読まない（記録の形は未確認）。
- `cwd` は、プロジェクトを不透明なラベルに置き換えるためだけに使い、書き出さない。

**読まない**
- 本文・thinking・tool 入出力の中身、入力履歴（`history.jsonl`）、セッションタイトル類、認証情報、環境変数の値、MCP 設定の中身。

**モデルのファミリーの判別**（コスト推定のため。モデル選択の指示ではない）
- `opus` / `sonnet` / `haiku` / `fable` などのファミリー名を、文字列の部分一致で大まかに判別する。リージョン接頭辞・世代・日付は気にしない。
- ARN などで読めないものは「不明」とする。

**重さの推定（定性）**
- 高いファミリーの多用、effort が高い（max・xhigh など）比率の高さ、長いセッション、出力やキャッシュ書き込みの多さは「重い寄り」。単価や倍率の数値は書かない。
- 観点の種は `references/lens-seeds.md` に 1 ファイルでまとめ、「これに縛られず発散してよい」と書く。

## 6. 調書の方針

- ファイル名の例: `claude-code-hearing_<氏名>_<YYYYMMDD>.md`。
- テンプレートは `references/report-template.md`（大まかでよい。厳格にしない）。目的は、調書の統一感と、「何を書き、何を書かないか」の基準を持つこと。
- 結論を先頭に置き、冗長に書かない。見出しは足し引きしてよい。書くのは、重そうな要因とその確度、利用の全体像、利用者談、改善の候補、制約。書かないのは、本文・パス・コマンド・固有名詞、金額、全件の一覧、検証の過程。
- 用語は必要なものだけ短く説明する（キャッシュ読み込み・書き込み、サブエージェントなど）。

## 7. 検証

検証役は 1 担当。観点は次の 4 つ。
- 推測が事実のように書かれていないか。
- プライバシー: 本文・パス・コマンド・固有名詞・認証情報の混入がないか。
- 数字の桁感が元の集計と大きくずれていないか（厳密な再計算はしない）。
- 読み手（ガバナンス課）が使えるか。

再検証は最大 1 回。残った指摘は調書の末尾に注意書きとして残す。

## 8. 実行環境と OS 差

- 実行環境は §2 の順で `--version` を試し、最初に動いたものを使う。Windows の `python` はストアのスタブのことがあるので、出力が空なら捨てる。どれも無ければ中止して理由を伝える。
- スクリプトは作業フォルダにファイルとして書き、`<コマンド> <ファイル>` で実行する（シェルのクォート差を避ける）。
- 設定ディレクトリは `CLAUDE_CONFIG_DIR`、なければホームの `.claude`。パスは標準 API で扱い、区切り文字を決め打ちしない。
- UTF-8 で行ごとに読み、BOM・不正バイト・CRLF・壊れた行を許容する（壊れた行は数えて飛ばす）。
- timestamp は UTC。日別に見るときは端末のローカル時刻で、そう書く。
- 氏名は `os.userInfo().username` か `getpass.getuser()`。社員番号のこともあるので、配置前に利用者が直せる。
- 一時領域の自動削除は OS 次第（Windows は未確認）。WSL とネイティブの履歴が両方見つかったら利用者に尋ねる。

## 9. ディレクトリ構成と保守

```
hearing/
├── DESIGN.md                  # 本書（配布しない）
├── skill/hearing/             # ~/.claude/skills/ にコピーする
│   ├── SKILL.md               # 固定指示（先頭）と手順だけ
│   ├── (scripts/ assets/)     # 必要が生じたら足す。当初は作らない
│   └── references/
│       ├── history-notes.md   # 履歴の読み方の覚え書き
│       ├── lens-seeds.md      # 観点の種
│       ├── report-template.md # 調書のテンプレート（大まか）
│       ├── bedrock.md         # Bedrock の短い注意
│       └── progress-template.md

```

| ファイル | 中身 |
|---|---|
| `history-notes.md` | 保存先、行の種類、usage の項目、重複排除キー（応答 ID＋リクエスト ID、欠ければ行 ID）、サブエージェントの置き場所、OS 差、確認日。「実データと食い違ったら実データを優先し、必要なら Web 検索する」と書く |
| `lens-seeds.md` | 発散のきっかけ。長時間・`/clear` しないセッション、キャッシュの失効・破壊（間隔が空く、モデルや effort の切り替え）、サブエージェント・並列実行、高いファミリーの常用、無人・自動実行、版に依存するキャッシュ異常、effort・拡張思考、大きなツール結果、MCP 定義の常駐、スキルの使われ方（冗長なワークフローのスキルの多用、無関係なタスクでの発火、導入数・description の多さによる常駐量）。末尾に「これに縛られず発散してよい」 |
| `report-template.md` | §6 のテンプレート |
| `bedrock.md` | モデル ID は接頭辞付きのことがある／ARN だとモデル名が読めない／キャッシュ TTL の既定は 5 分と報告されている（二次・未確認）。`message.model` の実際の値は実機で未確認のため仮置き（部分一致で判別し、読めなければ「不明」。必要なら実行時に Web 検索）。この程度にとどめる |

保守は「変わりやすい事実は references に確認日付きで置き、SKILL.md には手順だけ」を守る程度にする。

## 10. 評価（軽量）

合成 jsonl で 3〜4 シナリオを試す。
- 基準: 短いセッション中心。「目立つ要因なし」と書けるか。
- 長時間セッション＋重複行: 長さを拾えるか、重複を 1 回だけ数えるか。
- 壊れた行・未知の型: 落ちずに「読めなかった」と書けるか。
- プライバシー用カナリア: 本文・パス・コマンド・偽の鍵に埋めた目印が、調書にも作業フォルダにも出ないか。

あわせて、スキルなしで同じ依頼をした場合と比べ、固定指示が効いているかを簡単に確かめる。数値の厳密な正解照合はしない。

## 11. 未確認事項・要判断事項

**未確認**
- Bedrock 経由の transcript で `message.model` に実際に入る文字列（接頭辞付き ID か ARN か）、キャッシュ書き込みの内訳が残るか。当面は仮置き（§9 の bedrock.md）で進め、実機で確認できたら更新する。
- スキルの呼び出しが履歴にどんな形で残るか（`Skill` ツールの入力に skill 名が入るか、スラッシュ起動はどう見えるか）。
- effort が履歴のどこに、どの版から記録されるか。
- `disable-model-invocation` と `${CLAUDE_SESSION_ID}` の挙動（要約経由の情報）。
- サブエージェントの親子でキャッシュ書き込みが重複して記録される可能性（二次情報）。
- Windows の一時領域の自動削除、CRLF の有無、WSL との関係。

**要判断**
- なし（必要になれば評価の結果を見て足す）。

## 12. 削ったもの（旧版からの変更点）

| 項目 | 理由 |
|---|---|
| 金額の概算、単価・料金表、料金調査担当、`pricing.md`、Bedrock の料金調査手順 | 参考資料の温度感に対して過剰。ファミリー・effort・トークン量の定性比較で足りる |
| `stats-cache.json` や `/usage` との突き合わせ、許容誤差（±10%） | 厳密さは不要。桁感の確認にとどめる |
| references の確認日 90 日による鮮度判定 | 運用の手間に見合わない。食い違いは実データ優先と Web 検索で吸収する |
| lens ファイル群（L01〜L15・L99）と所見の固定形式 | 観点の発散はモデルに任せる。種を 1 ファイルにまとめた |
| 検証役 2 担当、再検証 2 回、重大／軽微の区分、独立スクリプトでの再計算 | 1 担当・再検証 1 回で足りる |
| 段階 P0〜P8、担当数の閾値（50MB・セッション 20 等）、中間ファイルの固定構成 | 段階を減らし、担当数と分割は監督役の判断に任せる |
| `environment.md`・`schema.md`・`metrics.md`・`privacy.md`・`orchestration.md`・`questions.md`・`verification.md` | `history-notes.md` と本書の §3 に集約した |
| 評価 12 シナリオ、±1% の正解照合、3 回ずつの反復 | 3〜4 シナリオの簡易確認で足りる |
| 「調書を自動送信しない」の固定ルール、配置前に全文を見せて直してもらう承認ゲート | スキルは送信手段を持たず、送付は利用者が行う。ガードレールは利用者環境の設定に任せ、承認待ちで止まらないようにする。配置後に「送る前に確認を」と伝えるだけにした |
| 直近 7 日との比較、日別推移の表、付録の金額注記 | 必須にしない。必要なら執筆時の判断で入れる |
