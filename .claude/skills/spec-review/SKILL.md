# 仕様レビューの手順

目的は、**仕様そのもの**を疑って Issue（仕様バグ・想定外）と Improvement（改善案）を洗い出すこと。コードの作法は対象外。
**直さない。**見つけたものは文書にまとめて報告し、直すのは別の作業にする。

## 着手前（合意を取る）

1. 範囲を決める。全体を見るか、差分を振り返るか（`git diff <base>..HEAD --stat` を親と `server/` の両方で取り、変わった流れだけのレーンを選ぶ）
2. 前提を確かめる。利用者の規模、捨ててよいケースの基準、テストの品質を範囲に含めるか、動的検証の許可範囲、出力先
3. 出力先はリポジトリの外にする（場所は利用者に確認する）。レビュー文書を `docs/` に置かない
4. 対象をスナップショットに固定する。`rsync -a --exclude .venv --exclude __pycache__` でスクラッチパッドに複製し、各リポジトリのブランチと commit を記録する。並行作業でブランチが動いても結果がぶれないようにするため

## 分担（レーン）

**リポジトリ単位ではなく、データと責務の流れで切る。**仕様バグは境目で起きるので、各レーンは担当する境界の両側を読む。全体を見るときの既定の分け方:

| レーン | 範囲 |
| --- | --- |
| ルール配布 | `policy.py`・`_policy_ops`・`_settings`・`session_start`・お知らせ ↔ `queries_policy` |
| 収集と送信 | `contract.py`・`collect`・`_spool`・`_sender`・`_identity`・`_context` ↔ `ingestion/ndjson` |
| 受信・保存・集計 | `server/ccgov/{ingestion,store}`・スキーマ・CSV 取込・性能 |
| 画面・セキュリティ・プライバシー | `server/ccgov/web`・認証・送る情報と見せる情報 |
| 配布・リリース・運用 | `scripts/`・`guide/`・版と自動更新・移行とバックアップ |
| 仕様の根本 | `spec/system.md`・`decisions/`・上流の最新機能（一次情報で確認）・測定の設計 |

## 共通指示書（全員に渡す。スクラッチパッドに 1 ファイル置き、各プロンプトから参照させる）

- **重大度の定義**
  - Issue Critical: 測定やルールが黙って誤る、漏洩・改ざんが現実的に起きる、運用が止まる
  - Issue Major: 想定内の運用で欠測・誤集計・事故が起きる
  - Issue Minor: 影響が限定的
  - Improvement は放置したときの損失で分ける。Critical は「目的を根本から損なう、またはより単純で確実な代替が明確にある」
- **件数を埋めない。**無ければ「無し」と書く
- 各指摘に `ファイル:行`・再現結果・一次情報の URL のいずれかを付け、確認済みか未検証かを書く
- `decisions/`・`remaining/` の判断を覆すなら、記録された理由の誤りか、前提の変化を示す。示せなければ棄却する
- 文書の最後に**「棄却した仮説」**を 1 行ずつ残す。後段の検証と、蒸し返しの防止に使う
- 動的検証
  - 作業はスクラッチパッドの `work-<レーン>/` で行う。Claude Code は `CLAUDE_CONFIG_DIR` で隔離する
  - サーバはランダムな空きポートで起動し、本番の受信先には送らない
  - 本物の `~/.claude/` を変える必要が出たら、自分では行わず報告する（並列のレーンと衝突するため）
  - 終わる前にプロセスと `$TMPDIR` の残骸を片付ける

## 反証（必ず挟む）

Critical と Major は、書いた本人とは別のエージェント（opus）に**誤りである可能性を探させる**。判定は次の 4 つ。

| 判定 | 意味 |
| --- | --- |
| CONFIRMED | 指摘どおり |
| CONFIRMED-ADJUSTED | 事実は正しいが、重大度か提案を修正する |
| PLAUSIBLE | 白黒を付けるには何を確かめればよいかを書く |
| REJECTED | 指摘は成り立たない |

特に次の誤りが起きやすい。

- **運用の前提の誤解。**例: マーケットプレイスは「リリース時だけ触る」ので、開発中の正本より古いのは正常な状態である
- **規模の見積もりに最大値を使う。**1 人の開発者の最大値ではなく、200 名の中央値で見積もる
- **「未検討」という主張。**判断記録の全体を grep してから判定する。記録が無ければ、それ自体を別の指摘にする
- 同じ根本原因の指摘がレーンをまたいでいないか。統合を前提に判定する

## 最終文書（責任者が書く）

- レーンの報告を並べるのではなく、**根本原因で束ね、重大度を付け直し、結論を最初に書く**
- 検証による振り分けの結果（何が棄却・降格されたか）を示す
- 「直す前にやるべき順序」と「本番の前に白黒を付ける確認」を分ける
- 棄却したものの要点と、レビュー自体の限界（見ていないもの・未検証の環境）を書く

## 仕上げ

- 残骸を確かめる。プロセス（`pgrep`）、`$TMPDIR`、本物の `~/.claude/` の mtime、スクラッチパッドの大きな DB
- 完了報告には、確かめた事実と推測を分けて書く。レビューで得た外界の事実は、`knowledge/` に移すかどうかを利用者に提案する
