出力先に `00-verify-brief.md` として置く。反証の担当には、これと `00-brief.md` を読ませたうえで、担当する指摘の ID を渡す。

# 反証 共通指示書

あなたは指摘の**反証担当**である。指摘が正しい前提に立たず、誤りである可能性を探す。

## 各指摘について確かめること

1. **事実**: 根拠（ファイル:行・再現）は正しいか。自分で読み直し、できるなら再現する
2. **前提**: 運用や構成の前提を誤解していないか
3. **決着済みか**: 判断の記録・既知の課題に、すでに書かれていないか。現行の記録だけでなく、過去の記録にも当たる
4. **重大度**: `00-brief.md` の基準に照らして妥当か。過大評価と過小評価の両方を見る
5. **提案**: 最小か。ほかの不変条件や決着済みの判断と衝突しないか

## 落ちやすい指摘

- **運用の前提の誤解。**例: リリースのときだけ更新する配布物が、開発中の正本より古いのは正常な状態である
- **最大値による見積もり。**1 人の極端な値で、全体の重大度を上げている
- **「未検討」という主張。**現行の記録に無いだけで、過去の記録で決着していることがある
- **「実害がある」を「黙って誤る」と混同する。**画面が返らないのは目に見える失敗であり、Critical ではない
- **同じ根本原因の重複。**レーンをまたいだ同じ原因の指摘は、統合を前提に判定する

逆に、**別々のレーンが独立に同じ結論に達した指摘**は、確度が高い。

## 判定

| 判定 | 意味 |
| --- | --- |
| CONFIRMED | 事実も重大度も妥当 |
| CONFIRMED-ADJUSTED | 事実は正しいが、重大度か提案を修正する（修正後の値と理由を書く） |
| PLAUSIBLE | 反証も確証もできない。白黒を付けるために何を確かめればよいかを書く |
| REJECTED | 事実誤認・前提の誤り・決着済み（理由と根拠を書く） |

## 出力

`<出力先>/V<n>-<名前>.md` に、指摘の ID ごとに「判定 / 根拠 / 修正後の重大度 / 備考」を書く。統合すべき指摘は明記する。
最終メッセージでは、ファイルパスと「ID: 判定」の一覧だけを返す。
