# 仕様レビュー 共通指示書

## 目的

<対象の一文説明> の**仕様を根本から敵対的に疑い**、仕様バグ（想定外のケース）と仕様上の改善案を洗い出す。

- 前提: <利用者の規模>。常識的な範囲に絞り、非常に稀なケースは捨ててよい
- **件数を埋めない。**無ければ「無し」と書く
- 範囲外: コードの作法、<合意した除外>。仕様の穴をテストが見逃している場合に限り、テストに触れてよい

## 対象

スナップショット: `<複製したパス>`（こちらを読む）

| リポジトリ | パス | ブランチ | commit |
| --- | --- | --- | --- |

報告に書くパスは、リポジトリのルートからの相対パスにする。まず `docs/spec/` の全体像と、担当に関係する判断の記録を読む（文書の置き場は `docs/CLAUDE.md` の「構成」を見る）。

## 決着済みの判断

記録済みの判断・既知の課題を覆す、または再び指摘する場合は、記録された理由のどこが誤りか、何の前提が変わったかを示す。示せなければ棄却する。
既知の課題と同じものは「既知」と明記する。**「未検討」と書く前に、判断の記録を全文で検索する。**

## 重大度

| 区分 | 重大度 | 基準 |
| --- | --- | --- |
| Issue | Critical | 結果やルールが**黙って誤る**。漏洩・改ざん・なりすましが現実的に起きる。運用が止まる |
| Issue | Major | 想定内の運用で、欠測・誤集計・事故・利用者体験の明確な毀損が起きる |
| Issue | Minor | 影響が限定的、または回避策がある |
| Improvement | Critical | 目的の達成を根本から損なっている。または、より単純で確実な代替が明確にある |
| Improvement | Major | 保守・性能・拡張性・収集の妥当性で、明確な損失がある |
| Improvement | Minor | あれば良い |

見積もりには、**想定規模の中央値**を使う。1 人の最大値で重大度を上げない。

## 根拠の書式

```
### [I-C1] 見出し（1 行）
- 種別/重大度:
- 場所: ファイル:行、文書と見出し名
- 何が起きるか: 状況 → 誤った結果
- 根拠: 確認した事実 / 実行結果 / 一次情報の URL と確認日。確度: 確認済み | 未検証
- 提案: 最小の対処（1〜3 行）
- 決着済み判断との関係: なし | 覆す（理由）| 既知
```

ID の接頭辞は I-C / I-M / I-m / P-C / P-M / P-m とする。上流の仕様は古い知識を前提にせず、公式の情報で確かめる。

## 動的検証

- 作業はスクラッチパッドの `work-<レーン>/` の中だけで行う。プロジェクトの実ファイルとスナップショットは変更しない
- 隔離の方法はリポジトリの `CLAUDE.md` に従う。**利用者本人の設定を変える必要が出たら、自分では行わず手順を報告する。**並列で動く他のレーンと衝突するためである
- サーバは空いているポートで起動し、本番の宛先には送らない
- 終わる前に、起動したプロセスと一時ファイルを片付ける。片付けられないものは報告に列挙する

## 出力

`<出力先>/L<n>-<名前>.md` に、次の構成で書く。

1. 範囲と読んだもの
2. 要約（3〜5 行）
3. Issue（Critical / Major / Minor）
4. Improvement（Critical / Major / Minor）
5. 棄却した仮説（1 行ずつ。反証と、蒸し返しの防止に使う）
6. 他レーンへの申し送り
7. 実施した動的検証と残骸

最終メッセージでは、ファイルパスと、Critical・Major の件数と見出しだけを返す。
