# 仕様レビュー

仕様そのもの（何を、なぜ、どういう前提で作っているか）を敵対的に疑い、**Issue**（仕様バグ・想定外のケース）と
**Improvement**（仕様上の改善案）を洗い出す。コードの書き方は見ない。**見つけても直さない。**
直すのは別の作業にする。レビューと修正を混ぜると、何を見て何を変えたのかが追えなくなるためである。

責任者（あなた）は監督に徹する。調査はサブエージェントに任せ、あなたは分担・進捗・最終判断に責任を持つ。

## 手順

毎回この順で進める。順序を固定するのは、実施ごとに結果の質がぶれないようにするためである。

### 1. 合意を取る（着手前）

次の 5 点を、推奨案付きの選択式で利用者に確認する。

1. 範囲: 全体か、差分の振り返りか。差分なら基準の commit を決める。未コミットの変更を含めるか
2. 前提: 利用者の規模、捨ててよいケースの基準。**規模が依頼に無ければ推奨値を置かない。**
   仕様書に書かれた値を示して尋ねる（前のレビューや記憶にある値を持ち込むと、別の前提でレビューしてしまう）
3. 除外: テストの品質、進行中の別作業など
4. 動的検証: どこまで実行してよいか（隔離の方法・本物の設定に触れてよいか）
5. 出力先: `.local/<作業名>/`（`.local/` はリポジトリのルート。無ければ作る。git 管理外）

確認と一緒に、**短い計画**を示す。中身は次の 3 つだけにする。

- 「レビューのみで、修正はしない」の一行
- レーンの表（名前・範囲・モデル）
- 反証の組み方の一行
ひな形の中身や細かな段取りは、計画に書き写さない。ひな形はそれぞれの段階で使う。
利用者の指示に過不足があれば、このときに指摘する。

### 2. 対象を固定する

- 対象（submodule を含む）を、合意した commit からスクラッチパッドに取り出す。各リポジトリのブランチと commit を記録する。
  並行作業でブランチや作業ツリーが動いても、結果がぶれないようにするためである
- 出力先に、進捗表 `progress.md` と共通指示書 `00-brief.md` を作る。
  指示書は `references/brief-template.md` を埋めて作る。各サブエージェントのプロンプトは、この指示書を読ませたうえで担当範囲と疑いどころだけを書く

### 3. レーンに分けてレビューする（並列）

**リポジトリやディレクトリの単位ではなく、データと責務の流れで切る。**仕様バグは部品の境目で起きる。そのため各レーンには、担当する境界の両側を読ませる。

**以前のレビューが残っていれば、そのレーンの分け方を再利用する。**分け方を毎回変えると、前回との比較ができなくなるためである。
残っていなければ、`docs/spec/` からデータの流れを読み取り、次の型に当てはめる。

| 型 | 見るもの |
| --- | --- |
| 流れの各段（段の数だけ） | 作る・運ぶ・貯める・集計する・見せる、など。段ごとに 1 レーン。隣の段の入口までを読む |
| 守り | 認証・改ざん・なりすまし・個人情報。何を集め、誰が見るか |
| 配る・動かす | リリース・版の混在・移行・バックアップ・手順書 |
| 前提 | 目的に対して仕組みが要るか。上流の現行機能で代替できないか（一次情報で確認）。測りたいことを本当に測れているか |

差分の振り返りでは、差分が触れた段と「前提」だけを選ぶ。このときの「前提」レーンが問うのは次の 2 点である。

- 差分が仕様の目的や決着済みの判断と整合しているか
- 差分によって、仕様書の記述が現実と食い違っていないか
- 差分で、仕様を守っていた検査が消えたり弱まったりしていないか

テストの品質を範囲外にしても、3 点目は仕様の問題として見る。一方で、テストの対応表のような実装の確認には流れないようにする。

判断が要るレーンには強いモデルを使う。手順や文書の確認が中心のレーンには軽いモデルでよい。
各レーンは `L<n>-<名前>.md` を書き、最終メッセージでは件数と見出しだけを返す（本文は責任者がファイルで読む）。

### 4. 反証する（省略しない）

Critical と Major は、書いた本人とは**別の担当**に、誤りである可能性を探させる。
指示は `references/verify-template.md` に従う。担当が被らないように、指摘を 3〜4 組に分けて並列に回す。

反証を省略しないのは、レビューが「ありそうな問題」を重く見積もりがちだからである。
過去には、Critical の候補の半数近くが反証で棄却されるか、格下げになった。
落ちやすい型は、テンプレートの「落ちやすい指摘」にまとめてある。

### 5. 最終文書を書く（責任者が自分で）

`references/final-template.md` の構成で `FINAL-review.md` を書く。
レーンの報告を要約して並べるのではない。次の 3 つを行う。

- 根本原因で束ねる
- 反証の結果で重大度を付け直す
- 結論と、何から直すかを最初に書く

### 6. 片付けと報告

- 残骸を確かめる。起動したプロセス、一時ディレクトリ、本物の設定ファイルの更新時刻、スクラッチパッドの大きな生成物
- 並行している別作業のプロセスには触れない
- 報告では、確かめた事実と推測を分ける。レビューで得た外界の事実（上流の仕様・実測値）は、
  `docs/` の知識の置き場へ移すかを利用者に提案する（移すかどうかの判断は `docs/CLAUDE.md` の基準に従う）
  レビュー書は**いつ消してもよい一時文書**である。コード・`docs/`・コミット・PR 本文から参照しない
