# 実機検証を実行する

目的は、**変更が実物の Claude Code と実サーバで動くことを、確かめたことと確かめられなかったことを分けて示すこと。**
正本は `docs/guide/e2e.md`（モジュールの一覧・前提・認証・安全の約束・罠・手動確認の項目）。
このスキルが示すのは、実行の道筋と、実行するときに踏みやすいところだけである。
E2E が起こさない状況は、一時スクリプトで実物を動かして確かめてよい。その約束と型は `references/adhoc.md`。

## 役割

- **責任者（あなた）**：実行・判断・利用者との対話・記録。pytest は自分で流してよい（1 コマンドで、出力も短い）
- **調査担当**：失敗が再現したときだけ呼ぶ。原因を切り分けて報告し、コードにもテストにも触れない。直すかどうか・どこで直すかは責任者が決める。
  モデルは sonnet。上流の仕様変化や設計の食い違いが疑われるときは opus
- **一時スクリプトの担当**：書いて流すのを任せてよい（モデルは用途で選ぶ）。ただし、判定を壊すと落ちたことと片付けが済んだことは、責任者が実物で確かめる。自己申告は証拠にしない

## 流れ

### 0. 記録を始める

`references/record-template.md` を読み、`.local/<作業名>/record.md` を作る（`.local/` はリポジトリのルート。無ければ作る。git 管理外）。
段を終えるたびに書き足す。セッションが長引いたり途中で止まったりしても、どこまで確かめたかが残るようにするため。
失敗も手動確認も無い短い実行なら、記録がそのまま報告になる。書き分けなくてよい。

### 1. 目的を決める

開発中（変更に関係するモジュールだけ）か、リリース前（全件）か、状況の検証（E2E に無い状況・上流の事実・監査）か。依頼から分からなければ選択式で聞く。
状況の検証なら、段 3・4 の代わりに `references/adhoc.md` に従う。段 0・2・7 は共通で、段 2 では skip の見込みの代わりに、要る資源（認証・Docker）を示す。

### 2. 前提を調べる（調べれば分かることは聞かない）

- OS、`claude` の版、git・Docker の有無、認証の環境変数の有無（**値は表示しない**）、ブランチとコミット
- 前回の残骸。Docker のラベル `cc-e2e` のコンテナ・イメージが残っているとサーバを使うテストが止まる。
  一時ディレクトリ（`tempfile.gettempdir()`。macOS では `/tmp` ではない）の `cc-e2e-*` はテストを止めないが、片付け漏れである（E2E が作ったものには目印 `.cc-e2e-root` がある）。
  自分が作ったものでなければ、消す前に利用者に確かめる
- ここから、どのモジュールが skip になるか（＝今回は確かめられないこと）を先に示す。
  変更に直結するモジュールが skip になるとき、または手動確認で対話の起動が要るときは、skip の理由（認証・Docker）ごとに用意できるかを聞く
  （認証が届かない理由は e2e.md の「認証」）。skip を避けるために環境変数や環境を書き換えない。書き換えが要りそうなら聞く
- Claude Code のセッション内から pytest を流してよい（E2E は子プロセスの環境変数を許可リストで組み直す）。`tests/` と同時には流さない
- 利用者が別の端末（例: Windows）で実行するときは、調べるコマンドを渡して結果を返してもらう

### 3. モジュールを選び、変更が本当に通るかを確かめる

- 開発中：分岐元のブランチ（PR の向き先。分からなければ聞く）との差分（未コミットの変更を含む）と、e2e.md の各章の冒頭（何を確かめるか）を突き合わせて選ぶ。
  マージ済みの変更を確かめる依頼なら、依頼が指すコミットやマージを差分の範囲にする。
  依頼が言う変更が差分に見当たらなければ、流す前に在り処を聞く（何も確かめない実行になるため）
  導入経路・`e2e/` の共通部分・端末とサーバで共有する契約の正本（`CLAUDE.md` が挙げるもの）に触れた変更は全件。迷ったら全件
- リリース前：全件
- **選んだテストが、変えたものを実際に通るかを、テストのコードで確かめる。**E2E は本物の代わりに見本を重ねる箇所があり、
  変えた振る舞いを起こさないテストもある。結果は 3 つに分けて報告する
  - 通る
  - 通るが、変更の結果は判定していない（結果を assert しない、期待値を変えたファイルそのものから作る、など。変更が壊れていても合格する）
  - 通らない：緑は証拠にならない
  - 通らないものと判定していないものは、次の順で補う。`tests/` の該当テスト（E2E とは別のコマンドで流す）→
    一時スクリプト（`-p` で足りる・非対話のもの。`references/adhoc.md`）→ 手動確認（対話でしか見えないもの）
- 選んだ理由と、補う方法を記録に 1 行ずつ

### 4. 実行する

- `-k` で絞って流す（複数は `-k "a or b"`）。**出力を途中で切らない**（失敗の全文が後の切り分けに要る）。ログなどの一時ファイルは `.local/<作業名>/` に置く
- リリース前は、`docs/guide/release.md` の前提のうち機械で確かめられるもの（`CLAUDE.md` の Commands のテスト・検証スクリプト）も流す
- 端末とサーバで共有する正本に触れたら、開発中でも正本と複製の同期を確かめる（`CLAUDE.md` の Commands の同期の手順）。
  サーバの E2E は複製どうしの一致しか見ないので、同期を忘れても合格する
- 落ちたら、まず打ち切り（`SessionStart` の hook が間に合わなかったと表示に名指しされる）かを見る。
  打ち切りなら変更の不具合ではない。並行して動かしているものを止めるか本数を絞って流し直す（e2e.md の「安全の約束」）
- 打ち切り以外で落ちたら、そのテストだけを `CC_E2E_KEEP=1` を付けて 1 回だけ流し直し、隔離ルートを残す
  - 2 回目に通れば「不安定」として、テスト名と 1 回目の表示を記録する。モデルの応答に頼るテストはまれに揺れる
  - 2 回目も落ちれば、調査担当に切り分けを頼む。渡すのは失敗の全文・残したルートのパス・差分。
    原因の見立ては 3 つ：変更による不具合／上流の Claude Code の仕様の変化（`docs/knowledge/` と突き合わせる）／テストの前提が古い
  - 調べ終えたら、残したルートを消す
- E2E 以外の検証（テスト・検証スクリプト）が落ちたときも、1 回だけ流し直し、両方の結果を記録する

### 5. リリースとして不自然な点を伝える（リリース前のとき）

- 配布リポジトリの作業ブランチからの導入の確認は、このスキルでは行わない。release-plugin スキルが、作業ブランチを作った後の段で行う
- 版が上がっていない・開発リポジトリの HEAD が push されていない・送信先が空など、リリースとして不自然な点に気づいたら報告に載せる。
  前提を調べる段で気づいたら、その時点で伝え、確認を続けるかを聞く

### 6. 手動確認を渡す

選んだモジュールに手動確認の項目（e2e.md）があるとき、または 3 で手動確認で補うと決めたものがあるときは、
`references/manual-template.md` を読み、利用者が行う手順書を `.local/<作業名>/manual.md` に作る。どちらも無ければ記録に「該当なし」と書いて次へ。

- 隔離ルートは e2e.md の「手動確認の準備」のコマンドで残す。その**実際のパスを各コマンドに直接書く。**変数は使わない。
  実行してみないと分からない値は `<準備 3 で出たパス>` のように日本語で差し込み位置を示す
- 項目は変更に関わるものに絞り、対象は変えたキーや文面に合わせて差し替える（e2e.md の項目は例を示しているにすぎない）
- 3 で「見本を重ねていて変更を通らない」と分かったものは、変えた本物を隔離ルートの導入先に写す手順を入れる
- e2e.md に項目が無いものは、項目を組む。失敗や値の変更は隔離ルートの導入先で起こし、本物のソースや設定には手を入れない
- **利用者の OS に合わせて書く。**Windows での実行は未検証なので、つまずいた点は記録し、e2e.md への反映を提案する
- 利用者が貼った出力で合否を判定し、記録に書く。画面での見え方など出力に出ないものは、利用者に聞く
- **サーバのモジュールを選んだときの画面の確認は、あなた側が行う。**e2e.md のサーバの手動確認の手順でサーバを起動し、
  変えた表や画面には、表示されるデータを先に入れる（見本の CSV だけでは空の表がある。全ての表を埋めるなら `scripts/seed_dashboard.py`）。
  ブラウザを操作できる手段で全ての画面を撮って目視で確認する（崩れ・欠け・文字化け・データが出ているか）。
  1 枚の画像は見えている範囲しか写さないので、縦はスクロールするか全体を撮り、横のはみ出しとコンソールの error・warning は
  ページ上の JavaScript で数値として見る（写らないため）。撮れた範囲と見落としうる点を自分で評価して報告する。
  撮った画像は `.local/<作業名>/screenshots/` に保存し、記録から参照する
  ブラウザを操作する手段が無ければ、この項目を手順書に入れて利用者に渡す

### 7. 片付けて報告する

- 手動確認の結果を受け取ってから、残骸が無いことを確かめる（一時ディレクトリの `cc-e2e-*`、Docker のラベル `cc-e2e`、手動確認用のルート、画面の確認に使った compose のプロジェクト、一時スクリプトが起こしたプロセスと生成物）
- 報告：合格／skip（確かめられなかったこと）／不安定／失敗／変更を通らなかったテスト／手動確認の結果／認証ありで流した回数（費用の目安）
- 上流の新しい事実（版つき）は `docs/knowledge/` への追記を、手順書の誤りは e2e.md の修正を提案する（直すのは別の作業）。
  E2E に常に流す価値があるもの（無言で壊れる・揺れない・安い、の 3 つを満たす）は、plan-implement への提案として載せる
- 最後に、記録・手順書・スクリーンショット・一時スクリプトのそれぞれについて、消すか残すかを選択式で聞く（作らなかったものは聞かない）。
  消した結果 `.local/<作業名>/` が空になれば消し、`.local/` も空になれば消す。ほかのファイルが残っていれば消さない

## 踏みやすいところ

- **本物の `~/.claude` を書き換えない。**隔離は `CLAUDE_CONFIG_DIR` だけで行う
- **`plugin/` のコードを直接 import して確かめない。**`plugin/` に `__pycache__` ができ、配布物の検証が落ちる。要るときは `python -B` で
- **`plugin/` を複製して動かすときは、送信先を空かローカルにする。**開発ツリーの設定には本番の送信先がある（e2e.md の「安全の約束」）
- **待機に `pgrep -f` を使わない。**パターンが自分のシェルのコマンド行にも一致し、待ちが終わらない
- **セッション内から `claude` を直接起動するとき**は、e2e.md の「手動確認の準備」と同じく親の変数を落として起動する。
  起動形態の変数を継承して判定が汚れる。対話型のコマンド（ログイン・トークンの発行）はセッション内から動かないので、利用者に別のターミナルで頼む
- **隔離した config で `/login` させない。**macOS ではキーチェーンに項目が残る。認証は環境変数で渡す（残ったときの消し方は e2e.md）
- **認証の値・トークンを表示しない、記録に書かない。**有無だけを見る
- **緑でも、skip が多い、または変更を通らないなら何も確かめていない。**報告でそれらを合格に混ぜない
- **ブラウザ操作手段で claude-in-chrome を使わない。**使える場合でも使わない。Playwright、HTTP 応答（`curl`/`urllib` で HTML 取得）など別の手段を使う
