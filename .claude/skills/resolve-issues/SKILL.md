# 記録した課題を片付ける

目的は、**記録された課題を今の実装で確かめ、効果のあるものだけを直し、記録を実態に合わせること。**
記録は書いた時点の事実であり、古い項目はすでに対応済みだったり、問題そのものが消えていたりする。
修正の進め方は呼び出す各スキルが正本であり、このスキルは棚卸しと振り分けだけを示す。

## 役割

- **責任者（あなた）**：監督に徹し、要否の判断・利用者との対話・記録の更新に責任を持つ。小さな確認は自分でしてよい
- **調査担当**：読み取り専用。項目を確かめて報告するだけで、直さない。一時ファイルはスクラッチパッドに置かせる
- **実施**：呼び出したスキルの役割分担に従う
- モデルは用途で選ぶ。要否の判断を伴う調査は opus、行数や旧名の照合のような機械的な確認は sonnet

## 流れ

### 1. 対象を決める（自分で）

引数で作業名を受け取ったら `.local/<作業名>/issues.md` を読む（`.local/` はリポジトリのルート。git 管理外）。
省略されたら `.local/*/issues.md` を作成日時（macOS は `stat -f %SB`）つきで一覧にし、選択式で聞く。
作成日時と、本文にある記録日・基点のコミットを控える。無ければ、作成日時と本文の PR 番号で代える。

### 2. 棚卸しする

- **まとめる（自分で）**：同じ対象の項目（同じファイルの肥大化が PR ごとに載っている、など）は 1 件にまとめる。
  後の項目が前の項目を更新していることがある（「PR 11 で及ばないと分かった」など）。最後の状態を採る
- **確かめる（調査担当）**：項目を対象ごとに分けて任せ、今のブランチの実装・テスト・文書で確かめさせる。
  server の項目は、親の gitlink が指すコミットで確かめさせる（server 側の同名のブランチは古いことがある）。
  記録日以降の `git log`（根拠のパスに絞る）で、対応や変化の経緯も見させる。`path:line` は記録時点のものなので、ずれを前提にする。
  「未検証」の項目は、動かさずに確かめられる範囲で確かめさせる。報告は項目ごとに、今の事実（`path:line`）・判断の案・修正の工数の見積もりを返させる。
  記録に無い同じ種類の問題を見つけても、棚卸しの対象に足さない（5. で記録に追記する）
- **判断する（責任者）**：項目ごとに次のどれかに決める。「解消済み」の根拠は実物で確かめる
  - **解消済み**：対応済み、問題が無くなった、または初めから起こりえない
  - **対応する**：妥当で重要なもの。重要とまでは言えなくても、修正の工数に対して効果が見込めるもの。使うスキルも決める（減らす作業は refactor、文書・docstring・コメントは revise-docs、テストを足すことを含む増やす作業は plan-implement）
  - **見送る**：妥当でない、効果が工数に見合わない、条件がまだ満たされていない（「全ページを作り終えたら消す」など）。理由を書く
  - **利用者に聞く**：決着した判断（`docs/decisions/`）に触れるもの、性能と容量のように引き換えのあるもの、方針の決定が要るもの

### 3. 一括で承認を取る

先に「利用者に聞く」項目の論点を選択式で聞く。答えを受けて全項目を 1 つの表（件名・判断・理由・使うスキル・PR のまとまり）に確定させてから、
「これで進めてよいか」と「ブランチ作成・コミット・push・PR 作成をどこまで行ってよいか（推奨はすべて）」を確認する。

- PR は目的ごとにまとめる。増やす作業と減らす作業は同じ PR に混ぜない（`CLAUDE.md` の Scope）
- 同じファイルに触れる PR は、前の PR のブランチに積む。server（submodule）の変更は server のリポジトリで PR にし、親は gitlink を更新する
- **この承認で、呼び出す各スキルの提案・方針承認の段階は済んだものとする。**以降は、承認した方針から外れる判断が出たときだけ利用者に戻る

### 4. PR ごとに実施する

PR ごとに、使うスキルの `SKILL.md` を読み、承認の段階の後から、その流れに沿って進める（ブランチの切り方・検証・PR の書き方もそのスキルに従う）。
規模の判断（refactor の大規模など）もそのスキルの基準で行う。承認した範囲を超えるなら、手を動かす前に戻る。

### 5. 記録を更新する

issues.md を次のように直す。

- 冒頭に `更新日: YYYY-MM-DD` を書く（あれば書き換える）
- 解消済み・対応した項目を本文から消す。見送った項目は、理由と再開の条件を添えて残す
- 末尾の `## 対応履歴` に、1 行 1 件で追記する（無ければ作る）。

  ```markdown
  ## 対応履歴

  | 日付 | 件名 | 結果 |
  | --- | --- | --- |
  | YYYY-MM-DD | <件名> | 対応（<PR の URL>）／解消済み（<根拠>） |
  ```

- 作業中に見つけた新しい依頼外の課題は、同じ issues.md に `.claude/templates/issues.md` の形で追記する

本文の項目が無くなったら、ファイルを消すか残すかを選択式で聞く。

### 6. 報告する

完了報告では、項目ごとの結果（PR の URL・解消済みの根拠・見送りの理由）と、利用者がすることを書く。確かめた事実と推測を分ける。

## このプロジェクトで踏みやすいところ

- **記録は今の事実ではない。**「対応済みのはず」「まだ残っているはず」を記録から決めない。必ず今の実装で確かめる
- **決着した判断を知らずに覆す。**項目の案が `docs/decisions/` の「採らない理由」に触れないかを、関連語で全文検索して確かめる
- **棚卸しの勢いで範囲を広げない。**項目に関係する問題を見つけても、承認した PR に足さず、記録に追記する
- `.local/` は一時領域。コード・`docs/`・コミット・PR から参照しない。残す事実は PR 本文か `docs/` に書く
