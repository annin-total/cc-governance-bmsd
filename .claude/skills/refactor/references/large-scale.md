# 大規模な減らす作業の流れ

複数の PR に分ける再編の手順。SKILL.md の「変えてよいもの」「検証」「並行作業の注意」はそのまま適用する。
小規模との違いは、次の 3 つである。

- 計画を先に固める
- 作業を委任する
- 検証を実装した担当から切り離す

責任者（あなた）は監督に徹し、調査・実装・検証はサブエージェントに任せる。
判断が要る作業は強いモデルに、機械的な追従は軽いモデルに渡す。

## 1. 調べてから意見を出す

- 対象を領域ごとに分け、読み取り専用のサブエージェントに並行で調べさせる。見させるもの：
  - 重複・肥大化・未使用・冗長
  - 命名・配置
  - 経緯のコメント
  - **壊してはいけない守りと設計判断**
- 候補ごとに「何を・どこを・どれだけ減るか・リスク・依存」を実測値で報告させる
- 必要性の意見と、やらないもの（理由つき）を利用者に示す。リファクタリングしない方がよい箇所を見つけるのも、この段階の仕事である

## 2. 計画を合意する

- **PR の分け方と順序を決める。**依存の向き（共通化を先、分割や改名を後）に並べ、1 本の PR は 1 つの目的に絞る
- 次の方針は、推奨案付きの選択式で先に決める。担当が作業の途中で止まらないようにするためである。
  - テストをどこまで削除してよいか
  - テスト ID の変更を許すか
  - 名前と配置の規則
  - 削除してよいかの判断が要るもの
- 全体計画 `REFACTOR-PLAN.md` を作る（ひな形は下）

## 3. PR ごとに進める

- **ブランチの積み方**：同じリポジトリの PR は、前の PR のブランチの上に積み、PR の base もそこにする。サブモジュールを持つ構成では、サブモジュールの PR を先に作る
- **担当への指示**：下のひな形で書く。進捗記録は 1 本の PR に 1 つ作る
- **問題の扱い**：担当は問題をその場で直さず、進捗記録に書いて止まる。判断は責任者がする
- **次の PR の前**：担当の報告を読んで判断を記録し、全体計画を更新してから次へ進む

## 4. 独立に検証する

- 実装した担当とは**別の担当**に検証させる。`git archive <branch>` で取り出したツリーの上で行わせ、作業ツリーには触らせない。こうすると、作業中の担当とぶつからず、実装した側の思い込みも混ざらない
- 変異検査は作業前の版にも同じ変異を当て、落ちるテストの集合を比べる。作業前の版でも落ちない変異は、既存の問題として記録する
- アプリを変えたなら、作業前の版を同じデータで別ポートに起動し、出力をバイト単位で比べる
- 差分を `CLAUDE.md` の Coding と `docs/CLAUDE.md` に照らした確認も、検証の担当に含める

## 5. PR を作り、報告する

- **PR 本文に書くこと**：
  - テスト件数の前後と、増減の理由
  - テスト ID の対応表（ID を変えた場合）
  - 検証の結果
  - 既存の問題
- **PR を作ったら**：全体計画の状態を更新し、その PR の進捗記録を消す
- **全部そろったら**：全体計画も消し、次の内容を報告する。
  - PR の URL とマージ順
  - 行数の前後
  - 私の判断で直したもの
  - やらなかったもの
  - 既存の問題（優先度をつけて、別の増やす作業の候補として）

## ひな形

どれも `local/<作業名>/` に置く（`local/` はリポジトリのルート。無ければ作る。git 管理外）。
計画・記録は**いつ消してもよい一時文書**である。コード・`docs/`・コミット・PR 本文から参照しない。
担当にはスクラッチパッドの中に自分用のサブディレクトリを使わせる。直下に置いたファイルは、別の担当に上書きされる。

### 全体計画 `REFACTOR-PLAN.md`

```markdown
# リファクタリング全体計画（すべて完了したら削除する）

## 承認済みの判断（日付）
- （テスト削除の範囲、テスト ID の変更、命名・配置の規則、削除するもの）
- やらない: （理由つき）

## 基準（作業開始時のブランチ、日付）
- （リポジトリごとのテスト件数・リンタの状態・対象の行数）

## PR 一覧
| id | リポジトリ | ブランチ | 内容 | 状態 |

## 別の作業として扱う既存の問題（今回は直さない）
- （見つけた順に追記する）
```

### 担当への指示（進捗記録 `REFACTOR-<id>.md` を兼ねる）

```markdown
リファクタリング PR <id>（<内容>）の担当です。日本語で書く。
振る舞いを変えない。アサーションを変えない。
問題や判断が要る点は独自に対処せず、進捗記録の「報告」節に書いて止まる。

## 前提
- リポジトリ: <path>（ブランチ <branch>。<base> の上に積んである）。触らない場所: <paths>
- まず読む: refactor スキル、<CLAUDE.md 群>、全体計画の「承認済みの判断」、前の PR からの引き継ぎ
- 進捗記録: <dir>/REFACTOR-<id>.md を最初に作る。冒頭にワークフロー表（手順・状態）、末尾に「報告」節。削除しない
- テスト: <command>（基準 <n> 件）。リンタ: <commands>
- コミット: 変えたパスだけを明示して git add。push しない。メッセージの形式: <形式と末尾の行>
- スクラッチパッドは <scratchpad>/<id>/ の下だけを使う

## 作業（候補ごとに 1 コミット。各コミットで全件緑）
<候補。事前調査の実測値と、壊してはいけない制約を添える>

## 検証（完了条件）
<SKILL.md の「検証」から当てはまるものを選び、この PR に合わせて具体的に書く>

## 報告節に書くこと
コミット一覧、行数の前後、件数の前後と理由、検証の結果、実施しなかった候補と理由、判断を待つもの、次の PR への引き継ぎ
```
