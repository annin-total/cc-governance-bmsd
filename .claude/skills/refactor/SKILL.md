# 減らす作業の手順

目的は**振る舞いを変えずに減らすこと**。機能の追加・変更はしない。途中で見つけた不具合や改善案は直さず、報告して別の作業にする。

## 着手前

1. 構成案・賛否・推奨度を示して合意を取る。いきなり手を動かさない
2. 両リポジトリ（server を触るなら submodule も）でブランチを切る。worktree は頼まれたときだけ
3. 基準を記録する: テスト件数（親・server）、`ruff check` / `format --check`、対象の行数
4. 進捗記録を `product/` の外に作り、冒頭にワークフロー（担当・状態）を書く。完了後に消す

## 進め方

- 責任者は監督に徹し、作業はサブエージェントに渡す（判断が要る作業は opus、機械的な追従は sonnet）
- **サブエージェントは問題をその場で直さない。**進捗記録に結果だけ書き、判断は責任者が行う
- 1 ステップ 1 コミット。どのコミットでもテストが全件通る状態を保つ。移動は `git mv`
- 同じリポジトリを並行して触る担当がいるときは、自分のパスだけを `git add` させる（`-A`・`commit -a` 禁止）
- 変異検査の前に必ずコミットする（戻しで自分の変更を消さない）

## 変えてよいもの・いけないもの

- ロジックとテストのアサーションは変えない。変えてよいのは、import パス・差し替え先・検査対象のパスの追従だけ
- 挙動が変わるものは、1 件ずつ承認を取ってから入れる
- 私的な定数は使う場所の隣に置く。複数モジュールにまたがる仕様値だけを集約する

## 削る基準

- docstring とコメントは、ルートの `CLAUDE.md` の Coding に従う。経緯・検証番号・仕様書の繰り返しは消す
- 生成物（`server/ccgov/vendor/`）と `tests/fixtures/hook_inputs/` は触らない
- 文書は `docs/CLAUDE.md` に従う。一方的に追記しない。直すときは周辺の古い記述・重複の削除とセットにする
- 削る理由に一次情報が要る記述を、新たに書き足さない

## 追従漏れを防ぐ

- 着手前に旧パス・旧モジュール名で両リポジトリを grep し、ヒットの一覧を進捗記録に置く
- 完了時に同じ語で grep して 0 件にする。ファイル名を書かずに旧構成を前提にした記述（「ルーティング層 1 ファイル」など）も探す
- 対象: コード・テストの docstring と検査対象のパス・`docs/`・`README.md`・各 `CLAUDE.md`・`scripts/`・`entry.sh`

## 検証（完了条件）

- テストが全件通る。件数の増減は理由を説明できる
- コメントだけを変えた Python は、docstring を除いた `ast.dump` が変更前と一致する（比較スクリプトも壊して検出できることを確かめる）
- server を触ったら: Docker の `python:3.9-slim` でテスト、`docker build`、waitress の実起動で認証・404・`/ingest`・`BASE_PATH` を確認
- 変異検査: 守っている仕組み（認証・複製のハッシュ検査・フレームワーク境界など）を壊すと検査が落ちる
- 作業前の版（`git archive <base> | tar -x`）を同じデータで別ポートに起動し、画面の HTML がバイト単位で一致する
- 生成物を動かしたら `scripts/sync_contract.py --check` と統合テスト

## 仕上げ

- PR は作業開始時のブランチへ向ける。server → 親の順（親は submodule のポインタを更新する）
- 進捗記録を消し、完了報告に「私の判断で直したもの」と「既存の問題（未対応）」を分けて書く
