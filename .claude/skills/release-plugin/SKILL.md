# プラグインをリリースする

目的は、**開発リポジトリで検証したプラグインを、そのままの中身で配布リポジトリへ入れ、導入できることを確かめた PR にすること。**
配布リポジトリの main へのマージが配布になる。このスキルはマージの手前で止まる。

対象の固有情報（リポジトリ・パス・名前・版の置き場・検証コマンド・設定値の扱い・手順書の場所）は `references/governance.md` にある。最初に読む。
手順書（前提・確認項目・配った後の作業）が別にあり、このスキルはそれを手順の中で読む。重ねて書かない。

## 前提を満たさないときは止まる

どの段でも、前提を満たさないもの（版が上がっていない、`release/<版>` がリモートに既にある、設定値が空、作業ツリーに変更がある、HEAD が push されていない、validate の `[NG]`、配布リポジトリの作業ツリーに変更がある など）に当たったら、
**その場で止まり、原因と対処の選択肢（推奨を付ける）を示して、利用者の承認を得てから進める。**
対処そのもの（版上げのコミットなど）も承認を得てから行う。自分の判断で飛ばしたり直したりしない。

## 流れ

コマンドは bash で書く。Windows でも Git Bash で同じコマンドが動く（Windows での通しは未検証）。
段を進めるたびに、何が通り何が残ったかを利用者に短く伝える。

### 1. 前提を調べる（調べれば分かることは聞かない）

- 開発リポジトリの作業ツリーに変更が無く、HEAD のコミットがリモートに push 済み（上流ブランチに含まれる）であること。ブランチは問わない。
  `git status --short` が空で、`git rev-parse --abbrev-ref @{u}` が上流ブランチを返し、`git fetch` の後に `git merge-base --is-ancestor HEAD @{u}` が成功すれば満たす。
  `rev-parse` が失敗すれば上流が未設定、`merge-base` だけが失敗すれば push されていない。
  このときのブランチ名と SHA を控え、コミットメッセージと PR 本文に書く
- **配布物のディレクトリに、OS が作るファイル（`.DS_Store`・`Thumbs.db`）以外の未追跡・無視されたファイルが無いこと**（`git status --short --ignored <配布物>`）。
  `git status` は無視されたファイルを表示せず、紛れたものはそのまま配られる
- 手順書の「前提」を 1 つずつ確かめる。テストは自分で流してよい。E2E（e2e スキルのリリース前の確認）を済ませたかは利用者に聞き、未実施なら先に行うかを聞く。
  作業ブランチからの導入の確認は e2e ではなく段 6 で行う
- 設定値の扱いは `references/governance.md`。**秘密の値は表示しない**（有無と形だけを見る）

### 2. 開発側で検証する

`references/governance.md` の開発側の検証を流す。`[NG]` が 1 つでもあれば差し込まない。直すのは開発リポジトリで、直したら 1 に戻る。

### 3. 配布リポジトリを用意する

配布リポジトリを clone する（既にあれば最新化する）。置き場と URL は `references/governance.md`。

```bash
git clone <配布リポジトリの URL> <置き場>                  # 無いとき
git -C <置き場> status --short                            # 既にあるとき。空であること
git -C <置き場> fetch origin && git -C <置き場> switch main && git -C <置き場> pull --ff-only
```

最新化した main で、開発リポジトリの版が差し込み先の版より上がっていることを確かめる（比べ方は `references/governance.md`）。
版を上げるのは開発リポジトリで、上げたら 1 に戻る。

版が上がっていれば、`release/<版>` がリモートに無いことを確かめてから作業ブランチを作る。
出力があればリモートに既にあるので、作らずに止まる。

```bash
git -C <置き場> ls-remote --heads origin release/<版>     # 何も出ないこと
git -C <置き場> switch -c release/<版>
```

配布リポジトリの main へは直接コミットしない。

### 4. 差し込んで一致を確かめる

差し込み先を開発リポジトリの配布物で丸ごと置き換える。差し込み先を直接編集しない（直すのは常に開発リポジトリ）。

```bash
rm -rf <置き場>/<差し込み先>
cp -R <開発リポジトリ>/<配布物> <置き場>/<差し込み先>
find <置き場>/<差し込み先> \( -name .DS_Store -o -name Thumbs.db \) -delete
diff -r -x __pycache__ -x .DS_Store -x Thumbs.db <開発リポジトリ>/<配布物> <置き場>/<差し込み先>
```

`diff` が何も出さずに終わることが合格。OS が作るファイルを消すのは、配布側の validate が無視されたファイルの混入として止めるため。`rm -rf` はパスを確かめてから実行する。シンボリックリンクの中を指定して消さない。

### 5. 配布側で検証してコミットする

配布リポジトリのルートで `python scripts/validate.py` を流し（`python` が無ければ `python3`）、**必ず全項目を通す。**
`[NG]` は配布リポジトリでは直さない。開発リポジトリを直して 1 からやり直す。

通ったら差し込み先だけを `git add` してコミットする。メッセージに版と、開発リポジトリのブランチ名と SHA を書く。

### 6. 作業ブランチから導入して確かめる

`references/verify-install.md` に従う。作業ブランチ（`release/<版>`）を配布リポジトリへ push し、そのブランチを ref に付けて導入する。
**push の前に利用者の承認を得る。**利用者本人の `~/.claude/` には触れず、`CLAUDE_CONFIG_DIR` で隔離する。
確かめた後で作業ブランチを変えたら、push と導入の確認をやり直す。

### 7. 確認項目を確かめ、PR を作成する

手順書の「確認項目」を 1 つずつ確かめる。機械で確かめられるものは自分で流し、人にしか確かめられないもの（サーバの Secret との一致など）は利用者に聞く。
すべて済んだら、6 で確かめた作業ブランチから配布リポジトリの main へ PR を作成する。本文には版・開発リポジトリのブランチ名と SHA・導入の確認の結果・確認項目の結果を書く。

### 8. 報告する

通した検証、導入の確認の結果、利用者が確かめた項目、確かめられなかった項目、残した一時ディレクトリを分けて報告する。
マージ後の作業（届いたことの確認）は手順書にあると伝える。

## 踏みやすいところ

- **版を上げ忘れると、変更は端末に届かないまま届いたことになる。**検出する仕組みは無いので、3 で配布リポジトリの版と比べる
- **配布側の validate の `[NG]` を配布リポジトリの中で直さない。**次の差し込みで消え、開発リポジトリとの一致も崩れる
- **緑でも、確認項目の人の確認が済んでいなければ PR に進まない。**送信先の誤りやトークンの不一致は検証スクリプトでは止まらない
- `diff` と validate は、差し込みのたびにやり直す（差し込み後に開発リポジトリを直したら 1 から）
