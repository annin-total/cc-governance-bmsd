# 文書を見直す

目的は、**文書・docstring・コメントを、実装と食い違わず、規約に沿った必要十分な量にすること。**
既定は減らす方向である。不要な情報は思い切って捨てる（履歴は git に残る）。
判断の基準は `docs/CLAUDE.md`（文書）と `CLAUDE.md` の Coding（docstring・コメント）が正本であり、このスキルは道筋だけを示す。

## 役割

- **責任者（あなた）**：監督に徹し、直すかどうかの判断に責任を持つ。小さな確認や修正は自分でしてよい
- **調査担当**：報告だけを行い、直さない
- **修正担当**：責任者が決めた修正だけを行う。想定外の判断が要る点は、直さずに報告して止まる
- モデルは用途で選ぶ。要否や食い違いの判断を伴う調査は opus、参照切れや旧名の照合のような機械的な作業は sonnet

## 流れ

1. **範囲を掴む（自分で）**：対象の文書と、`docs/CLAUDE.md`・`docs/README.md` の索引を読み、関係する実装を grep で当たる。
   深追いはせず、調査の分け方を決められれば足りる。対象・深さ・捨ててよい情報の種類などで迷う点が出たら、
   `AskUserQuestion` で選択式に、推奨 `(Recommended)` を付けて聞く。調べれば分かることは聞かない
2. **調査を任せる**：目的単位で、重ならず漏れないように分け、読み取り専用のサブエージェントに任せる。
   数は対象の量で決める（1 文書なら 1〜2、`docs/` 全体なら数本）。観点の例：
   - **実装との食い違い**：文書の主張を 1 つずつ、実装・テスト・設定と突き合わせる。どちらが正しいか分からないものは、推測で決めずに「不明」として返させる。
     `docs/knowledge/` は、一次情報（公式の文書・実測）と確認した版で照合させる
   - **要否と置き場**：実装を読めば分かることを書いていないか。1 つの事実を 1 か所にだけ書いているか。責務で閉じているか（混在していれば移動先）。関連する文書と矛盾していないか
   - **規約**：`docs/CLAUDE.md` の置き場・参照の向き・記述ルールに沿っているか
   - **docstring・コメント**：要るか。1 行に丸められるか（丸めても条件・例外・理由は落とさない）。経緯や仕様書の繰り返しになっていないか

   「失われると困る情報」だけでなく「**まだ削れる記述**」も探させる。前者だけを探すレビューは、文書を太らせる。
   報告は指摘ごとに、場所（`path:line`）・根拠・提案（削除・移動・修正・利用者に確認）を返させる。
   長くなるなら `.local/<作業名>/`（リポジトリのルート。git 管理外）に書かせ、パスだけを受け取る
3. **判断する（責任者）**：指摘ごとに採るかどうかを決める。食い違いと削除の根拠は、実物で確かめる。
   実装との食い違いは、聞く前に履歴（git log・PR・アーカイブ）で経緯を確かめる。
   利用者にしか決められないものは選択式で聞く。例：どちらが正しいか分からない食い違い、決着した判断に触れるもの、
   捨てると事故や誤った運用につながりうるもの、規約の例外にするもの、他のリポジトリに波及するもの。**迷ったら、推測で決めずに正直に聞く。**直すものがなければ、その旨を報告して終える
4. **ブランチを切って直す**：作業開始時のブランチから切り、PR もそこへ向ける。量が少なければ自分で、多ければ文書ごとに修正担当へ任せる
   - 移すときは、移動先に書いてから元を消す。移した先と参照元をそろえる。任せるなら、移動元と移動先を同じ担当に持たせる。
     移動先の層の性質に合うかも確かめる（未了の計画を手順書へ移さない、など）
   - 調査で対象外の文書との食い違いが見つかったら、同じ事実の食い違いは同じ PR で直す。それ以外の問題は報告に挙げるだけにする
   - 文書が正しく、実装のほうが誤っていると分かったら、実装は直さない。報告で別の作業として挙げる
   - サーバ（submodule）のコードの docstring・コメントは、サーバのリポジトリで別の PR にする
5. **確かめる**：当てはまるものだけを確かめる
   - 消した・移したファイルや見出しへの参照が、`docs/`・各 `CLAUDE.md`・README・コード・`.claude/skills/` の grep で 0 件
   - docstring・コメントだけを変えたなら、docstring を除いた `ast.dump` が作業前と一致し、`CLAUDE.md` の Commands のテストとリンタが通る。比較スクリプトも壊して、差を検出できることを確かめる
   - 中立的なサブエージェントに、差分を規約に照らして確認させる。消した記述ごとに行き先（移動先・decisions・コード）があるかも見させる。
     確認役は指摘だけを行い、採るかどうかは責任者が決める
6. **PR を作り、報告する**：PR作成は `CLAUDE.md` に従う。報告には、直したもの、捨てた情報とその理由、採らなかった指摘、見つけた実装側の問題を書く。
   未対応の実装側の問題は、`CLAUDE.md` の Scope 通り `.local/<作業名>/issues.md` に記録する。
   `.local/<作業名>/` を消すかどうかを選択式で聞くときは、この文書を残すかどうかも分けて聞く

## このプロジェクトで踏みやすいところ

- **文書と実装が食い違うとき、実装が誤っていることがある。**黙って文書を実装に合わせない
- **決着した判断の記録は、実装から読めないから価値がある。**`docs/decisions/` の「採らない理由」を、実装に現れないことを理由に「不要」として消さない
- **`docs/knowledge/` は実装と突き合わせられない。**古い疑いがあれば、一次情報で確かめるか「未検証」と明記する。公式の記述と実測が食い違うなら、どちらかに断定せず、版を添えて両方を書く
- **契約と設定値の正本は、コメントだけの変更でもサーバの複製に波及する。**`CLAUDE.md` の Design と Commands の同期の手順に従い、サーバ側の PR も要る
- コミットは自分が変えたパスだけを明示して `git add` する。自分以外の変更が混ざっていたら触らず、判断を仰ぐ
