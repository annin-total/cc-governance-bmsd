# 計画して実装する

目的は、**利用者と認識のずれがない変更を、確かめた PR にすること。**
道具は Claude Code の標準機能で足りる。このスキルが示すのは道筋と、このプロジェクトで踏みやすいところだけである。
段階を形式的に埋めるより、各段階の目的を果たすことを優先する。小さければ段階をまとめてよいが、**承認は省略しない。**

## 役割

- **責任者（あなた）**：主要な判断・利用者との対話・進捗記録のすべてに責任を持つ。作業は基本的にサブエージェントへ任せ、
  自分のコンテキストには結論だけを残す。小さな確認や修正は自分でしてよい
- **担当**：指示された範囲だけを行う。想定外の問題や判断が要る点は、直さずに報告して止まる
- **検証担当**：報告だけを行い、コードにも文書にも触れない。指摘を採るか、誰が直すかは責任者が決める
- モデルは用途で選ぶ。設計・判断・レビューは opus、範囲の決まった調査・機械的な追従・コマンドの実行は sonnet

## 流れ

### 1. ざっと掴む（自分で）

依頼を 1〜2 文で言い直し、`docs/README.md` の索引と grep で関係しそうな場所を当たる。
ここでは深追いしない。質問と調査の計画を立てられれば足りる。
依頼の前提が事実と違う（すでに満たされている、など）と分かったら、質問より先にその事実を示す。

### 2. すり合わせと調査（不明点がなくなるまで繰り返す）

- **聞く**：利用者にしか決められないこと（目的・範囲・優先・許容する限界）は `AskUserQuestion` で選択式に、推奨 `(Recommended)` を付けて聞く。
  散文で質問を並べない。調べれば分かることは聞かない。
  目的のように調査に依存しない問いは先に聞き、方式の選択肢は事実を調べてから示す（事実なしに並べた選択肢は公平にならない）
- **調べる**：読み取り専用のサブエージェントに任せる。観点は変更の広さに合わせて選び、無関係な観点は足さない
  - 実装：変更が触れる箇所と影響範囲。今どのテストが何を守っているか。端末とサーバの両側に及ぶなら両方
  - 文書：`docs/decisions/` の「採らない理由」「受け入れた限界」、`docs/remaining/` の未了の作業と未検証事項、`docs/spec/` の不変条件
  - 守り：誰の何を集め、誰が見るか。個人の特定や本人確認に触れないか
  - 外界：上流（Claude Code・DB・実行基盤）の挙動を前提にするとき。上流の既存機能で依頼が満たせないかも見る。`docs/knowledge/` と一次情報を見る
  - 動かして確かめるのは、方針の選択を左右する事実に限る。隔離の方法は `docs/guide/` の実機検証の手順に従う
- 報告は短く、根拠は `path:line` で返させる。長いものはファイルに書かせ、パスだけを受け取る。
  方針を左右する根拠だけは、責任者が実物で確かめる

### 3. 方針を提案し、承認を取る

- **論点を詰める**：先に、方針に含まれる利用者が決める論点（何を送るか・どこまでやるか・画面に出すか・PR の分け方など）を
  1問1論点で、推奨を付けて選択式で聞く。論点どうしが依存するなら、前の答えを受けてから次を聞く。
- **承認を取る**：論点がすべて決まってから、次のことを短く示し、「これで実装に進んでよいか」「ブランチ作成・コミット・push・PR作成
  をどこまで対応してよいか（推奨はすべて）」を選択式で確認する。**承認なしに実装に進まない。**
  - 何を変え、何を変えないか
  - 既存の判断に触れるなら、どの記録にどう触れるか。覆すなら、何の前提が変わったのか（示せないなら、覆す案を推奨しない）。
    判断の適用範囲を広げる・狭めるときや、「範囲の外」と解釈するときも、同じように明示する。黙って解釈しない
  - PR の分け方（目的ごとに 1 本）と順序
  - 検証の方法
  - 更新する文書

以降は、方針から外れる判断が出たときだけ利用者に戻る。

### 4. 進捗記録を作る

`references/progress-template.md` を読み、`.local/<作業名>/` に作る（`.local/` はリポジトリのルート。無ければ作る。git 管理外）。
PR が 1 本なら `progress.md` だけ。2 本以上なら全体の `progress.md` と、PR ごとの記録を**着手時に**作る。
記録は**いつ消してもよい一時文書**である。コード・`docs/`・コミット・PR 本文から参照しない。残すべき事実は `docs/` か PR 本文に書く。

### 5. PR ごとに実装する

- 作業開始時のブランチから切る。同じリポジトリの PR は前の PR のブランチに積む
- 担当への指示はひな形に沿って書く。テストを先に書かせ、今の実装で落ちることを確かめてから実装させる
- 担当の報告を読んで判断を進捗記録に残し、次へ進む
- 文書は同じ PR で直す。書くかどうか・書き方は `docs/CLAUDE.md` に従う。作業のメモは `docs/` や README ではなく進捗記録に書く
- 足すだけで終えない。この変更で古くなった記述・重複・使われなくなったコードは、文書でもコードでも同じ PR で消す（片付いた `docs/remaining/` の項目も）

### 6. 検証する

規模が小さければ自分で確かめてよい。そうでなければ、実装とは別の担当に任せる。確かめることは次のとおり。

- `CLAUDE.md` の Commands のテスト・リンタが通る（サーバを変えたなら `server/` でも）。件数の増減を説明できる
- 足したテストは、実装を壊すと落ちる（壊すのは作業ツリーの外の複製で）
- `CLAUDE.md` の Coding 規約に従っている。docstring とコメントが最小限になっている
- `CLAUDE.md` の Design が挙げる守りを崩していない
- 文書が実装と食い違っていない。この変更で古くなった記述や重複が残っていない。方針と差分に過不足がない

### 7. PR を作り、報告する

- PR 本文：目的、覆した判断とその理由、テスト件数の前後、検証の結果（壊して確かめたものを含む）、やらなかったこと、見つけた既存の問題、マージ順（複数のとき）
- 起動したプロセスや一時ファイルの残骸を片付ける
- 完了報告では、確かめた事実と推測を分ける。最後に、進捗記録を消すか残すかを選択式で聞く

## このプロジェクトで踏みやすいところ

- **決着済みの判断を知らずに覆す。**`docs/decisions/` を関連語で全文検索してから「記録なし」とする。別の見出しで決着していることがある
- **緑のテストは証拠にならない。**検査が存在するのに何もゲートしていない、がこのプロジェクトの支配的な失敗である
- **契約のずれは無言で起きる。**増えた項目は黙って捨てられ、減った項目は黙って NULL になる。端末とサーバをまたぐ変更は、
  実際のデータが両側を通ることで確かめる。正本を変えたら `CLAUDE.md` の Commands にある同期の手順を実行する
- **個人の監視にしない。**少人数に絞れる集計は実質的に個人を指す。サーバから本人にデータを返す案は、本人確認の設計を伴う
- **増やす作業と減らす作業を混ぜない。**この変更と無関係な肥大化や重複に気づいても、ここでは直さず、報告で refactor の候補として挙げる
- **利用者の実環境と本番に触れない。**利用者本人の設定を書き換えない。検証の送信先を本番に向けない
- **`git status` は無視されたファイルを見せない。**配布物にファイルを足したら、`git check-ignore` で飲まれていないかを確かめる
- コミットは自分が変えたパスだけを明示して `git add` する。自分以外の変更が混ざっていたら触らず、判断を仰ぐ
