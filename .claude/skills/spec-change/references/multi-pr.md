# PR が複数になるとき

計画で PR を分けるときに読む。調査・計画書・進捗の記録・承認の流れは SKILL.md のまま変えない。変わるのは、PR の積み方と進め方だけである。

## 分けるかどうか

次のどれかに当たれば分ける。

- submodule（`server/`）を変える。サーバのリポジトリに別の PR が要る
- 依存の向きがある（契約や共通部品を先に変え、使う側を後に変える）
- 1 本ではレビューできない大きさになる

**1 本の PR は 1 つの目的に絞る。**増やす変更と減らす変更を同じ PR に混ぜない。

## 積み方

- **submodule の PR を先に作る。**親の PR は、submodule のポインタをその PR の先端に向ける。
  サーバ側の作業とコミットは `server/` の中で行う
- 同じリポジトリの PR は、前の PR のブランチの上に積み、base もそこにする
- 契約を変えるときは、サーバが新しい列を受けられる状態を先にマージする。
  逆の順だと、プラグインが送った列をサーバが黙って捨てる

## 進め方

- 進捗は `progress.md` に PR ごとの行を作って管理する。PR ごとに実装 → 独立検証 → PR 作成を回す
- 次の PR に進む前に、前の PR の検証結果を読み、`PLAN.md` の PR の表を更新する
- 各 PR の本文にマージ順を書く（例: `cc-governance-server#12 → この PR`）
