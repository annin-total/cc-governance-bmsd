# 仕様変更

目的は、**過去の判断と矛盾しない変更を、検証済みの PR にすること。**主な用途は仕様変更と機能追加で、
原因が分かっている不具合の修正にも使える。減らす作業（リファクタリング・文書の見直し）は混ぜない。
途中で 200 行超えや重複に気づいても、この作業では直さず、報告で別の作業として挙げる。

このプロジェクトで最も起きやすい失敗は、次の 2 つである。

- **決着済みの判断を知らずに覆す。**`docs/decisions/` には「採らない理由」と「受け入れた限界」が書かれている。
  読まずに進めると、却下済みの案を理由も示さずに実装してしまう
- **何もゲートしていない検査を、検証済みと思い込む。**緑のテストは証拠にならない。実装を壊して落ちることを確かめる

この手順は、この 2 つを防ぐために組んである。

責任者（あなた）は監督に徹する。調査・実装・検証はサブエージェントに任せ、あなたは分担・進捗・判断・利用者との合意に責任を持つ。
判断が要る作業には強いモデルを、機械的な確認には軽いモデルを使う。

## 手順

規模にかかわらず、毎回この順で進める。PR が複数になるとき（submodule をまたぐときを含む）は、計画の段階で `references/multi-pr.md` を読む。

### 1. 受け止めて、足場を作る

- 依頼を 1〜2 文で言い直し、**作業名**（ケバブケース）を決める
- 作業の記録は `local/<作業名>/` に置く（`.gitignore` 済み）。`docs/` には置かない。`docs/` は現時点で正しいことだけを置く場所である
- 進捗表 `progress.md` を作る。段階・担当・状態・成果物のパスを 1 行ずつ書く。中断しても、ここから再開できるようにする
- **作業開始時のブランチと commit** を記録する（submodule も）。PR はこのブランチへ向ける
- `git status` で、自分以外の未コミットの変更がないかを確かめる。あれば触らず、進め方を利用者に確認する
- 調査対象を、記録した commit からスクラッチパッドに `git archive` で取り出す。並行作業で作業ツリーが動いても、調査結果がぶれないようにするためである

依頼が曖昧で調査の範囲すら決まらないときだけ、ここで選択式で確認する。それ以外の疑問は調査結果とまとめて、承認①で確認する。

### 2. 調査する

`references/investigation-brief.md` を埋めて `local/<作業名>/00-brief.md` を作る。各レーンにはこれを読ませ、プロンプトには担当と疑いどころだけを書く。

**調査の範囲は、変更が触れるところに絞る。**網羅的に疑うのは spec-review の役目であり、この作業の目的は変更を安全に入れることである。
レーンは次の 3 つを材料に、変更の広さに合わせて選ぶ。端末の中で閉じる変更なら、L1 と L2 を 1 つのレーンにまとめてよい。

| レーン | 見るもの | 置く条件 |
| --- | --- | --- |
| L1 実装 | 変更が触れる実装・テスト・契約（`contract.py` / `policy.py`）・サーバ側の受け口。影響範囲と、今どのテストが何をゲートしているか | 常に |
| L2 文書 | `decisions/` の採らない理由・受け入れた限界、`remaining/` の既知の課題・未検証事項、変更が触れる `spec/` の不変条件。**関連語で全文検索してから「記録なし」と書く** | 常に（L1 とまとめてもよい） |
| L3 外界 | `docs/knowledge/` と一次情報。変更が前提にする上流の挙動、上流の現行機能で代替できないか | 変更が上流（Claude Code・DB・実行基盤）の挙動を前提にするときだけ |

各レーンは `L<n>-<名前>.md` を書き、最終メッセージではファイルパスと要点 3 行だけを返す。

### 3. 反証する（省略しない）

レーンを書いた担当とは**別の担当**に、`references/verify-brief.md` に従って調査結果を疑わせる。
とくに次の 3 点を確かめさせる。

- 「記録なし」「未検討」と書いたもの
- 依頼の前提が事実と合っているか
- 提案が不変条件や決着済みの判断と衝突しないか

省略しないのは、「過去に検討済み」の見落としが、この作業で最も高くつく誤りだからである。
現行の記録に見当たらなくても、別の文書の別の見出しで決着していることがある。

### 4. 承認①: 調査結果と方針

責任者が調査と反証を読み、次のことを利用者に示す。

- 現行の仕様（事実）
- 関連する決着済みの判断（ファイルと見出し）
- 変更案の選択肢と、それぞれの長所と短所

方針は、推奨案付きの選択式で確認する。

- **決着済みの判断を覆すなら、それを明示して承認を取る。**どの記録を、何の前提が変わったから覆すのかを示す。示せないなら、覆す案を推奨しない
- 変更しない結論になったら、ここで止める。新しく「採らない」と決めたことを `decisions/` に残すかを提案する（残すなら、文書だけの小さな変更としてこの手順を続ける）

### 5. 計画書を書き、承認②を取る

`references/plan-template.md` の構成で `local/<作業名>/PLAN.md` を書く。利用者には要約（変更の一覧・PR の分け方・検証の方法・やらないこと）を示し、承認を取る。
**この承認に、ブランチの作成と PR の公開を含める。**以降は、計画から外れない限り PR 作成まで止まらない。

### 6. 実装する

- 作業開始時のブランチから、新しいブランチを切る（`feat/<作業名>`、不具合の修正なら `fix/<作業名>`）
- 実装はサブエージェントに任せる。`PLAN.md` と `CLAUDE.md` の Coding・Design を読ませ、手順ごとに `progress.md` を更新させる
- **テストを先に書き、今の実装で落ちることを確かめてから実装させる**
- 計画にない問題や判断に出会ったら、担当はその場で直さずに記録して止まる。判断は責任者がする。計画を変えるほどの判断なら、利用者に確認する
- 契約（`contract.py` / `policy.py`）を変えたら、`CLAUDE.md` の Commands にある `sync_contract.py` で複製を書き出す
- 文書は同じ PR で直す。決着済みの判断を覆したなら、`decisions/` と `spec/` を現在の正しい形に書き換える。書き方は `docs/CLAUDE.md` に従う
- コミットでは、自分が変えたパスだけを明示して `git add` する。`-A` や `commit -a` は使わない。コミットの前に `git status` と `git log -1` を見る

### 7. 独立に検証する

実装した担当とは**別の担当**に検証させる。`git archive <ブランチ>` で取り出したツリーの上で行わせ、作業ツリーには触らせない。
確かめさせることは、`PLAN.md` の「検証」の項目に加えて次のとおり。

| 確かめること | 方法 |
| --- | --- |
| テスト・リンタ・契約の複製 | `CLAUDE.md` の Commands を実行する（サーバを変えたなら `server/` でも）。件数の増減を説明できるか |
| 足したテストが実際にゲートしているか | 実装を 1 か所ずつ壊し、足したテストが落ちることを確かめる。作業前の版に当てても落ちるなら、それはこの変更のテストではない |
| 守りが残っているか | hook の `exit 0` と標準エラーへの無出力、収集の最小化など、`CLAUDE.md` の Design が挙げる守りを変更が崩していないか |
| 規約 | 差分が `CLAUDE.md` の Coding と `docs/CLAUDE.md` に沿っているか |
| 文書と実装 | `spec/`・`decisions/` の記述が実装と食い違っていないか。1 つの事実を 2 か所に書いていないか |
| 計画との差 | 計画にない変更が混ざっていないか。計画にある変更が抜けていないか |

検証の担当は指摘を報告するだけにする。指摘が妥当かどうかは責任者が判断し、直す作業は実装の担当に戻す。

### 8. PR を作り、片付けて報告する

- PR は作業開始時のブランチへ向ける。本文に次のことを書く
  - 概要
  - 覆した判断とその理由
  - テスト件数の前後と、増減の理由
  - 検証の結果（壊して確かめたものを含む）
  - マージ順（複数 PR のとき）
  - やらなかったこと
  - 見つけた既存の問題
- 残骸を確かめる。起動したプロセス、スクラッチパッドの大きな生成物、利用者の設定ファイルの更新時刻を見る
- `local/<作業名>/` は、PR がマージされたら消してよいと利用者に伝える
- 報告では、確かめた事実と推測を分ける。調査で得た外界の事実（上流の仕様・実測値）を `docs/knowledge/` へ移すかは、
  `docs/CLAUDE.md` の基準に照らして利用者に提案する
