**現在の設計がそうであり、作業では解消しないもの。**
やれば終わる作業は `remaining/` にある。ここにあるのは、やっても終わらないことである。

設計書 `design.md` §11 が挙げるものは繰り返さない。索引だけを置く。

| 設計書 | 中身 |
| --- | --- |
| §11.1 | 原理的に答えられない問い（誰が何に使ったか・端末別コスト・正確な利用回数・純粋な因果効果・自己選択バイアス・対照群の不在・暦日との交絡） |
| §11.2 | 意図的な割り切り（「書けたこと」は「効いていること」ではない・上書き前の利用者固有の値は復元しない・配布した設定値を即時に撤回できない・導入そのものは強制できない・`user_email` は自己申告・画面の認証を Ingress に委ねる・復旧できるのは最後の複製時点まで） |

## 1. データの型と桁

### MySQL では 2038 年以降の `ts` を保持できない

MySQL の `INTEGER` は 32bit（`INT`）である。契約は `ts` を `INTEGER` と宣言しているため、
`2147483647`（2038-01-19）を超える値は格納できない。
契約側の範囲検査は符号付き 64bit を通すので、ここで弾かれることはない。

SQLite の `INTEGER` は 64bit であり、**SQLite だけの確認では表に出ない。**
実接続での挙動は未検証である。

### ポリシーから消したキーの撤回を定義していない

誤った値は、正しい値を配り直して上書きする。
サーバから端末へ指示する経路を持たないため、キーそのものを消すことはできない。

---

## 2. 集計と画面

### 同一の `ts` を持つ行のタイブレークが定義されていない

「最後に観測した値」は `ts` の降順で 1 行を選ぶ。
同じ `ts` の行が複数あるとき、どれが選ばれるかは決まっていない。

### 版の分布は、参照キーの行を持たない端末を落とす

版の分布は特定のポリシー項目の行から取るため、その項目の行を持たない端末は分布に現れない。
実運用ではポリシーの全項目が同時に記録されるため、現状は表に出ない。
**MySQL では並び順も不定である。**

### コンテキスト量の分布は準拠者 1 人につき 1 クエリを発行する

利用者数に比例してクエリ数が増える。140 名規模では問題にならない。

### 取込ディレクトリが未設定のとき、取込は静かに「0 件成功」になる

起動スクリプトと `Dockerfile` が必ず設定するため、運用では表に出ない。

### 取込に失敗したファイルの文言には、ファイルの絶対パスが含まれる

その文字列はそのまま画面に出る。画面は Ingress 認証の内側にある。

## 3. 両 DB 対応の割り切り

### SQL の文字列リテラル中の `?` もプレースホルダとして置換される

方言の分岐を `db.py` 1 ファイルに閉じるための割り切りである（設計書 §5.5）。
集計 SQL に `?` を含む文字列リテラルを書かない前提に立っており、検査は持たない。

### SQLite 3.25〜3.31 では統計情報の収集量を絞れない

`PRAGMA analysis_limit` は SQLite 3.32 以降にしか無く、未対応の版では黙って無視される。
設計の前提は 3.25 以降であるため、この範囲の穴が残る。

### InnoDB の行フォーマット次第でインデックスの作成が失敗しうる

最長のインデックスは utf8mb4 換算で約 2,552 バイトである。
MySQL 8.0 既定の DYNAMIC（上限 3,072）には収まるが、COMPACT / REDUNDANT（767）では作成が失敗する。
接続先の設定は未検証である。

## 4. 検査の限界

### 切り詰めと置換が起きたこと自体は記録されない

契約は宣言長で切り詰め、符号化できない文字を置換する。行は失われないが、
**長い値が来ている列は、集計上は短い値に化けて見える。** 元の値を復元する手段は無い。

### Flask の `test_client()` ではヘッダの符号化欠陥を検出できない

`test_client()` はヘッダを復号済みの文字列としてそのまま渡し、
WSGI の latin-1 による線上の符号化を経由しない。
ヘッダに関する検査は WSGI 環境を直接組むか、実サーバを立てて行う必要がある。

### 案内日を記録しても、自己選択バイアスは残る

段階的な案内は効果測定の識別の前提を作るが、導入するかは利用者が決める。
早く導入する利用者がもともとヘビーユーザーである可能性は消せない。

---

## 5. 範囲外

- **配布物の署名・改ざん検知を持たない。**
- **群の割り当てを使った統計的な検定を行わない。** 効果測定の画面が出すのは相対日の傾きであり、因果効果ではない。
- **監視・アラートを持たない。** デプロイログの確認で足りる規模である。
- **負荷試験・スケールアウトを行わない。** SQLite 運用ではスケールアウトできない。
- **Kubernetes への移行手順を持たない。** `Dockerfile` を用意するところまでである。
