# 社内リポジトリへの到達が要る配布の作業

開発機からは社内リポジトリに到達できないため、到達できる端末で行う。
手順は `../guide/release.md` にある。ここにあるのは、まだ 1 度も通していない確認と作業である。

## git リモートを `source` にしたときの伝播を確かめる

`../guide/release.md` の「届いたことを確認する」と `../knowledge/claude-code-behavior.md` が置く
伝播の前提（次の起動か `/reload-plugins` で反映・到達不能でも複製で動き続ける）が、社内リポジトリの経路でも
成り立つかを確かめる。自動更新が走る条件は `../knowledge/claude-code-behavior.md`、所要時間の実測は
`../knowledge/measurements.md` にある。

1. 配布リポジトリを社内リポジトリへ push し、隔離した設定ディレクトリでマーケットプレイスとして登録・導入する
2. **確認 A — 更新が届くまで。**リモートの `version` を上げて push し、「対話セッションでメッセージを送り、
   10 分以上置いてから終了 → 次のセッションを開いて `claude plugin list` の版を見る」を繰り返す。
   反映までの起動回数とおおよその時間を記録する。隔離した設定で試すときは、未ログインではメッセージを送れないため
   自動更新を起こせないこと（推定）と、`autoUpdate` が次のセッションから効くことに注意する（`../knowledge/claude-code-behavior.md`）
3. **確認 B — 到達できないとき。**ネットワークか認証情報を外して新しいセッションを開き、
   最後に同期した状態で動き続けることを確かめる。前提と食い違えば、勝手に判断せず報告する
4. **確認 C — 導入の完了。**`/plugin` の一覧に版番号つきで現れることを確かめる
5. 隔離した設定ディレクトリを片付け、本人の登録と導入済みプラグインが作業前と同一であることを確かめる

**完了条件** — 確認 A・B・C のそれぞれに観測した事実が 1 つずつ `../guide/release.md` に
書かれていること。「おそらく」を残さず、確かめられなかったものはそう書く。

## 初回リリースと第 1 群への案内

上の確認と、`deploy.md` の本番デプロイが済んでから行う。

1. `../guide/release.md` の手順どおりに 1 回通す。手順書に無い操作が要ったら手順書の方を直す
2. 第 1 群へ案内を出し、出した日を `../guide/onboarding.md` の記録欄に書く
3. 第 1 群の数名が案内文のコマンドだけで導入を完了できるかを見て、詰まった箇所を `../guide/onboarding.md` に反映する

**完了条件** — `events` の件数が 0 より大きく、`policy_state` の版が初回リリースのものだけで、
サーバのログに受信の 401 が並んでいないこと。

## 配布が届いたことを確かめる

- 案内から 1 週間後、設定の適用状況のバージョンのタブの利用者数を第 1 群の人数と突き合わせる
- 第 2 群の案内後に 2 回目のリリースを行い、古い版が数日かけて分布から消えることを見る。
  残る端末は、自動更新の設定（`/plugin`）と `source` への到達を個別に見る

**完了条件** — 2 回目のリリース後に新しい版が分布に現れること。
