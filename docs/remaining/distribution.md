# 社内リポジトリへの到達が要る配布の作業

開発機からは社内リポジトリに到達できないため、**到達できる端末で行う。**
手順そのものは `../release.md` にある。ここにあるのは、まだ 1 度も通していない確認である。

---

## 1. git リモートを `source` にしたときの伝播を確かめる

**なぜ** — 実際の配布経路は社内リポジトリである。ここを 1 度通しておかないと、
「施策の変更がいつ端末に届くか」を運用として答えられない。
設計書 §8.5 が置く前提（約 15 分の遅れ・次の起動で反映・到達不能でも複製で動き続ける）が
この経路でも成り立つことを確かめる。

**やること**

1. 配布リポジトリを社内リポジトリへ push する（初回はリモートの作成を含む）
2. 隔離した設定ディレクトリで、社内リポジトリの https URL をマーケットプレイスとして登録し、プラグインを導入する
3. **確認 A — 更新が届くまでの時間。** リモート側の `version` を上げて push する。
   **1 回起動して即座に版が変わることを期待しない。**
   「セッションを開始して 15 分以上そのままにし、終了する → 次のセッションを開始する →
   `claude plugin list` の版を見る」という手順で、
   **push から端末に反映されるまでに何回の起動と、おおよそどれだけの時間が要ったかを記録する**
4. **確認 B — 到達できなくなったときの挙動。** ネットワークまたは認証情報を外して到達不能にし、
   新しいセッションを開始する。**端末にある複製がそのまま使われ、最後に同期した状態で動き続けること**を確かめる。
   止まるのは更新だけである。観測が設計書の記述と食い違った場合は、**勝手に判断せず報告する**
5. **確認 C — 導入が完了していることの確認。** 導入した端末で `/plugin` の一覧に**版番号つきで現れる**ことを確かめる。
   **設定ファイルに記載があるだけでは導入が完了しないことがある。** 確認 A で版が上がったあと、
   一覧の版番号が新しい版になっていることも合わせて見る
6. **原状復帰する。** 隔離した設定ディレクトリを片付け、本人のマーケットプレイス登録と
   導入済みプラグインが作業前と同一であることを確かめる
7. 結果を `../release.md` に書く

**終わりの判定** — 確認 A・B・C のそれぞれに、観測した事実が 1 つ書かれていること。
**「おそらく」「と思われる」を残さない。** 確かめられなかったものは「確かめられなかった」と書く。

## 2. 初回リリースと第 1 群への案内

**依存** — 上の「1.」と、`deploy.md` の本番デプロイ。

**やること**

1. サーバがデプロイ済みで待受していることを確認する
2. `governance/config.json` の送信先 URL が、デプロイ済みのサーバの URL と一致していることを確認する
3. `governance/config.json` の受信トークンが、サーバの Secret ファイルの `INGEST_TOKEN` と
   **文字列として完全に一致**していることを確認する。
   **不一致なら全端末の送信が 401 になり、イベントは 1 件も保存されない**
4. `../release.md` の手順どおりに 1 回通す。**手順書に書かれていない操作を差し込まない。**
   必要になったら手順書の方を直す
5. 配布リポジトリで PR を作り、マージする
6. 第 1 群へ案内を出す。実際に出した日を `../onboarding.md` の記録欄に書く
7. 第 1 群のうち数名で、案内文のコマンドだけを見て導入が完了することを確認する。
   詰まった箇所は `../onboarding.md` に反映する

**終わりの判定** — 導入した端末から実際にイベントが届いていること。
`events` の件数が 0 より大きく、`policy_state` の版が初回リリースのものだけであること。
**サーバのログに受信の 401 が並んでいないこと。** 並んでいればトークンの不一致であり、手順 3 に戻る。

## 3. 配布が届いたことを確認する

**依存** — 上の「2.」。

**やること**

- 第 1 群の案内から 1 週間後、概況画面の健全性の行を見る
- 版の分布に現れる端末数と、第 1 群の人数を突き合わせる。差が大きければ、
  導入が進んでいないのか、イベントが届いていないのかを切り分ける
- 第 2 群の案内後、2 回目のリリース（`version` を上げる変更）を 1 回行い、
  **古い版が分布から消えていくこと**を確認する。反映されるのは次に起動したときであるため、数日かけて見る
- それでも古い版が残る端末があれば、その端末で自動更新が有効になっているか（`/plugin` の画面）と、
  マーケットプレイスの `source` に到達できているかを個別に見る。
  **到達できていない端末は、最後に同期した版のまま黙って動き続ける。** 版の分布がその唯一の手がかりである
- 準拠開始日が群ごとにずれていることを、効果測定の画面の準拠者数の推移で確認する。
  **ずれていなければ、段階的な案内は効果測定の識別の前提として機能していない。** その事実を記録する

**終わりの判定**

- 健全性の行に版の分布が表示され、値が 1 つ以上出ている
- 2 回目のリリース後、新しい版が分布に現れている
- 準拠者数の推移に、群の案内日に対応する立ち上がりが見える
