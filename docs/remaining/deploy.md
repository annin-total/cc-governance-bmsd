# 実行基盤への到達が要る作業

開発機からは実行基盤にも社内リポジトリにも到達できないため、**到達できる端末で行う。**
順序は上から下へ。疎通の確認（1〜5）を通してから、本番の構築（6〜11）へ進む。

---

## 1. 社内リポジトリへ反映し、Function を作る

**やること**

- 社内リポジトリへ push し、自動デプロイの対象ブランチを決める
- リポジトリの設定に、基盤が公開している公開鍵をアクセスキーとして登録する（初回のみ）。
  **これが無いと基盤がリポジトリを取得できない**
- Function を作る。**次の設定項目はいずれも基盤側の手作業であり、リポジトリの中身では代替できない**
  - **タグ `NGINX_ENABLE_REWRITE_TARGET` を `false` にする。** 既定のままだと基盤がリクエストパスを書き換え、
    `SCRIPT_NAME` を与える前提（設計書 §4.3）と噛み合わなくなる。白黒は「4. 公開サブパスを確定する」で付く
  - **スケールアウトの設定をしない。** SQLite で運用する場合、永続領域上の 1 ファイルを
    複数のレプリカが掴むと壊れる

**終わりの判定** — 自動デプロイが走り、デプロイログが出ること。

## 2. Secret が無ければ起動しないことを確かめる

**なぜ** — 黙って起動すると、受信トークンが未設定のまま待ち受ける状態になる。
全端末の送信が 401 で跳ね返り続け、**端末は spool を残すので失われはしないが、誰も気づかないまま溜まる。**

**やること** — Secret ファイルを置かないままデプロイし、デプロイログを読む。

**終わりの判定** — 起動せずに終了していること。

## 3. Secret を置き、install と待受が通ることを確かめる

**やること**

- Open Terminal から `/mnt/data/secrets/` を作り、`cc-governance-bmsd.env` を `KEY=VALUE` 形式で置く。
  **権限を `600` に絞る**
- 置く鍵は `BASE_PATH` / `DB_DSN` / `INGEST_TOKEN` / `CSV_DIR` / `PKG_PROXY` の 5 つ（設計書 §4.6）。
  **値をこのリポジトリにも git にも書かない。社内のホスト名も同様である**
- `PKG_PROXY` は必須である。起動スクリプトは未定義の変数で落ちる
- **依存の install に使うコマンドが `pip` か `pip3` かを確かめる。** Open Terminal から
  `command -v pip; command -v pip3` を実行し、起動スクリプトが書いている方が PATH にあることを確認する。
  無ければ、実在する方に直して再デプロイする
- Function を restart する。**起動スクリプトは起動時に 1 度だけ Secret を読むため、ファイルを置いただけでは反映されない**
- **起動時にプロキシ設定が効いていることを確かめる。** install が失敗する場合、サーバは 1 度も上がらない
- デプロイログの時刻から、**スクリプト開始から待受までの所要時間を測って記録する**

**終わりの判定** — 待受に到達し、所要時間が記録されていること。

**測定値の使い道** — 依存の install を含んだこの実測値で、端末側の送信タイムアウト 60 秒（設計書 §3.5）の
妥当性が決まる。**60 秒を超える場合は、`_sender.py` の POST タイムアウトを
コールドスタート時間より長い値へ見直す。**

## 4. 公開サブパスを確定する

**やること**

- 基盤が払い出した URL のパス部分を控える。これが `BASE_PATH` の値になる
- Secret ファイルに `BASE_PATH` を実際の値で書く。**末尾スラッシュを付けない**
- restart し、公開サブパス付きの URL が `200` を返すことを確かめる
- 画面が生成するリンクにサブパスが載ることを確かめる。
  **ここが崩れると、画面のどのリンクを踏んでも基盤の共有ドメイン直下へ飛ぶ**

**前段の扱い** — **前段がサブパスを剥がすか剥がさないかで、設定も実装も変えない。**
ラッパは `PATH_INFO` が `BASE_PATH` で始まっていれば剥がし、始まっていなければ何もしない（設計書 §4.3）。
ただし**どちらだったかは観測して記録する。** `BASE_PATH` を空にしたまま
公開サブパス付きの URL を叩いたときの応答コードで分かる。

## 5. 作業ディレクトリがサーバのフォルダであることを確かめる

**やること** — **デプロイ単位はリポジトリルート、プロセスの作業ディレクトリはサーバのフォルダ**、
という 2 つが同時に成り立っていることを確かめる。

**なぜ** — ここが崩れると、サーバが契約の正本を参照する経路（設計書 §6.1）が成立しない。
`governance/` と `cc-governance-bmsd-server/` が同じ木の下に並んでいることが、
契約を 1 ファイルに保つ前提である。

## 6. アイドル時にコンテナが停止するかを確かめる

**やること**

- 一定時間（30 分・数時間・1 日の 3 点を目安）アクセスせずに放置し、
  そのあとの初回リクエストの応答時間を測る
- デプロイログに、放置期間中の停止と再起動の痕跡が出るかを見る

**判定**

- **停止しない、または初回応答が 60 秒未満** → 設計のまま。変更しない
- **停止し、かつ初回応答が 60 秒以上** → **`_sender.py` の POST タイムアウトを、
  実測のコールドスタート時間より長い値へ引き上げる**

**コールドスタートそのものは問題にならない。** 端末の送信は切り離されたプロセスの中で行われ、
Claude Code の応答をブロックしない（設計書 §3.5）。問題になるのは、
コールドスタートの所要時間が端末側の POST タイムアウトを超えることだけである。
短いタイムアウトは、守るものが無いところで spool を溜め、上限による破棄を早める。

## 7. MySQL 接続時の初期化を確かめる

接続先の MySQL が用意できる場合のみ行う。**用意できない場合は SQLite で運用し、
この項目を本番デプロイの前に必ず通す宿題として残す。**

**やること**

- `sql_require_primary_key` の値を確かめる
- Secret ファイルの `DB_DSN` を MySQL に向けて restart し、起動時の初期化が通ることを確かめる
  （DDL の適用・インデックスの存在確認・列の突き合わせ）
- 統計情報の更新が MySQL で動くことを確かめる

**判定**

- **`0`** → 設計のまま。変更しない
- **`1`** → **主キーを持たない 3 テーブルの `CREATE TABLE` が拒否される。**
  拒否されるのは初期化だけで、**テーブルさえ用意されていれば INSERT は通る**（設計書 §5.5）。
  取れる道は 2 つあり、どちらも管理者への依頼になる。**勝手に決めずに判断を仰ぐ**

**合わせて確かめること**

- ドライバの戻り値の列位置（`SHOW INDEX` の `Key_name`、`SHOW COLUMNS` の `Field`）。
  既定のカーソル（タプル返し）を前提にしている
- 置換後の文字列が問題なく保存されること
- 複数行 INSERT の部分失敗の粒度。ドライバが文をどう組み立てるかで変わる
- 初期化で例外が起きたときのロールバック。SQLite では DDL が暗黙コミットのため確認できていない

## 8. 本番の Function を作り、Secret を確定する

**やること**

- 「1.」と同じ設定項目で本番の Function を作る。**疎通用のものは残したまま**にする
  （以後の基盤側の変更をそこで先に試せる）
- Secret ファイルに本番の値を置き、**権限を `600` に絞る**
- **受信トークンは配布物の `governance/config.json` に載る値と一致させる**（設計書 §4.4）
- 取込ディレクトリを `/mnt/data/csv` に向ける

## 9. 全エンドポイントの疎通を通す

**やること**

- 設計書 §4.4 の 6 つのエンドポイントすべてに到達できることを確かめる
- 画面 4 枚のリンクを実際に踏み、サブパスが落ちないことを確かめる
- **受信の口にトークン無しで POST し、`401` が返ることを確かめる。**
  ここが 200 を返すと、端末が唯一の控えを消してデータが不可逆に失われる

## 10. CSV の置き場を用意し、取込を通す

**やること**

- `/mnt/data/csv/` を作り、CSV を 1 本置いて画面のボタンから取り込む
- **同じファイルをもう 1 度取り込み、コストが二重計上されないことを確かめる。** 冪等キーは `day` である
- **統計情報の更新にかかる時間を測って記録する。** 取込の応答時間に上乗せされる

## 11. 端末からの往復を通す

**やること**

- 配布するプラグインの `governance/config.json` の送信先を、本番 URL の受信の口に向ける
- 1 台の端末で `claude` を動かし、イベントが `events` に入ることを確かめる
- **送信後に端末の spool が消えることを確かめる。** 消えなければ、サーバが 2xx を返していない

## 12. 日次のバックアップ手順を確立する

**やること**

- **アプリケーションにバックアップ機構を持たせない。永続領域の複製を運用手順として行う**
- SQLite で運用する場合、DB ファイルと `/mnt/data/csv/` を、CSV 取込と同じ日次の操作として複製する
- **複製先を永続領域（`/mnt/data`）の外に置く。** 同じ領域に置いた複製は、領域ごと失う障害に対して何も守らない
- MySQL で運用する場合、基盤側のバックアップに委ねる。委ねられていることを確認し、取得間隔を記録する
- **復旧できるのは最後の複製時点までである**ことを、運用の前提として明示する

**3 テーブルの再現可能性は等しくない。** `cost_daily` は CSV から取り直せる。
`events` は端末の spool が残っている範囲までしか戻せない。
**`policy_state` は原理的に再現できない。** 準拠開始日は過去の観測にしか存在せず、端末から取り直す手段が無い。
これを失うことは、効果測定の基準点を永久に失うことと同じである。

---

## 合わせて通すこと

- **`docker build` / `docker run` を 1 度通す。** 基盤へ持って行く前に、手元で確かめる
- 年間規模での集計時間、MySQL で被覆インデックスが選ばれるか、統計情報の更新頻度が足りるか。
  **いずれも実データが溜まってから測る**（設計書 §11.3）
