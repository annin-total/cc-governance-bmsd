# 実行基盤への到達が要る作業

開発機からは実行基盤に到達できないため、到達できる端末で行う。手順は `../guide/deploy-aip.md`
にある。ここにあるのは、まだ 1 度も通していない確認と、結果で分岐する判断である。
観測した結果は `../guide/deploy-aip.md` に反映し、この文書から項目を消す。

## 疎通用の Function で手順を 1 回通す

`../guide/deploy-aip.md` の手順を、疎通の確認まで 1 回通す。途中で次を確かめる。

- 依存の install に使うコマンドが `pip` か `pip3` か。Open Terminal で
  `command -v pip; command -v pip3` を実行し、`entry.sh` が書いている方が PATH に無ければ直す
- 前段のリバースプロキシが公開サブパスを除くか除かないか。`BASE_PATH` を空にして公開サブパス付きの URL を
  叩いた応答コードで分かる。**どちらでも設定も実装も変えない**が、
  どちらだったかを記録する
- 社内の標準的な端末（macOS と Windows）の `python3` から、公開 URL へ `urllib` で `POST /ingest` して
  2xx が返るか。macOS の Python はキーチェーンの証明書を見ないため、社内 CA の証明書や TLS 検査の経路
  では全端末の送信が無言で失敗する。失敗したら、CA バンドルを `SSL_CERT_FILE` で渡す方法を案内に加える
- `../guide/deploy-aip.md` の「列を足すとき」の順（稼働中に Open Terminal から ALTER → restart）で、使い捨ての列を
  足してもサーバが起動し、受信が続くか

**完了条件** — 疎通の確認がすべて通り、上の 4 点の観測が記録されていること。
`../guide/deploy-aip.md` の未検証の点の結果を記録し、未検証の記述を消すこと。

## 起動時間とアイドル停止で、端末の送信タイムアウトを判定する

問題になるのは、所要時間が端末の POST タイムアウト（`plugin/config.json` の `timeout_sec`）を超えるかだけである。

- スクリプト開始から待受までの所要時間（依存の install を含む）を測る
- 30 分・数時間・1 日放置したあとの初回応答時間を測り、停止と再起動の痕跡をログで見る

**完了条件** — どちらも 60 秒未満なら変更しない。60 秒以上なら `plugin/config.json` の
`timeout_sec` を実測より長い値へ引き上げる。

## 本番でだけ確かめられること

- 本番の Function を疎通用とは別に作り、疎通用を残すか決める。`server/entry.sh` が Secret のパスを固定しているため、
  そのまま 2 つ作ると同じ `DB_DSN`（同じ SQLite）を開く。分けるなら Secret とデータのパスの分け方を決める
- 日次のバックアップを運用に載せる
- CSV 取込での統計情報の更新にかかる時間を測る（取込の応答時間に上乗せされる）

**完了条件** — 本番の Function の作り方が決まって `../guide/deploy-aip.md` に書かれ、バックアップが 1 回取れ、CSV 取込での統計情報の更新の所要時間が
`../knowledge/measurements.md` に記録されていること。
