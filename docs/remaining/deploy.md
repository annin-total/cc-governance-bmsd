# 実行基盤への到達が要る作業

開発機からは実行基盤に到達できないため、到達できる端末で行う。手順は `../guide/deploy-aip.md`
にある。ここにあるのは、まだ 1 度も通していない確認と、結果で分岐する判断である。
観測した結果は `../guide/deploy-aip.md` に反映し、この文書から項目を消す。

## 疎通用の Function で手順を 1 回通す

`../guide/deploy-aip.md` の手順を、疎通の確認まで 1 回通す。本番の Function は同じ設定で
別に作り、疎通用は残す（基盤側の変更を先に試せる）。途中で次を確かめる。

- 依存の install に使うコマンドが `pip` か `pip3` か。Open Terminal で
  `command -v pip; command -v pip3` を実行し、`entry.sh` が書いている方が PATH に無ければ直す
- 前段が公開サブパスを剥がすか剥がさないか。`BASE_PATH` を空にして公開サブパス付きの URL を
  叩いた応答コードで分かる。**どちらでも設定も実装も変えない**（ラッパは `PATH_INFO` が
  `BASE_PATH` で始まるときだけ剥がす）が、どちらだったかを記録する
- プロセスの作業ディレクトリが `server/` であること。崩れると契約の複製の検査が成立しない
- 前段が大きな本文（数十 MB）の `POST /ingest` を通すか。長期オフラインから復帰した端末は
  spool を 1 ファイルで送り、413 などで失敗するとそのファイルは破棄される

**完了条件** — 疎通の確認がすべて通り、上の 4 点の観測が記録されていること。

## 起動時間とアイドル停止で、端末の送信タイムアウトを判定する

端末の送信は切り離されたプロセスで行われるため、コールドスタート自体は利用者を待たせない。
問題になるのは、所要時間が端末の POST タイムアウト（60 秒）を超えることだけである。
短すぎるタイムアウトは spool を溜め、上限による破棄を早める。

- スクリプト開始から待受までの所要時間（依存の install を含む）を測る
- 30 分・数時間・1 日放置したあとの初回応答時間を測り、停止と再起動の痕跡をログで見る

**完了条件** — どちらも 60 秒未満なら変更しない。60 秒以上なら `plugin/config.json` の
`timeout_sec` を実測より長い値へ引き上げる。

## 本番でだけ確かめられること

- 日次のバックアップを運用に載せる
- CSV 取込での統計情報の更新にかかる時間を測る（取込の応答時間に上乗せされる）
- 基盤へ持って行く前に、手元で `docker build` / `docker run` を 1 度通す

**完了条件** — バックアップが 1 回取れ、所要時間が記録されていること。
