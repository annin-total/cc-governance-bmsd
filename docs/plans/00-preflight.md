## 2. 開発機で確かめること

### 0-1 対話モードでの `systemMessage` の表示

**なぜ確かめるか** — お知らせが利用者に届く経路そのものである。非対話で届かないことは分かっており、対話での見え方だけが未確認のまま残っている。

**やること**

1. `local/verify/systemmessage/` の検証環境を使う（`.claude/settings.json` に `SessionStart` hook が登録済み。**利用者の `~/.claude/settings.json` には触れない**）
2. そのディレクトリで対話モードの Claude Code を起動する。環境変数 `NOTICE_LEN` で出力する文字数を変える
3. 起動直後の画面を目視し、次を記録する
   - 表示されるか
   - どこに表示されるか（起動直後か、最初の応答の前か）
   - `SessionStart:<source> says: ` の接頭辞が付くか。複数行のとき、接頭辞が付くのは 1 行目だけか
   - 文字列の末尾まで見えるか、途中で切れるか。ファイルへ退避されてパスだけが出る状態になるか
4. `NOTICE_LEN` を 100 / 1,000 / 5,000 / 20,000 に変えて繰り返し、**表示内容が短くなる点があるか**を比べる

**合否の判定**

| 結果 | 判定 |
| --- | --- |
| 全長が表示される | **合格。** お知らせの文面の長さに制約を置かない |
| ある長さから切り詰められる | **条件つき合格。** 切り詰め（またはファイルへの退避）が始まる長さが 2,000 文字を上回っていれば、設計書 §3.7 が定める上限（お知らせ 1 件は 2,000 文字未満）で足りる。下回る場合は §3.7 の上限をその値まで下げる |
| 表示されない | **不合格** |

**不合格だったときに設計のどこを変えるか** — お知らせの配信経路（設計書 §3.7）が成立しない。`systemMessage` 以外に、**モデルのコンテキストを汚さずに利用者へ文字列を届ける hook 出力の手段**を探す。見つからない場合、お知らせの配信は設計から落とす。配布物（スキル・コマンド）と設定の適用は影響を受けないため、施策の本体は成立し続ける。**モデルのコンテキストに入れる形（標準出力への素の出力）で代替してはならない。** 利用者が 1 通も読めないうえ、全セッションにモデルへの指示が注入され、コストを下げる施策の効果測定に交絡する。

### 0-2 端末の Python の可用性

**なぜ確かめるか** — hook は Python で書かれる。`python3` が PATH から解決できない端末では、収集も設定の適用も一切動かない。

**やること** — 配布対象の端末の構成（OS・Python の導入経路）を確認する。全端末を調べる必要はなく、**構成の種類ごとに 1 台**でよい。

**合否の判定** — すべての構成で `python3 --version` が応答すれば合格。

**不合格だったときに設計のどこを変えるか** — hook の起動コマンドを、解決できるインタプリタの絶対パスにするか、Claude Code に同梱される実行環境を使う形に変える。どちらも取れない構成がある場合、その構成の端末は測定の対象外とし、**分母から除いた事実を画面に出す**（除外を黙って行うと準拠率が実態より良く見える）。

## 3. 実行基盤・社内リポジトリに到達できる端末で確かめること

### 0-3 git リモートを `source` としたマーケットプレイスの更新の伝播【要:基盤到達】

**なぜ確かめるか** — 配信の実体は git である。**更新が届かなくなった端末は、こちらから回復する手段を持たない**（設計書 §8.5）。伝播の契機が分からなければ、施策を変えてから全端末に行き渡るまでの時間も見積もれない。

ローカルディレクトリを `source` にした場合は、`version` を書き換えると次のセッション起動で反映されることが分かっている。**git リモート（社内リポジトリ）を `source` にした場合の挙動は、これとは別である。**

**やること**

1. 社内リポジトリに検証用のマーケットプレイスリポジトリを 1 つ作る（本番の配布用リポジトリとは別）
2. 端末から `claude plugin marketplace add <URL>` で登録し、ダミープラグインを導入する。ダミープラグインは `SessionStart` hook で自分の `version` をファイルに書き出すだけのものにする
3. リポジトリ側で `version` を上げて push する
4. 端末で新しいセッションを開き、**書き出された `version` が変わるか**を見る。変わらなければ `claude plugin marketplace update` を明示的に実行して再確認する
5. リモートに到達できない状態（ネットワークを切る、URL を壊す）で新しいセッションを開き、**古い版が黙って使われるのか、hook が実行されなくなるのか**を見る
6. 検証用のマーケットプレイス登録とプラグインを削除して原状復帰する

**記録すること** — 「push から端末に届くまでに何が必要か」「到達できないときに端末側に何が見えるか」の 2 点。

**合否の判定**

| 結果 | 判定 |
| --- | --- |
| セッション起動で自動的に更新される | **合格。** 設計書 §8.5 の前提どおり |
| 明示的な更新コマンドが要る | **条件つき合格。** 導入案内（§8.4）に更新操作を含めるか、更新を促す運用を別に用意する |
| 更新されない | **不合格** |

**不合格だったときに設計のどこを変えるか** — 配信を git に委ねる前提（設計書 §2.3）が崩れる。施策の変更が端末に届かないため、`plugin_version` の分布（§9.2）が唯一の観測手段として残るが、それは検知であって配信ではない。この場合、**配布物の更新を利用者の操作に依存する運用として明記し、更新率を画面に出す**。

### 0-4 マーケットプレイス単位で自動更新を止める設定の有無【要:基盤到達】

**なぜ確かめるか** — 止められるなら、それは**施策が特定の端末に永久に届かなくなる経路**である。存在するなら、その端末が `plugin_version` の分布のどこに現れるかを知っておく必要がある。

**やること** — 0-3 の検証環境で、端末のマーケットプレイス設定に自動更新を止める項目があるかを確認し、あれば設定して 0-3 の手順 3〜4 を繰り返す。

**合否の判定** — 合否ではなく、**事実の記録**である。止められる経路が存在するかどうかと、存在する場合に端末側で更新が止まったことを外から観測できるかを記録する。

**この結果で設計のどこが変わるか** — 止められる経路が存在する場合、設計書 §8.5 の「回復手段を持てないなら、せめて検知手段を持つ」の対象がもう 1 つ増える。検知は `plugin_version` の分布で足りるため、**新しい機構は足さない**。

### 0-5 実行基盤に関する事項【要:基盤到達】

次の 4 つは計画 [8-A] のタスクとして確かめる。この計画では扱わない。

- Ingress がサブパスを剥がすか剥がさないか
- 実行基盤上でのサーバの起動時間と、アイドル時にコンテナが停止するか
- MySQL 接続時の DDL 適用
- 接続先 MySQL の `sql_require_primary_key` の値
