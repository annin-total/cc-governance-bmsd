# [7] マーケットプレイスと配布

**目的:** 完成したプラグインを配布用マーケットプレイスへ差し込み、人が手で間違えない形のリリース手順と、効果測定の識別の前提を作る段階的な案内を確立する。
**設計書:** `../design.md` §8
**依存:** [2] 端末：収集 / [3] 端末：設定適用・お知らせ
**ブランチ:** `feat/distribution`

---

## 1. 作るもの

パスは `cc-governance-bmsd/` を基準に書く。配布リポジトリは `../cc-marketplace-governance-bmsd`、その親（開発リポジトリを含む作業ツリーの根）は `..` として参照する。

| ファイル | 責務 | 想定行数 |
| --- | --- | --- |
| `../cc-marketplace-governance-bmsd/.claude-plugin/marketplace.json` | マーケットプレイスの名前・所有者・収録プラグイン 1 件 | 12 |
| `../cc-marketplace-governance-bmsd/plugins/governance/` | 開発リポジトリの `governance/` の複製。**手で編集しない** | — |
| `../cc-marketplace-governance-bmsd/.gitignore` | 生成物の混入を配布リポジトリ側でも止める | 6 |
| `../cc-marketplace-governance-bmsd/README.md` | このリポジトリの役割と「手で編集しない」ことの明示 | 20 |
| `scripts/release.sh` | **差し込みと検査を 1 本で行う。** 除外パターンを 1 か所に持つ。`--check-only` で検査だけを走らせる | 145 |
| `docs/release.md` | リリース手順と確認項目 | 70 |
| `docs/onboarding.md` | 利用者向けの案内文面と、段階的な案内の設計 | 60 |
| `../.gitignore`（変更） | 配布リポジトリを開発リポジトリの作業ツリーから除く | +1 |

本計画で書く実行可能なファイルはシェルスクリプト 1 本だけである。`governance/` 配下と `cc-governance-bmsd-server/` 配下には**一切触れない**。

## 2. この計画に固有の前提

README §5 の共通制約に加えて、本計画だけに効く前提を置く。

| 項目 | 前提 |
| --- | --- |
| 計画 [2] [3] の完了 | `governance/` 配下（`.claude-plugin/plugin.json` / `hooks/` / `notices.json` / `config.json` / `skills/` / `commands/`）が `main` にあり、そのまま配れる状態である |
| テストの置き場所 | `governance/` の**外**（`tests/` 配下）にある。計画 [2] [3] がそう定めている。本計画の検査は、この前提が破られていないことも見る |
| 配布リポジトリの状態 | `../cc-marketplace-governance-bmsd` は**空のディレクトリ**であり、git リポジトリとして未初期化である |
| 2 つの git | 配布リポジトリは開発リポジトリとは別の履歴を持つ。開発リポジトリの作業ツリーの中に置いたままにするため、親の `.gitignore` で除外する。**入れ子のリポジトリとしてコミットしない** |
| 差し込みの向き | 常に開発リポジトリ → 配布リポジトリの一方向。配布リポジトリ側での編集は行わない。逆向きの取り込み手段を持たない |
| `version` の所在 | `governance/.claude-plugin/plugin.json` の 1 か所だけ。配布リポジトリ側の `plugin.json` は差し込みの結果であり、そこで書き換えない |
| 受信トークン | `governance/config.json` に平文で入り、配布物に含まれる（設計書 §4.4）。**機密防御ではなく誤送信の防止のために置く**（§11.2）。リポジトリに入れてよい |
| 案内の経路 | マーケットプレイスの登録とプラグインの導入は利用者が自分で行う。サーバから端末へ配る経路は持たない（§2.3） |
| `POLICY` の項目 | `env.CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` / `extraKnownMarketplaces.cc-marketplace-governance-bmsd.autoUpdate` / `env.FORCE_AUTOUPDATE_PLUGINS` の 3 つ（設計書 §3.6）。本計画はこの中身を決めず、**キーが削除されていないこと**だけを検査する |
| 利用者の画面に出るもの | お知らせ 1 件は目安として**日本語 600 字程度**まで、`hooks.json` の各コマンドは **1 行 100 文字未満**（設計書 §3.7 / §3.3）。どちらも利用者の画面に直接出るが、**リリース時の検査には含めない。** 文面は運用の判断であり、`hooks.json` は滅多に変わらない |
| 自動更新 | **社外のマーケットプレイスは自動更新が既定で無効である**（設計書 §8.5）。有効化は `POLICY` の `extraKnownMarketplaces.cc-marketplace-governance-bmsd.autoUpdate` によって SessionStart のたびに強制適用される（計画 [3] の担当）。**マーケットプレイスの登録をやり直すとこの設定は外れうるため、一度きりの設定ではない。** **`settings.json` が権威であることは実機で確認済み**であり、プラグインの書き込みでこの設定は維持できる（設計書 §3.6）。未検証なのは、有効にした結果として**実際に更新が降りてくるか**である（§11.3） |
| 到達不能時の挙動 | **マーケットプレイスの `source` に到達できなくなっても、プラグインは止まらない**（設計書 §8.5）。取得に失敗した場合は端末にある複製がそのまま使われ、最後に同期した状態で動き続ける。止まるのは更新だけである |
| 群の記録 | 記録するのは**案内した日付だけ**であり、誰がどの群かを個人単位で持たない。個人を特定する情報を開発リポジトリに置かない |
| `claude plugin` CLI | 非対話で実行できる。`marketplace add|list|update|remove`、`install|update|uninstall`、`list [--json]`、`enable|disable` を使う |
| 隔離環境 | 実機確認は `CLAUDE_CONFIG_DIR` を `local/` 配下に向けて行う。効かなければ `HOME` 差し替えに切り替える（計画 [3] と同じ規則）。**どちらも効かない場合は止め、利用者本人の環境で試さない** |

### タスク 2: 差し込みを自動化する

**ファイル:** 作成 `scripts/release.sh`
**依存:** タスク 1

差し込みを人の手で行うと、**差し込み漏れ**（新しく足したファイルが配布物に現れない）と**差し込み過剰**（開発用の生成物が配布物に混ざる）の両方が起きる。どちらも端末側では気づけない。手順から手作業を消す。

**やること**

- 引数で配布リポジトリのパスを受け取る（既定 `../cc-marketplace-governance-bmsd`）
- 実行前に 2 つを確かめ、満たさなければ何もせずに終了する
  - 配布リポジトリが git の作業ツリーであること
  - 配布リポジトリの作業ツリーが clean であること（前回の差し込みが未コミットのまま重なるのを防ぐ）
- 除外パターンを**スクリプト内の 1 か所の配列**に持つ。`__pycache__/` / `*.pyc` / `.pytest_cache/` / `.DS_Store` / `*.log` / `*.orig` / `*.rej` / `*~`
- `governance/` の内容を `plugins/governance/` へ、**削除も含めて同期する**。開発リポジトリで消したファイルは配布物からも消える
- 差し込み後に、配布リポジトリ側の変更ファイル一覧を標準出力に出す
- コミットも push もしない。**差し込みと検査が終わった状態で止め、人がコミットする**

**根拠:** 設計書 §8.3 手順 3（フォルダの内容をそのまま置き換える）

**テスト:** なし。下記の判定がそのまま検査である。

**完了の判定**

```
scripts/release.sh ../cc-marketplace-governance-bmsd
diff -r -x '__pycache__' -x '*.pyc' -x '.pytest_cache' -x '.DS_Store' \
  governance ../cc-marketplace-governance-bmsd/plugins/governance
echo $?
```

期待出力: `diff` は何も出力せず、

```
0
```

汚れた作業ツリーで中止することも確かめる。

```
touch ../cc-marketplace-governance-bmsd/plugins/governance/zzz.tmp
scripts/release.sh ../cc-marketplace-governance-bmsd; echo $?
rm ../cc-marketplace-governance-bmsd/plugins/governance/zzz.tmp
```

期待出力（末尾）:

```
1
```

**コミット:** 開発リポジトリ側は `feat: 配布リポジトリへの差し込みスクリプトを追加`。配布リポジトリ側は `feat: governance プラグインを収録`

### タスク 4: `version` の引き上げ忘れを検出する

**ファイル:** 変更 `scripts/release.sh`
**依存:** タスク 3

`plugin.json` の `version` は、端末側が更新の要否を判断する唯一の手がかりである（設計書 §8.3）。中身を変えて `version` を上げ忘れると、**変更は端末に届かないまま、届いたことになる**。気づく手段はこの検査しかない。

**やること**

- 検査 6「version」を足す
- 配布リポジトリの `HEAD` に `plugins/governance` が無ければ（初回リリース）、この検査を飛ばして `[SKIP]` を出す
- `HEAD` の `plugins/governance/.claude-plugin/plugin.json` と、差し込み後の作業ツリーのそれから `version` を取り出す
- `plugins/governance/` に 1 ファイルでも変更があるのに `version` が同じなら `[NG]` で落とす
- `version` が変わっている場合、ドット区切りの整数列として比較し、**前回より大きいこと**まで確かめる。下げると端末に届かない
- 変更が 1 件も無いのに `version` だけが上がっている場合は `[NG]` で落とす。中身の伴わないリリースは、届いたかどうかの判断材料を濁らせる

**根拠:** 設計書 §8.3（`version` を上げる場所は 1 か所・上げ忘れると端末に届かない）、§8.5 / §9.2（`plugin_version` の分布で到達を観測する）

**テスト:** なし。下記の判定がそのまま検査である。

**完了の判定**

変更あり・`version` 据え置きで落ちること。

```
printf '\n' >> governance/notices.json
scripts/release.sh ../cc-marketplace-governance-bmsd >/dev/null
scripts/release.sh --check-only ../cc-marketplace-governance-bmsd; echo $?
```

期待出力（末尾 2 行）:

```
[NG] version 据え置き: 0.1.0 のまま plugins/governance に 1 件の変更がある
1
```

`version` を上げれば通ること。`governance/.claude-plugin/plugin.json` の `version` を `0.2.0` に上げてから、

```
scripts/release.sh ../cc-marketplace-governance-bmsd >/dev/null
scripts/release.sh --check-only ../cc-marketplace-governance-bmsd; echo $?
```

期待出力（末尾 2 行）:

```
[OK] version 0.1.0 -> 0.2.0
0
```

確認が終わったら `governance/notices.json` と `version` を元に戻し、差し込みと検査をもう 1 回通して配布リポジトリの作業ツリーを clean に戻す。

**コミット:** `feat: version の引き上げ忘れを検出する`

### タスク 5: `POLICY` からのキー削除を検出する

**ファイル:** 変更 `scripts/release.sh`
**依存:** タスク 4

`POLICY` からキーを削除する操作は、**誤った値を全端末に固定する操作**である（設計書 §8.3）。適用処理が持つのは上書きだけであり、撤回は定義されていない。届かなくなるのは正しい値の方で、既に書き込まれた誤った値は端末に残り続ける。人が「間違えた設定を配ったから消す」と考えたときに、最も自然に手が伸びる操作がこれである。**手順の注意書きではなく検査で止める。**

**やること**

- 検査 7「POLICY のキー」を足す
- 配布リポジトリの `HEAD` に `plugins/governance/hooks/contract.py` が無ければ飛ばして `[SKIP]` を出す
- `HEAD` の `contract.py` を一時ディレクトリに取り出し、差し込み後のものと合わせて 2 つ読み込み、それぞれの `POLICY` のキー集合を取る。`contract.py` は純粋な定数と関数だけを持つ（設計書 §6）ため、読み込みに副作用が無い
- 前回あって今回無いキーが 1 つでもあれば `[NG]` で落とし、メッセージに正しい手順を出す — 「`POLICY` に正しい値を書き、`version` を上げて配り直す。施策をやめる場合は Claude Code の既定値を書く」
- **値の変更は検査しない。** 値を変えることは正規の操作であり、ここで止めてはならない
- キーの追加も検査しない

**根拠:** 設計書 §8.3「誤った設定値を配ったときの手順」、§3.6（適用は上書きだけで撤回を持たない）、§11.2（即時の撤回手段は存在しない）

**テスト:** なし。下記の判定がそのまま検査である。

**完了の判定**

まず、検査の対象が成立するように 1 回リリース相当の状態を作る（配布リポジトリにコミットが積まれ、`HEAD` に `contract.py` がある状態）。その上で `governance/hooks/contract.py` の `POLICY` からキーを 1 つ削り、`version` を上げて差し込む。

```
scripts/release.sh ../cc-marketplace-governance-bmsd >/dev/null
scripts/release.sh --check-only ../cc-marketplace-governance-bmsd; echo $?
```

期待出力（末尾 3 行）:

```
[NG] POLICY からキーが削除されている: env.CLAUDE_AUTOCOMPACT_PCT_OVERRIDE
[NG] 削除は誤った値を全端末に固定する操作である。正しい値を書いて version を上げること
1
```

次に、削ったキーを戻して**値だけを変えて**差し込むと通ること。

```
scripts/release.sh ../cc-marketplace-governance-bmsd >/dev/null
scripts/release.sh --check-only ../cc-marketplace-governance-bmsd; echo $?
```

期待出力（末尾 2 行）:

```
[OK] POLICY のキーは削除されていない
0
```

確認が終わったら `contract.py` と `version` を元に戻し、差し込みと検査を通して配布リポジトリを clean に戻す。**`governance/hooks/contract.py` を変更したまま残さない。**

**コミット:** `feat: POLICY のキー削除を検出する`

### タスク 6: リリース手順書を書く

**ファイル:** 作成 `docs/release.md`
**依存:** タスク 5

**やること**

次の章立てで書く。手順は上から順に実行すれば終わる形にし、判断の余地を残さない。

1. **前提** — 開発リポジトリの変更が `main` にマージ済みで、`pytest` が通っていること
2. **`version` を上げる** — `governance/.claude-plugin/plugin.json` の 1 か所。ここ以外に `version` を書く場所は無い
3. **差し込んで検査する** — `scripts/release.sh` を実行する。差し込みに続けて検査が走る。**1 つでも `[NG]` が出たらリリースを中止する。** 検査だけを飛ばす手段は用意しない。配布リポジトリ側を手で編集しない
4. **確認項目** — チェックリストとして並べる
   - `POLICY` からキーを削除していない（検査 7 が見るが、意図としても確認する）
   - `config.json` の送信先 URL が、デプロイ済みのサーバの URL と一致している
   - `config.json` の受信トークンが、サーバの Secret ファイルの `INGEST_TOKEN` と一致している。**一致していなければ全端末の送信が 401 で跳ね返り続ける**（設計書 §4.4）。端末は spool を保持するのでイベントは失われないが、誰も気づかないまま溜まる
   - 受信トークンが平文でリポジトリに入ることは設計上の前提である。**機密防御ではなく誤送信の防止のために置く**（設計書 §11.2）。到達制御はネットワーク境界が担う
   - トークンを入れ替える場合は、サーバ側の Secret ファイルの更新と同一のリリースで行う。新旧どちらでも通る期間を作る手段は無く、入れ替えの間の 401 は端末の spool が吸収する（設計書 §3.5 / §4.4）
5. **PR を作りマージする** — 配布リポジトリで PR を作る。マージされた時点で配布される
6. **届いたことを確認する** — 数日後に概況画面の健全性の行で `plugin_version` の分布を見る。古い版が残り続ける端末は配布が届いていない（設計書 §9.2）
7. **誤った設定値を配ってしまったときの手順** — `POLICY` に正しい値（施策をやめる場合は Claude Code の既定値）を書き、`version` を上げて配り直す。**即時の撤回手段は存在しない。** 全端末に行き渡るまで数日かかる
8. **列を足したとき** — 契約に列を足すリリースでは、サーバ側のテーブル作り直し手順（設計書 §4.3）を先に済ませる。順序を誤るとサーバが起動しない

**根拠:** 設計書 §8.3（リリース手順と誤った設定値を配ったときの手順）、§4.4（認証・応答コード）、§11.2（撤回できないこと・トークンは機密防御ではないこと）、§4.3（列の増減の運用手順）

### タスク 7: ローカルで予行演習する

**ファイル:** なし（`local/` での作業のみ）
**依存:** タスク 6

社内リポジトリに触る前に、ローカルの git リポジトリを `source` にしたマーケットプレイスで、導入から無効化までを一通り通す。**作業は git 管理外の `local/` で行い、終わったら必ず原状復帰する。利用者の既存のマーケットプレイス登録・導入済みプラグインには一切触れない。**

**やること**

1. **作業前の状態を記録する。** 本人の環境で `claude plugin marketplace list` と `claude plugin list` を実行し、出力を `local/rehearsal/before.txt` に保存する。最後にこれと突き合わせる
2. **隔離環境が効くことを先に確かめる。** `local/rehearsal/claude` を作り、`CLAUDE_CONFIG_DIR` をそこへ向けて `claude plugin marketplace list` を実行する。**本人の登録が 1 件も映らないこと**を確認する。映るなら `HOME` 差し替えに切り替える。どちらでも隔離できない場合は**ここで止める**。本人の環境で予行演習しない
3. **配布リポジトリの複製を作る。** `../cc-marketplace-governance-bmsd` を `local/rehearsal/marketplace` へ clone する。以降の `version` の書き換えはこの複製に対して行い、**本物の配布リポジトリを触らない**
4. **登録して導入する。** 隔離環境で複製のパスをマーケットプレイスとして追加し、プラグインを導入する。`claude plugin list` で有効かつ想定の `version` であることを確認する
5. **hook が発火することを確認する。** 隔離環境で `claude -p` を 1 回走らせ、隔離側の `settings.json` にポリシーの値が書かれ、`queue.jsonl` にイベントが積まれることを確認する。**プラグインとして導入した状態では、`queue.jsonl` は `${CLAUDE_PLUGIN_DATA}`（隔離側の `plugins/data/` 配下）にある**（設計書 §3.1）。隔離環境の外にファイルができていないことも合わせて見る
6. **伝播を確認する。** 複製側の `plugin.json` の `version` を上げてコミットする。**自動更新はセッション開始のあと最大 10 分のばらつきを持って走り、反映されるのは次に起動したときである**（設計書 §8.5）。したがって、1 回起動して即座に版が変わることを期待しない。手順は「セッションを開始して 10 分以上そのままにし、終了する → 次のセッションを開始する → `claude plugin list` の `version` を見る」とする。版が上がっていない場合は `claude plugin marketplace update` を実行して上がるかを確認し、どちらだったかを記録する
7. **到達できなくなったときの挙動を確認する。** 複製のディレクトリをリネームして到達不能にし、新しいセッションで `claude -p` を走らせる。**端末にある複製がそのまま使われ、プラグインが最後に同期した状態で動き続けること**を確認する。具体的には、設定の適用が働き、`${CLAUDE_PLUGIN_DATA}` の `queue.jsonl` にイベントが積まれ、`claude plugin list` に従来どおりの版で現れることを見る。止まるのは更新だけである
8. **復旧を確認する。** 名前を戻し、手順 6 と同じ待ち方で更新が再び取得されることを確認する
9. **無効化を確認する。** `claude plugin disable` でイベントが止まり、`claude plugin enable` で戻ることを確認する
10. **原状復帰する。** 隔離環境で `claude plugin uninstall governance` と `claude plugin marketplace remove cc-marketplace-governance-bmsd` を実行し、`claude plugin list` と `claude plugin marketplace list` が空であることを確認してから `local/rehearsal/` を削除する。**アンインストールで `${CLAUDE_PLUGIN_DATA}` の配下が消えること**（設計書 §3.1）も確認する。残っていれば、状態を規約外の場所に書いている
11. **本人の環境が不変であることを確認する。** 手順 1 の記録と突き合わせる

**根拠:** 設計書 §8.4（導入手順）、§8.5（更新の伝播・更新が届かない端末）、計画索引 §4（hook の登録と発火は実機で確認する）

### タスク 8: 段階的な案内を設計する

**ファイル:** 作成 `docs/onboarding.md`
**依存:** タスク 6

全員に同時に案内すると準拠開始日が数日に固まり、相対日がほぼ暦日と一致する。すると同時期に起きた他のすべて（モデルの変更・料金改定・繁忙期・社内アナウンス）が施策の効果として計上される。**ばらつきは待つものではなく、作るものである。** 配布の仕掛けは変えず、案内する日をずらすだけでよい（設計書 §7.1 / §8.4）。

**やること**

- `docs/onboarding.md` に、利用者へそのまま送れる案内文の雛形を書く。含めるもの
  - マーケットプレイスを登録するコマンドと、プラグインを導入するコマンド。**社内リポジトリの https URL をそのまま書く**
  - 導入後、最初の SessionStart で設定の適用とお知らせの表示が働くこと
  - 収集する項目と、**収集しない項目**（プロンプト本文・ツールの応答・会話の内容には触れない）
  - **自動更新が有効にならなかった場合の手順。** 社外のマーケットプレイスは自動更新が既定で無効であり（設計書 §8.5）、有効化は `POLICY` による強制適用に委ねている。ユーザー設定の層でこれが効くかは未検証であるため、効かなかった場合に備えて `/plugin` の画面でマーケットプレイスごとに自動更新をトグルする手順を、案内文に書ける形で用意しておく。手順が要るかどうかはタスク 9 の確認 C で決まる
  - 困ったときの連絡先
- 同じファイルに、段階的な案内の設計を書く
  - **群は 2〜3 とし、1〜2 週間ずらして案内する**
  - **群は部署を横断して作る。** 部署ごとに群を作ると、部署の業務差が群差と区別できなくなる。同一部署の人が別々の群に入るように割り当てる
  - 群ごとの人数は大きく偏らせない
  - 案内日を決めたら**前倒し・後ろ倒しをしない**。ずれたら実際の日付を記録に残す
- 同じファイルの末尾に、**案内した日付だけ**を記録する欄を設ける。書くのは「案内日 / 案内した範囲の呼び名 / おおよその人数」の 3 列で、**個人を特定する情報を書かない**
  - 案内を出した時点で記入し、**後から書き換えない**。書き換えると、事後に都合のよい群分けを作れてしまう
  - 前倒し・後ろ倒しをした場合は、予定日ではなく**実際に出した日**を書く

**誰がどの群かを個人単位で記録しない。** イベントスタディの基準になる準拠開始日は `policy_state` から求まり、群の記録を使わない。個人単位の名簿は異動と入退社で古くなる保守対象を 1 つ増やすが、それによって除ける交絡は無い。案内日を記録しても、実際に導入するかどうかは利用者が決めるため、自己選択バイアス（設計書 §11.1）は残る。

**根拠:** 設計書 §7.1「識別の前提」、§8.4（案内は 2〜3 群に分け 1〜2 週間ずらす・群分けに仕掛けは要らない・記録するのは案内日だけ）

**テスト:** なし。下記の判定がそのまま検査である。

**完了の判定**

案内文の雛形に、導入コマンドと収集項目の説明と連絡先が揃っていること。目視で確かめる。

案内の設計が、群の数・間隔・部署を横断する割り当ての 3 点を定めていること。目視で確かめる。

**ずらしが効いたかの判定は、案内の後に `/policy` の準拠開始日の分布で行う**（このタスクの完了条件ではない）。分布に群の数と同じだけの山が立っていれば成功、1 つの山に潰れていれば失敗である。失敗した場合、相対日は暦日とほぼ一致し、効果測定は同時期の他の変化と区別できない。その事実を `/effect` の読み方として残す。

### タスク 9: 【要:基盤到達】git リモートを `source` にしたときの伝播を確かめる

ローカルディレクトリを `source` にした場合の挙動はタスク 7 で分かっている。**git リモートを `source` にした場合は分かっていない。** 実際の配布経路はこちらであり、ここが分からないままだと「施策の変更がいつ端末に届くか」を誰も答えられない。開発機からは社内リポジトリに到達できないため、別の端末で行う。

**根拠:** 設計書 §8.5（自動更新は既定で無効・届くまでの時間・到達不能時も複製で動き続ける）、§11.3（`autoUpdate` がユーザー設定の層で効くかは未検証）、§9.2（`plugin_version` の分布）

### タスク 11: 【要:基盤到達】配布が届いたことを確認する

**ファイル:** なし（観測のみ）
**依存:** タスク 10

回復できない故障を、少なくとも見えるようにする（設計書 §8.5）。

**やること**

- 第 1 群の案内から 1 週間後、概況画面の健全性の行を見る
- `plugin_version` の分布に現れる端末数と、第 1 群の人数を突き合わせる。差が大きければ、導入が進んでいないのか、イベントが届いていないのかを切り分ける
