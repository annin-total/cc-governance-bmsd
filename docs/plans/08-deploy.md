# [8] 実行基盤へのデプロイ

**目的:** サーバを実行基盤の上で起動し、サブパス配下で待ち受ける状態にする。
**設計書:** `../design.md` §4.6（§1.2 / §4.1〜§4.3 / §11.3 を併せて根拠とする）
**依存:** [8-A] は [1] / [8-B] は [4] [5] [6] [7]
**ブランチ:** `feat/deploy`

この計画は 2 段に分かれる。

| 段 | いつ行うか | 何を確かめるか |
| --- | --- | --- |
| **[8-A] デプロイ疎通** | [1] の直後に 1 回 | 依存が install できる / ポート 5000 で待ち受ける / サブパス配下で応答する / Secret が読める |
| **[8-B] 本番デプロイ** | [4] [5] [6] [7] の完了後 | 受信・画面・CSV 取込が揃った状態を配置し、端末からの往復を通す |

[8-A] を先に行うのは、実行基盤の制約に起因する手戻りを、コードが増える前に潰すためである。
[8-A] は空の DB でよく、集計も画面も要らない。

## 1. 作るもの

| ファイル | 責務 | 想定行数 |
| --- | --- | --- |
| `cc-governance-bmsd-server/requirements.txt` | 本番の依存。直接依存 3 つと推移的依存を合わせた 9 パッケージを `==` で完全固定する | 10 |
| `cc-governance-bmsd-server/requirements-dev.txt` | 開発依存（pytest / ruff）。本番の依存に混ぜない | 2 |

| `cc-governance-bmsd-server/Dockerfile` | ベースイメージ・install・ソースのコピー・`CMD` | 15 |
| `cc-governance-bmsd-server/app.py`（[8-A] 限定の最小版） | 待受の実体。`db.init()` を呼び、`GET /` に応答するだけ | 20 |

`app.py` は [4] が本体を書く。[8-A] では「waitress が WSGI アプリを掴める最小の形」だけを置き、[4] がこれを拡張する。

## 2. この計画に固有の前提

| 前提 | 内容 |
| --- | --- |
| デプロイ単位 | 開発リポジトリのルート。基盤に登録する Entrypoint は `cc-governance-bmsd-server/start.sh`（設計書 §4.6） |
| プロセスの作業ディレクトリ | `cc-governance-bmsd-server/`。`start.sh` が `cd` で移す |
| 待受 | `waitress-serve --listen=0.0.0.0:5000 app:app`。ポートは基盤が固定しており、環境変数では変えられない |
| 永続領域 | `/mnt/data`。同一ワークスペースの全 Function で共有される |
| Secret | `/mnt/data/secrets/cc-governance-bmsd.env`。基盤の Open Terminal またはワークスペースの Notebook から手で作る。リポジトリに入れない。**プロキシの設定値（`PKG_PROXY`）もここに置く。社内のホスト名は、リポジトリにも本計画書にも書かない** |
| 作業ディレクトリ | 本書のコマンドとパスは、断りのない限り `cc-governance-bmsd/`（開発リポジトリのルート）を基準とする |
| `BASE_PATH` の値 | **初回デプロイまで確定しない。** 基盤が払い出す URL のパス部分がそのまま値になる（タスク 8） |
| 開発機の Python | 3.13。**基盤は 3.9。** 開発機で解決した版が 3.9 で install できる保証は無い（タスク 1） |
| MySQL の可用性 | 接続先が用意できる場合のみタスク 11 を行う。用意できない場合は SQLite で運用し、タスク 11 を [8-B] 前の宿題として残す |
| 作業場所 | 開発機から実行基盤にも社内リポジトリにも到達できない。**【要:基盤到達】** を付したタスクは別の端末で行う。受け渡しは git（計画索引 §6） |

## 3. [8-A] デプロイ疎通

### タスク 1: 依存の固定版を決め、`requirements.txt` / `requirements-dev.txt` を作る

**ファイル:** `cc-governance-bmsd-server/requirements.txt` / `requirements-dev.txt`
**依存:** なし
**やること:**

- 直接依存は flask / waitress / pymysql の 3 つだけとする。これ以外を足さない
- **Python 3.9 で解決できる版を、解決器に 3.9 を明示して求める。** 開発機の Python は 3.13 であり、3.13 の上で `pip install` や `pip freeze` をして得た版は、`Requires-Python` が 3.10 以上の版を掴んでいることがある。**この落とし穴は install がそのまま失敗する形で基盤上に現れ、サーバは 1 度も上がらない**
- 推移的依存も含めて全行を `==` で固定する。環境マーカーによる分岐を残さない（基盤は 3.9 / Linux の 1 通りしかない）
- **推移的依存を含めて 9 パッケージである**（設計書 §4.3）
- 生成物の先頭に、直接依存が 3 つであることを示すコメントを手で 1 行置く
- **`markupsafe` はコンパイル済み拡張を含み、アーキテクチャ依存のホイールになる**（設計書 §4.3）。したがって、**依存を取得する環境と実行する環境で Python の版・ABI・プラットフォームを揃える**。下のコマンドが `--python-version` / `--abi` / `--platform` を明示しているのはこのためであり、省いて解決した結果を基盤へ持って行かない
- `requirements-dev.txt` は pytest と ruff の 2 行。`==` で固定する。**本番の `requirements.txt` には混ぜない**

**根拠:** 設計書 §4.3（依存パッケージ / 過剰にしないための制約）、§1.2（サーバの Python 3.9 固定）

**完了の判定:**

固定版を求める。

```
printf 'flask\nwaitress\npymysql\n' | uv pip compile - \
  --python-version 3.9 --python-platform x86_64-manylinux2014 \
  --no-annotate --no-header -o cc-governance-bmsd-server/requirements.txt
```

期待出力: `Resolved 9 packages in ...`。`requirements.txt` は 9 行すべてが `==` で、環境マーカー（`; python_full_version ...`）を 1 つも含まない。

> `uv` が使えない端末では `python3 -m pip download flask waitress pymysql --python-version 3.9 --implementation cp --abi cp39 --platform manylinux2014_x86_64 --only-binary=:all: -d <一時ディレクトリ>` で解決し、得られたホイールのファイル名から版を書き起こす。

3.9 / Linux 向けのホイールが実在することを確かめる。

```
python3 -m pip download -q -r cc-governance-bmsd-server/requirements.txt \
  --python-version 3.9 --implementation cp --abi cp39 \
  --platform manylinux2014_x86_64 --only-binary=:all: -d /tmp/wheels
ls /tmp/wheels
```

期待出力: 次の 9 件（版は解決時点のもの）。

```
blinker-1.9.0-py3-none-any.whl
click-8.1.8-py3-none-any.whl
flask-3.1.3-py3-none-any.whl
itsdangerous-2.2.0-py3-none-any.whl
jinja2-3.1.6-py3-none-any.whl
markupsafe-3.0.3-cp39-cp39-manylinux2014_x86_64.manylinux_2_17_x86_64.manylinux_2_28_x86_64.whl
pymysql-1.2.3-py3-none-any.whl
waitress-3.0.2-py3-none-any.whl
werkzeug-3.1.8-py3-none-any.whl
```

`markupsafe` だけがアーキテクチャ依存のホイール（`cp39` / `manylinux2014_x86_64`）であり、他の 8 件は `py3-none-any` である。ここでエラーになる行は、その版が 3.9 では使えないということであり、固定版を選び直す。**この検査を通さずに基盤へ持って行かない。**

環境マーカーが残っていないことを確かめる。

```
grep -c ';' cc-governance-bmsd-server/requirements.txt
```

期待出力: `0`

**コミット:** `依存パッケージの版を Python 3.9 向けに固定する`

### タスク 5:【要:基盤到達】社内リポジトリへ反映し、Function を作る

**ファイル:** なし（基盤側の設定）
**依存:** タスク 1〜4
**やること:**

- 社内リポジトリへ push し、自動デプロイの対象ブランチを決める
- リポジトリの設定に、基盤が公開している公開鍵をアクセスキーとして登録する（初回のみ）。**これが無いと基盤がリポジトリを取得できない**
- Function を作り、次を設定する。**設定項目はいずれも基盤側の手作業であり、リポジトリの中身では代替できない**

| 設定項目 | 値 |
| --- | --- |
| Function type | WebApp |
| Function Base | Python 3.9 系のベース |
| Input Method | Git Repository（**SSH のクローン URL のみ有効**） |
| Branch | 自動デプロイの対象ブランチ |
| Entrypoint | `cc-governance-bmsd-server/start.sh` |
| HTTP Access Mode | 決めて記録する。`/ingest` はトークンで保護されるが、画面の認証は境界に委ねる（設計書 §4.4） |
| 資源 | 初期は 1cpu × 4GiB（設計書 §1.2） |
| タグ | `NGINX_ENABLE_REWRITE_TARGET` = `false` |

- **タグ `NGINX_ENABLE_REWRITE_TARGET` を `false` にする。** 既定のままだと基盤がリクエストパスを書き換え、`SCRIPT_NAME` を与える前提（設計書 §4.3）と噛み合わなくなる。白黒はタスク 8 で付ける
- **スケールアウトの設定をしない。** SQLite で運用する場合、永続領域上の 1 ファイルを複数のレプリカが掴むと壊れる

**根拠:** 設計書 §4.6（デプロイ単位 / 環境変数）、§1.2（資源）、§4.4（認証）

**完了の判定:**

Function の一覧に対象が現れ、デプロイログが出力されている。この時点では Secret がまだ無いため、**起動は失敗しているのが正しい**（タスク 6）。

**コミット:** `疎通確認用の構成をデプロイ対象ブランチへ載せる`

### タスク 7:【要:基盤到達】Secret を置き、install と待受が通ることを確かめる

**ファイル:** なし（永続領域上の Secret ファイル）
**依存:** タスク 6
**やること:**

- Open Terminal から `/mnt/data/secrets/` を作り、`cc-governance-bmsd.env` を `KEY=VALUE` 形式で置く。**権限を `600` に絞る**
- 置く鍵は `BASE_PATH` / `DB_DSN` / `INGEST_TOKEN` / `CSV_DIR` / `PKG_PROXY` の 5 つ（設計書 §4.6）。**値をこの計画書にも git にも書かない。社内のホスト名も同様である**
  - この時点では `DB_DSN` を永続領域上の SQLite に向け、`BASE_PATH` は空のままにする（タスク 8 で確定させる）
- **依存の install に使うコマンドが `pip` か `pip3` かを確かめる。** Open Terminal から `command -v pip; command -v pip3` を実行し、`start.sh` が書いている方が PATH にあることを確認する。無ければ、実在する方に `start.sh` を直して再デプロイする
- Function を restart する。`start.sh` は起動時に 1 度だけ Secret を読むため、ファイルを置いただけでは反映されない
- デプロイログの時刻から、**スクリプト開始から待受までの所要時間を測って記録する**。依存の install を含んだ実測値であり、端末側の送信タイムアウト 60 秒（設計書 §3.5）の妥当性がこれで決まる
- **起動時にプロキシ設定が効いていることを確かめる。** install が失敗する場合、サーバは 1 度も上がらない

**根拠:** 設計書 §4.6（環境変数 / 起動スクリプト 要点 1）、§3.5（送信タイムアウト）、§11.3（起動時間）

**完了の判定:**

`pip` / `pip3` のどちらが PATH にあるかが確認され、`start.sh` の記述がそれと一致している。

```
command -v pip; command -v pip3
```

期待出力: 少なくとも一方のパスが出力され、それが `start.sh` の install 行で使っている名前と一致する。

デプロイログに次の 3 つが順に出ている。

1. 依存の install が成功した旨（`Successfully installed ...`）
2. `Serving on http://0.0.0.0:5000`
3. エラー行が無い

```
curl -s -o /dev/null -w '%{http_code}\n' https://<払い出された URL>/
```

期待出力: この時点では `404`（タスク 8 で白黒を付ける）。**接続自体が成立している**ことがここでの判定である。

起動時間の記録:

- 計測値が 60 秒を超える場合 → **[2] の `_sender.py` の POST タイムアウトを、コールドスタート時間より長い値に見直す**（設計書 §3.5）。見直しの要否を [2] の担当へ伝える

**コミット:** なし（観測のみ。所要時間を報告に残す）

### タスク 8:【要:基盤到達】Ingress がサブパスを剥がすかを確かめ、`BASE_PATH` を確定する

**ファイル:** なし（永続領域上の Secret ファイル）
**依存:** タスク 7
**やること:**

- 基盤が払い出した URL のパス部分を控える。これが公開サブパスであり、`BASE_PATH` の値になる
- **`BASE_PATH` を空にしたまま**、公開サブパス付きの URL を叩き、応答コードで白黒を付ける

| 観測 | 意味 |
| --- | --- |
| `404` | **剥がさない。** アプリはサブパスを含んだパスを受け取っている。設計どおり `BASE_PATH` を `SCRIPT_NAME` として与えれば解決する |
| `200` | **剥がす。** アプリはサブパスを含まないパスを受け取っている |

- 剥がさない（`404`）場合: Secret ファイルに `BASE_PATH` を実際の値で書き、restart して `200` になることを確かめる。**これが設計どおりの経路である**
- 剥がす（`200`）場合: **設計書 §4.3 の「WSGI ラッパ 1 個」の中身が変わる。** `SCRIPT_NAME` を立てるだけでは、アプリが生成するリンクとリダイレクトにサブパスが載らない。ラッパで `SCRIPT_NAME` を立てつつ受け取ったパスからサブパスを取り除く形にする。**ラッパは 1 個のままで足りるため、§4.2 の規律は保てる。** この分岐に入った場合は [4] の担当へ伝える

**根拠:** 設計書 §4.3（サブパスは `SCRIPT_NAME`）、§4.6（環境変数 `BASE_PATH`）、§11.3（Ingress がサブパスを剥がすか剥がさないか）

### タスク 10:【要:基盤到達】アイドル時にコンテナが停止するかを確かめる

**ファイル:** なし
**依存:** タスク 8
**やること:**

- 一定時間（30 分・数時間・1 日の 3 点を目安）アクセスせずに放置し、そのあとの初回リクエストの応答時間を測る
- デプロイログに、放置期間中の停止と再起動の痕跡が出るかを見る
- **端末の送信は detach されたプロセスの中で行われ、Claude Code の応答をブロックしない**（設計書 §3.5）。したがってコールドスタートそのものは問題にならない。問題になるのは、コールドスタートの所要時間が端末側の POST タイムアウトを超えることである

**根拠:** 設計書 §11.3（基盤がアイドル時にコンテナを停止するか）、§3.5（送信タイムアウト 60 秒）

**完了の判定:**

```
curl -s -o /dev/null -w 'total=%{time_total}\n' https://<払い出された URL>/
```

- **白（停止しない、または初回応答が 60 秒未満）** → 設計のまま。変更しない
- **黒（停止し、かつ初回応答が 60 秒以上）** → **[2] の `_sender.py` の POST タイムアウトを、実測のコールドスタート時間より長い値へ引き上げる。** 短いタイムアウトは、守るものが無いところで spool を溜め、上限による破棄を早めるだけである（設計書 §3.5）

**コミット:** なし（観測のみ。実測値を報告に残す）

### タスク 16:【要:基盤到達】日次のバックアップ手順を確立する

**ファイル:** なし（運用手順）
**依存:** タスク 15
**やること:**

- **アプリケーションにバックアップ機構を持たせない。永続領域の複製を運用手順として行う**
- SQLite で運用する場合、DB ファイルと `/mnt/data/csv/` を、CSV 取込と同じ日次の操作として複製する
- **複製先を永続領域（`/mnt/data`）の外に置く。** 同じ領域に置いた複製は、領域ごと失う障害に対して何も守らない
- MySQL で運用する場合、基盤側のバックアップに委ねる。委ねられていることを確認し、取得間隔を記録する
- 3 テーブルの再現可能性は等しくない。**`policy_state` は再現できない。** 準拠開始日は過去の観測にしか存在せず、端末から取り直す手段が無い。これを失うことは、効果測定の基準点を永久に失うことと同じである
- **復旧できるのは最後の複製時点までである**ことを、運用の前提として明示する

> **決めること 2 つ。** どちらもこの計画では決めない。
> 1. **複製先。** 永続領域の外で、日次の操作として現実に届く先を選ぶ
> 2. **手順の記録先。** この計画書は不要になった時点で削除されるため、運用手順をここに残せない

**根拠:** 設計書 §4.6（バックアップ）、§4.5（CSV 取込の起動は画面のボタン）

**完了の判定:**

複製を 1 回行い、複製先から DB ファイルを取り出して開ける。

```

```

期待出力: 複製元と同じ行数

**コミット:** なし（運用手順）
