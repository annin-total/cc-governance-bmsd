## 裁定

- **R-24: 計画 [8-A] が置いた `tests/test_app_base_path.py` の 7 ケースを壊さない。**
  本計画は `app.py` を育てるが、サブパスのラッパは**1 個のまま**にする（設計書 §4.3 の制約 5）。
  リポジトリ全体のテストは 91 + 33 = **124** になる見込み。
  外れたときの損 — ラッパが増えると、前段の挙動に依存する分岐が生まれる。
- **R-25: `app.py` は import 時に `db.init()` を呼ぶ。テストは `DB_DSN` を設定してから `app` を import する。**
  `app.py` にテストのための入口（遅延初期化のフラグ等）を作らないこと。
  理由 — 起動時に契約と実テーブルを突き合わせて落ちることが、この設計の関門そのものである（設計書 §4.3）。
  テストの都合でそれを緩めない。
  外れたときの損 — テストの書き方が少し面倒になる。実装は変わらない。

## タスク 1〜2 のレビュー結果

**Spec ❌。Critical 1 件、Important 1 件。**

### Critical C-1: 不正な `ts` の 1 行がリクエスト全体を落とす

`ingest.py` が `to_day(obj.get("ts"))` を**検査前の生の値**で呼ぶため、`ts` が int / float 以外だと `TypeError` が
`ingest()` の外へ出る。**制御側の実測:**

```
ts が文字列 : 例外 TypeError: can only concatenate str (not "int") to str
ts が配列   : 例外 TypeError: can only concatenate list (not "int") to list
ts が真偽値 : {'stored': 1, 'dropped': 0}     ← bool は int のサブクラスなので通る
ts が辞書   : 例外 TypeError: unsupported operand type(s) for +: 'dict' and 'int'
保存された行数: 1（毒の行を含むリクエストは 1 行も保存されない）
```

**なぜ Critical か** — 設計書 §4.4 の応答規則では保存失敗は 5xx であり、端末は spool を残して再送する（§3.5）。
毒の 1 行が spool に残る限り**同じリクエストが永久に 5xx を返し続け、その端末のキュー全体が詰まって測定が失われる。**
逐語制約「壊れた行は捨てて続行する。1 行の不正でリクエスト全体を失敗させない」に反する。
`/ingest` は外部入力を受ける唯一の境界であり、ここが値の型を前提にしてはならない。

### Important C-2: `tests/conftest.py` に fixture を置いていない

**これは実装者の判断ではなく、制御側の指示による。** 並列で進んでいる計画 [2] も `tests/conftest.py` を触るため、
衝突を避けて「テストファイルの中に置く」よう私が指示した。判断の責任は制御側にある。

- **R-26: `db_conn` 相当の fixture は当面テストファイルの中に置く。`tests/conftest.py` には移さない。**

### レビュアが認めた設計上の逸脱

`parse_line(line, columns)` → `parse_line(line)` への変更は **妥当**と判定された。
設計書 §4.4 が守らせたいのは「列と型は契約が単一の事実として持つ」「契約の 3 つの列定義を 1 つの形に揃えない」の
2 点であり、どちらも保たれている。**レビュアは契約に列を 1 つ足して import し、`ingest` 側が自動で追随して
INSERT に新列が乗ることを実測で確認している。**
検査 2（`kind` で投入先が決まる）は `json.loads` の後でなければ列定義を選べないため、逸脱しない書き方は
二重パースか責務の悪化を招く。設計書のサンプルは `kind` の分岐を省いた形である。

### レビュアが実測で確認した良い点

  1 番目の `events` の 2 行も確定しなかった（`COUNT(*)` = 0）

## タスク 3〜6 と修正の再レビュー結果

**C-1 は ADDRESSED**（レビュアが独立に 4 パターンを再現）。**ただし Critical が 2 件残った。**

### Critical K-1: 非 ASCII のトークンで 401 が 500 になる【裁定 R-27 が持ち込んだ退行】

`hmac.compare_digest` は `str` 同士の場合 **ASCII のみ**を受け付け、それ以外は `TypeError` を送出する。
WSGI はヘッダ値を latin-1 で `str` に復号するため、`0x80`〜`0xFF` のバイトを 1 つ含むヘッダで確実に発火する。

**制御側の実測:**

```
ASCII 不一致    : 401     ← 正しい
非 ASCII ヘッダ : 500     ← TypeError: comparing strings with non-ASCII characters is not supported
```

実害は 2 つ。① 設計書 §4.4 の「トークン不一致 → 401」に反し、壊れたトークンを持つ端末が永久に再送し続ける。
② 運用者が `INGEST_TOKEN` に非 ASCII（全角・コピペ混入の NBSP など）を設定すると、
**正しいトークンを送っている全端末の受信が恒久的に 500 になる。**

**R-27 は「1 行で済み、外れたときの損はなし」という前提で出した裁定だったが、その前提が成り立っていなかった。
制御側の誤りである。** 直し方はバイト列での比較（`compare_digest` の `bytes` 版に ASCII 制限は無い）。

### Critical K-2: 64bit を超える整数が C-1 と同じ形でリクエスト全体を落とす

**制御側の実測:**

```
ts が 40 桁             : 500 （正常な行 2 行も含めて保存 0）
context_tokens が 40 桁 : 500
```

例外は `executemany` から `OverflowError: Python int too large to convert to SQLite INTEGER` として出る。
`coerce(value, "INTEGER")` が**桁の上限を持たない**ため、`ts` に限らず INTEGER / BIGINT のどの列でも
大きな整数が毒の行になる。

- **R-30: 範囲検査は `contract.py` の `_coerce_int_like` に置く。符号付き 64bit の範囲外は `None`。**
  理由 — 共通制約「桁に収める責務は契約だけが持ち、受信側で再解釈しない」と同じ責務である。
  設計書 §3.2 が切り詰めを契約に置いた理由（「MySQL は桁超過を拒否し、`executemany` の 1 行が落ちると
  リクエスト全体が失われる」）が K-2 にそのまま当てはまる。契約に置けば `ts` 以外の列も自動で救われる。
  **`contract.py` は計画 [1] の成果物だが、この変更を許可した。**
  外れたときの損 — この変更が `feat/server-ingest` にのみ入るため、突き合わせまで `feat/client-collection` の
  `contract.py` と差が出る。端末側が自分で組み立てる値（`ts` は `time.time()`、`day` は `to_day`、
  `context_tokens` は transcript の合計）が 64bit を超えることは現実には起こらないため、実害は無い。

### 残る既知の限界（記録のみ。今は直さない）

**MySQL の `INTEGER` は 32bit（`INT`）であり、64bit の範囲検査を通った値でも `[2^31, 2^63)` は拒否されうる。**
契約は `ts` を `INTEGER` と宣言しており、**MySQL では 2038-01-19（epoch 2147483647）以降の `ts` が格納できない。**
SQLite の `INTEGER` は 64bit なのでこの問題は SQLite だけの確認では表に出ない。
**計画 [8] の MySQL 実接続で確かめること。**

## 再レビュー（K-1・K-2 の修正）

**K-2 は closed。** レビュアが実サーバ + curl で境界値まで確認した（`2**63-1` と `-(2**63)` は通り、

### K-1 は未解決だった — 符号化の非対称

500 は消えたが、**実害②（運用者が非 ASCII の `INGEST_TOKEN` を設定すると全端末の受信が壊れる）が残っていた。**

**制御側が実サーバ（waitress + curl）で実測:**

```
INGEST_TOKEN="トークン" で起動
  同じ値を送る : 401   ← 200 であるべき
  違う値       : 401
  ASCII        : 401
```

原因は両辺のエンコード方式の非対称。

| 値 | 復号のされ方 | 元のバイトを取り戻す符号化 |
| --- | --- | --- |
| ヘッダ | WSGI が **latin-1** で復号 | `latin-1` |
| 環境変数 | `os.environ` が **utf-8/surrogateescape** で復号 | `utf-8` |

両辺に `utf-8` を使っていたため、ヘッダ側だけが二重エンコードされ、永久に一致しなかった。

### ⚠️ テストの忠実性に関する発見（重要）

**Flask の `test_client()` では、この種の符号化欠陥を原理的に検出できない。**

制御側が `test_client()` で試したときは **200** が返り、実サーバでは **401** だった。
`test_client()` はヘッダを復号済みの `str` としてそのまま渡し、**WSGI の latin-1 による線上符号化を経由しない**ためである。

**`/ingest` のヘッダに関する検査は `environ_overrides` で WSGI 環境を直接組み立てるか、実サーバを立てて行うこと。**
この発見は計画 [5] [6] が `app.py` を育てるときにも効く。

### 新 Critical S-1: 孤立サロゲートを含む文字列がリクエスト全体を落とす

**制御側の実測:**

```
user_email に "\ud800"  : 500
event_id   に "\ud800"  : 500
host       に "a\udfffb": 500
session_id に "\ud83d"  : 500
保存された行数: 0 （正常な行も失われている）

json.loads('"\ud800"') = '\ud800'   ← JSON として完全に妥当
```

例外は `executemany` から `UnicodeEncodeError: 'utf-8' codec can't encode character '\ud800' ...
surrogates not allowed` として出る。**K-2 と同型で、VARCHAR 側に同じ責務が無かった。**
hook の payload に不対サロゲート（切れた絵文字など）が 1 つ紛れ込むだけで、そのリクエストの全行が失われる。

- **R-31: `contract.py` の `_coerce_varchar` で、符号化できない文字を置換する。**
  理由 — 共通制約「桁に収める責務は契約だけが持ち、受信側で再解釈しない」と同じ責務である。
  **行を捨てるのではなく値を置換する**（切り詰めと同じ扱い。値は劣化するが行は残る）。
  桁での切り詰めより前に置換する（置換で文字数が変わりうるため）。
  外れたときの損 — 不正な文字を含む値が `?` などに化ける。元の値は復元できないが、行は失われない。
