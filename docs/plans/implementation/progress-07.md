## 裁定

**R-52: 配布リポジトリは `git init` で独立化し、親の追跡から外す。**
理由: 計画書タスク 1 の指示どおり。前提が「未初期化」と食い違っていたため `git rm --cached` の 1 手順を追加した。
最終的には配布経路のリポジトリに置くものであり、開発リポジトリの履歴を持ち込まない（設計書 §8）。
外れたときの損: 親の履歴に配布物が混ざる。

**R-53: 親リポジトリの変更は `main` に直接コミットせず、ブランチを切って PR にする。**
理由: 利用者の運用（ブランチごとに PR・マージはしない）に揃える。既定ブランチへの直接コミットを避ける。
外れたときの損: 利用者がレビューする前に親の `main` が動く。

**R-54: `config.json` の送信先は空のままリポジトリに残す。検査 5 は実装し、ローカルでは一時的に値を入れて「通る／落ちる」の両方を確認してから戻す。**
理由: 基盤の URL とトークンはこの PC から分からない。**誤った URL を配布物に焼き込むより、検査で止まる方が安全である。**
検査 5 の存在意義は、空のまま配ると端末が 1 件も送信しないまま「導入済み」に見えることを防ぐ点にある。
案内文の URL も `<社内リポジトリの https URL>` と明示的な差し込み箇所にする。
リリース手順書に「初回リリース前に埋めること」を必須手順として書く。
外れたときの損: 初回リリース時に埋め忘れる。→ 検査 5 がリリースを止めるため、事故には至らない。

**R-55: タスク 9〜11 は基盤到達が要るため保留する。**
外れたときの損: git リモートを `source` にしたときの伝播と、初回リリースが未検証のまま残る。台帳と PR に明記する。

## スコープの確定（2026-09-22）

利用者の判断により、計画 [7] の範囲を次のとおり確定した。

### 裁定 R-56: 差し込みは手動で行い、`scripts/release.sh` は削除する

理由: 利用者が「差し込みは手動で行う。`release.sh` のようなものは不要」と判断した。
あわせて「開発環境に Windows と macOS の両方がある」ため、**シェルスクリプトを開発者が触る範囲に残さない**方針となった。
`release.sh` は POSIX シェル専用であり、Windows の開発者には使えない。

**削除によって失われる 3 つの自動検査を、`docs/release.md` の確認項目に人の作業として明記した。**
- 送信先（`ingest_url` / `ingest_token`）が埋まっていること
- `version` を上げ忘れていないこと
- `POLICY` からキーを削除していないこと

外れたときの損: 人が確認を飛ばすと、上げ忘れた版が「届いたことになる」、あるいは誤った値が全端末に固定される。
→ 確認項目として文書に残し、PR のレビューで見る運用とする。

### 裁定 R-57: 検証スクリプトは Python で書き、シェルを使わない

理由: 開発環境に Windows がある。`python` / `python3` のどちらでも、macOS / Windows のどちらでも動く。
`pathlib` を使い、`find` / `grep` / `shasum` のような外部コマンドを呼ばず、ファイル入出力は `encoding="utf-8"` を明示する
（**Windows の既定は cp932 であり、明示しないと日本語を含むファイルで落ちる**）。

**サーバ側は対象外。** `cc-governance-bmsd-server/start.sh` は AIP の Linux コンテナが実行するものであり、
設計書 §4.6 が中身を規定している。リポジトリ全体でシェルスクリプトはこの 1 本だけになる。
Docker Compose は追加しない。`requirements.txt` と起動コマンドを二重に持つ保守対象が増えるためで、
`Dockerfile` が既にあるので AIP と同じ構成でのローカル起動は現時点でも可能である。

### 裁定 R-58: `hooks.json` の `python3` は変えない

理由: Windows の python.org 版には `python3.exe` が無く、hook が 1 つも動かない可能性がある
（設計書 §1343 / 計画 [0] の未検証項目）。しかし次の理由により、コード側では対処しない。

- `hooks.json` に OS 条件のフィールドが無い
- 同じ hook を 2 エントリ登録すると**並列実行され二重計上**になる
- 設計書 §3.3 がコマンドにパイプ・`;`・`&&`・リダイレクトを禁じており、フォールバックを書けない
- ランチャー方式は、Windows で Git Bash が無い端末が PowerShell になるため `.sh` だけでは足りず、検証対象が増える

代わりに **`docs/onboarding.md` で導入の前提条件として扱い、`/policy` の未導入者一覧で検知する。**
`queries_policy.not_introduced` は、直近 30 日に `cost_daily` に居るのに `policy_state` に 1 行も無い利用者を出す。
**`python3` が解決できない端末は必ずここに現れる。**

外れたときの損: Windows 端末が全滅しても、案内後に未導入者一覧を見るまで気づかない。

### 配布まわりの成果物

| ファイル | 役割 |
| --- | --- |
| `scripts/validate_plugin.py` | 差し込み前にプラグインを検証（11 項目） |
| `../cc-marketplace-governance-bmsd/scripts/validate.py` | コピー後にマーケットプレイスを検証（6 項目・プラグイン名を決め打ちしない） |
| `docs/release.md` | 手動での差し込み手順 |

検証スクリプトの設計方針は「**在ること**は見るが**何であるか**は見ない」。
列名・キー・件数・ファイル一覧・version の大小・開発リポジトリとの差分は、いずれも検証しない。
仕様が変わるたびに保守が必要になるためである。

### 監督役が見つけて直したもの

| 内容 | 実測した故障 |
| --- | --- |
| `.DS_Store` による恒久的な誤検出 | macOS が再生成するため、削除しても 20 秒後には戻り、検証が常に赤くなっていた |
| `ruff` の取りこぼし | PATH だけを探しており `.venv/bin/ruff` を見落とし、py39 構文の検査が常に `[SKIP]` だった |
