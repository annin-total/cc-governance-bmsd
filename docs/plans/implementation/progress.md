### 裁定

- **R-1: 開発依存の版は `pytest==9.1.1` / `ruff==0.16.8` に固定する。**
  理由 — どちらも現時点の最新であり、開発機（3.13.2）で動く。pytest 9.x は `requires_python >= 3.10` だが、
  開発依存は本番に載らず、サーバの 3.9 固定の対象外である。
  外れたときの損 — テストを 3.9 で回したくなった時点で pytest を 8.x 系へ落とす必要がある（`requirements-dev.txt` の 1 行）。
- **R-2: ruff の設定はリポジトリ直下の `ruff.toml` に置き、`target-version = "py39"` だけを書く。**
  理由 — 計画は「作る Python ファイルは 3 つ」と言うが、設定ファイルは対象外。`pyproject.toml` を新設すると
  パッケージ定義という別の保守対象が生まれる。
  外れたときの損 — 設定の置き場所を移す 1 ファイルの移動。
- **R-3: `init()` は引数を取らず内部で `connect()` する。`analyze(conn)` は接続を受け取る。**
  理由 — タスク 11 が「接続を受け取り」と明記し、タスク 9 は何も言わない。タスク 9 のケース 6（`init()` 前に INSERT した行が残る）は
  `init()` が自前で接続を開く形でないと書けない。
  外れたときの損 — `init()` の呼び出し側（計画 [4] の `app.py`）の 1 行。
- **R-4: `db.py` の内部関数は `_` 接頭辞で区別し、テストはそれを直接呼んでよい。**
  方言判定は `_dialect()`、SQLite のパス解決は `_sqlite_path()` とする。
  理由 — タスク 8 ケース 1 は方言と解決パスを検査するが、完了条件は「`connect` / `q` / `init` / `analyze` の 4 つ以外を公開しない」。
  `CLAUDE.md`「内部関数・内部メソッドは識別子を付与して区別する」に従えば両立する。
  外れたときの損 — 名前の変更のみ。
- **R-5: タスク 10 のテストは、`db` の名前空間に束縛された契約定数（`db.HOOK_FIELDS` 等）を差し替える。**
  理由 — 設計書 §6.1 は `from shared import HOOK_FIELDS, ...` と書くことを定める。この形では `contract` の属性を差し替えても
  `db.py` には伝わらない。`db` の束縛を差し替えれば、テーブルは既存のまま列の突き合わせだけが不足を検出するため、
  タスク 10 ケース 2（`ALTER TABLE` が発行されない）も同時に成立する。
  外れたときの損 — テストの差し替え対象の変更のみ。実装には影響しない。
- **R-6: インデックス名は `ix_<テーブル名>_<列を _ で連結>` とする。**
  例 — `ix_events_skill_name_day_user_email_event_id`（44 文字。MySQL の識別子上限 64 文字に収まる）。
  理由 — 計画に定めが無い。列の並びから一意に決まる名前なら、定義表とインデックス名がずれない。
  外れたときの損 — 既存 DB があるときに古い名前のインデックスが残る。作り直しで解消する。
- **R-7: 一時 SQLite の fixture は autouse にしない。** テストが明示的に要求する。
  理由 — タスク 8 ケース 3 が「`DB_DSN` 未設定」を検査するため。
  外れたときの損 — なし（テストの書き方のみ）。

### タスクの記録

- **R-8: 開発用の仮想環境を `cc-governance-bmsd/.venv` に置く。** 以降のコマンドは `.venv/bin/pytest` / `.venv/bin/ruff` を使う。
  理由 — 開発機の global には ruff が無く、pytest の版も固定できない。`.gitignore` に `.venv/` は既にある。
  外れたときの損 — なし（環境の置き場所のみ）。
- **R-9: `ruff.toml` に `extend-exclude = ["docs/"]` を足す。**
  理由 — `ruff format` は Markdown 中の Python コードフェンスも整形対象にする。実際に `docs/design.md` の 4 か所が
  「要整形」と判定されることを確認した。設計書のコードフェンスは桁を揃えた説明用の断片であり、整形の対象ではない。
  `CLAUDE.md` が `ruff format .` をルートで実行すると定めている以上、除外は設定側に持たせる。
  外れたときの損 — `docs/` 配下に本物の Python ファイルを置いた場合に整形されない。現時点でそのような配置は無い。
- **R-10: AI Gateway CSV のヘッダ名の正本は `../data/` の実ファイルとする。**
  設計書はヘッダ名を持たず DB 列名しか書いていないため、実ファイルの 1 行目を直接読んで確認した（15 列。
  うち `Workspace ID` / `User ID` / `User Name` は収集しない）。
  外れたときの損 — ヘッダ名が違えば CSV 取込（計画 [6]）が全列を取りこぼす。計画 [6] の実機確認で表に出る。

- **R-11: `ruff.toml` で `FA100` を無効にする（`[lint] ignore = ["FA100"]`）。**
  理由 — ruff 0.16.8 の既定ルールセットは、`typing.Optional` に対して FA100（`from __future__ import annotations` を足せ）を出す。

  「py39 の `typing.Optional` を使う」はリポジトリ全体の方針であり、設定に 1 回書くべきもので、コードに `# noqa` として散らすものではない。

  既に積んだ履歴の書き換えは、得るもの（見た目の整合）より失うもの（履歴の安全性）が大きい。
