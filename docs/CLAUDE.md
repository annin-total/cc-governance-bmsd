# CLAUDE.md - docs

文書を書くときの判断基準と規約。親リポジトリ・サーバ（submodule）・`verification/` の文書すべてに適用する。

## 何を書くか（判断基準）

文書の目的は、将来の読者（人と AI）の判断を助けることにある。記録を網羅することではない。

- ドキュメント管理コストを抑えることを優先する
- **漏らさず書こうとしない。**妥当な範囲で情報を捨ててよい。変更は最小限にとどめる
- **実装・テスト・設定を読めば分かることは書かない。**実装と二重管理になり、必ず古くなる
- 書く価値があるのは、実装から読み取れないことだけ:
  - なぜそうしたか
  - 何を守るか（不変条件）
  - 採らないと決めたことと、その理由（決着した判断の蒸し返しを防ぐ）
  - 外界の事実（上流の仕様、実測値）
  - 人が手を動かすときの順序と、踏みやすい罠
- **残すかどうかは、失ったときに事故・誤った運用・蒸し返しに直結するかで決める。**
  「あると便利」「再現に手間がかかる」だけでは残す理由にならない
- **1 つの事実は 1 か所にだけ書く。**書く前に、置き場（「構成」）と、既にどこかに書かれていないかを確かめる
- 機微情報（実在のメールアドレス・ホスト名・社員 ID・トークンの値）は書かない

## 構成

```
docs/
  README.md    索引。誰がどれを読むか
  CLAUDE.md    この文書
  spec/        仕様。今どうなっているか
  decisions/   設計判断の記録。なぜそうしたか（契約とプラグインは plugin.md、サーバは server.md）
  guide/       手順書。導入・リリース・デプロイ・検証
  knowledge/   外界の事実。Claude Code・DB・フレームワークの仕様と実測値
  remaining/   未了の作業。すべて片付いたらディレクトリごと消す
```

サーバの文書もここに置く。サーバのリポジトリに文書を置かない。
コードの規約と罠は各リポジトリの `CLAUDE.md` に置く。理由がコードの 1 行に結びつくなら、文書ではなくそのコードのコメントに書く。
検証の道具の引数と挙動は各スクリプトの冒頭に書き、`verification/README.md` は道具のカタログとして
1 行の説明だけを持つ。

### knowledge/ に置くもの

- **判定は 1 つ: 我々のリポジトリが消滅しても真であり続けるか。**我々の設計・採否・使用状況
  （「使っている」「採らない」「だから Z にした」）には触れない
- 1 項目は数行。事実とそれがいつ効くかだけを書き、再現手順は書かない
- 確認した版（と環境）を添える。数字には測定条件を添え、`knowledge/measurements.md` に置く。
  測らずに決まっている仕様は `knowledge/db-and-framework-facts.md` に置く

### remaining/ に置くもの

- **完了条件が書けるものだけ。**やれば終わる作業と、確かめれば白黒が付くこと。完了条件を必ず書く
- 項目の状態が変わったら書き足さずに動かす:
  - 終わった → 項目を消す（「完了」と書き残さない）
  - 白黒が付いた → 項目を消す。結果が外界の事実なら `knowledge/` へ移す
  - やっても終わらない（受け入れる限界）と分かった → `decisions/` へ移す
- 文書が空になったら消し、`README.md` の一覧からも外す

## 参照の向き

- `spec/`・`decisions/`・`guide/` はファイル単位で互いに参照してよい。仕様書は「なぜ」を `decisions/` に任せ、本文に混ぜない
- **`knowledge/` は何も参照しない。**外界の事実は定義上どこも指す必要がなく、だから誰からでも参照してよい
- **`remaining/` は他から参照しない。**消える前提の文書であり、参照されると消せなくなる。
  例外は `README.md` の一覧と、スキルがディレクトリとして参照すること（ファイル名は指さない）だけ。
  コード・設定ファイル・コミットメッセージからも参照しない。
  `remaining/` から他を参照するのはよい
- 参照はファイルのパスで行う。**章番号・§・アンカーで参照しない**（章の増減で黙って壊れる）。
  見出しの名前で補足するのはよい（例: `spec/plugin.md` の「蓄積と送信」）

## ファイル名

- `README.md` と `CLAUDE.md` 以外は小文字のケバブケースにする。採番の接頭辞（`01-`）を付けない
- 一時的な文書は `product/` の外か `remaining/` に置く

## 記述ルール

1. **本文に修正の経緯を残さない。**「〜に変更した」「当初は〜だったが」を書かない。
   現時点で正しいことだけを、初めからそう設計されていたかのように書く
2. 更新時は、経緯・変更履歴を末尾の「改訂履歴」章に分離・集約する
3. 旧実装の固有名詞・検証の経緯（特定のファイル名・検証番号・過去の判断への言及）を持ち込まない
4. **事実と推測を区別する。**未検証のことは「未検証」と明記する
5. 日本語で書く。ファイル名・関数名・変数名など英語が適する箇所は英語を使う
