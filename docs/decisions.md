# 設計判断

**現在のコードがなぜそうなっているかの記録であり、成果物ではない。**
仕様書（`SPEC.md` / `SPEC-plugin.md`）が「何を作るか」を定めるのに対し、
ここは「読んだだけでは理由が分からず、善意で元に戻すと壊れるもの」だけを集めている。

**`CLAUDE.md` を除き、他のドキュメント・実装コード・設定ファイル・コミットメッセージから、
この文書を参照してはならない。** 参照してよいのは `CLAUDE.md` の 1 か所だけである。
この文書から仕様書や `knowledge/` を参照するのは構わない。

**したがってこの文書は将来削除してよい。** 削除しても他のどこも壊れない。
誰からも参照されず、読みたい人が自分で見つける文書という位置づけである。

**契約（`plugin/hooks/contract.py`）とプラグイン（`plugin/`）に関する判断はここに集約する。**
サーバ（`cc-governance-monitor`）に関する判断は `server/docs/decisions.md` に置く。境界事例
でも分割しない。

各項目は **何がそうなっているか → なぜか → 変えるとどうなるか** の順で書く。

## 1. アーキテクチャ上の判断

| # | 論点 | 採った案 | 採らなかった案と理由 |
| --- | --- | --- | --- |
| 1 | 受信 API の検査 | **契約から導出した検査** | *バリデーションライブラリ* — 列と型は契約が既に持っており、別の語彙で書き直すと正本が 2 か所になる。*画面の表示データにも型を置く* — 検査対象が増えるだけで、検査で防げる誤りが無い |
| 2 | 準拠の記録 | **適用前後の値そのもの。判定は適用前の値** | *版番号だけ* — 60 と 80 を区別できない。*適用後の値だけ* — 直前に自分が書いた値なので全員が常に準拠になる |
| 3 | 施策の適用モード | **強制のみ** | *利用者が選択的に適用* — 準拠者と非準拠者の差が施策の効果なのか自己選択なのか区別できず、効果測定が成立しない |
| 4 | 通知の配信 | **`notices.json` を git で配り端末が表示** | *サーバのポーリング API* — サーバ停止で通知が止まる。配信の実体が git である前提に反する |
| 5 | 収集の抽出 | **キーパスを名指しで `get`** | *hook 入力を丸ごと保存して後で選別* — `tool_input` にプロンプト本文が入るため、上流が自由文キーを足した瞬間に流出する |
| 6 | hook 登録 | **7 種のみ・共通エントリ** | *全 hook を網羅登録* — 種類が増え続けるため網羅は原理的に達成できず、維持コストだけが残る。*画面が必要とする列の供給元を登録しない* — その列を主題にした画面が恒久的に空になる |
| 7 | 送信 | **hook 内は追記のみ・送信は detach** | *hook 内で同期 POST* — Claude Code の応答をネットワーク遅延でブロックする。体感を損なう施策は推進の妨げになる |
| 8 | 送信の信頼性 | **spool ファイル + 上限で破棄** | *ローカル DB + ACK + 再送制御* — 高い正確性が要求されていないのに、端末側に DB とトランザクション管理を持ち込むことになる |
| 9 | `context_tokens` | **絶対値のみ** | *使用率* — モデルごとの窓サイズ表が必要になり、モデルの増減が保守を呼ぶ |
| 10 | 値の解釈 | **生の文字列のまま保存** | *許可リスト・分類辞書* — 上流が新しい値を出した瞬間に取りこぼす。解釈は集計時に行えば十分 |
| 11 | 設定適用の失敗時 | **何もしない** | *壊れた settings.json を修復・再生成* — 利用者の設定を壊すリスクが、ポリシー適用の利益を上回る |
| 12 | 無効化スイッチの範囲 | **収集・送信・表示のみ** | *設定適用も止める* — 環境変数 1 つで施策から離脱できることになり、「強制のみ」の原則が裏口から崩れる |

## 2. 端末プラグイン

### `plugin/hooks/` のファイル名は標準ライブラリと衝突させない

spool を扱うモジュールは `_spool.py` である。hook は `python3 "${CLAUDE_PLUGIN_ROOT}/hooks/collect.py" <hook名>` の形でスクリプトとして起動され、Python はスクリプト自身のディレクトリ（`plugin/hooks/`）を `sys.path` の**先頭**に自動で入れるため、このディレクトリに置いたファイル名は標準ライブラリの同名モジュールを覆いうる。

`_queue` は CPython の標準ライブラリ（`queue` モジュールの C 実装）の名前である。
配布物がこれを覆うと、`import queue` の時点で `queue.SimpleQueue` が純 Python 実装へ静かに降格し、
`_queue` が builtin として組み込まれたビルドでは逆に配布物の方が読まれず、
送信モジュールからの呼び出しが `AttributeError` になって**無言で送信が止まる**。
端末の Python の版とビルドは選べない。

`types.py` / `queue.py` / `platform.py` のような名前をこのディレクトリに置くと、
プラグイン全体の import が静かに壊れる。ファイルを足すときは標準ライブラリの名前を避ける。

### `collect.py` は `_signal` で SIGINT を無視し、それを `__main__` の内側で行う

hook は「常に `exit 0` で終わり、標準エラーにも何も出さない」。
利用者が Ctrl+C を押した瞬間に hook が走っていると、`KeyboardInterrupt` のトレースバックが
利用者の画面に出る。hook は数十 ms 走るので、この窓は実在する。

`signal` ではなく `_signal` を使うのは import の代のためである（`_signal` は 66 µs、`signal` は 4,615 µs。
40 ms 台のプロセスでは無視できない）。`_signal` は CPython に常に組み込まれる builtin である。

**`if __name__ == "__main__":` の内側に置くのは、これが import 副作用だからである。**
モジュールのトップレベルに置くと、`import collect` しただけで呼び出し元プロセスの SIGINT が
無視に変わり、テスト実行中に Ctrl-C が効かなくなる。

### `collect.py` の入口は `except BaseException` で囲む

`except Exception` では `KeyboardInterrupt` を捕まえられず、上の SIGINT 対策と噛み合わない。
hook は 0.05 秒程度の短命プロセスであり、中断処理は Claude Code 本体が別に持つ。
狭めると、中断のたびに利用者の画面がトレースバックで汚れる。

### `import _sender` は送信条件の判定の内側にある

`_sender` を使うのは `Stop` と `SessionStart` だけである。モジュールの先頭で import すると、
`urllib.request` と `ssl` の読み込み（約 33 ms）を**ツール実行のたびに**払うことになる。
遅延させることで、最高頻度の hook の実行時間は 0.08 秒から 0.04〜0.05 秒になる。

先頭へ戻すと、その差が毎ツール実行で復活する。

### `_spool.mark_sent()` は `_sender.launch()` より先に呼ぶ

`launch()` の後に呼ぶと、子プロセスの起動と `mark_sent()` の間に、
別セッションが送信条件を真と読む窓が残る。送信プロセス側で呼ぶのはさらに悪い
（起動から到達まで数十〜数百 ms あり、その間に他のセッションが一斉に送信を起こす）。

順序を入れ替えると、同時に開いているセッションの数だけ送信プロセスが立つ。

### 送信の成否にかかわらず `sent_at` を更新する

成否に連動させると、サーバが止まっている間、全端末が hook のたびに送信プロセスを起こし続ける。
再送は spool が担保しており、`sent_at` は「起こす頻度の制御」だけを担う。

連動させると、サーバの停止が全端末の負荷に変わる。

### `session_start.py` は `collect.main()` を呼ばない

無効化スイッチ（`CC_GOVERNANCE_DISABLE`）が止めるのは、利用ログの収集とお知らせの表示だけである。
**ガバナンスの適用とその記録の伝達は止めない。** `collect.main()` はスイッチが立つと冒頭で return し、
送信条件の判定にすら到達しないため、委譲すると無効化した端末の policy イベントが端末に溜まり続ける。
その端末は準拠率の分母から静かに消え、施策の効果が実態より良く見える。

`session_start.py` は収集部分を自分で組み立て、送信条件の判定を無効化スイッチの**外側**に置いている。
委譲に直すと、無効化した端末がサーバから消える。

### `_identity` は `Path.home()` を関数の中でだけ評価する

import 時に評価すると、テストが環境変数で隔離しても効かず、
**利用者本人の `~/.claude/` に書き込む。** 状態ディレクトリの解決は `_spool._state_dir()` に集約され、
`_identity` はそれを参照する。

トップレベルへ移すと、隔離が無効になる。

### `_identity` の git 呼び出しは `ValueError` も捕まえ、タイムアウトを 3 秒にする

git が非 UTF-8 の `user.email` を返すと `UnicodeDecodeError`（`ValueError` 派生）になる。
捕まえないと、キャッシュの保存にすら届かず、**以後すべての hook が同じ経路で無言のまま落ち続ける。**
サーバからは「使っていない利用者」と区別が付かない。

タイムアウトが hook 全体の制限（5 秒）と同値だと余白がゼロになり、
git が固まったときに hook ごと打ち切られてキューに 1 行も残らない。

### `_context.py` は合計が 0 の `message.usage` を読み飛ばす

`message.usage` の 3 値がすべて 0 の行は、API エラー応答として実在する。
採ってしまうと**文脈量 0 が実データに混ざり、画面からは区別できない。**

読み飛ばして前の行へ遡ると、その行が無かったときと同じ扱いになる。
0 を有効値として採ると、分布の左端が汚れる。

### `collect.py` は追加列を `raw_extra.get(name)` で引く

契約は複数の箇所が共有する正本であり、列は現実に増える側の定数である。
添字（`raw_extra[name]`）で引くと、列を 1 つ足しただけで `KeyError` が入口の例外処理に飲まれ、
**終了コード 0 のままキューに 0 行**という無言の全損になる。

添字に戻すと、契約への列追加が端末側の全損に変わる。

### `_settings.py` はシンボリックリンクを解決してから書く

`os.replace` はリンク**そのもの**を置き換える。解決しないと、dotfiles 管理下（stow / chezmoi など）の端末で
`settings.json` が普通のファイルに化け、実体は空のまま取り残される。しかも適用結果は成功として記録される。

解決を外すと、利用者の管理構成が沈黙して壊れる。

### `_settings.py` は同じディレクトリに一時ファイルを作ってから `os.replace` する

`settings.json` は利用者の資産であり、再構築できない。書き込み中に電源が落ちると、
直接書きでは切れた JSON が残る。一時ファイルを別のディレクトリに作ると、
ホームが別のファイルシステムにある端末でクロスデバイスになり、恒久的に書き込みが失敗する。

`dir=` を外すと、その端末では設定が二度と適用されない。

### `_settings.py` の読み込みは `RecursionError` も捕まえる

深い入れ子の JSON は `RecursionError` を投げる。これは `ValueError` の派生ではない。
漏らすと `SessionStart` のたびに落ち、お知らせも policy イベントも届かず、
その端末が準拠率の分母から静かに消える。非 UTF-8 の `settings.json` に対する `UnicodeDecodeError` も同じ理由で捕まえる。

### 値の比較は型を含めて厳密に行う

Python では `1 == True` が真である。素の `==` で比べると、`autoUpdate` が整数 `1` の端末を
準拠済みと誤認し、JSON 上は `true` でない値が残り続ける。

### `session_start.py` は標準出力への書き込みに失敗したら fd 1 を `/dev/null` へ差し替える

パイプの読み口が閉じていると、`write` / `flush` の例外を捕まえても、
バッファに残った書き込み済みデータがインタプリタ終了時の最終 flush で再送され、そこで再び失敗する。
結果は**終了コード 120 と標準エラーへの出力**であり、「常に `exit 0`・標準エラーに出さない」に反する。

差し替えを外すと、この経路が戻る。

### `_notices.py` は壊れたお知らせ項目だけを飛ばす

本文が文字列でない項目が 1 件混ざると、整形の段で例外になり、
**同じファイルの正常な項目まで 1 つも表示されなくなる。**
絞り込みで型を検査し、壊れた項目だけを落とす。

### `hooks.json` の起動コマンドは `python3` のままにする

Windows の python.org 版には `python3.exe` が無く、その端末では hook が 1 つも動かない。
それでもコード側では対処しない。

- `hooks.json` に OS 条件のフィールドが無い
- 同じ hook を 2 エントリ登録すると**並列実行され二重計上**になる
- `SPEC-plugin.md` §3 がコマンドにパイプ・`;`・`&&`・リダイレクトを禁じており、フォールバックを書けない

代わりに `docs/onboarding.md` が導入の前提条件として扱い、`/policy` の未導入者一覧で検知する。
`python3` が解決できない端末は必ずそこに現れる。

フォールバックを書き足すと、禁止している記号を持ち込むか、二重計上を招く。

## 3. 契約

### `coerce` はスカラ以外（dict / list）を `None` にする

「収集は最小限にする。契約が名指ししたものだけを読む。本文には触れない」はこの設計の中核の約束である。
上流がキーパスの先の型を dict に変えたとき、`str(value)` で文字列化すると
**名指ししたキーパスの値ではなく、その中身全部が宣言長まで載る。** 自由文の流出経路そのものである。

`str()` に戻すと、上流の型変更がそのまま流出になる。欠測の方がはるかに良い。

### `coerce` は整数を符号付き 64bit の範囲に収める

範囲外の整数は保存の段で例外になり、**同じリクエストに含まれる正常な行まで 1 行も保存されない。**
`/ingest` は外部入力を受ける唯一の境界であり、毒の 1 行が spool に残る限り
その端末のキューは永久に詰まる。範囲検査を契約に置くと、`ts` 以外の列も自動で救われる。

### `coerce` は符号化できない文字を置換してから切り詰める

孤立サロゲートは JSON として妥当であり、`json.loads` を素通りする。
保存の段で符号化に失敗すると、上と同じ形でリクエスト全体が失われる。
**行を捨てるのではなく値を置換する**（切り詰めと同じ扱いで、値は劣化するが行は残る）。

置換は切り詰めより**前**に行う。置換で文字数が変わりうるためである。

### `coerce` は未知の型トークンに対して例外を投げず `None` を返す

契約は端末にそのまま配布される。hook が例外を出す経路を作ると、
「1 列が NULL」より悪い「イベント全件の欠落」になりうる。
防御はテスト側の型トークン検査が担う。

## 4. 配布と検証

### 配布への差し込みは手動で行い、シェルスクリプトを開発者が触る範囲に置かない

開発環境に Windows と macOS の両方がある。POSIX シェル専用のスクリプトは Windows の開発者には使えない。
このリポジトリの中に開発者が日常的に触るシェルスクリプトは無く、sh 前提の起動スクリプト
（`server/entry.sh`）は別リポジトリ `cc-governance-monitor` の中で、Linux コンテナだけが実行する。

**その代償として、`version` の上げ忘れ・送信先の空・ポリシーからのキー削除を自動で検出する仕組みは無い。**
これらは `docs/release.md` の確認項目として人が見る。飛ばすと、
上げ忘れた版が「届いたことになる」か、誤った値が全端末に固定される。

### 検証スクリプトは Python で書き、外部コマンドを呼ばない

`python` / `python3` のどちらでも、macOS / Windows のどちらでも動く必要がある。
`find` / `grep` / `shasum` を呼ばず `pathlib` を使い、ファイル入出力は `encoding="utf-8"` を明示する。
**Windows の既定は cp932 であり、明示しないと日本語を含むファイルで落ちる。**
パスの正規化に `shlex.split(posix=True)` を使わないのも同じ理由で、バックスラッシュをエスケープとして食う。

### 検証スクリプトは「在ること」しか見ない

列名・キー・件数・ファイル一覧・版の大小・開発リポジトリとの差分は、いずれも検証しない。
見るのは形式と、実装の詳細が変わっても残る不変条件
（契約の正本が在ること・標準ライブラリだけで動くこと・hook が静かに `exit 0` で終わること・py39 構文であること）だけである。

**「何であるか」を見る検査を足すと、仕様が変わるたびに保守が要る。** 将来ここに列名やキーの検査を足さない。

### hook の起動検査で無効化スイッチを立てない

スイッチが立つと `collect.py` は冒頭で return するため、**実際の収集経路を一度も通らないまま「exit 0 だった」と判定する。**
終了コードが 0 でなくなる欠陥は、いずれもその経路の内側にある。

### `plugin/config.json` の送信先は空のままにする

基盤の URL と受信トークンは、開発機からは分からない。
**誤った URL を配布物に焼き込むより、リリース前の確認で止まる方が安全である。**
空のまま配ると端末が 1 件も送信しないまま「導入済み」に見えるため、
`docs/release.md` が初回リリース前に埋めることを必須手順として持つ。

## 5. 開発環境と検証の作法

### 実機確認は `HOME` ではなく `CLAUDE_CONFIG_DIR` で隔離する

macOS では `HOME` を差し替えると、Security フレームワークが login Keychain を
`$HOME/Library/Keychains/login.keychain-db` で解決しようとしてパスが存在せず、
**Keychain が書き込み不可になって認証トークンが定着しない。**
認証フロー自体は成功するため、成功表示の直後に未ログインへ戻る。

Keychain のエントリは設定ディレクトリごとに分かれるため、
隔離環境でのログインが利用者本来の認証情報を上書きすることはない。

この方式では利用者の他のプラグインも通常どおり発火する。したがって、
**本人の環境が汚れていないことの判定は、ディレクトリ全体の指紋の一致ではなく、
「このプラグインの痕跡（状態ディレクトリ・キュー・識別子のキャッシュ）が 1 件も無いこと」で行う。**

### 設定を書く hook は、実 config ディレクトリでは決して実行しない

`session_start.py` は `settings.json` を書く。
収集側（`collect.py`）の書き込み先はすべて状態ディレクトリの配下に閉じている。

### `pytest.ini` で収集範囲を `tests/` に固定する

指定が無いとリポジトリのルートから全部収集し、git 管理外の作業領域に落ちた
第三者プラグインのテストまで拾って赤くなる。
パスを明示した呼び出しでは `testpaths` が効かないため、`norecursedirs` を併せて持つ。

### `ruff.toml` が `FA100` を無効にし、`docs/` を除外する

既定のルールセットは `typing.Optional` に対して「`from __future__ import annotations` を足せ」を出し、
足すと今度は同じ箇所に「`X | None` にしろ」が出る。
**py39 の `typing.Optional` を使うのはこのリポジトリ全体の方針**であり、
設定に 1 回書くべきもので、コードに `# noqa` として散らすものではない。

`ruff format` は Markdown 中の Python コードフェンスも整形対象にする。
仕様書のコードフェンスは桁を揃えた説明用の断片であり、整形の対象ではない。

### `requirements-dev.txt` はリポジトリのルートに置く

テストは `tests/` に集約され、端末側（`plugin/`）も対象にする。開発依存はこのリポジトリの
テスト専用であり、本番のデプロイは別リポジトリ `cc-governance-monitor`（`server/`）の
`requirements.txt` だけを使う。

## 6. 受け入れている限界

直せば変わるが、今は直していないものである。

### ポリシーから消したキーの撤回を定義していない

誤った値は、正しい値を配り直して上書きする。

サーバから端末へ指示する経路を持たないため、**キーそのものを消す操作が無い。**
一度配った設定項目は、値を変えられても消せない。

撤回を持たせるには、端末が受け取って実行する指示の形式と、その到達の確認が要る。
配布を「値を配るだけ」に保つ判断と引き換えになる。

### 切り詰めと置換が起きたこと自体は記録されない

契約は宣言長で切り詰め、符号化できない文字を置換する。行は失われないが、
**長い値が来ている列は、集計上は短い値に化けて見える。** 元の値を復元する手段は無い。

記録するには、契約が端末側で診断情報を作り、それを送る経路が要る。
収集を契約が名指ししたものだけに限る方針と引き換えになる。

### 案内日を記録しても、自己選択バイアスは残る

段階的な案内は効果測定の識別の前提を作るが、**導入するかは利用者が決める。**
早く導入する利用者がもともとヘビーユーザーである可能性は消せない。

消すには割り当てを管理者が決める必要があり、導入を利用者の判断に委ねる前提を崩す。

## 7. 採らないと決めたこと

- **配布物の署名・改ざん検知を持たない。**

収集の範囲についても、次を採らないと決めている。
実在は確認できており、何が取れるかは `knowledge/` にある。

- **最高頻度帯の hook を増やさない。** `PreToolUse` が増やす情報は `PostToolUse` との差分だけであり、
  ツール呼出ごとのプロセス起動が倍になる代償に見合わない。
- **文脈量を取る hook を増やさない。** `SessionEnd` の値は `Stop` の最終値と同じで、
  `UserPromptSubmit` の値は前ターンの `Stop` の値と同じである。どちらも重複にしかならない。
- **文脈量の取得元を transcript 末尾読取に一本化する。** 再開時のキーからも取れるが、
  同じ列に取得元が 2 つできる。再開時の値は末尾読取の検算にだけ使う。
- **端末側に金額を持たない。** コストの正本は AI Gateway の CSV（利用者 × 日）である。
  端末に USD を持つと突合の軸が増える。
- **サブエージェントの種別で層別しない。** 親子の分離は `agent_id` の有無で足りる。
- **`tool_input` から名指しで読むキーを増やさない。** 現在は `skill` の 1 つだけである。

### 採らないが、条件が変われば再検討すること

いずれも今は採らない。**再検討の条件**を満たしたときだけ開く。

| 選択肢 | 何が変わるか | 再検討の条件 |
| --- | --- | --- |
| `env.FORCE_AUTOUPDATE_PLUGINS` | 本体の自動更新を抑止している端末でも、プラグインの更新だけを生かす保険になる | 本体の自動更新を抑止している端末が社内に実在すると分かり、かつその端末でプラグインの版が古いまま止まったとき |
| マネージド設定による配布 | 管理者が配る層（`managed-settings.json`）でマーケットプレイスと施策を配る | 端末の `~/.claude/settings.json` への書き込みが上位の設定に負けて効かない端末が出たとき、または導入そのものを利用者任せにできなくなったとき |
| `model` によるモデル別の層別 | `SessionStart` の `model` を文字列のまま保存して `GROUP BY` する。率を出さないので名寄せ表は要らない | **文脈量は絶対値で見るため、窓サイズの区別が要らない。**`PreCompact` 時点の文脈量の分布が多峰性を示し、窓サイズの違いのせいで解釈が止まったとき。**AI Gateway CSV の `Model` とは突き合わせない**（名寄せ表という人手の保守が発生する） |
| `PostCompact` の登録 | 圧縮**後**のコンテキスト量が取れれば、「圧縮がどれだけ効いたか」を直接測れる | 圧縮の回数と `PreCompact` 時点の分布シフトだけでは効果を説明できなくなったとき。先にキー構成の調査が要る |
| `seconds_since_last_response` / `prompt_cache_likely_expired` の収集 | 「前回応答から N 分でキャッシュが切れる」を実データで示せる、唯一の組み合わせ。どちらも公式ドキュメント未記載で消失リスクがある | 「**N 分以内に再開せよ**」型の施策を立案する段になったとき。測るだけでなく閾値を決めたくなったら、これ以外に材料が無い |
| `estimated_cache_write_usd` の収集 | 上流が算出済みの USD 見積で、AI Gateway CSV の日次 Cache Write を「どの再開が生んだか」に分解できる | コストの上位者が特定できた後、その内訳を「どの行動が生んだか」まで割りたくなったとき |
| transcript 読取窓（256KB）の拡大 | 末尾から `message.usage` を取れない割合を下げるつまみ | その割合がベースライン（窓由来 約 0.5% ＋ 応答なし由来 約 3%）を大きく超えたとき。**1 行が窓を超える構造は拡大では消えない**ので、上限のある対処ではない |
| `PermissionDenied` の登録 | 権限を拒否した事象そのものが取れる。安全性の観点で現在持っている材料は `permission_mode` の 1 つだけで、それを増やせる唯一の低頻度な候補である | 安全性の観点で `permission_mode` だけでは足りないと分かったとき。**先に対話セッションでの発火条件とキー構成の確認が要る。**`PermissionRequest` は採らない（「求めた」だけでは判断材料にならず、頻度帯も中〜高になりうる） |
