# cc-governance-bmsd 設計書

## 1. 目的と範囲

### 1.1 目的

社内で利用する Claude Code に対して、次の 2 つを同時に成立させる。

1. **ガバナンスの適用** — 決めた設定値を全端末に確実に行き渡らせ、お知らせを届け、配布物（スキル・コマンド）を配る
2. **効果の測定** — 適用した施策が、実際にコストと利用行動を変えたかを数字で示す

この 2 つを 1 つのシステムとして設計する。適用と測定を別々の仕組みにすると、「いつ誰に適用されたか」と「そのときコストがどう動いたか」を突き合わせる作業が、システムをまたいだ手作業になるためである。

### 1.2 対象規模と制約

| 項目 | 値 |
| --- | --- |
| 利用者数 | 約 140 名 |
| サーバの Python | 3.9 固定 |
| 端末の Python | hook の実行に必要 |
| サーバの待受ポート | 5000 固定 |
| サーバの公開形態 | サブパス配下（`https://<host>/<base-path>/...`） |
| 永続領域 | `/mnt/data`（コンテナ再起動をまたいで残る） |
| 資源 | 拡張可能。初期は 1cpu × 4GiB |
| 想定データ量 | イベント 日次 3〜5 万行 / 年間 約 1,500 万行 |

### 1.3 範囲に含めないこと

- 会話本文・プロンプト本文の保持・送信・記録。hook の入力からは**キー名を名指しで指定したものだけ**を読む
- 端末利用者の個別監視。目的は施策の評価であり、個人の行動追跡ではない
- リアルタイム性。端末からサーバへの反映は分単位、コストは日次

### 1.4 設計原則

- SRP・DRY・YAGNI・KISS を守る。**「将来必要になるかもしれない」という理由で何かを足さない**
- コードファイルは **200 行以内**を目安とする
- 端末とサーバで共有する契約は**正本 1 ファイル**に置き、DDL・INSERT・抽出処理をすべてそこから導出する
- 集計は SQL の `GROUP BY` に寄せる。アプリケーション側で全行を走査しない
- 端末側の処理は、**ネットワーク I/O を一切ブロック経路に含めない**。同期に行うのはローカルのファイル操作だけである（インタプリタの起動時間そのものはブロックする。実測値は未取得）

## 2. 全体構成

### 2.1 構成要素と責務

| # | 要素 | 実体 | 責務 |
| --- | --- | --- | --- |
| 1 | 端末プラグイン | Claude Code プラグイン（git で配布） | 設定の自動適用 / お知らせ表示 / hook によるイベント収集・送信 / スキル・コマンドの配布 |
| 2 | 収集サーバ | waitress で動く 1 プロセス | 受信・保存・集計・管理画面・CSV 取込 |
| 3 | AI Gateway 日次 CSV | ファイル | コストとトークンの正本。端末側では一切集計しない |

### 2.2 データの流れ

```
[管理者] ─ git push（設定値・お知らせ・配布物）
   ▼
[マーケットプレースの git リポジトリ] ─ プラグインの自動更新 ─▶
   ▼
[端末の Claude Code]
   ├ SessionStart hook : settings.json へポリシー値を強制適用 /
   │                     適用前後の「値そのもの」を policy イベント化 / 未読のお知らせを表示
   └ 各種 hook         : 契約に定義されたキーだけを抽出 → ローカル JSONL に追記
   │
   │ HTTP POST /ingest（NDJSON バルク・detach プロセス）
   ▼
[収集サーバ] ◀─ [取込]ボタン ─ /mnt/data/csv/*.csv ◀─ 手動配置 ─ [AI Gateway 日次 CSV]
   │ 管理画面（4 枚）
   ▼
[管理者]
```

### 2.3 通信の非対称性

**「配信」は git、「収集」は HTTP。** サーバから端末へ何かを指示する経路は作らない。

この非対称性は意図的なものである。設定値もお知らせも配布物も、すべて git リポジトリの内容として端末に届く。したがって**サーバが停止してもガバナンスは止まらない**。停止したときに止まるのは測定だけであり、測定の欠損は後から回復できる（端末側に送信待ちが残る）が、ガバナンスの停止は回復できない。

### 2.4 サーバを 1 つにする理由

ガバナンスと利用ログでサーバを分けない。

- 配信を git が担うため、ガバナンス側にサーバ機能がほとんど残らない。残るのは「適用状況の受信と表示」だけで、これは利用ログと受信経路も画面も同じである
- 効果測定は `policy_state × cost_daily` の突き合わせである。分離するとプロセスをまたいだ結合が必要になり、永続領域のファイル共有や 2 系統の接続管理という、要件にない複雑さが生まれる
- 規模が小さい。日次 3〜5 万行は 1cpu × 4GiB の 1 コンテナに十分収まる

将来、受信処理が画面の応答を圧迫した場合は、**同じコード・同じ DB を指す 2 個目のプロセスを起こし、Ingress で `/ingest` だけそちらに振る**ことでコード変更ゼロで分離できる。この逃げ道があるため、今は分けない。

## 3. 端末プラグイン

### 3.1 ディレクトリ構成とファイルの責務

開発リポジトリ内のフォルダ名は `governance`。`plugin.json` の `name` も `governance`。

```
governance/
  .claude-plugin/plugin.json    # プラグイン定義（name / version / description）
  hooks/hooks.json              # hook 登録（どのイベントで何を呼ぶか）
  hooks/contract.py             # ★ 契約の正本。端末もサーバもこれ 1 つを読む
  hooks/collect.py              # 全 hook 共通のイベント収集エントリ
  hooks/session_start.py        # 設定適用 + お知らせ表示 + collect
  hooks/_context.py             # transcript 末尾から context_tokens を取る
  hooks/_queue.py               # ローカルキューへの追記・ローテート
  hooks/_sender.py              # detach して POST する独立プロセス
  hooks/_identity.py            # user_email / host / event_id の解決とキャッシュ
  hooks/_settings.py            # settings.json の読み書き（原子的置換）
  notices.json                  # お知らせ文面（ロジックを持たない純データ）
  config.json                   # 送信先 URL・受信トークン・送信条件
  skills/                       # 配布スキル
  commands/                     # 配布コマンド
```

`_` 始まりのファイルはプラグイン内部のモジュールであり、hook の入口にはならない。入口は `collect.py` と `session_start.py` の 2 つだけ。

**契約の正本を `governance/hooks/contract.py` に置く。** プラグインの中に置くことで、配布物にそのまま含まれ、端末側で追加の解決処理が要らない。サーバは開発リポジトリ内の相対パスからこのファイルを読む（§6）。

端末の状態は **`${CLAUDE_PLUGIN_DATA}` 配下**に置く。これはプラグインの永続データ置き場として公式に定められた場所（`~/.claude/plugins/data/<識別子>/`）であり、hook に環境変数として渡る。**プラグインをアンインストールすると自動で削除される**ため、規約外の場所に置いた場合のような残骸が出ない。

この変数が渡らない経路で動いたときのために、`~/.claude/cc-governance/` を代替の置き場所とする。判定は 1 行で済む。

```
${CLAUDE_PLUGIN_DATA}/          # 無ければ ~/.claude/cc-governance/
  identity.json     # user_email / host / インストール識別子のキャッシュ
  seen.json         # 既読のお知らせ ID 集合
  queue.jsonl       # 送信待ちイベント（追記のみ）
  spool/            # 送信中・送信失敗のファイル
  sent_at           # 最終送信時刻（空ファイルの mtime で表現する）
```

### 3.2 収集する項目と取得元

`collect.py` は **hook の種類で分岐しない**。標準入力の JSON に対して、契約に定義されたキーパスを `dict.get` で順に引くだけである。来ないキーは `None` になる。

```python
# contract.py（抜粋・正本）
HOOK_FIELDS = (
    # (列名, キーパス, 型) の 3 つ組。行末の註記は届く hook であって要素ではない
    ("session_id",      ("session_id",),          "VARCHAR(255)"),  # 全 hook
    ("prompt_id",       ("prompt_id",),           "VARCHAR(255)"),  # 広範
    ("tool_name",       ("tool_name",),           "VARCHAR(255)"),  # PostToolUse / PostToolUseFailure
    ("source",          ("source",),              "VARCHAR(255)"),  # SessionStart
    ("compact_trigger", ("trigger",),             "VARCHAR(255)"),  # PreCompact
    ("command_name",    ("command_name",),        "VARCHAR(255)"),  # UserPromptExpansion
    ("command_source",  ("command_source",),      "VARCHAR(255)"),  # UserPromptExpansion
    ("skill_name",      ("tool_input", "skill"),  "VARCHAR(255)"),  # PostToolUse
    ("effort_level",    ("effort", "level"),      "VARCHAR(255)"),  # PostToolUse / Stop / PostToolUseFailure
    ("permission_mode", ("permission_mode",),     "VARCHAR(255)"),  # 複数 hook
    ("agent_id",        ("agent_id",),            "VARCHAR(255)"),  # サブエージェントのツール呼出
    ("is_interrupt",    ("is_interrupt",),        "INTEGER"),       # PostToolUseFailure
)
```

`compact_trigger` の列名が `trigger` でないのは、`trigger` が MySQL の予約語であるためである。

**キーパスの解決は契約が持つ 1 つの関数で行う。** 途中のキーが無い場合でも例外にせず `None` を返す。

```python
def dig(obj, path):
    cur = obj
    for k in path:
        cur = cur.get(k) if isinstance(cur, dict) else None
    return cur
```

**値の型変換も契約の 1 関数に閉じる。** 型の宣言が契約にある以上、送る値の型を列の型に合わせるのは契約の責務であり、受信側での再解釈は行わない。

| 列の型 | 変換 |
| --- | --- |
| `VARCHAR` | `str()`。ただし**真偽値は小文字の `true` / `false`** にする |
| `INTEGER` / `BIGINT` | 真偽値・整数・整数文字列を `int` に寄せる |
| `DOUBLE` | 数値と数値文字列を `float` に寄せる |

いずれも解釈できない値は `None` にする。`None` は `None` のまま通す。

真偽値を小文字で文字列化するのは、`policy_state` の `value` / `prev_value` が `settings.json` の値の文字列表現だからである（§5.2）。`settings.json` は JSON であり、そこでの真偽値の表記は `true` / `false` である。Python の `str(True)` が返す `True` を記録すると、記録された値が JSON の表記と一致しなくなり、準拠判定が言語の内部表現に依存する。

これに加えて、端末側で組み立てる列がある。

| 列 | 取得元 |
| --- | --- |
| `event_id` | 端末で `uuid.uuid4()` を 1 イベントにつき 1 つ生成 |
| `ts` | `int(time.time())` |
| `day` | 契約の `to_day(ts)`。`ts` を JST に寄せた epoch 日（`(ts + 9*3600) // 86400`） |
| `user_email` | `_identity.py`（§3.8） |
| `host` | `platform.node()` |
| `hook_event` | hook 登録時にコマンド引数で渡す hook 名 |
| `context_tokens` | transcript 末尾から算出（§3.4） |

**`tool_input` は `skill` キーのみを名指しで読む。** dict 全体を保持・送信するコードは存在しない。プロンプト本文が入り得る `prompt` / `tool_response` / `message` には一切触れない。値は**分類も語彙の検査もせず**、列の型に合わせた変換だけを行って生のまま送る（`None` は `None` のまま）。

これにより、**同じ 1 ファイルがどの hook からでも動く**。hook を増やしても収集コードは変わらず、Claude Code 側が hook を増やしても影響を受けない。

### 3.3 登録する hook

登録は 7 種にとどめる。網羅登録はしない。**登録する hook は「その hook でしか取れないキーがある」ことを理由に選ぶ。**

| hook | 目的（その hook でしか取れないもの） |
| --- | --- |
| `SessionStart` | 設定の適用・お知らせ表示・`source` の記録・送信のトリガ |
| `UserPromptSubmit` | `prompt_id` / `permission_mode`（本文は読まない） |
| `UserPromptExpansion` | `command_name` / `command_source`（本文は読まない） |
| `PostToolUse` | `tool_name` / `skill_name` / `agent_id` |
| `PostToolUseFailure` | `is_interrupt` / 失敗時の `tool_name` |
| `PreCompact` | `compact_trigger` + 圧縮直前の `context_tokens` |
| `Stop` | ターン終了時の `context_tokens` / 送信のトリガ |

`command_name` / `command_source` は配布物の効果測定（§7.3）の中核であり、`is_interrupt` は作業の中断を見る唯一の材料である。どちらも 1 種類の hook にしか届かないため、その hook を登録しないと列が恒久的に NULL になる。**「届かなければ NULL になるだけ」で済むのは、その列を主題にした画面が無い場合に限られる。**

hook は**例外を握り潰し、常に `exit 0` する**。標準出力にも標準エラーにも何も出さない。Claude Code の動作を妨げないことを、収集の正確さより優先する。

**hook の実行は、登録したコマンド文字列とともに利用者の画面に表示されうる。** hook 自身が何も出力しなくても、この表示は止められない。したがってコマンド文字列そのものが利用者から見える設計物である。次を守る。

- `hooks.json` に登録するのは **`python3 "${CLAUDE_PLUGIN_ROOT}/hooks/collect.py" <hook名>` の形の 1 行**とする
- パイプ・`;`・`&&`・リダイレクトを含めない。**条件分岐や後処理はすべて Python 側に置く**
- 無効化スイッチ（§3.9）の判定も Python 側で行う。コマンド文字列を条件付きにしない
- **1 行 100 文字未満に収める。** 設計の想定形は 60 文字程度に収まる

長いワンライナーを直接登録すると、ツールを実行するたびにその全文が画面に流れる。「得体の知れないものが動いている」という印象は、施策の推進そのものの妨げになる。

### 3.4 コンテキスト使用量の取得

hook 入力の `transcript_path` を使い、**末尾 256KB だけを読む**。行を逆順に走査して最初に見つかった `message.usage` の 3 値を足す。全文パースはしない。

```python
def context_tokens(path, tail=256 * 1024):
    try:
        with open(path, "rb") as f:
            f.seek(0, 2)
            f.seek(max(0, f.tell() - tail))
            chunk = f.read()
    except OSError:
        return None
    for line in reversed(chunk.split(b"\n")):
        try:
            u = json.loads(line).get("message", {}).get("usage")
        except Exception:
            continue
        if u:
            return (u.get("input_tokens", 0)
                    + u.get("cache_creation_input_tokens", 0)
                    + u.get("cache_read_input_tokens", 0))
    return None
```

呼ぶのは `PreCompact` と `Stop` の 2 か所のみ。**率には変換せず、絶対値のまま送る。** 率にするとモデルごとの窓サイズ表という保守対象が生まれ、モデルが増減するたびに人手が要る。

### 3.5 蓄積と送信

**蓄積** — 状態ディレクトリの `queue.jsonl` に 1 行 1 イベントを追記する（`open(..., "a")` + 1 回の `write`）。ロックもインデックスも持たない。

**追記が壊れない根拠は、`O_APPEND` を付けた 1 回の `write` では、書き込み位置の決定と書き込みが分割されないことである。** 複数のセッションが同時に追記しても行は混ざらない。

**送信の起動条件** — `SessionStart` と `Stop` の末尾で、次のいずれかを満たすときだけ送信プロセスを起動する。

- 前回送信から 10 分以上経過している（`sent_at` の mtime で判定する）

**起動方法** — `subprocess.Popen` による detach（`stdin/stdout/stderr` を `DEVNULL`、`start_new_session=True`）。hook 自身は待たずに即座に `exit 0` する。

**送信プロセスの動作**

1. `queue.jsonl` を `spool/<epoch>-<uuid4hex>.jsonl` に `os.rename` する（アトミック。以降の hook は新しい `queue.jsonl` に追記する）

   ファイル名に UUID を含めるのは、**複数のセッションを同時に開くのが常態**であり、2 つの送信プロセスが同一秒に退避しうるためである。`os.rename` は既存ファイルを黙って置き換えるため、秒だけの名前では先に退避されたイベントが無言で消える。ロックを導入せずに衝突を消せる最小の手段が、名前の一意化である。

2. `spool/` 内のファイルを古い順に `POST /ingest` する（`Content-Type: application/x-ndjson`、タイムアウト 60 秒、トークンをヘッダに付与）

   **タイムアウトを短く取らない。** この POST は detach された独立プロセスの中で行われ、Claude Code の応答を一切ブロックしない。一方、実行基盤はコンテナ起動のたびに `pip install` を行うため、その日の最初の POST はコールドスタートに当たりうる。短いタイムアウトは、守るものが無いところで spool を溜め、後述の上限による破棄を早めるだけである。

3. 2xx なら削除。それ以外は**残す**（次回まとめて再送される）

**送信失敗時** — リトライループも指数バックオフも ACK も持たない。失敗したファイルは `spool/` に残り、次の送信機会に自然に再試行される。サーバが半日停止しても自動で回復する。ただし `spool/` の合計が **5MB または 7 日**を超えたら、古いものから黙って削除する。永久に溜まる状態を作らない。

**重複と取りこぼし** — 再送で同じイベントが二重に登録されうるが、`event_id` があるため集計側の `COUNT(DISTINCT event_id)` で件数は正確になる。逆に、オフライン・spool 上限超過・hook 失敗による取りこぼしは**仕様として受け入れる**（§11）。

### 3.6 設定の自動適用

`session_start.py` は、**設定の適用 → お知らせの表示 → イベントの収集**の順に実行する。収集が失敗しても、ガバナンスの本体である前 2 つは既に終わっている。

設定の適用は `~/.claude/settings.json` に対して次の手順で行う。

1. ファイルを読み、同時に **mtime を控える**
2. ポリシー値と現在値を比較する。**差分がなければ書かない**
3. 書き込み直前に mtime を読み直し、**1 で控えた値と異なっていたら今回は書かずに諦める**
4. 書き込みは一時ファイル + `os.replace` で原子的に行う
5. パース失敗時は**何もしない**（利用者の設定を壊さない方を優先する）
6. 結果を policy イベントとしてキューに積む

手順 3 を置くのは、`os.replace` が保証するのはファイル置換の原子性だけで、**read-modify-write の lost update を防がない**ためである。Claude Code 自身も `/config` などの操作で同じファイルを書き、**起動時に古い形式の設定を新しい形式へ移す書き換えも行う**。読んでから書くまでの間に他者の書き込みが入ると、利用者の変更が黙って巻き戻る。諦めても次の SessionStart で再試行されるため、失うものは無い。

#### policy イベントが持つもの

policy イベントには、**書き込み前の値と書き込みの結果**を含める。

| 項目 | 内容 |
| --- | --- |
| `key_name` | ポリシー項目のキー（`settings.json` 内のパス） |
| `value` | 適用後の値 |
| `prev_value` | **書き込み前に `settings.json` にあった値**（キーが無ければ NULL） |
| `apply_result` | `already_ok` / `applied` / `skipped_conflict` / `skipped_missing` / `parse_failed` / `write_failed` のいずれか |
| `plugin_version` | 端末で動いているプラグインの版。`${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` の `version` を読む |

**準拠しているかを判定する材料は `prev_value` である。** 適用後の値だけを記録すると、それは自分が直前に書いた値そのものなので、必ずポリシー値と一致する。「全員が常に準拠している」という無内容な記録にしかならず、未準拠者も、キー名が上流で変わって適用が空振りしている状態も、画面に現れない。`prev_value` を持てば、**セッションを開いた時点で既にポリシー値だった端末**を数えられる（§7.2）。

`plugin_version` を持つのは、配布経路が生きているかを見る唯一の材料だからである。設定値もお知らせも配布物も git 経由で届く以上、**古い版のまま更新が止まった端末は、こちらから見えなければ永久に古い施策のまま居座る**。列 1 つで版の分布が出る（§9.2）。

#### ポリシーの定義

ポリシーの定義は契約の `POLICY` 1 か所に置く。

```python
POLICY = {
    # キーは settings.json 内のパス。`.` で入れ子をたどる
    "env.CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "60",  # 自動圧縮の窓の 60% で圧縮する
    "extraKnownMarketplaces.cc-marketplace-governance-bmsd.autoUpdate": True,  # 配布経路の自動更新
    "env.FORCE_AUTOUPDATE_PLUGINS": "1",          # 本体の自動更新を止めた端末でも配布は生かす
}
```

キーを `.` 区切りのパスにするのは、`env` セクションのように入れ子の中へ書き込む項目があるためである。`policy_state` に記録する `key_name` はこのキーそのもの（`env.CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`）、`value` はその値の文字列表現（`"60"`）である。

**この表記の制約として、パスの途中に現れる名前に `.` を含められない。** マーケットプレイス名を含むキーがあるため、`marketplace.json` の `name` に `.` を使わない（キーになるのはこの `name` であって、リポジトリ名ではない）。エスケープの仕組みは持たない。

**入れ子の途中のキーが存在しないとき、`env` セクションは作ってよいが、それ以外は作らない。** `extraKnownMarketplaces.<名前>` はマーケットプレイスの登録によって作られるエントリであり、こちらが作ると **`source` を持たない壊れた定義**が利用者の設定に生まれる。エントリが無い端末では書かずに `skipped_missing` を記録する。プラグインが動いている以上そのマーケットプレイスは登録されているはずなので、この結果が出ること自体が異常の印になる。

**自動圧縮は割合で指定する。** 自動圧縮の窓の何 % に達したら圧縮するかを与えるため、モデルの窓の大きさによらず同じ割合で発火する。モデルごとに値を変える必要がなく、モデル定義という保守対象も生まれない。

**発火する絶対トークン数はモデルによって異なる。** 割合の基準は自動圧縮の窓であり、その大きさはモデルの窓に依存する。したがって `PreCompact` 時の `context_tokens` は、モデルの構成が混ざれば複数の山を持つ。

**この施策は、コンテキストの上限に達する前に圧縮するセッションにのみ効く。** 上限に当たってから対処する動作のセッションでは働かない。

> **この環境変数は公開された仕様である。** 値は 1〜100 の割合で、低い値ほど早く圧縮が走る。**既定より高い値は無視される**ため、この施策で指定できるのは既定より厳しい側だけである。名称が変わった場合に備え、施策の定義は契約 1 か所（`POLICY`）に閉じる。書き換えるのはこの 1 行であり、適用処理・`policy_state` の記録・準拠判定のすべてがそこから導かれる。

**自動更新の設定を施策に含めるのは、配布経路そのものを維持するためである。** 社外のマーケットプレイスは自動更新が既定で無効であり（§8.5）、有効にしなければ施策の変更は端末に届かない。この設定はマーケットプレイスの登録をやり直すと外れうるため、**毎回のセッション開始で確認して戻す**。強制適用がそのまま維持の機構になる。

`FORCE_AUTOUPDATE_PLUGINS` を併せて配るのは、**Claude Code 本体の自動更新を止めている端末でも、プラグインの更新だけは生かすため**である。組織の方針で本体の更新を抑止している場合、それに巻き込まれて配布経路が死ぬ。1 行で塞げる。

**`~/.claude/settings.json` が権威である。** Claude Code はセッション開始時に、`settings.json` の `extraKnownMarketplaces` を内部の一覧（`~/.claude/plugins/known_marketplaces.json`）へ上書き同期する。両者に異なる値を仕込んで起動すると、内部の一覧が `settings.json` の値に揃う。したがって**プラグインが `settings.json` に書けば、この設定は維持できる**。

有効にした結果として実際に更新が降りてくるかは**未検証である**（§11.3）。

環境変数による通信抑止など、設定ファイルより優先度の高い経路で更新が止まっている場合、プラグイン自身の書き込みでは回復できない。**「自動更新が自分で自分を回復する」とは主張しない。** 代わりに `plugin_version` の分布で、届いていない端末を観測する（§9.2）。

**適用モードは「強制」のみである。** 利用者が施策を選択的に適用するモードは設けない。選択的適用を許すと、準拠者と非準拠者の差が「施策の効果」なのか「もともと意識の高い人が選んだから」なのかを区別できなくなり、効果測定の土台が崩れる。強制であれば、準拠開始日の差を生むのは導入と起動のタイミングだけになり、そのタイミングを意図的にずらすことで比較の軸を作れる（§7.1・§8.4）。

施策を変えるときは `POLICY` を直して git push する。JSON カタログ化はしない。配信の実体が git push である以上、JSON を直すコストと Python を直すコストは同じであり、カタログを挟むだけ読む場所が増える。

> 書き込むのは `~/.claude/settings.json` であり、これは設定の優先順位が最も低い層である。より上位の設定（プロジェクト設定・管理設定・起動時の指定）が同じキーを持つ場合、書き込みは成功するが効かない。**上位の設定を読みに行く機構は持たない。**「書けたこと」と「効いていること」が一致するとは主張せず、この差は §11.2 に割り切りとして記載する。

### 3.7 お知らせの配信

`notices.json` はロジックを持たない純データである。

```json
[
  {"id": "2026-09-01-a", "title": "...", "body": "..."}
]
```

`session_start.py` が、ローカルの既読 ID 集合（状態ディレクトリの `seen.json`）に無い項目を、hook の JSON 出力の **`systemMessage`** として返す。**サーバもポーリング API も不要。** お知らせを追加する操作は、`notices.json` に 1 要素足して git push することである。

**お知らせはモデルのコンテキストには入れない。** hook の標準出力はモデルが読む文脈として扱われるため、素の出力ではお知らせの宛先が人ではなくモデルになる。害は 2 つある。利用者が 1 通も読めないこと、そして業務指示を含む文面が全セッションにモデルへの指示として注入され、**コストを下げる施策の効果測定に、モデルの応答傾向の変化が交絡する**ことである。利用者に見せる経路と、モデルに渡す経路を混ぜない。

**未読が複数あるときは、空行 1 つで区切って 1 つの `systemMessage` にまとめる。** 接頭辞が付くのは全体の 1 行目だけであり、件ごとには付かない。

既読に加えるのは**出力が成功した後**である。出力前に既読を立てると、表示されないままお知らせが消費される。

**`systemMessage` は対話モードで、セッション開始直後に利用者の画面へ表示される。** 非対話実行では利用者向けの出力に現れない。非対話は人が画面を見ていない実行であり、お知らせを届ける相手がいないため、これは欠落ではない。

**表示には `SessionStart:<source> says: ` の接頭辞が付く。** `source` は `startup` / `resume` / `clear` / `compact` のいずれかであり、利用者はこの接頭辞込みで文面を読む。文面の先頭に「【お知らせ】」のような目印を重ねない。複数行の場合、接頭辞が付くのは 1 行目だけである。

長い文面は Claude Code がファイルへ退避し、先頭のプレビューとパスだけが表示される。**目安として、お知らせ 1 件は日本語で 600 字程度までに収めると安全である**（退避が始まるのは日本語で約 680 字、ASCII で約 2,000 字）。検査は設けない。お知らせがこの長さに達する運用を想定しない。

### 3.8 識別子

| 識別子 | 解決方法 |
| --- | --- |
| `user_email` | 環境変数 `CC_GOVERNANCE_USER_EMAIL` → `git config --global user.email` → NULL の順に**初回のみ**解決して `identity.json` にキャッシュする。小文字化のみ行う |
| `host` | `platform.node()` |
| `event_id` | イベントごとに `uuid.uuid4()` を生成する。**主キーにも UNIQUE 制約にもしない**（§5.5） |

`user_email` を毎回 subprocess で取りに行かないのは、hook の実行時間に外部コマンド起動を含めないためである。

**`user_email` は効果測定の唯一の突合キーである。** `cost_daily` 側は AI Gateway が記録するアドレスであり、端末の git 設定とは別系統で決まる。個人のアドレスを git に設定している利用者、未設定の端末、ドメインが複数ある組織では、悪意なしに不一致が起きる。不一致の利用者は `events` にも `cost_daily` にも行があるのに**結合できず、効果測定から静かに脱落する**。

そのため 2 つを置く。第 1 に、環境変数による上書き経路を先頭に置く（組織側で正しいアドレスを配れる逃げ道）。第 2 に、**突合率を健全性行に出す**（§9.2）。突合率が下がっても `user_email` 列は非 NULL のままなので、NULL 率では気づけない。

### 3.9 無効化スイッチ

環境変数 `CC_GOVERNANCE_DISABLE` が空でない値に設定されているとき、プラグインは**利用ログの収集とお知らせの表示を止める**。

- `collect.py` は冒頭 2 行で判定し、即 `exit 0` する
- `session_start.py` は**設定の適用だけを行い**、お知らせの表示と収集を飛ばす

CI・スクリプトからの非対話実行・バッチ処理で Claude Code を動かす場面を想定している。これらは「人の利用」ではないため、測定に混ぜると数字が歪み、お知らせの出力は機械可読な出力を汚す。

**設定の適用と、その記録はこのスイッチでは止まらない。** 止められるようにすると、それは「利用者が施策を選択的に適用できる」ことと同義になり、§3.6 が強制のみを選んだ理由（準拠者と非準拠者の差が施策の効果なのか自己選択なのかを区別できなくなる）がそのまま崩れる。

**適用が止まらない以上、適用結果の policy イベントも積み、送信もする。** 止めると、無効化した端末が準拠率の分母から静かに消え、施策の効果が実態より良く見える。**送信まで止めると同じことが起きる**（積んだ記録が端末に溜まるだけで、サーバには一度も届かない）。スイッチが止めるのは**利用ログの収集とお知らせの表示**であって、ガバナンスとその記録の伝達ではない。

## 4. サーバ

フォルダ名は `cc-governance-bmsd-server`。

### 4.1 ディレクトリ構成とファイルの責務

```
cc-governance-bmsd-server/
  app.py              # ★ ルーティング層。Web フレームワークを import する唯一のファイル
  ingest.py           # NDJSON パース・契約由来の検査・INSERT
  db.py               # 接続生成・プレースホルダ変換・初期化（抽象はこの 3 つだけ）
  queries_events.py   # ★ SQL。/ と /assets の集計・健全性
  queries_policy.py   # ★ SQL。/policy と /effect の集計
  csv_import.py       # CSV の走査・取込・冪等化
  shared.py           # 契約の正本を import するためのシム（4 行）
  templates/
    base.html
    overview.html     # /
    policy.html       # /policy
    effect.html       # /effect
    assets.html       # /assets
  requirements.txt
  start.sh            # 起動スクリプト（Secret 読み込み・install・待受の開始）
  Dockerfile
```

**画面の集計 SQL を `queries_*.py` に集約する。** これは DRY のためではなく、変更の影響範囲を閉じるためである。DB を別の製品に変える場合も、接続プールやトランザクション管理を足す場合も、画面側の変更はこの 2 ファイルの中だけで完結する。画面の系統で分けるのは 200 行の上限に収めるためであり、探す場所は接頭辞で一意に決まる。

**SQL を書いてよいのは `queries_events.py` / `queries_policy.py` / `ingest.py` / `db.py` / `csv_import.py` の 5 つだけである。** 保存側の 3 つは、書き込む文をそれぞれの責務の中に置く。**`app.py` とテンプレートには SQL を書かない。**

### 4.2 Web フレームワークは 1 ファイルに閉じる

**Web フレームワークに依存するコードは、ルーティング層 1 ファイル（`app.py`）に閉じる。**

- リクエストの解釈（ヘッダ・ボディ・クエリの取り出し）と、レスポンスの組み立ては、この層だけで行う
- **集計・保存・契約・CSV 取込は、Web フレームワークを一切 import しない。** 引数として素の値（dict・list・str・bytes）を受け取り、素の値を返す
- テンプレート描画もこの層で行い、他の層はテンプレート名とデータだけを返す
- **載せ替えるときに書き直すのは、この 1 ファイルだけである**

| ファイル | 受け取るもの | 返すもの |
| --- | --- | --- |
| `app.py` | フレームワークのリクエスト | フレームワークのレスポンス |
| `ingest.py` | 生のバイト列（NDJSON）と接続 | 保存件数・破棄件数の dict |
| `queries_*.py` | 接続と絞り込みの引数（int・str） | タプルのリスト |
| `csv_import.py` | ディレクトリパスと接続 | 取り込んだファイル名と行数の list |
| `db.py` | 環境変数の値 | 接続オブジェクト |
| `shared.py` | — | 契約の定数と関数 |

この規律だけで、載せ替えのコストは `app.py` の分量に等しくなる。**アダプタ層もインタフェース定義も置かない。** レイヤを足すと、載せ替えないうちから毎日の読み書きにコストがかかり、しかも「フレームワークを import する場所が 1 か所である」という検証しやすい事実が、抽象の正しさという検証しにくい問題に置き換わる。

守られているかは `grep` 1 回で確かめられる。**`app.py` 以外のファイルにフレームワーク名の import が現れないこと**が、この節の全部である。

Python 3.10 以上が使える環境へ移る場合、`app.py` を ASGI フレームワークで書き直し、起動コマンドを差し替える。他の 6 ファイルとテンプレートは変更しない。

### 4.3 技術選定と、過剰にしないための制約

| 項目 | 選択 | 理由 |
| --- | --- | --- |
| Web フレームワーク | Flask | サーバの Python が 3.9 に固定されているため、**3.9 で最新版が使えることを第一の基準とする**。Flask と Werkzeug は現行最新版が 3.9 を対象に含む。必要なのはルーティングとテンプレート描画だけであり、それ以上の機能を持たないことが利点になる |
| サーバ | waitress（`0.0.0.0:5000`・スレッド既定） | 純 Python の WSGI サーバ。現行最新版が 3.9 を対象に含む。140 名規模ではプロセスマネージャを足す理由がない |
| テンプレート | Jinja2 | Flask に同梱される。直接依存として数えない |
| サブパス | `SCRIPT_NAME`（WSGI ラッパ 1 個） | `BASE_PATH` を `SCRIPT_NAME` として与えるだけでよい。Flask の `url_for` はこの値に追従する |
| DB | `sqlite3`（標準）/ `PyMySQL` | 接続先が 2 種類「現に存在する」ため、ここだけ抽象を入れる |
| フロント | 素の HTML + インライン CSS | JS ライブラリ・CDN 依存を持たない。棒グラフは `div` の `width: N%` |

#### 依存パッケージ

直接依存は 3 つ。

```
flask==<固定版>
waitress==<固定版>
pymysql==<固定版>
```

Jinja2 と Werkzeug は Flask の推移的依存として入る。推移的依存を含めて 9 パッケージであり、**すべて Python 3.9・manylinux2014 の既製ホイールが存在し、ビルド不要である。3 つとも、現行最新版が Python 3.9 を対象に含む。**

コンパイル済み拡張を含むのは `MarkupSafe` の 1 つだけである。これはアーキテクチャ依存のホイールになるため、**依存を取得する環境と実行する環境で、Python の版・ABI・プラットフォームを揃える**必要がある。

**バージョンは `==` で完全に固定する。推移的依存も含めて固定する。** コンテナ起動のたびに `pip install` が走る実行基盤では、固定しないと「同じコードのまま、再起動しただけで別のバージョンが走る」状態になる。上流の任意のリリースが、こちらの操作を伴わずに本番を止めうるということであり、止まったときに変更履歴から原因を辿れない。加えて、FaaS は起動時に、Dockerfile はビルド時に依存を解決するため、固定していなければ 2 つの経路は原理的に別物になり、§4.6 の「起動コマンドが同じだから移行時の作業は最小」という前提が崩れる。依存の更新は `requirements.txt` の差分を git push する明示的な操作とする。

依存を足すことは設計上の判断事項として扱う。

#### 過剰にしないための制約

1. **バリデーションライブラリを足さない。** 受信 API の検査は契約（`HOOK_FIELDS` 等）から導出する（§4.4）。列とその型はすでに契約が単一の事実として持っており、そこから導ける検査のためにスキーマ定義を別の語彙で書き直すのは、同じ事実を 2 か所に置くことである
2. **画面側に型を置かない。** 画面が扱うのは SQL の集計結果（タプルのリスト）であり、そこに型を被せても検査対象が増えるだけで、検査によって防げる誤りが無い
3. **Flask の拡張を使わない。** `Flask-SQLAlchemy`・`Flask-Login`・`Flask-WTF` などを入れない。使うのは `route` / `request` / `render_template` / `Response` の 4 つだけである
4. **ブループリントもアプリケーションファクトリも使わない。** エンドポイントは 6 つであり、`app.py` 1 ファイルに収まる。分割の器を先に作らない
5. **`before_request` / `after_request` を使わない。** DB 接続はエンドポイント関数の中で取得して閉じる。暗黙の実行経路を作らない。WSGI のラッパは、サブパスを `SCRIPT_NAME` として与える 1 個だけに限る

#### ORM を使わない

**SQLAlchemy を含む ORM を使わない。**

- MySQL と SQLite の両対応は、抽象レイヤを積むのではなく「方言が出る機能を使わない」ことで実現する（§5.5）。この方式なら**同じ SQL 文字列が両方の DB で動く**ため、ORM が提供する方言吸収の価値が無い
- 起動のたびに `pip install` が走る環境で、ORM の追加は起動時間の実費になる
- 扱うテーブルは 3 つ・すべて append-only で、リレーションの辿り方もオブジェクトのライフサイクル管理も必要ない

`db.py` が持つ抽象は次の 3 つだけである。依存性逆転はここで完結し、レイヤは積み増さない。

1. `connect()` — 環境変数 `DB_DSN` が `sqlite:///...` なら `sqlite3`、`mysql://...` なら `PyMySQL`
2. `q(sql)` — プレースホルダ変換。MySQL 接続時のみ `sql.replace("?", "%s")`（1 行）
3. `init()` — 契約から DDL を組み立てて実行し、**実テーブルの列と契約を突き合わせる**

#### 契約と実テーブルの突き合わせ

**この設計はマイグレーション機構を持たない。** 持たないからこそ、契約と実テーブルがずれた状態を無言で通してはいけない。

DDL は `CREATE TABLE IF NOT EXISTS`（§5.5）であり、**テーブルが既に存在する 2 回目以降の起動では何もしない**。一方、INSERT 文の列リストは契約から毎回組み立てられる。契約に列を 1 つ足すと、この 2 つが食い違う。実テーブルにその列は無いため、`executemany` は `no such column` / `Unknown column` で例外になる。INSERT は 1 トランザクションでまとめて実行する（§4.4）ので、落ちるのは 1 行ではなくリクエスト全体である。**契約に 1 行足した瞬間から、全端末のイベントが受け取られなくなる。**

`HOOK_FIELDS` と `POLICY` と `CSV_COLUMNS` は、上流の変化に人手で追随する箇所そのものである（§9.3）。列の増減はこの設計が前提としている運用であり、起きるかどうかではなく、いつ起きるかの問題である。

そこで `init()` は、DDL 実行のあとに次を行う。

1. 実テーブルの列名集合を取得する（SQLite は `PRAGMA table_info(<t>)`、MySQL は `SHOW COLUMNS FROM <t>`）。インデックスの存在確認（§5.5）で同じ形の分岐を既に持つため、分岐の器は増えない
2. 契約が要求する列のうち、実テーブルに無いものを集める
3. **1 つでもあれば、不足している列名を出力して例外を投げ、起動を中止する**

**列を自動で追加しない。** `ALTER TABLE ADD COLUMN` を自動発行すれば起動は通るが、それはマイグレーション機構の 1 段目であり、次に列の改名・型変更・削除が来たときに適用順序と適用済み管理を要求する。この設計はそこへ踏み込まない。

代わりに、**列の増減は明示的な運用手順として扱う**。手順は次のとおりで、管理者が接続先の DB に対して直接実行する。

1. サーバを止める
2. 対象テーブルを退避名にリネームする
3. サーバを起動する（新しい契約で `CREATE TABLE` が走る）
4. 共通する列だけを `INSERT INTO <t> (<共通列>) SELECT <共通列> FROM <退避名>` で移す
5. 退避テーブルを残したまま、画面の数字を確認してから削除する

3 テーブルとも append-only であり、行を個別参照しない。したがってこの手順で失うものは無い。**起動時の突き合わせが果たす役割は、この手順を踏まずにデプロイしたとき、無言でデータを捨てる代わりにサーバが上がらないことである。** 上がらなければ気づく。

### 4.4 API

| メソッド | パス | 用途 |
| --- | --- | --- |
| POST | `/ingest` | NDJSON バルク受信。トークン認証 |
| GET | `/` | 概況 |
| GET | `/policy` | 適用状況 |
| GET | `/effect` | 効果測定 |
| GET | `/assets` | 配布物の利用状況 |
| POST | `/import` | `CSV_DIR` の CSV をすべて取り込み直す（画面上のボタン） |

#### `/ingest` の受信処理

1 リクエスト = 複数行の NDJSON。`app.py` がリクエストボディを生のバイト列として取り出し、`ingest.py` に渡す。`ingest.py` はフレームワークを知らない。

**検査は契約から導出する。バリデーションライブラリを持たない。** 検査の内容は次の 3 つだけである。

1. 行が JSON の dict としてパースできること
2. `kind` が `"event"` / `"policy"` のいずれかであること。これで投入先テーブルが決まる
3. そのテーブルの列集合（`HOOK_FIELDS` + `EXTRA_COLUMNS`、または `POLICY_COLUMNS`）に対して、契約の `coerce(value, type)` を通すこと。知らないキーは捨て、来ないキーは `None` にする

`event_id` と `ts` だけは必須とし、欠けている行は捨てる。前者は重複排除（§5.4）、後者は `day` の再計算の材料であり、どちらも欠けると行が集計に乗らないためである。

```python
def parse_line(line, columns):                   # columns は (列名, 型) の対のリスト
    obj = json.loads(line)                       # 失敗したら捨てる
    if not obj.get("event_id") or obj.get("ts") is None:
        return None
    return [coerce(obj.get(name), type_) for name, type_ in columns]
```

**`columns` は契約の定数そのものではなく、そこから組み立てた `(列名, 型)` の対のリストである。** 契約の 3 つの列定義は、中央の要素が異なる（`HOOK_FIELDS` はキーパス、`CSV_COLUMNS` は CSV のヘッダ名、`EXTRA_COLUMNS` と `POLICY_COLUMNS` は持たない）。**これを 1 つの形に揃えると、意味の無い要素を埋める列が生まれる。** 対を作るのは受信側の 1 行であり、契約の形を歪めない。

**列とその型は契約がすでに単一の事実として持っている。** 同じ内容を別のスキーマ定義として書き直せば、契約に列を足したときに直す場所が 2 か所になり、「契約は正本 1 か所」（§1.4）が成立しなくなる。契約から導出する形にすると、検査は契約に自動で追随する。

- **壊れた行は捨てて続行する。** 1 行の不正でリクエスト全体を失敗させない。**空白のみの行は捨てた数に数えない**（末尾の改行で毎回 1 件が計上されるのを避けるため）
- 応答ボディは `{"stored": <保存した行数>, "dropped": <捨てた行数>}` の JSON とする。端末はこれを読まないが、**受信が静かに減っていることに画面の健全性行（§9.2）より早く気づく手段**になる
- `kind` で投入先テーブルを振り分け、`executemany` で 1 トランザクション INSERT する
- **値の語彙は検査しない。** 許可リストを持たない。上流が新しい値を出しても取りこぼさないことを、値の正しさより優先する
- `day` はサーバ側で `ts` から再計算する。端末の時計ずれが日次集計の軸を壊さないようにするため

#### 応答コードの規則

端末は「2xx なら spool を削除、それ以外なら残す」だけを行う（§3.5）。**端末側にそれ以上の判断をさせない代わりに、サーバは「そのデータを受け取ったか」を応答コードで正しく表明する義務を負う。**

| 状況 | 応答 | 理由 |
| --- | --- | --- |
| 1 行以上のパース失敗 | **200** | 不正な行を捨てて残りを保存した。再送しても同じ行がまた落ちるだけで、再送に意味がない |
| トークン不一致 | **401** | 受け取っていない。200 を返すと端末が唯一の控えを消し、データが不可逆に失われる |
| DB への書き込みに失敗 | **5xx** | 受け取っていない。端末の spool に残せば、復旧後の次の送信機会で自然に回復する |
| 正常 | **200** | |

「壊れた行でリクエスト全体を失敗させない」という方針は、**行の内容に対するもの**であって、認証や保存の失敗には及ばない。ここを一律 200 にすると、`INGEST_TOKEN` の設定漏れやストレージ枯渇・DB 再起動の最中に届いたイベントが、端末側もサーバ側も控えを持たないまま消える。§2.3 が置いた「測定の欠損は後から回復できる」という前提は、この規則があって初めて成立する。

値の検査を行うのはここだけである。受信は外部（端末）からの入力を受ける唯一の境界であり、検査が意味を持つのはこの境界だけである。

#### 認証

画面の認証は Ingress 側に委ねる。アプリケーションにログイン機構を持たない。

`/ingest` のみ、環境変数 `INGEST_TOKEN` と突き合わせるトークンで保護する。トークンはプラグインの `config.json` に平文で置き、配布物に含める。**端末はこれを `X-Ingest-Token` ヘッダに載せる。**

**`INGEST_TOKEN` が未設定または空のときは、すべての受信を 401 にする。** 通せば、設定漏れのまま待ち受けているサーバが誰の送信でも受理することになる。起動スクリプトが Secret の不在で失敗する（§4.6）のと同じ理由であり、こちらは設定が存在しても値が空である場合の受け皿である。

> **このトークンは機密防御ではなく、誤送信の防止のために置く。到達制御はネットワーク境界（VPN）が担う。**

### 4.5 CSV 取込

`/mnt/data/csv/` を走査して取り込む。

- ヘッダから契約の `CSV_COLUMNS` に**列挙された列だけ**を拾う。知らない列は捨てるため、CSV に列が増えても壊れない
- `Date` は **`YYYY-MM-DD` と `YYYY/M/D`（ゼロ埋めなし）の 2 書式を受理し**、epoch 日に変換して `day` 列（INTEGER）に入れる。どちらでもない行は破棄し、破棄件数を取込結果に出す。**書式を 1 つに決め打つと、もう一方の書式のファイルが丸ごと欠測する**
- `Provider` は生の文字列のまま保存し、**分離は集計時の `WHERE` で行う**。他社モデルの分類辞書を持たない

#### 取込の単位と冪等性

**1 ファイルの取込は「そのファイルが含む `day` の行を `DELETE` → `INSERT`」を 1 トランザクションで行う。**

- **冪等キーはファイル名ではなく `day` である。** ファイル名を冪等キーにすると、期間が重なる 2 つのファイル（日次ファイルと週次ファイルなど）が置かれたときに同じ日のコストが二重に入り、`SUM(cost)` が倍になる。`cost_daily` には主キーも UNIQUE も無い（§5.5）ため、DB 側の防御は無い。コストは効果測定の正本であり、二重計上は §7.1 の曲線を施策と無関係に跳ねさせる
- **1 トランザクションにするのは、部分取込を確定させないためである。** 取込中にプロセスが落ちると、途中までの行が「取込済み」として恒久化し、無言で欠けたまま固定される
- UPSERT は使わない（方言の回避）。`DELETE` + `INSERT` で足りる

#### 起動

**起動は画面のボタンである。** 実行基盤に定期実行の仕組みが無いため、日次 1 回の手動クリックを正式な運用とする。監視デーモンやスケジューラを持ち込まない。

**ボタンは 1 つであり、押すたびに `CSV_DIR` の全ファイルを取り直す。** 「未取込のファイルだけを処理する」という区別を持たない。

区別を持たない理由は、**取込済みかどうかを判定する材料が無い**ことにある。冪等キーは `day` であり、期間の重なるファイルを取り込むと、同じ日の行は後から取り込んだファイル由来のものに置き換わる。したがって「どのファイルを取り込んだか」を保存済みの行から逆算することはできず、逆算を試みると、押すたびに同じ日の値が別のファイルの値へ入れ替わる。

全ファイルを取り直せば、結果は置かれているファイルの集合だけで決まり、押す回数にも順序にも依存しない。AI Gateway が同名ファイルを訂正版で再発行した場合も、置き換えて押すだけで反映される。年間数十ファイルの規模であり、処理時間は問題にならない。

同時押下は想定しない。1 人の管理者が日次で押す前提である。

### 4.6 実行基盤とデプロイ

**現在は FaaS 基盤上で動かす。将来 Kubernetes 上で動かす可能性がある。**

**基盤が求めるのは「ポート 5000 で HTTP を待ち受けること」だけである。WSGI で直接待ち受ければよく、ASGI での待受は要求されない。** 同じ基盤上では、Flask を `0.0.0.0:5000` で待ち受けるアプリケーションが複数稼働している。

起動コマンドは FaaS でも Kubernetes でも同じである。

```
waitress-serve --listen=0.0.0.0:5000 app:app
```

Flask の開発サーバは本番向けではないため、待受は waitress に任せる（§4.3）。

#### 環境変数

| 項目 | 値 |
| --- | --- |
| `BASE_PATH` | 公開サブパス。`SCRIPT_NAME` として WSGI 環境に与える |
| `DB_DSN` | `sqlite:////mnt/data/governance.db` または `mysql://user:pass@host/db` |
| `INGEST_TOKEN` | 受信トークン |
| `CSV_DIR` | 既定 `/mnt/data/csv` |
| `PKG_PROXY` | 依存を取得するためのプロキシ。社内のホスト名を含むためリポジトリに書かない |

**これらは Secret ファイル `/mnt/data/secrets/cc-governance-bmsd.env` に置き、起動スクリプトが読み込む。** ファイル名はアプリ名に対応させる。ファイル自体は基盤の Open Terminal から事前に作成しておく。DB 接続文字列と受信トークンを含むため、リポジトリには入れない。

#### 起動スクリプト

起動スクリプトが行うのは、Secret の読み込み・プロキシの設定・依存の install・待受の開始の 4 つだけである。

```bash
#!/bin/sh
set -eu

# Secret ファイルを読み込む（基盤の Open Terminal から事前に作成しておく）
SECRET_FILE="/mnt/data/secrets/cc-governance-bmsd.env"
if [ -f "$SECRET_FILE" ]; then
  set -a
  . "$SECRET_FILE"
  set +a
else
  echo "ERROR: Secretファイルが見つかりません: $SECRET_FILE" >&2
  exit 1
fi

# パッケージ取得にプロキシが要る
export http_proxy="$PKG_PROXY"
export https_proxy="$PKG_PROXY"

cd "$(dirname "$0")"
pip install -r requirements.txt
waitress-serve --listen=0.0.0.0:5000 app:app
```

要点は 4 つである。

1. **`pip install` にはプロキシの設定が必須である。** 基盤からパッケージ配信元へ直接到達できないため、これが無いと install がそのまま失敗し、サーバは 1 度も上がらない
2. **Secret ファイルが無ければ、その場で失敗して終了する。** 黙って起動すると、`INGEST_TOKEN` が未設定のまま待ち受ける状態になり、全端末の送信が 401 で跳ね返り続ける（§4.4）。端末は spool を残すので失われはしないが、誰も気づかないまま溜まる。起動しなければ気づく
3. **作業ディレクトリをスクリプトの位置に移してから install と起動を行う。** `requirements.txt` も `app.py` も `cc-governance-bmsd-server/` にあり、起動のされ方に依存しない
4. **POSIX sh の範囲で書く。** 基盤がスクリプトをどのシェルで起動するかは、こちらが指定できる保証がない。bash 拡張を使わなければ、どちらで起動されても同じ結果になる。`sh -n` による構文検査が通ることを、配置前の確認に含める

#### 基盤側で行う設定

リポジトリの内容だけではデプロイは完了しない。基盤の管理画面で次を設定する。

| 項目 | 内容 |
| --- | --- |
| Entrypoint | リポジトリルートからの相対パスで `cc-governance-bmsd-server/start.sh` |
| リポジトリの URL | SSH 形式。**基盤が発行する公開鍵を、リポジトリ側のアクセスキーに登録する**（初回のみ） |
| ブランチ | デプロイ対象のブランチ |
| タグ `NGINX_ENABLE_REWRITE_TARGET` | **`false`。** 既定のままだと基盤がリクエストパスを書き換え、`SCRIPT_NAME` によるサブパス対応（§4.3）と噛み合わない |
| 公開形態 | サブパス。**公開される URL の実際の形は、最初のデプロイまで確定しない。** `BASE_PATH` はそれを見てから決める |

**push だけでは反映されない。** ソースの更新も Secret の作成も、基盤の再起動操作を経て初めて効く。

`/mnt/data/secrets/` の Secret ファイルは、基盤のターミナルが Function の作成後にしか開けないため、**初回の起動は Secret 不在で必ず失敗する。** これは想定された順序であり、失敗を見てから Secret を置いて再起動する。

#### デプロイ単位

**デプロイ単位は開発リポジトリのルートである。** FaaS に渡すルートも、Docker のビルドコンテキストも、同じくリポジトリルートとする。プロセスの作業ディレクトリは `cc-governance-bmsd-server/` とする。

これを決めておかないと、サーバが契約の正本を参照する経路（§6.1）が成立するかどうかが決まらない。`governance/` と `cc-governance-bmsd-server/` が同じ木の下に並んでいることが、契約を 1 ファイルに保つ前提である。

**Dockerfile を 1 枚用意する。** 内容は「ベースイメージ・`requirements.txt` の install・ソースのコピー・`CMD` で waitress 起動」だけの十数行である。起動コマンドが FaaS と同じであるため、Dockerfile があれば移行時の作業は最小になる。移行手順の詳細はここには書かない。

Dockerfile は契約の正本（`governance/hooks/contract.py`）とサーバのソースの両方をコピーする。ビルドコンテキストがリポジトリルートであるため、この 2 つは同じコンテキストの中にある。**コンテナ環境では Secret の渡し方が変わる**（永続領域のファイルからの読み込みではなく、基盤が与える環境変数を直接受け取る形になる）。

デプロイは、開発リポジトリの指定ブランチへの push で行う。

#### バックアップ

**アプリケーションはバックアップ機構を持たない。永続領域の複製を運用手順として行う。**

3 テーブルの再現可能性は等しくない。

| テーブル | 失ったとき |
| --- | --- |
| `cost_daily` | CSV から再取込できる。ただし CSV の正本も `/mnt/data/csv/`（§4.5）にあり、領域ごと失えば一緒に消える |
| `events` | 端末の spool は 5MB / 7 日で破棄される（§3.5）ため、それより前は再現できない |
| `policy_state` | **再現できない。** 準拠開始日は過去の観測にしか存在せず、端末から取り直す手段が無い |

`policy_state` を失うことは、§7.1 のイベントスタディの基準点（準拠開始日）を失うことであり、このシステムの存在理由に最も近い画面が永久に描けなくなることと同義である。

運用は次のとおりとする。

- SQLite で運用する場合、DB ファイルと `/mnt/data/csv/` を、CSV 取込（§4.5）と同じ日次の操作として複製する。**複製先は永続領域の外に置く。** 同じ領域に置いた複製は、領域ごと失う障害に対して何も守らない
- MySQL で運用する場合、基盤側のバックアップに委ねる

復旧できるのは最後の複製時点までである。この割り切りは §11.2 に記載する。

## 5. データモデル

テーブルは 3 つ。**すべて append-only、サロゲートキーなし、外部キーなし。**

### 5.1 `events` — 端末の利用ログ

| 列 | 型 | 意味 |
| --- | --- | --- |
| `event_id` | VARCHAR(36) | 端末が生成した UUID。重複排除に使う |
| `ts` | INTEGER | epoch 秒 |
| `day` | INTEGER | epoch 日（JST 基準）。突合・日次集計の軸 |
| `user_email` | VARCHAR(255) | 突合キー |
| `host` | VARCHAR(255) | 端末識別 |
| `hook_event` | VARCHAR(64) | どの hook から来たか |
| `session_id` `prompt_id` `tool_name` `source` `compact_trigger` `command_name` `command_source` `skill_name` `effort_level` `permission_mode` `agent_id` | VARCHAR(255) | `HOOK_FIELDS` から自動生成される列 |
| `is_interrupt` | INTEGER | `HOOK_FIELDS` から自動生成される列（型は契約が持つ）。0 / 1 / NULL |
| `context_tokens` | INTEGER | transcript 由来。`PreCompact` / `Stop` のときのみ非 NULL |

#### インデックス

インデックスは**画面のクエリから逆算した被覆インデックス**にする。

| インデックス | 対応する画面 |
| --- | --- |
| `(day, user_email, event_id)` | `/` の日次推移・利用者数、`/effect` の突合 |
| `(skill_name, day, user_email, event_id)` | `/assets` のスキル別集計 |
| `(tool_name, day, user_email, event_id)` | `/` のツール分布 |
| `(day, hook_event, context_tokens)` | `/effect` のコンテキスト分布 |

**単独列のインデックスを置かない。** `skill_name` は 9 割が NULL の列であり、単独インデックスを置くと、絞り込みの後に大量のランダムな行参照が発生して**インデックスが無い場合より遅くなる**。必要な列を末尾に並べてインデックスだけで集計が完結する形にすると、年間規模でも 1 秒を大きく下回る。列を 2〜3 個足すだけで、事前集計テーブルという新しい保守対象を持たずに済む。

4 本とも `day` か、`day` を後続に持つ列から始まる。**`events` に対して、`day` で絞らない全期間スキャンのクエリを画面に置かない**ことが、この設計の前提である（§5.4）。`policy_state` の準拠開始日は性質上すべての行を見る必要があるが、専用のインデックスで完結する（§5.2）。

### 5.2 `policy_state` — 適用した設定値の時系列

| 列 | 型 | 意味 |
| --- | --- | --- |
| `event_id` | VARCHAR(36) | 端末が生成した UUID |
| `ts` | INTEGER | epoch 秒 |
| `day` | INTEGER | epoch 日 |
| `user_email` | VARCHAR(255) | |
| `host` | VARCHAR(255) | |
| `key_name` | VARCHAR(128) | 例: `env.CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`。**マーケットプレイス名を含むキーは 64 文字に達する**ため桁に余裕を持たせる |
| `value` | VARCHAR(255) | **適用した値そのもの**（`"60"`） |
| `prev_value` | VARCHAR(255) | **書き込み前の値**。キーが無ければ NULL |
| `apply_result` | VARCHAR(32) | `already_ok` / `applied` / `skipped_conflict` / `skipped_missing` / `parse_failed` / `write_failed` |
| `plugin_version` | VARCHAR(32) | 端末で動いているプラグインの版 |

インデックス: `(key_name, prev_value, user_email)` / `(user_email, ts)`

縦持ちにする理由は 2 つ。施策項目が増えても DDL 変更が要らないこと、JSON 型の方言差を避けられることである。

**値そのものを記録する。** 版番号だけを記録すると、割合 60 と 80 を区別できず、施策を変更したときに「どの値に準拠していたか」が失われる。効果測定の核はここにある。

**準拠の判定は `prev_value` で行う。**

- **準拠している** = セッションを開いた時点で `prev_value` が既にポリシー値と一致している
- **準拠開始時点** = `key_name` と `prev_value` がポリシー値に一致する行の `MIN(day)` を `user_email` で `GROUP BY`
- **準拠区間** = その日以降、`prev_value` が別の値になるまで

`value` は適用後の値であり、それは直前に自分が書いた値そのものである。これを準拠の根拠にすると全員が常に準拠していることになり、未準拠者も、キー名が上流で変わって書き込みが空振りしている状態も、数字の上では一切現れない。**`prev_value` で見れば、「書いたのに次のセッションでポリシー値になっていない」＝設定が効いていない端末が、準拠率の低下として画面に出る**（§7.2・§9.2）。

**`SessionStart` は `startup` / `resume` / `clear` / `compact` の 4 つの契機で発火する。** セッションを開いたときだけでなく、`/clear` のたびにも、自動圧縮が走るたびにも発火する。自動圧縮を早める施策（§3.6）が効くほど `compact` の発火は増える。

行数はこの頻度で決まる。140 名が 1 日 8 回・年 250 日・3 項目とすると年間 84 万行であり、圧縮の増加を見込んでもこの桁に収まる。

### 5.3 `cost_daily` — AI Gateway CSV

| 列 | 型 |
| --- | --- |
| `day` | INTEGER（epoch 日） |
| `user_email` | VARCHAR(255) |
| `provider` `model` `currency` | VARCHAR(255) |
| `cost` | DOUBLE |
| `input_tokens` `output_tokens` `cache_read_tokens` `cache_write_tokens` `cached_input_tokens` `uncached_input_tokens` | BIGINT |
| `source_file` | VARCHAR(255)（どのファイル由来の行かを残す） |

インデックス: `(day, user_email)`

**突合は `user_email × day` の 2 軸に固定する。** モデル軸では突合しない。モデル名の表記揺れを吸収する名寄せ表は、モデルが増えるたびに人手を呼ぶ保守対象になる。`model` 列は保持するが、それは CSV 単独での内訳表示にのみ使う。

### 5.4 `event_id` の扱い

`event_id` は**主キーにも UNIQUE 制約にもしない**。

- UNIQUE 制約を置くと、重複 INSERT が DB エラーになり、エラーを無視する方法が方言で分かれる（`INSERT IGNORE` と `ON CONFLICT DO NOTHING`）。方言差を持ち込まないという方針に反する
- 主キーを置かないのは append-only で行を個別参照しないためであり、`event_id` も同じ理由で制約にしない

代わりに、**件数を数える集計はすべて `COUNT(DISTINCT event_id)` を使う**。送信のリトライで重複行が入っても件数は正確になる。重複行はストレージ上は残るが、規模から見て問題にならない。

#### 重複が守るものと守らないもの

重複は例外ではなく**定常状態**である。送信にはタイムアウトがあり、サーバが INSERT に成功してもレスポンスが間に合わなければ、端末は spool を残して次回まるごと再送する。したがって、次の 2 つを不変条件として置く。

1. **`event_id` が保護するのは件数だけである。** `COUNT(*)` で数えた度数は、再送しやすい端末の分だけ水増しされる。しかも再送は特定の端末に偏るため、分布の形そのものが歪む
2. **分布・率を出すクエリも、必ず `DISTINCT event_id` を経由する。** ヒストグラムの度数は `COUNT(DISTINCT event_id)`、NULL 率の分子は `COUNT(DISTINCT CASE WHEN col IS NULL THEN event_id END)` とする。分母だけを重複排除して分子を重複込みにすると母集団が食い違い、率が 100% を超える

#### 絞り込みの不変条件

**`COUNT(DISTINCT event_id)` を全期間に対して実行しない。必ず `day` で範囲を絞る。** UUID の `DISTINCT` は一時 B-tree を作るため、行数が増えると線形以上に悪化し、一定規模を超えるとメモリからディスクへ溢れる。`day` で絞れば §5.1 の被覆インデックスの範囲内で完結する。

`event_id` 単独のインデックスは置かない。上の不変条件により、`event_id` は常に `day` で絞り込んだ後の集計の中でしか使われないためである。

### 5.5 両 DB 対応の実現方法

抽象レイヤを積むのではなく、**方言が出る機能を使わない**ことで実現する。

| 方言が出る箇所 | 回避策 |
| --- | --- |
| `AUTOINCREMENT` / `AUTO_INCREMENT` | **主キーを持たない。** 3 テーブルとも append-only で、行を個別参照しない |
| 日時型・日付関数（`julianday` と `DATEDIFF`） | **日時型を使わない。** epoch 秒・epoch 日の INTEGER のみ。相対日は単なる整数の引き算 |
| UPSERT（`ON CONFLICT` と `ON DUPLICATE KEY`） | **使わない。** 再取込は `DELETE WHERE day IN (...)` + `INSERT`（§4.5） |
| JSON 型・JSON 関数 | **使わない。** policy は縦持ち |
| TEXT へのインデックス長 | インデックス対象列を `VARCHAR(255)` にする（SQLite は TEXT として受理する） |
| プレースホルダ（`?` と `%s`） | SQL は `?` で書き、MySQL 接続時のみ `sql.replace("?", "%s")` |
| 真偽値 | INTEGER 0 / 1 |

結果、**DDL も集計 SQL も 1 本で両方に通る**。`CREATE TABLE IF NOT EXISTS` は両対応である。インデックスは MySQL 8.0 に `CREATE INDEX IF NOT EXISTS` が無いため、`SHOW INDEX` で存在確認してから作る分岐を `db.py` の `init()` に持つ（3 行）。実テーブルの列を取得する分岐も同じ場所に置く（§4.3）。

**window 関数（`ROW_NUMBER() OVER (...)`）は使う。** MySQL 8.0 と SQLite 3.25 以降の両方で同じ構文が通るため、方言にならない。これは「最新の 1 行」を取る集計（§7.2）に必要であり、代替手段は相関サブクエリのネストになって読みにくくなる。**前提として、SQLite 3.25 未満の環境は対象外とする。**

## 6. 契約（端末とサーバで共有する定義）

### 6.1 正本の位置

正本は `governance/hooks/contract.py` ただ 1 ファイルである。

- **端末** — プラグインの一部としてそのまま配布されるため、追加の解決処理が要らない
- **サーバ** — `cc-governance-bmsd-server/shared.py` が `sys.path` に `governance/hooks` を足して import する。4 行のシムであり、サーバ側のコードはすべて `from shared import HOOK_FIELDS, ...` と書く

パスは **`__file__` 起点で解決する**。作業ディレクトリからの相対パスにしない。

```python
# shared.py
import os, sys
sys.path.insert(0, os.path.join(os.path.dirname(os.path.abspath(__file__)),
                                os.pardir, "governance", "hooks"))
from contract import (HOOK_FIELDS, EXTRA_COLUMNS, POLICY, POLICY_COLUMNS,  # noqa
                      CSV_COLUMNS, dig, coerce, to_day, ddl)
```

`os.pardir` が開発リポジトリのルートを指すことは、デプロイ単位をリポジトリルートと定めたこと（§4.6）によって保証される。作業ディレクトリ依存にすると、起動のされ方が変わった瞬間に import が失敗してサーバが上がらない。

開発リポジトリ `cc-governance-bmsd` にプラグインとサーバを同居させるのは、この 1 ファイルを両者が直接参照できるようにするためである。契約が 2 か所にあると、同期ツールという新たな保守対象が生まれ、ずれたときに気づく手段が無い。参照が 1 つなら、ずれようがない。

### 6.2 契約が持つもの

`contract.py` が持つのは次の 5 つの定数と、4 つの小さな関数だけである。

| 定数 | 導出されるもの |
| --- | --- |
| `HOOK_FIELDS` | ① 端末の抽出処理 ② `events` の DDL 列と型 ③ INSERT 文の列順 ④ 受信 API の検査 ⑤ 起動時の列の突き合わせ |
| `EXTRA_COLUMNS` | `event_id` `ts` `day` `user_email` `host` `hook_event` `context_tokens` の型定義 |
| `POLICY` | ① 端末が適用する設定値 ② `policy_state` に記録する `key_name` / `value` ③ 画面の準拠判定 |
| `POLICY_COLUMNS` | ① `policy_state` の DDL 列と型 ② INSERT 文の列順 ③ 受信 API の検査 ④ 起動時の列の突き合わせ |
| `CSV_COLUMNS` | ① CSV ヘッダ → 列名の対応 ② `cost_daily` の DDL ③ INSERT 文 ④ 起動時の列の突き合わせ |

`CSV_COLUMNS` の要素は `(CSV ヘッダ名, 列名, 型)` の 3 つ組である。`source_file` は CSV に対応するヘッダを持たないため、ヘッダ名を `None` として同じ表に並べる。列の定義を 1 か所に保つために、対応の有無で表を分けない。

| 関数 | 責務 |
| --- | --- |
| `dig(obj, path)` | キーパスの安全な解決（§3.2） |
| `coerce(value, type)` | 列の型に合わせた値の変換（§3.2） |
| `to_day(ts)` | epoch 秒から JST 基準の epoch 日を求める。端末とサーバの両方がこれを呼ぶ |
| `ddl()` | 定数から `CREATE TABLE` 文を組み立てる |

**`to_day` を契約に置くのは、端末が `day` を組み立て（§3.2）、サーバが `ts` から再計算する（§4.4）ためである。** 同じ式が 2 か所にあると、片方だけを直したときに日次集計の軸が静かにずれる。

**`HOOK_FIELDS` と `EXTRA_COLUMNS` の列名集合は互いに素である。** これは契約の不変条件であり、`ddl()` の先頭で重複を検出して例外を投げる（1 行）。両方から `events` の列を生成する以上、同じ列名が両方にあると `CREATE TABLE` が重複列で落ち、サーバが起動しない。**`is_interrupt` は hook 入力から取る値であるため `HOOK_FIELDS` に属する。** `EXTRA_COLUMNS` が持つのは、端末側で組み立てる列だけである。

DDL 生成は 10 行程度の関数 1 つで済む。列型が VARCHAR / INTEGER / BIGINT / DOUBLE の 4 種しかなく、分岐が少ないためである。

**同期ツールも差分検査ツールも作らない。** 契約と実テーブルの食い違いは、`init()` の突き合わせが起動時に落とす形で扱う（§4.3）。契約と端末の食い違いは、配布が 1 ファイルの複製であるため起こらない。

### 6.3 これは設定ファイルではない

`HOOK_FIELDS` は挙動を切り替える設定ファイルではない。「どのキーパスがどの列になるか」という**単一の事実**である。書き換えたときに変わるのは列の集合だけで、処理の構造は変わらない。したがって、これを読み込んで動作を分岐させるコードは存在しない。

## 7. 管理画面

画面は 4 つ。すべて SQL の `GROUP BY` 1〜2 本で、表と CSS バーだけで描く。

### 7.1 `/effect` 効果測定 — 「窓の強制はコストを下げたか」

システムの存在理由に最も近い画面。

**イベントスタディ** — 端末ごとの準拠開始日を 0 日目とし、相対日 −14 〜 +14 の「1 人あたり日次コスト」「1 人あたり日次入力トークン」を平均して折れ線（表 + CSS バー）で出す。

**コンテキスト分布** — `PreCompact` 時の `context_tokens` のヒストグラムと、`Stop` 時の `context_tokens` のヒストグラム。度数は `COUNT(DISTINCT event_id)` で数える（§5.4）。

**設定値の妥当性を読むのは `Stop` の分布である。** ターン終了時にどれだけ積んでいるかが、圧縮を早めるべきかどうかの材料になる。`PreCompact` の分布は圧縮が発火した時点の量であり、発火の閾値は自動圧縮の窓の割合で決まる（§3.6）ため、**モデルの構成が混ざれば複数の山になる。** これは設定値の妥当性ではなく、**発火そのものが起きているか**を確かめるために見る。

**準拠者数の推移** — 分母の透明性のため。

#### 集計の規約

3 つを設計上の規約として固定する。どれも選び方で結果の符号が変わりうる箇所であり、実装者に委ねない。

1. **利用の無い日は `cost = 0` として埋める。** 存在する行だけの平均を取ると、相対日ごとに分母の人数が変わり、「使わなかった人が抜けて 1 人あたりが上がる」という組成の変化を効果として読んでしまう。分母は**その相対日に在籍している準拠者数**に固定する
2. **相対日 0 は比較から除く。** 準拠開始日は定義上「Claude Code を使った日」であり、前後の日は使わなかった日を含む。0 日目には施策と無関係に機械的なコストの山が立つ。−14〜−1 と +1〜+14 を比較する
3. **準拠前のコンテキスト分布は、初回展開では描けない。** `events` はプラグインが入って初めて発生するため、初回展開では準拠開始日より前の行が 1 行も存在しない。初回は「準拠後の分布のみ」を設定値の妥当性の材料として使う。2 回目以降の施策変更（値の変更）では、変更前の区間に行があるため 2 本並ぶ

元になるクエリは 2 本。相対日の計算は epoch 日の引き算なので両 DB で同一である。

**基準にする施策項目は `env.CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` に固定する。** この画面が問うのは「窓の強制はコストを下げたか」であり、他の 2 項目は配布経路の維持であってコストに直接効かない。

**`provider` に入れる値は、最初の CSV 取込の後に確定して `queries_policy.py` の定数に置く。** これは上流の変化に人手で追随する箇所（§9.3）には含めない。Gateway が扱う事業者が増えても、Claude の値が変わらなければ直す必要がないためである。

```sql
-- 準拠開始日（書き込み前から既にポリシー値だった最初の日）
SELECT user_email, MIN(day) AS d0 FROM policy_state
 WHERE key_name = ? AND prev_value = ? GROUP BY user_email;

-- 日次コスト（指定 provider 分のみ）
SELECT user_email, day, SUM(cost), SUM(input_tokens) FROM cost_daily
 WHERE provider = ? GROUP BY user_email, day;
```

2 本の結果（それぞれ約 140 行・数万行）を Python で突き合わせて相対日に畳む。**これは全走査ではなく集計済み結果の後処理**であり、行数は端末数 × 日数に抑えられている。

#### 識別の前提

この画面が測るのは**相対日の傾き**であって、施策の因果効果ではない。強制適用である以上、処置を受けない対照群は存在しない。また、展開が数日に集中すれば相対日はほぼ暦日と一致し、同時期に起きた他のすべて（モデルの変更・料金改定・繁忙期・社内アナウンス）が施策の効果として計上される。

**ばらつきは待つものではなく、作るものである。** 導入を 2〜3 群に分け、1〜2 週間ずらして案内する（§8.4）。配布の仕掛けを変える必要はなく、**案内する日をずらすだけでよい**。これが、追加の機構をまったく持たずに識別の前提を成立させる唯一の手段である。残る交絡は §11.1 に明記する。

### 7.2 `/policy` 適用状況 — 「どの端末がポリシーに準拠しているか」

- 準拠率（施策項目別）
- **未準拠者の一覧**（`user_email` / `host` / 最後に観測した値 / 最終観測日）

**1 台でも未準拠なら、その利用者は未準拠とする。** 準拠の判定は端末（`user_email` × `host`）単位で出るが、準拠率の分母は利用者単位である（後述）。畳み方を決めないと、1 人が 2 台使っている場合に分子の作り方で率が動く。ガバナンスの目的は「行き渡っていない端末を見つけること」であるから、甘い側に倒さない。一覧には端末を行として出し、率は利用者で数える。
- **未導入者の一覧**（`cost_daily` に居るが policy イベントが来ていない `user_email`）
- **14 日以上イベントが来ていない端末**（離脱、または収集の停止の兆候）。判定は **`policy_state`** に対して行い、直近 30 日の範囲で端末ごとの最終 `day` を取る。`events` で判定すると、無効化スイッチ（§3.9）を入れた端末が恒久的にこの一覧に並ぶ。全期間を走査しない（§5.4）。7 日にしないのは、長期休暇で 1 週間端末に触れない利用者が毎回並ぶためである。30 日を超えて来ていない端末はこの一覧から外れ、未導入者一覧（`cost_daily` に居るが policy イベントが無い）の側に現れる
- `plugin_version` の分布（配布が届いていない端末）

**実務上ここが最も使われる画面である。声かけ対象がそのまま出る。**

#### 最後に観測した値

端末ごとの「現在の値」は、`prev_value` の**最新の 1 行**である。`GROUP BY user_email, host, prev_value` は「過去に観測されたすべての値」を 1 行ずつ返すため、これでは現在値にならない。ポリシー値を一度でも変更すれば全員が 2 行以上になり、どちらが現在なのかが結果から決まらなくなる。**ポリシーの変更こそがこのシステムの主用途であるから、これは必ず起きる。**

```sql
SELECT user_email, host, prev_value, ts FROM (
  SELECT user_email, host, prev_value, ts,
         ROW_NUMBER() OVER (PARTITION BY user_email, host ORDER BY ts DESC) AS rn
    FROM policy_state WHERE key_name = ? AND day >= ?
) t WHERE rn = 1;
```

**`day` で絞る。** 全期間に対して window 関数を走らせない（§5.4）。絞った窓より前にしか行が無い端末は、この一覧から外れて未導入者側に現れる。

#### 準拠率の分母

**分母は「直近 30 日に `cost_daily` にコストが立っている `user_email` の集合」とする**（離脱の判定期間と揃える）。 つまり、実際に Claude Code を使っている利用者である。

利用者の名簿はこのシステムの中に存在しない。一方、コストの正本は**プラグインの導入有無と無関係に全利用者を覆っている**。分母をこちらに取ると、`policy_state` に 1 行も無い利用者が「未導入者」として自動的に浮かび上がる。プラグインを入れていない人は準拠率の分母にすら現れない、という状態を避けられる。

```sql
-- 未導入者 = Gateway には居るが policy イベントが無い
SELECT c.user_email FROM (
  SELECT DISTINCT user_email FROM cost_daily WHERE day >= ?
) c LEFT JOIN (
  SELECT DISTINCT user_email FROM policy_state WHERE day >= ?
) p ON c.user_email = p.user_email
WHERE p.user_email IS NULL;
```

導入そのものは利用者の操作に依存する（§8.4）。**強制する手段を持たない以上、せめて「入っていない人が誰か」は出す。**

### 7.3 `/assets` 配布物の利用状況 — 「配ったものは使われているか」

- `skill_name` 別の呼出回数・利用者数・直近 7 日と前 7 日の比較
- `command_name` × `command_source` 別（社内配布か個人設定かの切り分け）
- `agent_id` の有無によるサブエージェント利用の割合。**`agent_id` はサブエージェント内のツール呼出にのみ付く**ため、有無がそのまま親子の分離になる

```sql
SELECT skill_name,
       COUNT(DISTINCT event_id),
       COUNT(DISTINCT user_email)
  FROM events
 WHERE skill_name IS NOT NULL AND day >= ?
 GROUP BY skill_name
 ORDER BY 2 DESC;
```

**値の分類辞書を持たない**ため、社内配布のスキルと個人のスキルは `command_source` の生値でそのまま並ぶ。どれが社内配布かは見る人が知っている。

### 7.4 `/` 概況 — 「全体でいくらかかり、誰が使っているか」

- 日次コスト推移（`provider` 別の内訳をそのまま表示。他社モデルは別行として見えるだけで、分類処理はしない）
- 利用者数・セッション数の推移
- `permission_mode` / `effort_level` / `source` の分布（生値のまま）
- **健全性の 1 行**（§9.2）

### 7.5 作らない画面

- 端末ごとのドリルダウン詳細 — 誰が何をしたかの監視は目的ではない
- セッション単位のタイムライン — 会話本文がない以上、見ても読めない
- リアルタイムダッシュボード — コストの正本が日次である以上、意味がない

## 8. マーケットプレイスと配布

設定値もお知らせも配布物も、サーバからの配信ではなく **git によるプラグイン更新**で端末に届く。したがって配布経路は設計の一部である。

### 8.1 リポジトリの分離

| リポジトリ | 役割 |
| --- | --- |
| `cc-governance-bmsd` | 開発リポジトリ。プラグイン（`governance/`）とサーバ（`cc-governance-bmsd-server/`）を同居させ、**収集項目の契約を 1 か所で共有する** |
| `cc-marketplace-governance-bmsd` | 配布用マーケットプレイス。**完成したプラグインを差し込む箱**であり、開発中のコミットは入れない |

**なぜ分けるか** — マーケットプレイスは全利用者の端末が直接 clone する先であり、そこに開発の履歴（作業中のコミット・サーバのソース・実験ブランチ）を混ぜると、配布物の内容と履歴の両方が肥大する。配布経路には「配るものだけ」を置く。

### 8.2 マーケットプレイスリポジトリの構造

```
cc-marketplace-governance-bmsd/
  .claude-plugin/marketplace.json
  plugins/
    governance/             # 開発リポジトリの governance/ をそのまま差し込む
      .claude-plugin/plugin.json
      hooks/
      skills/
      commands/
      notices.json
      config.json
```

`.claude-plugin/marketplace.json` に書くのは、マーケットプレイス自体の名前と所有者、そして収録プラグインの一覧である。

```json
{
  "name": "cc-marketplace-governance-bmsd",
  "owner": { "name": "<管理チーム名>", "email": "<連絡先>" },
  "plugins": [
    {
      "name": "governance",
      "source": "./plugins/governance",
      "description": "Claude Code のガバナンス設定の適用・お知らせ配信・利用状況の収集"
    }
  ]
}
```

`source` は同一リポジトリ内の相対パスを指す。プラグインの実体を別リポジトリに置いて参照する形も取れるが、収録が 1 つである以上、同梱が最も単純である。

### 8.3 リリース手順

1. 開発リポジトリ `cc-governance-bmsd` で変更をマージする（設定値の変更・お知らせの追加・スキルの追加・収集項目の追加など）
2. `governance/.claude-plugin/plugin.json` の `version` を上げる。**バージョンを上げる場所はここ 1 か所だけである**
3. 開発リポジトリの `governance/` を、マーケットプレイスリポジトリの `plugins/governance/` へ差し込む（フォルダの内容をそのまま置き換える）。**差し込みと、その結果の検査はスクリプト 1 本で行う。** リリースの手作業は 140 端末に直接届くため、ここの誤りは高くつく。検査するのは、配布物に入ってはいけないもの（テスト・fixture・開発依存）が混入していないこと、差し込み漏れと差し込み過剰が無いこと、`version` が上がっていること、`POLICY` からキーが削除されていないことである
4. マーケットプレイスリポジトリで PR を作り、マージする
5. マージされた時点で配布される

`plugin.json` の `version` は、端末側が更新の要否を判断する唯一の手がかりである。中身を変えて `version` を上げ忘れると、端末に届かない。

#### 誤った設定値を配ったときの手順

**`POLICY` からキーを削除してはならない。**

§3.6 の適用処理が行うのは上書きだけであり、撤回（`POLICY` から消えたキーを `settings.json` から取り除く）は定義されていない。したがって `POLICY` からキーを削除する操作は、**誤った値を全端末に固定する操作**である。届かなくなるのは正しい値の方であり、既に書き込まれた誤った値はそのまま残る。

正しい手順は 1 つだけである。

1. `POLICY` に**正しい値を書く**（施策そのものをやめる場合は、Claude Code の既定値を書く）
2. `version` を上げて配り直す

反映は利用者が次に Claude Code を起動したときであり、全端末に行き渡るまで数日かかる（§8.5）。**即時の撤回手段は存在しない。** サーバから端末へ指示する経路を作らない（§2.3）ことの裏返しであり、この割り切りは §11.2 に記載する。

### 8.4 利用者への導入手順

マーケットプレイスを登録する。

```
/plugin marketplace add <配布用リポジトリの URL>
```

プラグインを導入する。

```
/plugin install governance@cc-marketplace-governance-bmsd
```

導入後、最初の SessionStart で設定の適用とお知らせの表示が働く。

**案内は 2〜3 群に分け、1〜2 週間ずらして行う。** 全員に同時に案内すると準拠開始日が数日に固まり、効果測定が暦日の変化と区別できなくなる（§7.1）。群分けに仕掛けは要らない。案内する相手と日付を分けるだけである。

**群は部署を横断して作る。** 部署ごとに群を作ると、群の差が施策の効果なのか部署の業務の差なのかを区別できなくなり、ずらして案内した意味が失われる。

**記録するのは「いつ、どの範囲に案内したか」の日付だけである。** 誰がどの群かを個人単位で持たない。イベントスタディの基準になる準拠開始日は `policy_state` から求まり、群の記録を使わない。ずらしが効いたかどうかは、**準拠開始日の分布に 2〜3 の山が立っているか**で確かめられる。1 つの山に潰れていれば、ずらしは失敗している。

個人単位の名簿を持てば、異動と入退社で古くなる保守対象が 1 つ増える。それによって除ける交絡は無い。**案内日を記録しても、実際に導入するかどうかは利用者が決める**ため、自己選択バイアス（§11.1）は残る。

### 8.5 更新の伝播

#### 自動更新は既定で無効である

**社外のマーケットプレイスは、自動更新が既定で無効になっている。** 有効なのは公式のマーケットプレイスと claude.ai 経由で追加したものだけであり、**配布用リポジトリはこれに当たらない。何もしなければ、施策の変更は一度も端末に届かない。**

有効化の経路は 2 つある。利用者が `/plugin` の画面でマーケットプレイスごとに切り替えるか、`extraKnownMarketplaces` の該当エントリに `autoUpdate` を立てるかである。**後者は `settings.json` に書けばよい**（§3.6）。**この設計は後者を `POLICY` に含め、SessionStart のたびに強制適用する**（§3.6）。マーケットプレイスの登録をやり直すとこの設定は外れうるため、一度きりの設定ではなく、毎回戻す対象として扱う。

`extraKnownMarketplaces` をユーザー設定の層に書いて有効になるかは**未検証である**（§11.3）。効かない場合、有効化は利用者の操作に依存することになり、`plugin_version` の分布が唯一の観測手段として残る。

**手動で更新するときは 2 段階である。** `claude plugin marketplace update <名前>` が更新するのはカタログだけで、**導入済みプラグインの版は上がらない**。本体は `claude plugin update <プラグイン名>` で上げる。自動更新が働かない端末に手順を案内するときは、この 2 つを両方伝える。

#### 届くまでの時間

- 自動更新は**セッション開始のあと、最大 10 分のばらつきを持って走る**。走行中のセッションは起動時に読んだ版を使い続けるため、**反映されるのは次に起動したときである**
- したがって、施策を変更してから全端末に行き渡るまでの時間は、利用者が Claude Code を起動する頻度に依存する。全員に届くまで数日かかることを前提に、効果測定は「日付」ではなく「端末ごとの準拠開始日」を基準にする（§7.1）

#### 更新が届かない端末

更新が止まると、施策の変更が永久に届かなくなる。これは配布経路が git だけであることの裏返しであり、この設計で最も回復しにくい故障である。

対策は 2 段構えである。

1. `POLICY` で自動更新の設定を毎回戻す（§3.6）
2. policy イベントの `plugin_version` で、**端末側で実際に動いている版を観測する**（§9.2）

1 だけでは足りない。設定ファイルより優先度の高い経路（環境変数など）で更新が止まっている端末には、プラグイン自身の書き込みは届かない。**「自動更新が自分で自分を回復する」とは主張しない。**

**リポジトリに到達できなくなっても、プラグインは止まらない。** 取得に失敗した場合、端末に既にあるマーケットプレイスの複製がそのまま使われ、**最後に同期した状態で動き続ける**。止まるのは更新であって、収集でも設定の適用でもない。この状態は `plugin_version` の分布に古い版として現れる。

2 は、回復できない故障を少なくとも**見えるようにする**。古い版のまま止まった端末が版の分布に残るため、個別に対処できる。回復手段を持てないなら、せめて検知手段を持つ。

## 9. 上流仕様の変化への備え

### 9.1 変化したとき何が起きるか

| 上流の変化 | 起きること | 壊れるか |
| --- | --- | --- |
| hook 入力にキーが**増える** | 何も起きない（取らない） | 壊れない |
| キーが**改名・消滅**する | その列が以後 NULL になる | 壊れない・**静かに欠測する** |
| hook の**種類が増える** | 登録していないので来ない | 壊れない |
| hook の**入力形式が変わる** | 収集処理が例外 → 握り潰し → イベントが止まる | 壊れない・**静かに止まる** |
| transcript の `usage` 構造が変わる | `context_tokens` が NULL になる | 壊れない・静かに欠測する |
| ポリシーの**キー名・環境変数名が変わる** | 書き込みは成功するが、次のセッションで `prev_value` に現れない | **施策が無効化される（最も重大）・準拠率の低下として現れる** |
| プラグインの更新が端末に**届かなくなる** | 古い版のまま施策が固定される | **施策の変更が伝播しない・`plugin_version` の分布に現れる** |
| CSV に列が増える | 知らない列を捨てる | 壊れない |

**どの変化でも Claude Code の動作は妨げられない**（hook は常に `exit 0`）。問題はすべて「静かに欠測する」形で現れる。

### 9.2 どう気づくか

**概況画面の隅に「健全性」の 1 行を出す。** アラート機構・通知・監視デーモンは作らない。

```
健全性（直近7日 / 前7日）: イベント 38,210 / 41,003 ・ 送信端末 128 / 131
  NULL率  tool_name 0.2%/0.2%  skill_name 91%/90%  context_tokens 88%/87%  command_source 62%/61%
  突合率  94% / 95%      plugin_version  1.4.0:121  1.3.0:7
```

読み方は 5 つだけである。

- **イベント件数の急落** → hook 入力形式の変化・収集の停止
- **特定列の NULL 率が急に 100% に跳ねる** → キーの改名・消滅。ただし次の 2 列は別の理由でも動く
  - **`effort_level` はモデル依存で欠測する。** 跳ねたら、まずモデル構成の変化を疑う。**この仕組みが推進しようとしている施策そのもの**（安価なモデルへの誘導）で跳ねうる。内部のデータにモデルは無いため、確認は AI Gateway CSV の `model` 列（§5.3）で行う
  - **`permission_mode` は実行形態で値が動く。** 非対話実行では対話時と違う値になる
- **準拠率の急落**（`/policy`）→ 設定キー名の変化・適用の空振り・上位設定による上書き
- **突合率の低下** → `user_email` が `cost_daily` と噛み合っていない。効果測定の対象人数が静かに減る
- **古い `plugin_version` が残り続ける** → 配布が届いていない端末

突合率と版の分布を置くのは、**どちらも列の NULL 率では絶対に見えない**ためである。`user_email` は不一致でも非 NULL であり、更新が止まった端末はイベントを送り続ける。

SQL は 2 本。件数と NULL 率が 1 本（`SELECT COUNT(DISTINCT event_id), COUNT(DISTINCT CASE WHEN col IS NULL THEN event_id END) ... WHERE day >= ? GROUP BY`）、突合率と版の分布が 1 本である。**分子も分母も `DISTINCT event_id` を通す**（§5.4）。片方だけを重複排除すると母集団が食い違い、率が 100% を超える。実装は 30 行程度である。

これで全部を検知できるとは主張しない。**検知できるのは「来ていたものが来なくなったこと」と「効いているはずのものが効いていないこと」だけ**であり、それで十分と判断している。新しいキーが増えたことは、そもそも知る必要がない。

### 9.3 人手で追随する箇所

**3 か所だけ**である。

1. `contract.py` の `HOOK_FIELDS` — hook 入力のキーパスの改名時
2. `contract.py` の `POLICY` — 設定キー名・環境変数名の変更時、施策の変更時
3. `contract.py` の `CSV_COLUMNS` — CSV のヘッダ名の変更時

いずれも `contract.py` の中にある。**保守の負債は 1 ファイルに閉じている。**

## 10. 設計判断

| # | 論点 | 採った案 | 採らなかった案と理由 |
| --- | --- | --- | --- |
| 1 | サーバの数 | **1 プロセス** | *ガバナンスとログで 2 分割* — 配信が git である以上ガバナンス側にサーバ機能がほぼ無く、効果測定は 3 テーブルの突合。分けるとプロセス間結合という要件にない問題が生まれる |
| 2 | リポジトリ構成 | **開発 1 + 配布 1** | *全部を 1 リポジトリ* — 配布経路に開発の履歴が混ざる。*契約をプラグイン側とサーバ側に複製* — 同期ツールという保守対象が生まれる |
| 3 | Web フレームワーク | **Flask + waitress** | *ASGI フレームワーク* — サーバの Python が 3.9 に固定されており、主要な ASGI スタックは 3.9 では最新版に追随できない。基盤が求めるのはポート 5000 での待受だけであり、ASGI での待受は要求されない（§4.6）。*素の WSGI* — ルーティングとテンプレート結合を自前で書くことになる |
| 4 | 非同期 | **使わない（すべて同期）** | *非同期で書く* — DB ドライバが同期であるため速くならず、同期呼び出しの混入でイベントループを止める危険だけが増える |
| 5 | 受信 API の検査 | **契約から導出した検査** | *バリデーションライブラリ* — 列と型は契約が既に持っており、別の語彙で書き直すと正本が 2 か所になる。*画面の表示データにも型を置く* — 検査対象が増えるだけで、検査で防げる誤りが無い |
| 6 | DB アクセス | **生 SQL + `queries_*.py` に集約** | *ORM* — 方言吸収の価値が無く（方言機能を使わない設計のため）、起動時の install が実費になり、レイヤが 1 段増える |
| 7 | MySQL / SQLite 両対応 | **方言が出る機能を使わない**（主キーなし・epoch INTEGER・UPSERT 不使用・JSON 不使用） | *方言ごとの DDL 2 本* — 同じ定義が 2 か所になる。*自動採番 id / 日時型 / UPSERT / JSON 列* — いずれも方言が分岐し、分岐の数だけ検証対象が倍になる |
| 8 | 重複排除 | **`event_id` + `COUNT(DISTINCT)`**（分布・率の分子も含めて必ず通す） | *UNIQUE 制約* — 重複 INSERT のエラー無視が方言で分かれる。*重複を放置* — 再送のたびに件数が水増しされ、相対比較すら成り立たなくなる |
| 9 | policy の持ち方 | **縦持ち（key_name, value）** | *JSON 列* — JSON 関数の方言差。*施策ごとの横列* — 施策追加のたび DDL 変更 |
| 10 | 準拠の記録 | **適用前後の値そのもの。判定は適用前の値** | *版番号だけ* — 60 と 80 を区別できない。*適用後の値だけ* — 直前に自分が書いた値なので全員が常に準拠になる |
| 11 | 施策の適用モード | **強制のみ** | *利用者が選択的に適用* — 準拠者と非準拠者の差が施策の効果なのか自己選択なのか区別できず、効果測定が成立しない |
| 12 | 通知の配信 | **`notices.json` を git で配り端末が表示** | *サーバのポーリング API* — サーバ停止で通知が止まる。配信の実体が git である前提に反する |
| 13 | 収集の抽出 | **キーパスを名指しで `get`** | *hook 入力を丸ごと保存して後で選別* — `tool_input` にプロンプト本文が入るため、上流が自由文キーを足した瞬間に流出する |
| 14 | hook 登録 | **7 種のみ・共通エントリ** | *全 hook を網羅登録* — 種類が増え続けるため網羅は原理的に達成できず、維持コストだけが残る。*画面が必要とする列の供給元を登録しない* — その列を主題にした画面が恒久的に空になる |
| 15 | 送信 | **hook 内は追記のみ・送信は detach** | *hook 内で同期 POST* — Claude Code の応答をネットワーク遅延でブロックする。体感を損なう施策は推進の妨げになる |
| 16 | 送信の信頼性 | **spool ファイル + 上限で破棄** | *ローカル DB + ACK + 再送制御* — 高い正確性が要求されていないのに、端末側に DB とトランザクション管理を持ち込むことになる |

## 11. この設計で答えられないこと

### 11.1 原理的に答えられない問い

- **「誰がどんなタスクに使ったか」** — 会話本文もプロンプトも保持しないため答えられない。これは制約ではなく設計の前提であり、代わりに `skill_name` / `command_name` / `tool_name` の分布で間接的に見る
- **「1 人が複数台使っているときの端末別コスト」** — コストの正本が利用者粒度のため按分できない。`host` は準拠状況の把握にのみ使う
- **「取りこぼしを含めた正確な利用回数」** — オフライン・spool 上限超過・hook 失敗で黙って落ちる。`event_id` が防ぐのは重複であって欠損ではない。イベント件数は**相対比較にのみ使い、絶対値としては扱わない**
- **「設定値以外の要因を除いた純粋な因果効果」** — イベントスタディは自然実験の**近似**であり、相対日の傾きを見るための道具と位置づける。次の 4 つは除去できない
  - **自己選択バイアス** — 早く再起動する人はもともとヘビーユーザーかもしれない
  - **対照群の不在** — 強制適用であるため、処置を受けない群が作れない。反事実は時系列の傾きしかない
  - **暦日との交絡** — 展開が短期間に集中するほど相対日は暦日に近づき、同時期のモデル変更・料金改定・繁忙期と区別できなくなる。§8.4 の段階的な案内はこれを緩和するが、消しはしない
  - **観測されていることによる行動変化** — 施策の展開と同時に案内を出す通常の運用では、施策そのものの効果と分離できない
- **「他社モデルの利用実態」** — CSV の `provider` 別内訳として見えるだけ。端末ログは Claude Code のものしかない
- **「Claude Code だけの費用」** — `cost_daily` は AI Gateway を通るすべての利用を含む。`provider` で他社を分けても、同じ Gateway を通る Claude Code 以外の Claude 利用は残る。§7.1 が見るのは**相対日の傾き**であり、この混入は水準を押し上げるが傾きの向きは変えない、という前提で読む

### 11.2 意図的な割り切り

- **`context_tokens` の分布をモデルで層別しない。** モデルごとに分けるとモデル定義という保守対象が生まれるため、1 本で見る
- **「書けたこと」は「効いていること」ではない。** 書き込む `~/.claude/settings.json` は設定の優先順位が最も低い層であり、上位の設定が同じキーを持てば書き込みは効かない。上位の設定を読みに行く機構は持たない。`prev_value` による準拠判定は、**次のセッションでポリシー値が見えているか**を確かめるところまでであり、それ以上の実効性は保証しない
- **導入そのものは強制できない。** 利用者が `/plugin install` を打たなければ何も始まらない。代わりに `/policy` の未導入者一覧で、入っていない人を名指しできる状態を保つ
- **`user_email` は端末の自己申告**であり、詐称を防げない。140 名の社内向けであり、目的が監査ではなく施策評価であることから受容する。悪意なしの不一致は突合率（§9.2）で検知するが、**不一致が起きた後の名寄せ手段は持たない**
- **受信トークンは機密防御ではない。** 誤送信の防止のために置く。到達制御はネットワーク境界が担う
- **リアルタイム性がない。** 端末からサーバへは分単位、コストは日次
- **画面の認証を Ingress に委ねる。** アプリケーションにログイン機構を持たない
- **データの削除・保持期間の設計を持たない。** 年間 1,500 万行は問題にならず、必要になった時点で `DELETE WHERE day < ?` を足せばよい
- **`/import` は同時押下を想定しない。** 1 人の管理者が日次で押す前提
- **配布した設定値を即時に撤回できない。** サーバから端末へ指示する経路を持たない（§2.3）ため、誤って配った値は「正しい値を配り直す」以外の方法で戻せず、全端末に行き渡るまで数日かかる（§8.3）。また、上書きする前に `settings.json` にあった利用者固有の値は保存しない。施策をやめるときに戻るのは Claude Code の既定値であって、利用者がもともと持っていた値ではない
- **復旧できるのは最後の複製時点までである。** `cost_daily` は CSV から再取込できるが、`events` は端末の spool が残っている 7 日分を超えると再現できず、`policy_state` は**原理的に再現できない**（§4.6）。欠損した期間について効果測定は行わない
- **契約に列を足すときはテーブルを作り直す。** マイグレーション機構を持たない。手順を踏まずにデプロイした場合はサーバが起動しない（§4.3）
- **テストは、壊れたときに実害が出る 4 領域と、受信から保存までの往復 1 本に留める。** 4 領域とは、契約からの DDL / INSERT 列の生成（ずれるとサーバが起動しない）、hook 入力からの値の抽出（上流の変更で列が静かに NULL になる）、`settings.json` の読み書き（利用者の設定を壊す）、CSV 取込の冪等化（コストが二重計上される）である。画面と hook の統合テストは持たない。Claude Code 本体の挙動に依存するため、実測での確認に委ねる

### 11.3 未検証の事項

次の 2 つは、**実装の最初に確かめる**。いずれも設計の土台であり、空振りすると施策そのものが成立しない。

- **`autoUpdate` を有効にしたとき、実際に更新が端末に降りてくるか**（§3.6・§8.5）。**配布経路そのものの維持がこれに懸かっている。** 設定が `settings.json` で維持できることは確かめたが、その結果として新しい版が取り込まれるところまでは確かめていない。確かめるには、自動更新が確実に働く構成で 1 度は更新が降ることを先に示す必要がある（それが無ければ、降らなかったことと観測できなかったことを区別できない）
- **`env.FORCE_AUTOUPDATE_PLUGINS` が実際に効くか**（§3.6）。本体の自動更新を抑止している端末でプラグインの更新だけを生かす保険として入れているが、**そのような端末が社内に実在するかも確認していない**。実在しないか、効かないことが分かれば `POLICY` から外す
- **git リモートを `source` としたマーケットプレイスの更新の伝播**（§8.5）。自動更新を有効にしたうえで、push から端末に届くまでに何が必要か

次の 7 つは、壊れても検知できるか、後から直せる。**実装時に確認するにとどめ、起きる前提での対処は設計に持たない。**

- **`COUNT(DISTINCT event_id)` の年間規模での実行時間**（§5.4）。被覆インデックスによる完結を前提にしているが、実データでの確認は行っていない
- **MySQL 接続時の DDL 適用**。インデックスの存在確認分岐と列の突き合わせ（§4.3）を含め、両 DB での初期化は実機で確認する
- **接続先 MySQL の `sql_require_primary_key` の値**（§5.5）。有効なら主キーなしテーブルの作成が拒否される
- **Ingress がサブパスを剥がすか剥がさないか**（§4.3）。`SCRIPT_NAME` の与え方に関わる
- **端末の Python の可用性**（§1.2）。全端末で `python3` が PATH から解決できるか
- **実行基盤上でのサーバの起動時間**。依存 3 パッケージの install を含めた所要時間は未計測。基盤がアイドル時にコンテナを停止するかどうかも合わせて確認する（§3.5 の送信タイムアウトの妥当性がこれで決まる）
