# 実測値

将来スケールを見積もるときの材料。**測定条件から外れた数字を外挿しない。**

## SQLite

測定条件: SQLite 3.51.0（Python 3 標準の `sqlite3`）／ macOS (Darwin 25.6.0) ／
19 列・**200 万行**（40 日 × 5 万行/日）／利用者 140 名・`skill_name` は 9 割 NULL ／
一様乱数のダミーデータ ／ 各クエリ 3 回実行の最小値。

### 投入と索引の作成

| 項目 | 実測 |
| --- | ---: |
| 200 万行の INSERT | 49.8 s |
| DB サイズ（索引なし） | 392 MiB |
| 索引 4 本の作成 | 73.8 s |
| DB サイズ（索引込み） | 857 MiB |

1 行あたり約 450 バイト（索引込み）。**年間 1,500 万行なら 6 GiB を超える**見積もり。

### クエリ所要時間（窓 30 日 = 150 万行、ミリ秒）

| クエリ | 索引なし | 索引あり | 索引あり + `ANALYZE` |
| --- | ---: | ---: | ---: |
| 1 日 件数 | 688.8 | 41.9 | 39.4 |
| 30 日 件数（日次推移） | 3,580.9 | 1,268.6 | **1,239.7** |
| 30 日 利用者数 | 2,383.5 | 166.9 | **8.3** |
| 30 日 スキル別 | 2,375.3 | 4,838.0 | **407.3** |
| 30 日 ツール分布 | 1,799.7 | 4,766.9 | **369.7** |
| 30 日 コンテキスト分布 | 1,215.3 | 198.8 | 180.2 |
| 全期間 40 日 件数（`GROUP BY` 無し） | 5,497.5 | 4,318.7 | 5,192.1 |

**`ANALYZE` を実行していないと、`skill_name` / `tool_name` を先頭列に持つ索引が選ばれず、
索引が無い場合より約 2 倍遅い。** 先頭列が `WHERE` の範囲条件に現れないため、
SQLite は統計情報なしに skip-scan の可否を判断できない。

### 窓サイズに対する伸び（索引あり + `ANALYZE`）

| 窓（日） | 行数 | `GROUP BY day` 付き | `GROUP BY` 無し |
| ---: | ---: | ---: | ---: |
| 1 | 50,000 | 33.1 ms | 34.5 ms |
| 5 | 250,000 | 175.2 ms | 198.7 ms |
| 10 | 500,000 | 338.8 ms | 492.6 ms |
| 20 | 1,000,000 | 737.1 ms | 1,272.9 ms |
| 30 | 1,500,000 | 1,055.2 ms | 1,829.4 ms |
| 40 | 2,000,000 | 1,459.0 ms | 3,744.1 ms |

`GROUP BY day` 付きは行数にほぼ線形（約 0.73 µs/行）。
**`GROUP BY` 無しの単一集計は線形以上に悪化する**（1 行あたり 0.69 → 1.87 µs）。

**測定の範囲外**: 200 万行を超える規模は未測定。窓のクエリは窓の行数で決まるが、
テーブル全体が大きくなったときの B-tree の深さの増分は未測定である
（影響は小さいと見られるが**推測**）。実データの偏り（特定利用者への集中など）も反映していない。

## MySQL

測定条件: MySQL 8.4.11（公式 Docker イメージ `mysql:8.4`）／ Colima ／ `mysql` CLI 経由。

| 項目 | 実測 |
| --- | --- |
| 既定の `sql_mode` | `ONLY_FULL_GROUP_BY, STRICT_TRANS_TABLES, NO_ZERO_IN_DATE, NO_ZERO_DATE, ERROR_FOR_DIVISION_BY_ZERO, NO_ENGINE_SUBSTITUTION` |
| 既定の `sql_require_primary_key` | `0` |
| `CREATE INDEX IF NOT EXISTS` | **8.4 でも存在しない**（`ERROR 1064`）。同名の再作成は `ERROR 1061` |
| 既存索引の確認 | `SHOW INDEX FROM <table>` の `Key_name` 列で取れる |
| 実テーブルの列の確認 | `SHOW COLUMNS FROM <table>` で取れる |
| `sql_require_primary_key=ON` | 主キーなしの `CREATE TABLE` は `ERROR 3750` で拒否。**既存テーブルへの `INSERT` は通る** |
| strict モードでの桁超過 | `ERROR 1406` で**拒否**（切り詰めではない） |
| 非 strict での桁超過 | 64 文字に切り詰め + `Warning 1265`。アプリが拾わなければ表に出ない |
| 複数行 INSERT の部分失敗 | **1 行でも桁を超えると、そのステートメントの全行が入らない**（3 行中 2 行目が超過 → 0 行） |
| SQLite との非対称 | **SQLite は `VARCHAR(n)` の桁を一切強制しない**（100 文字がそのまま入る）。同じデータが SQLite では入り MySQL では落ちる |

**測定の範囲外**: いずれも `mysql` CLI での確認であり、Python ドライバ経由（`executemany`）は未測定。
ドライバが複数行 INSERT をどう組み立てるかで、部分失敗の粒度は変わりうる。
8.0 系の挙動は**未確認**（`sql_require_primary_key` と `CREATE INDEX IF NOT EXISTS` は同じと見られるが**推測**）。
クエリ性能も未測定で、InnoDB の skip-scan の可否も `ANALYZE TABLE` の要否も SQLite とは別問題である。

## イベントスタディの偽の効果

測定条件: AI Gateway の日次 CSV（マスク済み、aws-bedrock、53 日・150 名）。施策の無いデータに、
案内 3 回・7 日間隔・案内から 0〜3 日で導入という偽の準拠開始日を 900 通り割り当て、
`/effect` と同じ計算（相対日 ±14・0 日を除く・欠損日は 0）で前 14 日と後 14 日の平均を比べた。

| 項目 | 実測 |
| --- | ---: |
| 前後差（対照を引かない） | 中央値 −12.5% ／ 5 パーセンタイル −27.6% ／ 95 パーセンタイル +6.7% |
| 前後差（その暦日の全員平均を引く） | 中央値 +0.3% ／ 90% の範囲 ±17% |
| 1 人・1 日あたりコスト | 中央値 $2.7 ／ 90 パーセンタイル $25 ／ 上位 5 名でコストの 35〜37% |
| `Input Tokens` の Cache Read に対する比 | 約 1/166（`Input Tokens` は全行で `Uncached Input Tokens` と一致） |
