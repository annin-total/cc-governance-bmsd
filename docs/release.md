# リリース手順書

`governance/` を配布リポジトリ（`../cc-marketplace-governance-bmsd`）へ差し込み、社内マーケットプレイスとして配布する手順である。手順は上から順に実行すれば終わる。判断の余地は残さない。

## 概要

- 差し込みと検査は `scripts/release.sh` が 1 本で行う。差し込みに続けて検査が走る
- スクリプトはコミットも push もしない。差し込みと検査が終わった状態で止まるので、その後は人がコミットする
- 配布リポジトリ側（`plugins/governance/` 配下）は手で編集しない。変更は必ず開発リポジトリの `governance/` に対して行う

## 1. 前提

- 開発リポジトリの変更が `main` にマージ済みであること
- `pytest -q tests` が通っていること

初回リリース前に必ず行う手順が 1 つある。

- **`governance/config.json` の `ingest_url` と `ingest_token` を埋める。** どちらも空のままでは、`scripts/release.sh` の検査 7（送信先が埋まっている）が必ず止める。値の埋め方は本書の「4. 確認項目」を参照する

## 2. `version` を上げる

`governance/.claude-plugin/plugin.json` の `version` を上げる。**`version` を書く場所はここ 1 か所だけである。**

`version` は端末側が更新の要否を判断する唯一の手がかりである。中身を変えて `version` を上げ忘れると、変更は端末に届かないまま「届いたことになる」。上げ忘れは `scripts/release.sh` の検査 5 が検出する。

## 3. 差し込んで検査する

```
scripts/release.sh
```

配布リポジトリの既定パス（`../cc-marketplace-governance-bmsd`）以外へ差し込む場合は、パスを引数で渡す。

差し込みに続けて次の検査が順に走る。1 つでも `[NG]` が出たら、その場でリリースを中止する。**検査だけを飛ばす手段は用意しない。**

1. 混入なし（テスト・生成物・`requirements*.txt` 等が配布物に無いこと）
2. 必須ファイルあり
3. 開発リポジトリと一致（差し込み漏れ・差し込み過剰・配布リポジトリの `.gitignore` による無視がないこと）
4. 名前の一致
5. `version` の引き上げ忘れがないこと
6. `POLICY` からキーが削除されていないこと
7. 送信先が埋まっている

配布リポジトリ側を手で編集しない。差し込みと検査の結果に不満があれば、開発リポジトリの `governance/` を直し、もう一度この手順を実行する。

## 4. 確認項目

- `POLICY` からキーを削除していない（検査 6 が見るが、意図としても確認する）
- `config.json` の送信先 URL が、デプロイ済みのサーバの URL と一致している
- `config.json` の受信トークンが、サーバの Secret ファイルの `INGEST_TOKEN` と一致している。**一致していなければ全端末の送信が 401 で跳ね返り続ける。** 端末は spool を保持するのでイベントは失われないが、誰も気づかないまま溜まる
- 受信トークンが平文でリポジトリに入ることは設計上の前提である。**機密防御ではなく誤送信の防止のために置く。** 到達制御はネットワーク境界が担う
- トークンを入れ替える場合は、サーバ側の Secret ファイルの更新と同一のリリースで行う。新旧どちらでも通る期間を作る手段は無く、入れ替えの間の 401 は端末の spool が吸収する

## 5. PR を作りマージする

配布リポジトリで PR を作る。マージされた時点で配布される。

## 6. 届いたことを確認する

数日後に概況画面の健全性の行で `plugin_version` の分布を見る。**この列が表すのはセッションを開始した時点の版である。** 長く開いたままのセッションは古い版を報告し続ける。更新の直後に新旧の版が混じること自体は異常ではない。**古い版が何日も残り続けることが、配布の届いていない端末の印である。**

ローカルディレクトリを `source` にしたマーケットプレイスでの検証では、次のことが分かっている。

- push から端末が取り込むまでに約 15 分の遅れがある。反映されるのは次に起動したセッションからであり、起動して即座に版が変わることは期待しない
- 確認の手順は「起動 → 15 分以上の待機 → 終了 → 次のセッションを開始 → `claude plugin list` の `version` を見る」の形になる
- 15 分待っても上がらない場合は、手動更新の 2 段階（`claude plugin marketplace update <名前>` でカタログを更新し、`claude plugin update <プラグイン名>` で本体を上げる）を行う
- 社内リポジトリを `source` にした場合の伝播はこの限りではなく、別途確認する

## 7. 誤った設定値を配ってしまったときの手順

`POLICY` からキーを削除する操作は、**誤った値を全端末に固定する操作である。** 適用処理が持つのは上書きだけであり、撤回は定義されていない。届かなくなるのは正しい値の方であり、既に書き込まれた誤った値は端末に残り続ける。

- `POLICY` に正しい値を書く。施策をやめる場合は Claude Code の既定値を書く
- `version` を上げて配り直す
- **即時の撤回手段は存在しない。** 全端末に行き渡るまで数日かかる
- `POLICY` からキーを削除する操作は検査 6 が止める。値を変えることは正規の操作であり、検査は通す

## 8. 列を足したとき

契約（`governance/hooks/contract.py`）に列を足すリリースでは、サーバ側のテーブル作り直し手順を先に済ませる。**順序を誤るとサーバが起動しない。**
