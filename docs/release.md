# リリース手順書

`governance/` を配布リポジトリ（`../cc-marketplace-governance-bmsd`）へ差し込み、社内マーケットプレイスとして配布する手順である。手順は上から順に実行すれば終わる。判断の余地は残さない。

## 概要

- 差し込みは手で行う。開発リポジトリでプラグインを検証 → `governance/` を配布リポジトリへ手でコピー → 配布リポジトリでマーケットプレイスを検証 → PR → マージ、の順で進める
- 2 本の検証スクリプト（`scripts/validate_plugin.py` と配布リポジトリの `scripts/validate.py`）は、いずれも Claude Code のプラグイン／マーケットプレイスとしての**形式**だけを見る。ファイルを作成・削除・変更することはない。標準ライブラリだけで動き、`python3` / `python` のどちらでも、macOS / Windows のどちらでも実行できる
- 配布リポジトリ側（`plugins/governance/` 配下）は手で編集しない。変更は必ず開発リポジトリの `governance/` に対して行う

## 1. 前提

- 開発リポジトリの変更が `main` にマージ済みであること
- `pytest -q tests` が通っていること

初回リリース前に必ず行う手順が 1 つある。

- **`governance/config.json` の `ingest_url` と `ingest_token` を埋める。** 空のまま配ると、端末は 1 件も送信しないまま「導入済み」に見える。
  **検証スクリプトはこれを見ない。**値が正しいかどうかは形式では判定できないため、人が確かめるほかない。値の埋め方は本書の「6. 確認項目」を参照する

## 2. `version` を上げる

`governance/.claude-plugin/plugin.json` の `version` を上げる。**`version` を書く場所はここ 1 か所だけである。**

`version` は端末側が更新の要否を判断する唯一の手がかりである。中身を変えて `version` を上げ忘れると、変更は端末に届かないまま「届いたことになる」。

**上げ忘れを検出する仕組みは無い。**手順 6 の確認項目で必ず人が確かめる。

## 3. プラグインを検証する（開発リポジトリ）

差し込む前に、開発リポジトリ側で `governance/` を検証する。

```
python scripts/validate_plugin.py
```

`[NG]` が 1 つでも出たら、差し込む前に `governance/` を直す。このスクリプトが見るのはプラグインとしての形式（`plugin.json` の必須項目、JSON・Python の構文、`hooks.json` が参照するファイルの実在、開発用ファイルの混入なし、git に無視されているファイルが無いこと）だけである。`config.json` の値や `POLICY` の中身は見ないので、「6. 確認項目」で別途手で確認する。

## 4. 配布リポジトリへコピーする

`governance/` を配布リポジトリの `plugins/governance/` へ手でコピーする（既存の内容を上書きする）。配布リポジトリ側を先に・後に手で編集しない。

## 5. マーケットプレイスを検証する（配布リポジトリ）

コピーしたら、配布リポジトリ側で `scripts/validate.py` を実行する。

```
cd ../cc-marketplace-governance-bmsd
python scripts/validate.py
```

`[NG]` が 1 つでも出たら、コミットする前に開発リポジトリの `governance/` を直し、もう一度「3. プラグインを検証する」からやり直す。このスクリプトも形式だけを見る（`marketplace.json` の整合性、収録プラグインの `plugin.json` の名前一致、JSON の構文、開発用ファイルの混入なし、git に無視されているファイルが無いこと）。

## 6. 確認項目

- **`version` を上げた。**上げ忘れを検出する仕組みは無い。ここで人が確かめる
- **`POLICY` からキーを削除していない。**削除を検出する仕組みは無い。ここで人が確かめる
- `config.json` の送信先 URL が、デプロイ済みのサーバの URL と一致している
- `config.json` の受信トークンが、サーバの Secret ファイルの `INGEST_TOKEN` と一致している。**一致していなければ全端末の送信が 401 で跳ね返り続ける。** 端末は spool を保持するのでイベントは失われないが、誰も気づかないまま溜まる
- 受信トークンが平文でリポジトリに入ることは設計上の前提である。**機密防御ではなく誤送信の防止のために置く。** 到達制御はネットワーク境界が担う
- トークンを入れ替える場合は、サーバ側の Secret ファイルの更新と同一のリリースで行う。新旧どちらでも通る期間を作る手段は無く、入れ替えの間の 401 は端末の spool が吸収する

## 7. PR を作りマージする

配布リポジトリで PR を作る。マージされた時点で配布される。

## 8. 届いたことを確認する

数日後に概況画面の健全性の行で `plugin_version` の分布を見る。**この列が表すのはセッションを開始した時点の版である。** 長く開いたままのセッションは古い版を報告し続ける。更新の直後に新旧の版が混じること自体は異常ではない。**古い版が何日も残り続けることが、配布の届いていない端末の印である。**

ローカルディレクトリを `source` にしたマーケットプレイスでの検証では、次のことが分かっている。

- push から端末が取り込むまでに約 15 分の遅れがある。反映されるのは次に起動したセッションからであり、起動して即座に版が変わることは期待しない
- 確認の手順は「起動 → 15 分以上の待機 → 終了 → 次のセッションを開始 → `claude plugin list` の `version` を見る」の形になる
- 15 分待っても上がらない場合は、手動更新の 2 段階（`claude plugin marketplace update <名前>` でカタログを更新し、`claude plugin update <プラグイン名>` で本体を上げる）を行う
- 社内リポジトリを `source` にした場合の伝播はこの限りではなく、別途確認する

## 9. 誤った設定値を配ってしまったときの手順

`POLICY` からキーを削除する操作は、**誤った値を全端末に固定する操作である。** 適用処理が持つのは上書きだけであり、撤回は定義されていない。届かなくなるのは正しい値の方であり、既に書き込まれた誤った値は端末に残り続ける。

- `POLICY` に正しい値を書く。施策をやめる場合は Claude Code の既定値を書く
- `version` を上げて配り直す
- **即時の撤回手段は存在しない。** 全端末に行き渡るまで数日かかる
- **`POLICY` からキーを削除してはならない。**削除は誤った値を全端末に固定する操作である。適用処理は上書きだけを持ち、撤回を持たない。値を変えることは正規の操作である

## 10. 列を足したとき

契約（`governance/hooks/contract.py`）に列を足すリリースでは、サーバ側のテーブル作り直し手順を先に済ませる。**順序を誤るとサーバが起動しない。**
