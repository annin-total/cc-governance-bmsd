# cc-governance-bmsd 仕様書

## 概要

社内（約 140 名）で使う Claude Code について、次の 2 つを同時に実現する仕組みである。

1. **ルールを行き渡らせる** — 決めた設定値を全員の端末に自動で反映し、お知らせを届ける
2. **効果を測る** — そのルールが実際にコストや使い方を変えたかを、数字で確かめる

仕組みは 3 つの部品でできている。

- **端末プラグイン** — 各自の Claude Code に入る追加機能。設定を反映し、お知らせを表示し、
  「どの機能をいつ使ったか」という記録を集計サーバへ送る。会話の中身は読まない・送らない
- **集計サーバ** — 端末から届いた記録と、AI Gateway が日ごとに出すコストの CSV を突き合わせ、
  管理者向けの画面（4 枚）に表示する
- **AI Gateway の日次 CSV** — コストとトークン数の正本。コストは端末側では数えない

ルールの配布は git、記録の収集は HTTP という別々の経路で行う。サーバから端末へ指示を出す
経路は無いため、**サーバが止まってもルールの配布は止まらない。**止まるのは測定だけで、
送れなかった記録は端末に残り（上限は 7 日分・5MB）、後から送られる。

範囲に含めないもの。

- 会話本文・プロンプト本文の保持・送信・記録
- 利用者個人の監視。目的は施策の評価である
- リアルタイム性。反映は分単位、コストは日次

## 構成

| 要素 | 実体 | 責務 |
| --- | --- | --- |
| 端末プラグイン | `plugin/`（配布名 `governance`。マーケットプレイスの git 経由で配布） | 設定の自動適用・お知らせ表示・利用イベントの収集と送信 |
| 集計サーバ | `server/`（submodule。単独でデプロイする 1 プロセス） | 受信・保存・集計・管理画面・CSV 取込 |
| マーケットプレイス | `cc-marketplace-governance-bmsd`（別リポジトリ） | 完成したプラグインを差し込む配布用の箱 |

このリポジトリ（`cc-governance-bmsd`）は統合開発環境であり、プラグインのソース・統合テスト・
横断ドキュメント・契約の正本を持つ。サーバの実行環境の制約（Python 3.9・ポート 5000・
サブパス配下での公開・永続領域 `/mnt/data/cc-governance-server/`）は `../guide/deploy-aip.md` にある。

```
[管理者] ─ git push（設定値・お知らせ・配布物）
   ▼
[マーケットプレイスの git リポジトリ] ─ プラグインの自動更新
   ▼
[端末の Claude Code]
   ├ SessionStart hook : 設定を適用し、適用前後の値を記録 / 未読のお知らせを表示
   └ 各種 hook         : 契約に定義されたキーだけを抜き出してローカルに溜める
   │ HTTP POST /ingest（まとめて・切り離したプロセスから）
   ▼
[集計サーバ] ◀─ 画面の取込ボタン ─ AI Gateway 日次 CSV（手動配置）
   ▼
[管理者]（管理画面）
```

サーバをガバナンス用とログ用に分けないのは、効果測定が「設定の適用状況 × 日次コスト」の
突き合わせだからである。分けるとプロセスをまたいだ結合が要る。受信が画面の応答を圧迫した
場合は、同じコード・同じ DB を指す 2 個目のプロセスへ `/ingest` だけを振り分けて分離できる。

## 契約（端末とサーバで共有する定義）

収集項目（`HOOK_FIELDS` / `EXTRA_COLUMNS`）・policy イベントの列（`POLICY_COLUMNS`）・
CSV 列（`CSV_COLUMNS`）の定義は、**`plugin/hooks/contract.py` ただ 1 ファイルが正本である。**
端末の抽出処理、サーバの DDL・INSERT・受信時の検査・起動時の列の突き合わせは、すべて
ここから導出する。配る設定値（標準設定）は変わりやすいため `plugin/hooks/policy.py` に分け、
こちらが正本になる。どちらもほかの場所で複製や再定義をしない。

- 端末には、プラグインの一部としてそのまま配布される
- サーバには、正本に生成物ヘッダを付けた複製（`server/contract.py` / `server/policy.py`）と
  ハッシュ記録（`server/contract.sha256` / `server/policy.sha256`）を置く。どちらも `scripts/sync_contract.py` が正本から生成し、
  `--check` で一致を検証する。起動時の検査は `server.md` にある
- `HOOK_FIELDS` は挙動を切り替える設定ではなく「どのキーパスがどの列になるか」という
  事実である。これを読んで動作を分岐させるコードは置かない
- **契約は追加のみで変える。**列の改名・型変更は、端末とサーバのどちらでもエラーにならず、
  値が黙って捨てられるか NULL になる

横断的な不変条件は `../../CLAUDE.md` の Design、サーバ固有の規約は `server/CLAUDE.md` にある。

## 上流仕様の変化への備え

どの変化でも Claude Code の動作は妨げられない。問題はすべて「静かに欠測する」形で現れる。

| 上流の変化 | 起きること |
| --- | --- |
| hook 入力のキーが増える / hook の種類が増える | 何も起きない（取らない） |
| キーが改名・消滅する | その列が以後 NULL になる |
| hook の入力形式が変わる | 収集が例外で止まり、イベントが来なくなる |
| transcript の `usage` 構造が変わる | `context_tokens` が NULL になる |
| 設定キー名・環境変数名が変わる | 書き込みは成功するが効かず、次のセッションの `prev_value` に現れない |
| プラグインの更新が届かなくなる | 古い版のまま施策が固定される |
| CSV に列が増える | 知らない列を捨てる |

欠測は管理画面の概況にある「健全性」の行で気づく。イベント件数の急落は収集の停止、特定列の
NULL 率が 100% に跳ねるのはキーの改名・消滅、準拠率の急落は設定キーの変化や上位設定による
上書き、突合率の低下は `user_email` と CSV の不一致、古い `plugin_version` の残留は配布の
未達を示す。

人手で追随する箇所は 3 つだけである。`contract.py` の `HOOK_FIELDS`（hook 入力の
キーパスの改名時）と `CSV_COLUMNS`（CSV のヘッダ名の変更時）、`policy.py`（設定キー名の
変更時・施策の変更時）。
