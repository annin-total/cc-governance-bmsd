# 導入案内と段階的な展開

利用者への導入案内の雛形と、案内を 2〜3 群に分けて日付をずらす設計を記す
（`../spec/server.md` §5.2 / `cc-marketplace-governance-bmsd/README.md`）。

## 1. 導入前の前提条件（Windows 端末）

案内を送る前に、対象者に次を確認してもらう。

`hooks.json` は `python3 "${CLAUDE_PLUGIN_ROOT}/hooks/..."` の形でコマンドを登録している。Windows の python.org 版インストーラは `python.exe` と `py.exe` のみを作り、**`python3.exe` を作らない**。`python3` が PATH から解決できない端末では、収集も設定の適用も一切動かない。

hook は例外を握り潰して常に成功するフェイルオープン設計のため、**`python3` が無くても利用者の画面には何も異常が出ない。** 導入したつもりのまま何も収集されない状態になりうるため、この確認は導入手順の一部であり、後回しにできない。

- ターミナルで `python3 --version` が応答することを、導入前に確認する
- 応答しない Windows 端末では、次のいずれかで対処する
  - Microsoft Store 版の Python を入れる（`python3` が使えるようになる）
  - `python3` という名前で `python` を呼ぶシムを PATH に置く
- **確認できない場合は導入を進めず、情報システム部門に連絡する**

## 2. 案内文の雛形

以下は利用者へそのまま送れる文面の雛形である。`<...>` の箇所を差し込んで使う。

---

**件名: Claude Code ガバナンスプラグインの導入について**

お疲れ様です。Claude Code の利用状況の把握と設定の一元管理のため、社内配布のプラグインを導入してください。

**事前確認（Windows 端末のみ）**

ターミナルで次を実行し、応答することを確認してください。

```
python3 --version
```

応答しない場合は、導入を進めずに `<連絡先>` へご連絡ください。

**導入手順**

1. マーケットプレイスを登録する

   ```
   /plugin marketplace add <社内リポジトリの https URL>
   ```

2. プラグインを導入する

   ```
   /plugin install governance@cc-marketplace-governance-bmsd
   ```

導入後、最初にセッションを開始したタイミング（SessionStart）で、設定の適用とお知らせの表示が自動的に行われます。追加の操作は不要です。お知らせによっては、関連ページが既定のブラウザで自動的に開きます（対話セッションでのみ、1 回だけ）。

**導入できたことの確認**

次の順に確認してください。

1. `python3 --version` が応答する
2. マーケットプレイスを登録する（上記 1）
3. プラグインを導入する（上記 2）
4. `/plugin` の一覧に `governance` が版番号つきで現れる
5. セッションを開き直し、お知らせが表示されることを確認する

設定ファイルに記載があるだけでは導入が完了しないことがあるため、4 の一覧表示までを確認の対象とする。5 は、設定の適用処理（SessionStart hook）が実際に動いたことを利用者自身が確認できる唯一の手がかりであるため、必ず行ってください。

**収集する項目**

Claude Code の利用状況（利用日時・利用したツールの種別・セッションの単位・コンテキスト使用量・導入している設定の値など）を収集します。

**収集しない項目**

プロンプトの本文、ツールの応答内容、会話の内容は一切収集しません。収集するのは利用状況の項目のみです。

**自動更新が働かない場合の手動更新手順**

社外のマーケットプレイスは既定で自動更新が無効です。通常は設定により自動更新が有効化されますが、環境によってはこの設定が届かず、手動での更新が必要になることがあります。その場合は次の 2 段階を両方行ってください（片方だけでは更新されません）。

```
claude plugin marketplace update cc-marketplace-governance-bmsd
```

このコマンドはカタログの情報を更新するだけで、導入済みのプラグイン本体は上がりません。続けて次を実行してください。

```
claude plugin update governance
```

## 3. 未導入の検知

案内を送った後、`/policy` の未導入者一覧（`cost_daily` に居るが `policy_state` に 1 行も無い利用者）を確認する。`python3` が解決できない Windows 端末は、hook が一度も実行されないため必ずここに現れる。

一覧に残っている利用者には、案内メールが届いていないか、上記 1 の前提条件で止まっているかのいずれかであるため、個別に声をかけて状況を確認する。この運用は案内を送るたびに繰り返す。

## 4. 段階的な案内の設計

全員に同時に案内すると、準拠開始日が数日に固まり、相対日がほぼ暦日と一致する。すると同時期に起きた他のすべて（モデルの変更・料金改定・繁忙期・社内アナウンス）が施策の効果として計上され、効果測定が成立しなくなる。**ばらつきは待つものではなく、作るものである。** 配布の仕掛けは変えず、案内する日をずらすことでこれを作る。

- **群は 2〜3 とする。** 1〜2 週間ずらして案内する
- **群は部署を横断して作る。** 部署ごとに群を作ると、部署の業務差が群差と区別できなくなる。同一部署の人が別々の群に入るように割り当てる
- 群ごとの人数は大きく偏らせない
- 案内日を決めたら**前倒し・後ろ倒しをしない**。ずれた場合は、予定日ではなく実際に出した日を下記の記録欄に残す

群分けそのものに特別な仕掛けは要らない。案内する相手と日付を分けるだけでよい。

## 5. 記録欄

**案内した日付だけ**を記録する。個人を特定する情報（誰がどの群かの名簿）は記録しない。イベントスタディの基準になる準拠開始日は `policy_state` から求まり、群の記録は使わない。個人単位の名簿は異動と入退社で古くなる保守対象を増やすだけで、それによって除ける交絡は無い。

案内を出した時点で記入し、**後から書き換えない**。書き換えると、事後に都合のよい群分けを作れてしまう。前倒し・後ろ倒しをした場合は、予定日ではなく実際に出した日を書く。

## 6. 効果測定を読むときの注意

ずらしが効いたかどうかは、案内の後に `/policy` の準拠開始日の分布で確かめる。分布に群の数と同じだけの山が立っていれば成功、1 つの山に潰れていれば失敗である。失敗した場合、相対日は暦日とほぼ一致し、`/effect` が示す効果は同時期に起きた他の変化と区別できない。

また、案内日を記録しても、実際に導入するかどうかは利用者が決めるため、**自己選択バイアスは残る。** 案内を受け取った人の中で早く導入する人と遅く導入する人が入れ替わりに存在すること自体は制御できない。この段階的案内が作るのは「案内日」のばらつきであり、「導入の意思」のばらつきではない。
