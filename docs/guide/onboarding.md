# 導入案内と段階的な展開

利用者へ送る導入案内の雛形と、案内を 2〜3 回に分けて日付をずらす進め方を記す。

## 1. 案内を送る前に（Windows 端末）

プラグインは `python3` というコマンドで動く。Windows の標準的な Python のインストーラでは、この名前のコマンドが入らないことがある。**入っていなくても画面にはエラーが出ず、導入したつもりのまま何も動かない。**そのため、次の確認は導入手順の一部であり、省略できない。

- ターミナルで `python3 --version` が応答することを確認してもらう
- 応答しない場合は、Microsoft Store 版の Python を入れると使えるようになる
- **確認できない場合は導入を進めず、情報システム部門に連絡する**

## 2. 案内文の雛形

利用者へそのまま送れる文面である。`<...>` の箇所を差し込んで使う。

---

**件名: Claude Code ガバナンスプラグインの導入について**

お疲れ様です。Claude Code の利用状況の把握と設定の一元管理のため、社内配布のプラグインを導入してください。

**事前確認（Windows 端末のみ）**

ターミナルで次を実行し、応答することを確認してください。応答しない場合は、導入を進めずに `<連絡先>` へご連絡ください。

```
python3 --version
```

**送信に使うメールアドレスの確認**

利用状況は会社のメールアドレスで AI Gateway の記録と突き合わせます。ターミナルで次を実行し、会社のメールアドレスが表示されることを確認してください。

```
git config --global user.email
```

何も表示されない・個人のアドレスが表示される・git が入っていない場合は、`~/.claude/settings.json` の `env` に `"CC_GOVERNANCE_USER_EMAIL": "<会社のメールアドレス>"` を書いてください。一致しないと、導入済みでも未導入として扱われます。

**導入手順**

Claude Code の中で、次の 2 つを順に実行してください。

```
/plugin marketplace add <社内リポジトリの git URL（https、末尾 .git）>
/plugin install governance@cc-marketplace-governance-bmsd
```

**導入できたことの確認**

1. `/plugin` の一覧に `governance` が版番号つきで現れることを確認してください
2. Claude Code を開き直し、お知らせが表示されることを確認してください。これが、プラグインが実際に動いたことを確かめられる唯一の手がかりです

**収集する項目**

Claude Code の利用状況（利用日時・利用したツールの種別・セッションの単位・コンテキストのトークン数・導入している設定の値など）を、会社のメールアドレスと端末名とともに収集します。収集した記録と AI Gateway の利用明細は、組織の名簿と照合して氏名・部署とともに表示します。管理者は利用者ごとのコスト・利用状況・設定の適用状況を画面で確認します。プロンプトの本文、ツールの応答内容、会話の内容は一切収集しません。

**更新が届かない場合**

通常は自動で更新されますが、環境によっては手動での更新が必要です。その場合は次の 2 つを両方実行してください（1 つ目だけでは更新されません）。

```
claude plugin marketplace update cc-marketplace-governance-bmsd
claude plugin update governance
```

**困ったときの連絡先**

`<連絡先>`

## 3. 導入していない人を見つける

案内を送った後、管理画面の設定の適用状況（`/policy`）の利用者ごとの適用状況で、状態が「未導入」の利用者を見る。AI Gateway の利用記録には現れるのに、どの端末からも直近に報告が届いていない人が並ぶ（CSV を取り込んでいる間だけ。`../spec/server.md`）。「案内を送る前に（Windows 端末）」の確認で止まっている Windows 端末も、その人のほかの端末から届いていなければここに現れる。

一覧に残っている人には、案内が届いていないか、事前確認で止まっているかのどちらかなので、個別に声をかける。案内を送るたびにこれを繰り返す。

## 4. 案内を分けて送る

全員に同じ日に案内すると、施策の効果と、同じ時期に起きた他の変化（モデルの変更・料金改定・繁忙期・社内アナウンスなど）が区別できなくなる。**案内する日をずらし、準拠開始日を散らす。**散らしても同じ時期の変化は打ち消されない。配布の仕組みは変えず、案内する相手と日付を分けるだけでよい。

- **2〜3 回に分け、1〜2 週間ずつずらす**
- **部署を横断して分ける。**同じ部署の人が別々の回に入るようにする。部署ごとに分けると、部署の業務の違いと区別できなくなる
- 各回の人数は大きく偏らせない
- 決めた案内日を前後させない。ずれた場合は、実際に送った日を記録する

## 5. 記録欄

**案内した日付だけ**を、送った時点で記入し、後から書き換えない。誰がどの回かの名簿は作らない（効果の測定には使わず、異動や入退社で古くなるだけである）。

## 6. 効果測定を読むときの注意

案内日はずらせても、実際にいつ導入するかは利用者が決める。早く導入する人と遅い人の違いは効果の数字に混ざったまま残る。

コストの前後差は施策の効果ではない（`../decisions/server.md` の「採らないと決めたこと」）。施策が効いたかは、セッションの大きさと自動コンパクトに達した割合が準拠の前後でずれたかで見る。
