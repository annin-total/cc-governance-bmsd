# 設計判断（サーバ）

**現在のコードがなぜそうなっているかの記録である。**
仕様書（`../spec/server.md`）が「何を作るか」を定めるのに対し、ここは「実装を読んでも理由が分からず、
善意で元に戻すと壊れるもの」と「採らないと決めたこと」だけを置く。
コードの docstring・コメントに理由が書かれているものは、ここに重ねて書かない。

参照規約は `../CLAUDE.md` に従う。
契約（`contract.py`）とプラグインに関する判断は `plugin.md` に置く。

## 1. アーキテクチャ上の判断

| # | 論点 | 採った案 | 採らなかった案と理由 |
| --- | --- | --- | --- |
| 1 | サーバの数 | **1 プロセス** | *ガバナンスとログで 2 分割* — 配信が git である以上ガバナンス側にサーバ機能がほぼ無く、効果測定は 3 テーブルの突合。分けるとプロセス間結合という要件にない問題が生まれる |

| 3 | 非同期 | **使わない（すべて同期）** | *非同期で書く* — DB ドライバが同期であるため速くならず、同期呼び出しの混入でイベントループを止める危険だけが増える |
| 4 | DB アクセス | **生 SQL + `queries_*.py` に集約** | *ORM* — 方言機能を使わない設計のため方言吸収の価値が無く、起動時の install が実費になり、レイヤが 1 段増える |
| 5 | MySQL / SQLite 両対応 | **方言が出る機能を使わない**（主キーなし・epoch INTEGER・UPSERT 不使用・JSON 不使用。主キーの例外はサーバ専用の `company_holidays` とサマリーの表だけで、理由は `server/CLAUDE.md` と「サマリーの表の行の識別」） | *方言ごとの DDL 2 本* — 同じ定義が 2 か所になる。*自動採番 id / 日時型 / UPSERT / JSON 列* — 方言が分岐し、分岐の数だけ検証対象が倍になる |

| 9 | 突合軸 | **`user_email × 日`** | *モデル軸を含む突合* — 表記揺れの名寄せ表という保守対象が生まれる |
| 10 | 集計の実行場所 | **SQL の `GROUP BY`** | *アプリ側での全走査* — 行数に線形なメモリと応答時間。アプリ側で行うのは、SQL で絞り込んだ行に対する処理（イベントスタディの畳み込み・準拠の判定・ビン分けなど）だけ |
| 11 | フロントエンド | **素の HTML + CSS** | *チャートライブラリ* — CDN 到達性が不明で、表と棒で判断には足りる |
| 12 | 監視 | **収集の状態の画面の表示**（受信・欠け・エラー・照合・利用明細の鮮度）。概況には利用明細の古さの警告だけを期間の表示の横に出す | *アラート・通知・定期実行の監視* — 見に行く画面に表示があれば気づける。*概況に届き具合の群を置く* — 概況はコストと利用の要点に絞り、同じ表示を 2 か所に置かない。利用明細の取り込み忘れは期間のページの数字を古くするため、警告だけは期間の表示の横に残す |

| 14 | コンテナ化 | **Dockerfile 1 枚** | *マニフェスト一式* — 現時点で不要。起動コマンドが同じなので移行時に書けばよい |
| 15 | 準拠率の分母 | **今日までの `POLICY_DAYS` 日に `cost_daily` に現れる利用者。`cost_daily` に行が 1 つも無いときだけ `policy_state` に現れる利用者**（窓を今日で切り、状態のページを今日の時点で数えることにそろえる） | *常に `policy_state` に現れる利用者* — 未導入者が分母から消え、「何%に適用済みか」に答えられない。*CSV が無ければ準拠率を出さない* — CSV は任意の補強であり、CSV が無くても画面が成り立つことを優先する。代わりに未導入者を含まないことを画面に注記する |

## 2. 実装

- **`create_app()` は呼ぶたびに `db.init()` を呼ぶ。** 起動時の契約との突き合わせがこの設計の関門であり、
  テスト用の遅延初期化フラグはそれを緩める。テスト側が接続先を設定してから `create_app()` を呼ぶ。
- **トークンの比較は両辺をバイト列にし、ヘッダは `latin-1`、環境変数は `utf-8`（surrogateescape）で符号化する。**
  WSGI はヘッダを latin-1 で、`os.environ` は utf-8 で復号するため、揃えると非 ASCII のトークン
  （全角文字や貼り付け由来の NBSP）が永久に一致しない。`str` 同士の `compare_digest` は非 ASCII で
  `TypeError` になる。Flask の `test_client()` は線上の符号化を経由しないためこの欠陥を検出できず、
  検査は WSGI 環境を直接組むか実サーバで行う。
- **ラッパがサブパスを除いた結果が空文字なら `/` に寄せる。** 公開サブパスそのものへのアクセスで Werkzeug が
  末尾スラッシュ付きへリダイレクトするのと、末尾スラッシュ付きの設定値での自己リダイレクトのループを防ぐ。
  ラッパは 1 個だけにする（増やすと前段のリバースプロキシがサブパスを除くかどうかに依存する分岐が生まれる）。
- **列の追加でテーブルを退避名に改名して作り直さない。** SQLite ではインデックスが元の名前のまま退避テーブルに
  残り、起動時の `CREATE INDEX` が名前の衝突で失敗し続ける。手作業の `ALTER TABLE ... ADD COLUMN` で足す。
- **SQL に `?` を含む文字列リテラル（`LIKE '%?%'` など）を書かない。** `db.q()` は方言分岐を
  `db.py` に閉じるため、リテラル中の `?` も MySQL のプレースホルダに置換する。
  これを強制する検査は持たない（SQL の構文解析が要り、目的と釣り合わない）。
- **集計の NULL を避ける。** AI Gateway の CSV は `Cost` が空のセルを含むため `SUM` は
  `COALESCE(..., 0)` で包む（NULL のままだと画面全体が 500 になる）。
- **本番の依存は推移的依存まで含めて `==` で固定する。** 毎起動 `pip install` が走る基盤では、
  固定しないと再起動だけで別の版が走る。`pip download --python-version` は環境マーカーを実行中の
  インタプリタで評価するため、3.9 でのみ要る `importlib-metadata` / `zipp` を静かに落とす。
  固定一覧を作り直すときはこの 2 つの欠落に注意する。

## 3. 受け入れている限界

- **同一の `ts` を持つ行のタイブレークが定義されていない。** 同着は同じ端末が 1 秒以内に 2 回書いた
  場合に限られ、値は実質同じ。定義するには全書き込み経路で単調増加する第 2 の整列キーの保証が要る。
- **版の分布は、参照キーの行を持たない端末を落とす。** ポリシーの全項目は同時に記録されるため運用では
  生じない。全項目を横断して数える形は集計が項目数に比例して重くなる。
- **コンテキストトークン数の分布は準拠者 1 人につき 1 クエリを発行する。** 1 本ごとの速さは、`user_email` を含む
  被覆インデックスで保っている。
  1 本にまとめるには利用者ごとの分位を DB 側で出す必要があり、方言差の出る構文に踏み込む。
- **送信者の名義（`user_email`）は端末の自己申告であり、受信トークンを持つ社員なら他人の名義で送れる。**
  トークンは誤送信の防止のためのもので、社内の利用者を相手に名義の真正性までは担保しない。
  記録から数える利用者ごとの値（利用状況など）も、この名義で氏名に結びつく。利用者ごとのコストは利用明細のメールアドレスで数えるため、この限界を受けない。
- **取り込み先に書き込めないときの文言に `CSV_DIR` の絶対パスが含まれ、そのまま画面に出る。** 画面は Basic 認証の内側にある。
  伏せると運用者が原因の場所を特定できない。
- **再起動すると、開いたままの画面からの POST は 403 になる。** CSRF のトークンが起動ごとに変わるためで、読み込み直せば通る。
  管理画面を複数のプロセスで動かすなら、プロセス間で共有するトークンが要る。
- **CSV が月の途中から始まる月は、その月の営業日あたりと見込みが小さく出て、翌月の見込みのカードの前月比が大きく出る。**
  経過営業日を月の初日から数えるためである。起きるのは CSV の最初の月とその翌月だけである。
- **準拠前のセッションの大きさは、初回展開では描けない。** 収集はプラグインの導入と同時に始まり、準拠開始日はその直後になるため、
  準拠前の行がほとんど無い。
- **`/` 概況は最も重い画面であり、`ANALYZE` では速くならない。** 健全性の表示が複数の列の NULL 率を独立に数えており、
  単一のインデックスで被覆しきれない。`ANALYZE` で縮まないことの根拠は `../knowledge/measurements.md` の SQLite の表の
  「全期間 40 日 件数（`GROUP BY` 無し）」の行である。所要は総量ではなく直近の行数で伸び、数秒級になる
  （`../knowledge/measurements.md` の「画面の応答時間（1 年分・200 名の合成データ）」）。

## 4. 採らないと決めたこと

- **群の割り当てを使った統計的な検定を行わない。** 効果測定の画面が出すのは相対日の傾きであり、因果効果ではない。
  利用者ごとのハッシュで施策の適用日をずらす案も採らない。利用者を 3 群に分けても、コストの偶然の揺れ
  （`../knowledge/measurements.md`）に埋もれる
- **コストの前後差を施策の効果として読まない。** `/effect` の前後差は暦日の変動を差し引いておらず、施策が無くても出る。
  暦日の全員平均を差し引いても ±17% 揺れ、この規模では効果を言えない（実測は `../knowledge/measurements.md`）。
  施策の作用は、セッションの大きさ（セッションごとの最大の中央値）と自動コンパクトに達した割合の前後で直接見る
- **負荷試験・スケールアウトを行わない。** SQLite 運用ではスケールアウトできない
- **会話の本文・セッション単位のタイムライン・リアルタイムの画面を作らない。** 分析の単位は利用者までとし（「利用者単位の分析」）、
  セッションの中で何をしたかの再現とリアルタイム性は範囲に含めない（`../spec/system.md`）
- **`/ingest` の行の検査を厳密にしない。** `event_id` がスカラ以外（dict など）の行は `event_id` が NULL のまま、
  `ts` が真偽値や `1` の行は 1970 年の行として保存される。本文の大きさの上限（`MAX_CONTENT_LENGTH`）も置かない。
  端末は契約どおりの値を送るのでこうした行が届く経路が無く、受信はトークンで守られている。
  大きさの上限は取込の経路にだけ掛ける。画面から受け取った CSV を共有の永続領域に書くためである

### 条件が変われば再検討すること

| 選択肢 | 何が変わるか | 再検討の条件 |
| --- | --- | --- |
| MySQL 側の `ANALYZE TABLE` と索引の見直し | SQLite では `ANALYZE` の有無で 10 倍以上の差が出た（`../knowledge/measurements.md`）。InnoDB では skip-scan の可否も統計の要否も別問題である | MySQL を本番に選び、画面が遅いと感じたとき |
| 量の対策（データの保持期間、古い生データの日次集計への圧縮など） | 年間 1,500 万行で DB は 6 GiB を超える見積もりである | ディスクが逼迫したとき、または集計期間で絞らない全期間の集計が遅くなったとき |
| `/ingest` を 2 個目のプロセスへ分ける | 同じコード・同じ DB を指す 2 個目のプロセスへ `/ingest` だけを振り分け、受信と画面の応答を切り離す | 受信が画面の応答を圧迫したとき |

SQLite の計測は `scripts/sqlite_bench.py` で測り直せる（表とインデックスはサーバの現在の定義を使う）。
