# 設計判断（プラグインと契約）

**現在のコードがなぜそうなっているかの記録である。**
仕様書（`../spec/system.md` / `../spec/plugin.md`）が「何を作るか」を定めるのに対し、
ここは「実装を読んでも理由が分からず、善意で元に戻すと壊れるもの」と「採らないと決めたこと」だけを置く。
コードの docstring・コメントに理由が書かれているものは、ここに重ねて書かない。

参照規約は `../CLAUDE.md` に従う。

契約（`plugin/hooks/contract.py`）とプラグイン（`plugin/`）の判断はここに、
サーバ（`server/`）の判断は `server.md` に置く。

---

## 1. アーキテクチャ上の判断

| # | 論点 | 採った案 | 採らなかった案と理由 |
| --- | --- | --- | --- |
| 1 | 受信 API の検査 | **契約から導出した検査** | *バリデーションライブラリ* — 列と型は契約が既に持っており、別の語彙で書き直すと正本が 2 か所になる。*画面の表示データにも型を置く* — 検査対象が増えるだけで、防げる誤りが無い |
| 2 | 準拠の記録 | **適用前後の値そのもの。判定は適用前の値** | *版番号だけ* — 60 と 80 を区別できない。*適用後の値だけ* — 直前に自分が書いた値なので全員が常に準拠になる |
| 3 | 施策の適用モード | **強制のみ** | *利用者が選択的に適用* — 準拠者と非準拠者の差が施策の効果か自己選択か区別できず、効果測定が成立しない |
| 4 | 通知の配信 | **`notices.json` を git で配り端末が表示** | *サーバのポーリング API* — サーバ停止で通知が止まる。配信の実体が git である前提に反する |
| 5 | 収集の抽出 | **キーパスを名指しで `get`** | *hook 入力を丸ごと保存して後で選別* — `tool_input` にプロンプト本文が入るため、上流が自由文キーを足した瞬間に流出する |
| 6 | hook 登録 | **画面が必要とする列の供給元だけ（`hooks.json`）** | *全 hook を網羅登録* — 種類が増え続けるため網羅は原理的に達成できず、維持コストだけが残る。*画面が必要とする列の供給元を登録しない* — その列を主題にした画面が恒久的に空になる |
| 7 | 送信 | **hook 内は追記のみ・送信は detach** | *hook 内で同期 POST* — 応答をネットワーク遅延でブロックする。体感を損なう施策は推進の妨げになる |
| 8 | 送信の信頼性 | **spool ファイル + 上限で破棄** | *ローカル DB + ACK + 再送制御* — 高い正確性が要求されていないのに、端末側に DB とトランザクション管理を持ち込む |
| 9 | `context_tokens` | **絶対値のみ** | *使用率* — モデルごとのコンテキストウィンドウのサイズ表が必要になり、モデルの増減が保守を呼ぶ |
| 10 | 値の解釈 | **生の文字列のまま保存** | *許可リスト・分類辞書* — 上流が新しい値を出した瞬間に取りこぼす。解釈は集計時に行えば十分 |
| 11 | 設定適用の失敗時 | **何もしない** | *壊れた settings.json を修復・再生成* — 利用者の設定を壊すリスクが、ポリシー適用の利益を上回る |
| 12 | 無効化スイッチの範囲 | **利用ログの収集とお知らせの表示のみ（URL を開くことも含む）。設定の適用と policy イベントの記録・送信（`SessionStart` での送信判定）は続け、`Stop` では送信しない** | *設定適用も止める* — 環境変数 1 つで施策から離脱でき、「強制のみ」が裏口から崩れる |
| 13 | サーバの統合 | **submodule** | *subtree・monorepo* — 版が固定されず、古いサーバと新しいプラグインの組み合わせが起きる。契約の複製が正本とずれても気づけない |

## 2. 端末プラグイン

- **`plugin/hooks/` に標準ライブラリと同名のファイルを置かない。** スクリプト起動では
  このディレクトリが `sys.path` の先頭に入るため、`queue.py` / `types.py` / `_queue.py` などが
  標準ライブラリを覆い、import が静かに壊れる。spool のモジュールが `_spool.py` なのはこのため。
- **spool の破棄は送信の後に行う。** 前に置くと、長期オフラインから復帰した端末の、単体で上限を超えた
  ファイルが一度も送られずに消える。分割送信は持たない。
- **送信の HTTP エラー応答は、1 回の送信につき状態コードごとに 1 行だけ error 行に積み、打ち切りの条件を持つ。**
  ファイルごとに積むと、失敗が続く間 error 行が送信の回数の二乗で増え、spool の上限（`config.json` の
  `spool_max_bytes`）に達して本物のイベントを押し出す。送信先か受信トークンの誤りを表す状態コード
  （`_sender.py` の `_HALT_STATUSES`）ではどのファイルも通らないので、その回を打ち切る。5xx は
  `_MAX_CONSECUTIVE_5XX` 回続いたら打ち切る。1 回で打ち切ると、そのファイルだけが 5xx になる
  毒ファイル 1 本で後続が止まり、打ち切らないとサーバの全体障害の間に全端末が全ファイルを送って
  負荷を増幅する。ほかのエラー応答（400・413 など）は
  ファイル固有の失敗とみなして次のファイルへ進む。
- **`sent_at` は送信の成否にかかわらず更新する。** 成否に連動させると、サーバ停止中に全端末が
  hook のたびに送信プロセスを起こし続ける。再送は spool が担い、`sent_at` は起動頻度の制御だけを担う。
- **`session_start.py` は `collect.main()` に委譲しない。** `collect.main()` は無効化スイッチで
  冒頭 return するため、委譲すると無効化した端末の policy イベントが送られず、その端末が
  準拠率の分母から消えて施策の効果が良く見える。
- **hook の失敗は、固定値の段名（`stage`）と例外クラス名（`error_type`）だけを error 行として送る。**
  例外メッセージ・トレースバックは、マスクして送る案も採らない。メッセージにはパスや値が混ざりうり、
  マスクの消し漏れに誰も気づけない。固定値とクラス名だけなら「契約が名指ししたものだけを収集する」
  原則に収まる。
- **`collect.py` は追加列を `raw_extra.get(name)` で引く。** 添字で引くと、契約に列を 1 つ
  足しただけで `KeyError` が入口の例外処理に飲まれ、「終了コード 0・キュー 0 行」の無言の全損になる。
- **`_settings.py` の一時ファイルは `settings.json` と同じディレクトリに作る。** 別ディレクトリだと、
  ホームが別ファイルシステムにある端末で `os.replace` がクロスデバイスになり、恒久的に書けない。
- **施策値の比較は型まで含める。** `1 == True` のため、素の `==` では `autoUpdate: 1` を準拠と誤認する。
  `ADD` / `REMOVE` の要素の比較も同じ。
- **policy イベントの `key_name` は `SET` だけ接頭辞を付けない。** 同じパスに `ADD` と `REMOVE` を
  並べると行が区別できないため接頭辞を付けるが、`SET` は記録済みの行と同じ key_name を保つ。
  列は増やさない（契約の列を増やすとサーバ側で `ALTER TABLE ... ADD COLUMN` の手作業が要る）。
- **`prev_value` はスカラ以外を NULL にする。** `env` などの dict を丸ごと送ると、利用者の
  トークンなどが載りうる。代償として dict 値の `SET` は `prev_value` で準拠を判定できない。
  管理者が書いた `value` は JSON 文字列にしてよい。
- **`ONCE` の記録と `value` は置換前の値で作る。** 置換後の値は端末ごとのパス（利用者名を含む）になり、
  記録が端末に依存し、サーバにも個人のパスが載る。
- **バックアップ・`ONCE` の記録・`statusline.js` は `<config_dir>/governance/` に置く。**
  `settings.json` から参照されるファイルがプラグインの削除で消えると、利用者のステータスラインが
  壊れる。バックアップも削除後に要る。バックアップに失敗したら書かない（戻せない書き込みをしない）。
- **Claude Code 本体の版は、自動更新を強制する設定の配布でそろえる。**
  - `claude update` を hook から実行しない。本体の書き換えを利用者の作業中に割り込ませることになり、
    自動更新を有効にしておけば本体が自ら取りに行くため、別の更新経路を持つ理由が無い。
  - managed settings では配らない。プラグインが書けるのは利用者の `settings.json` までであり、
    managed settings の配置は管理者権限の作業になる（再検討の条件は下の表）。
  - `DISABLE_AUTOUPDATER`・`DISABLE_UPDATES` はキーを消さずに `"0"` で上書きする。消すと利用者がシェルで
    export した値が生き残るが、settings の `env` は export に勝ち、`"0"` は無効化しないと読まれる
    （`../knowledge/claude-code-behavior.md`）。
  - 受け入れる限界: プロジェクトの settings の `env` は利用者の `env` に勝つので、プロジェクトで更新を無効化されると
    打ち消せない（優先順位は `../knowledge/claude-code-behavior.md`）。
- **`hooks.json` の起動コマンドは `python3` のままにする。** Windows の python.org 版には
  `python3.exe` が無いが、`hooks.json` に OS 条件は書けず、同じ hook の 2 重登録は並列実行で
  二重計上になり、パイプ・`;`・`&&` によるフォールバックは `../spec/plugin.md` が禁じている。
  導入の前提条件としての確認と検知は `../guide/onboarding.md` が扱う。
- **起動形態の判定（`_browser.py`）**
  - 対話判定は `CLAUDE_CODE_ENTRYPOINT == "cli"` の許可リストにする。この環境変数は未文書化で
    値が変わりうるため、変わったときに「開かない」側へ倒す。拒否リストでは未知の起動形態で本物のブラウザを開く。
  - 非対話判定は `sdk-` の接頭辞一致だけにする。VS Code 拡張などの値は未確認で、非対話に含めると
    既読にならず同じお知らせが出続ける。接頭辞一致なのは `sdk-ts` などの増加を個別列挙せずに拾うため。
- **ブラウザで開くのは未読の先頭 1 件だけ。** 初回導入時は過去のお知らせがまとめて未読になり、タブが一斉に開く。
- **macOS は `open` を detach 起動し、`webbrowser.open` を使わない。** `webbrowser.open` は
  osascript の完了を約 1.4 秒待つ（`../knowledge/measurements.md`）。
  macOS と Windows 以外では何もしない（利用者端末はこの 2 OS に限られ、未検証の起動方法を持ち込まない）。

## 3. 契約（`coerce`）

- **スカラ以外（dict / list）は `None` にする。** `str()` で文字列化すると、上流がキーパスの先を
  dict に変えたときに中身全部が宣言長まで載り、自由文の流出経路になる。欠測の方がはるかに良い。
- **整数は符号付き 64bit の範囲に収める。** 範囲外の 1 行が保存の段で例外になると、同じリクエストの
  正常な行まで失われ、その行が spool に残る限り端末のキューが永久に詰まる。契約に置けば全列が救われる。
- **符号化できない文字（孤立サロゲート）は行を捨てずに置換し、置換を切り詰めより前に行う。**
  `json.loads` を素通りし、保存の段でリクエスト全体を失わせるため。置換で文字数が変わりうるので順序が要る。
- **未知の型トークンでも例外を投げず `None` を返す。** 契約は端末に配布されるため、例外は
  「1 列が NULL」より悪い「イベント全件の欠落」になる。防御はテスト側の型トークン検査が担う。

## 4. 配布と検証

- **開発者が日常的に触るシェルスクリプトを置かない。** 開発環境に Windows がある。
  代償として、`version` の上げ忘れ・送信先の空・ポリシーからのキー削除を自動で検出する仕組みは無く、
  `../guide/release.md` の確認項目として人が見る。
- **検証スクリプトは Python で書き、外部コマンド（`find` / `grep` / `shasum`）を呼ばず、
  ファイル入出力は `encoding="utf-8"` を明示する。** Windows の既定は cp932 で、日本語を含むファイルで落ちる。
- **初回リリースの前に開発ツリーの `plugin/config.json` に本番の送信先を埋め、以後は開発ツリーに置いたままにし、
  検証の側で送信先を差し替える。**
  `plugin/` はそのまま配布物になり、`../guide/release.md` は開発ツリーと配布物の一致を確かめるため。
  埋める手順は同じ文書が持つ。検証は本番へ送らない: E2E は組み立てで送信先を空にし（送信のテストは
  ローカルの集計サーバへ向け直す）、`validate_plugin.py` は隔離した状態ディレクトリに送信済みの印を置いて
  送信プロセスを起動させず、`tests/` は複製した `config.json` の送信先を空にする。

## 5. 開発環境と検証の作法

- **実機確認は `HOME` ではなく `CLAUDE_CONFIG_DIR` で隔離する。** `HOME` を差し替えると認証が壊れる
  （`../knowledge/claude-code-behavior.md`）。この方式では利用者の他のプラグインも発火するため、
  本人の環境が汚れていないことは「このプラグインの痕跡（状態ディレクトリ・キュー・識別子の
  キャッシュ）が 1 件も無いこと」で判定する。
- **`session_start.py` は実 config ディレクトリで実行しない。** `settings.json` を書く。
  `collect.py` の書き込み先は状態ディレクトリの配下に閉じている。
- **開発依存に `jsonschema` を加える。** `policy.py` とその見本を適用した結果を、上流の
  settings.json のスキーマ（`tests/fixtures/` に保存）で検証するため。端末には配らない。
- **`ruff.toml` で `FA100` を無効にし、`docs/` を除外する。** py39 で `typing.Optional` を使うのは
  リポジトリ全体の方針で、`FA100` に従うと別のルールと衝突する。`# noqa` を散らさず設定に 1 回書く。
  `docs/` を除くのは、`ruff format` が Markdown 中の説明用コード断片まで整形するため。

## 6. 受け入れている限界

- **`policy.py` から消した項目は撤回されない。** 撤回は `SET` の `None` と `REMOVE` で明示的に配る。
  「前回配ったもの」を端末が覚えて自動で戻すには配布の履歴と到達確認が要り、「値を配るだけ」の配布を崩す。
- **切り詰めと置換が起きたこと自体は記録されない。** 長い値の列は集計上短い値に化け、復元できない。
  error 行が記録するのは段が例外で止まったことだけで、値を変えて続行した処理は対象にしない。
- **hook のタイムアウト（`hooks.json` の `timeout`）と状態ディレクトリの書き込み不可は、イベントを静かに失う。**
  「利用者の作業を止めない」設計の代償であり、`../spec/plugin.md` が取りこぼしを仕様として受け入れている。
  error 行も同じキューに書くため、この 2 つは error 行としても残らない。
  キュー自体は壊れない（`append` が単一 `write` のため）。直すには順序保証か別経路への退避が要り、
  「端末側はローカルのファイル操作のみ」という単純さと引き換えになる。
- **送信先 URL のスキームを検査しない。** `http://` にすると受信トークン（共有秘密）・`user_email`・`host` が
  平文で流れる。`ingest_url` に `https://` を設定する運用（`../guide/release.md` の確認項目）で防ぐ。
- **自動圧縮を早める施策（`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`）の効く範囲は、上流の仕様で限られる**（`../knowledge/claude-code-behavior.md`）。
- **案内日を記録しても自己選択バイアスは残る。** 導入するかは利用者が決めるため、早期導入者が
  もともとヘビーユーザーである可能性は消せない。消すには割り当てを管理者が決める必要がある。
- **2 つ目以降の施策は、案内日をずらせない。** 導入済みの端末には自動更新でほぼ一斉に届くため、
  前後比較のほかに材料が無い。

## 7. 採らないと決めたこと

- **配布物の署名・改ざん検知を持たない。**
- **OpenTelemetry を使わない。** 社内の OpenTelemetry はシステム管理部門が運用しており、当部署は使えない
  （AI Gateway の CSV はその出力である）。技術的には `settings.json` の `env` だけで有効になり、収集の大部分を
  置き換えられるが、送信先は 1 つしか持てない。端末に `OTEL_*` を配ると、全社の送信先を上書きするか、
  上位の設定に負けて当部署の収集が黙って空になる。

収集の範囲について次を採らない。何が取れるかは `../knowledge/` にある。

- **最高頻度帯の hook を増やさない。** `PreToolUse` が増やす情報は `PostToolUse` との差分だけで（権限で拒否された呼出が
  `PreToolUse` にだけ現れるかは未検証）、ツール呼出ごとのプロセス起動が倍になる代償に見合わない。
- **コンテキストトークン数を取る hook を増やさない。** `SessionEnd` の値は `Stop` の最終値と、
  `UserPromptSubmit` の値は前ターンの `Stop` の値と同じで、重複にしかならない。
- **コンテキストトークン数の取得元を transcript 末尾読取に一本化する。** 再開時のキーからも取れるが、
  同じ列に取得元が 2 つできる。再開後に 1 度でも応答すれば `Stop` で取れるため、失うのは応答の無いまま閉じた
  セッションの値だけである。再開時の値は末尾読取の検算にだけ使う。
- **サブエージェントの種別で層別しない。** 親子の分離は `agent_id` の有無で足りる。
- **`tool_input` から名指しで読むキーを増やさない。**
- 端末側に金額を持たない理由は `server.md`（トークン / コストの正本）にある。

### 条件が変われば再検討すること

いずれも今は採らない。**再検討の条件**を満たしたときだけ開く。

| 選択肢 | 何が変わるか | 再検討の条件 |
| --- | --- | --- |
| `env.FORCE_AUTOUPDATE_PLUGINS` | 本体の自動更新を抑止している端末でも、プラグインの更新だけを生かす | 本体の自動更新を抑止している端末が社内に実在し、かつその端末でプラグインの版が古いまま止まったとき |
| マネージド設定による配布 | 管理者が配る層（`managed-settings.json`）でマーケットプレイスと施策を配る | `~/.claude/settings.json` への書き込みが上位の設定に負けて効かない端末が出たとき、または導入を利用者任せにできなくなったとき |
| `model` によるモデル別の層別 | `SessionStart` の `model` を文字列のまま `GROUP BY` する。率を出さないので名寄せ表は要らない | `PreCompact` 時点のコンテキストトークン数の分布が多峰性を示し、コンテキストウィンドウのサイズの違いで解釈が止まったとき。**AI Gateway CSV の `Model` とは突き合わせない**（名寄せ表という人手の保守が発生する） |
| `PostCompact` の登録 | 圧縮の直後に発火する。入力に圧縮後のコンテキストトークン数は無く（`trigger` と `compact_summary` だけ）、その時点の transcript から読めれば圧縮の効き目を直接測れる | 圧縮の回数と `PreCompact` 時点の分布シフトだけでは効果を説明できなくなったとき。先に、その時点の transcript から圧縮後のコンテキストトークン数を読めるかの確認が要る |
| `seconds_since_last_response` / `prompt_cache_likely_expired` の収集 | 「前回応答から N 分でキャッシュが切れる」を実データで示せる唯一の組み合わせ。どちらも公式ドキュメント（hooks）に記載がある | 「N 分以内に再開せよ」型の施策で閾値を決める段になったとき |
| `estimated_cache_write_usd` の収集 | AI Gateway CSV の日次 Cache Write を「どの再開が生んだか」に分解できる | コストの上位者が特定でき、その内訳を行動単位まで割りたくなったとき |
| transcript の読み取り範囲（`plugin/hooks/_context.py` の `_TAIL_BYTES`）の拡大 | 末尾から `message.usage` を取れない割合を下げる | その割合がベースライン（読み取り範囲由来 約 0.5% ＋ 応答なし由来 約 3%。`../knowledge/measurements.md`）を大きく超えたとき。1 行が読み取り範囲を超える構造は拡大では消えない |
| `PermissionDenied` の登録 | 権限拒否の事象が取れる。安全性の材料は現在 `permission_mode` だけで、それを増やせる唯一の低頻度な候補 | `permission_mode` だけでは足りないと分かったとき。先に、auto mode の分類器による拒否で発火するかと、キー構成の確認が要る（確かめた範囲は `../knowledge/upstream-features.md`）。`PermissionRequest` は採らない（「求めた」だけでは判断材料にならず、頻度帯も中〜高になりうる） |
| `session_start.py` で SessionStart の行の追記を先頭の段へ移す | hook が打ち切られても SessionStart の行が残る見込みが上がる。効果は未確認で、同時起動で全件が打ち切られたときは最初の段（利用者の解決と `statusline.js` の複製）も済んでいなかった（処理が始まる前に打ち切られている、と推定） | 今の `hooks.json` の `SessionStart` の `timeout` のもとで、SessionStart の行の欠けが観測されたとき（`../knowledge/measurements.md` の一斉起動の打ち切りは、測定条件に書いた `timeout` での値であり、これに当たらない） |
| OpenTelemetry による収集 | 収集の大部分を `settings.json` の `env` だけで置き換えられる | システム管理部門が当部署への分岐を認めたとき |
| 送信プロセスの多重起動の排他 | 送信プロセスが重なって同じ spool を繰り返し POST することがなくなる。件数はサーバが集計時に `event_id` で一意化するため水増しされないが、挿入では重複を除かないため重複した行は DB に残る。今の実害は、遅いサーバへの負荷の上乗せと、重複した行による DB の増加である | 重複の送信がサーバの負荷や応答の遅れとして実害になったとき |
