## 3. 取りこぼし
- **型違いを配ったときの復旧手順がどこにも無い**（報告書・`release.md:127-133`）。notes（uc-01 125-136）には手順がある。直した版を先に出し、その後で利用者が `claude doctor` の `Invalid settings` が名指ししたキーの型を直すか、キーを消す。順序を逆にすると、旧版の hook が再開して同じ値を書き直し、再び止まる（推論）。更新が届いても hook は起動しないので、配り直しだけでは直らない（uc-01 R4 s4 の事実）。
- **既存のゲートを素通りする再発経路。**schemastore と本体の検証はずれていることが分かっている。env の int は、本体が受け付け schemastore が拒否する（uc-01 notes 68）。逆向きのずれ（schemastore が通して本体が捨てる値）と、fixture が古くなった後の上流の厳格化は、今のテストでは捕まらない。
- **書き戻しによる 2 MiB の自己超過。**膨張は事実である（`indent=2`、`_settings.py:69`。5000 段の入れ子で 10 KB が 50 MB になった。uc-13 notes）。その後に本体が読まなくなり、プラグインが止まる部分は推論である。病的な入力に限られるので、記録に留める。
- 導入どおりの状態で `parse_failed` の行が届くのは、BOM 付きと Latin-1 のときだけである。サーバで parse_failed が 0 件でも、壊れた端末が無いとは言えない（監視の読み方）。

## 6. 他領域へ・未確認のこと
- D3: 利用者は hook のタイムアウトを 10〜30 秒に延ばすことを許容している。これを前提にすると、SessionStart の打ち切りへの対策は、行の追記の位置を動かすことより `hooks.json` の SessionStart の `timeout` を延ばすほうが単純で効く。UC 14 で全部が cancelled になった段では、`statusline.js` の同期より前で止まっていた（推定。uc-14 notes）。identity の git には 3 秒のタイムアウトがあり（`_identity.py:17-18`）、延ばすならこの値と合わせて決める。延ばしたときの起動の遅れ（高負荷時だけ）は許容の範囲。取りこぼしそのものは `decisions/plugin.md:139-140` で受け入れ済み。
- D4: 読み捨てで止まった端末と使っていない端末を区別できない件は、サーバの「最後に届いた時刻・途絶えた端末」の見せ方の問題である。parse_failed が 0 件でも健全の証拠にならない。
- D5: E2E の撤回の判定の穴（`e2e/test_settings.py:33-39,84-85`）はコードで確かめ、正しかった。本体が捨てる settings.json の E2E 1 本の追加もこちらで扱う。
- 未確認: 逆向きのずれ（schemastore が通して本体が捨てる値）が実在するか。Windows での `os.replace` の失敗の頻度。対話起動での表示。`pytest` は実行していない。スキーマの検証はレビュー担当の追試（scratchpad での apply とスキーマの検証）と、読み取り専用の確認による。
