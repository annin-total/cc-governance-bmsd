# D3 送信・蓄積・回復 の精査

## 1. 結論（5 行以内）
1. 送信・蓄積について報告書が書いた事実は、コードで概ね裏付けられた。ただし UC46 の「重複 0」は誤りで、打ち切りの位置を事実として断定した箇所がある。error 行の二次的な増加を 401・404 だけに限っているのも不正確で、HTTP エラー全般で起きる。
2. 手順に矛盾がある。release.md に沿ってリリースすると、開発ツリーの `config.json` に本番の値が残る。そのため 2 回目以降のリリースでは、前提の `pytest e2e` が 12 件落ちる。値をコミットしない clone で作業すると、逆に空の送信先を配る側（全端末が無言で止まる）に倒れる。送信先の扱いは選択肢として 4 章に並べた（D5 と共通）。
3. release.md:56 の「401 の間もイベントは失われない」は誤りである。7 日・5 MiB の上限で失われ、error 行が二次的に増えて押し出しを早める。
4. 報告書 P2 の「5xx で打ち切る」は、1 本の毒ファイルで後続が止まる（コードからの推定）。一方、打ち切らないとサーバ全体の障害（ロックによる 500）を増幅する。「連続 2 回の 5xx で打ち切る」と「error 行の集約」を併せるのがよい。
5. 名前解決の失敗が無言なのは「接続不可を記録しない」設計の帰結であり、明示的に受け入れた記録は無い。タイムアウトによる喪失は `decisions/plugin.md:139-141` で受け入れ済みである。ただし利用者はタイムアウトを 10〜30 秒に延ばすことを許容している。

## 3. 取りこぼし
- **リリース手順の矛盾（P1）**
  - 手順の上から見ると次のとおり。初回は `:11` の E2E が通る。その後 `:13` で送信先を埋め、`:31` で丸ごと置き換え、`:50` の `diff -r` で一致を求める。この結果、開発ツリーに本番の値が残る。
  - 2 回目以降は `:11` が `_market.py:77` で 12 件落ちる。`decisions/plugin.md:112`（「送信先は空のまま置く」）とも食い違う。
  - 値をコミットしない clone（会社 PC）でリリースすると、`:31` の置き換えで空の `config.json` が配布側を上書きする。全端末が無言で送信をやめる。これを防ぐのは `:55` の人の目だけである。
  - 開発ツリーは空・配布側は本番値という方向は、報告書 :234 に既にある。報告書に無いのは、release.md との矛盾と、E2E の前提が崩れることの指摘である。
- **release.md:56・58 の誤り**：「イベントは失われない」は、7 日・5 MiB の上限と error 行の二次的な増加で成り立たない。
- **5xx の扱いの両面**
  - 打ち切ると、1 本の毒ファイルで後続が最長 7 日止まり、その error 行も届かない。UC39 notes:132-134 のコードからの推定で、実物では流していない。
  - 打ち切らないと、全体障害を増幅する。UC77 notes:84-89 のロックによる 500 では、全端末が全ファイルを 1 本ずつ POST し、1 本ごとに busy timeout の 5 秒だけスレッドを握る。今の実装がこの状態である。
- **staging で実際に届いたかを見ていない**：最初のセッションは `sent_at` が無いので即座に送る（`_spool.py:89-90`）。それなのに release.md の 7 は、版と動作しか見ない。
- **プロキシ**：送信プロセスは `HTTPS_PROXY` に従う（UC50 notes）。トンネルの失敗は記録されない。会社 PC で `NO_PROXY` が要るかは未確認である。
- **送信先の変更**：境界は「送った時刻」になる（UC46 (2)）。サーバを移行するとき、旧側の件数で締めると少し欠けて見える。
- **UC77 notes の「hook は普段 0.5 秒」**：pyenv のシムを含んだ数字である（`time_hook.py:34`）。

## 4. 改善案

### 送信先の扱い（D3-01。利用者が選ぶ。D5 と共通）
| 案 | 内容 | 代償 |

| A（推奨） | 開発ツリーに本番値を置く（今の手順どおり）。E2E の `publish` は、`config.json` を上書きしないモジュールでも送信先をローカルか空で組み立てる。`decisions:112` を改める | E2E が組み立てる物と配る物が `config.json` だけずれる（送信先の値は元々 E2E では試していない）。トークンは開発リポジトリに平文で入る（`release.md:58` で既に前提） |
| B | 開発ツリーは空にし、配布側でだけ埋める。4 の置き換えで `config.json` を保持し、`diff -r -x config.json` にする。配布側の値を機械で検査する（空でない・`https://`・ローカルでない・トークンがある） | 手順が 1 段増える。除外を誤ると空の送信先を配り、全端末が止まる。検査の置き場所（配布リポジトリの `validate.py`）を決める必要がある |
