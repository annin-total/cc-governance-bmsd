# D5 検証の仕組み の精査

## 1. 結論（5 行以内）
1. 報告書が挙げた E2E の穴（撤回を判定しない・`cancelled` を見ない・送信の失敗を 1 回しか起こさない・キーパスを全行まとめて見る）は、どれも今のコードで裏が取れた。
2. 最重要の発見は、送信先の扱いが二つの手順で両立しないことである。`release.md` は「`plugin/config.json` に本番の値を埋める」ことと「`pytest e2e` が合格している」ことを同時に求めるが、`_market.py` はローカル以外の送信先では publish を拒む。今は配布側の `config.json` が空なので害は出ていない。本番の値を初めて入れるリリースで顕在化するので、それより前に決める必要がある（P1。案は D5-01 に並べ、選ぶのは利用者）。
3. 報告書の P1 のうち「`conftest` で E2E を止める」と「e2e.md の『空の開発ツリーで流す』」は、この矛盾を解消しない。E2E を流せなくするだけである。
4. `test_2回目` の偽の赤は、`release.md` が撤回の手段として指示する SET の `None` でも起きる。このため最初の撤回リリースで E2E が偽の赤になる（P2）。
5. ほかの改善案は利用者の方針（厳格にしすぎない・hook のタイムアウトは 10〜30 秒まで許容）に合わせて P2〜P3 に下げた。受け入れ済みの限界は蒸し返さない。

## 3. 取りこぼし
- **送信先の設計の食い違い（最重要）。**
  - 矛盾の中身: `release.md:10-13` は「E2E の合格」と「初回リリースの前に `plugin/config.json` を埋める」の両方を求める。`:50` の `diff -r` は `plugin/` と配布物の一致を求め、`:58` はトークンを平文でリポジトリに入れることを認めている。一方 `_market.py:76-77` はローカル以外の送信先では publish を拒む。
  - 今の状態: 配布側の `plugins/governance/config.json` はまだ空（収録は 0.2.0 まで）なので、害は出ていない。本番の値を初めて入れるリリースで表に出る。
  - 同じ前提に立つ箇所: 報告書 4.3 の P1、4.4 の P2（`report.md:234`）、UC 50 の notes（`:83-85`・`:101`）は、どれも「開発ツリーは空」を前提にしており、`release.md:13,50` と矛盾する。
- **`ask()` の経路は `outcome` を見られない。**`_flow.py:42-48` は stream-json を付けない。
- **`test_notices.py:31-33` は SessionStart の出力が空だと `JSONDecodeError` で落ち、原因が読めない**（UC 50 の notes の範囲外の節）。
- **`_quiet` の前提（推定・未検証）。**`_quiet.py:8-9` は送信の遅れを数百 ms とみなし、2 秒静止したら終わったと判断する。UC 43 では高負荷時に最大 5.95 s かかった。
- **e2e.md に `CC_E2E_RUN` が書かれていない。**準備のコミット `0750fa0` は `_server.py` しか変えておらず、`e2e.md:179-180` は `cc-e2e=1` のままである。
- **UC 47 の昇格候補が抜けている。**「送信先が空の版で積み、送信先を入れた版に上げると、積んだ分が届く」の 1 本（notes `:157`）が、報告書から黙って落ちている。
