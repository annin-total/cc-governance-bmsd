# UC76 画面の性能（No.76）

## 目的

1 年分・200 人分の合成データを入れた DB で、管理画面の 4 画面（`/` 概況・`/policy`・`/effect`・`/assets`）の応答時間を測る。
インデックスの有無・ANALYZE の前後で比べ、EXPLAIN QUERY PLAN で全表走査を探し、データ量を増やしたときの伸び方を見る。

**この Mac の SQLite の数字は本番（AIP・Python 3.9・MySQL の可能性）の性能を表さない。相対比較と壊れ方の確認にだけ使う。**

## 前提として確かめたこと（実装を読んで）

- **4 画面には期間フィルタなどの引数が無い。**集計期間は定数で固定（`RECENT_DAYS=7`・`POLICY_DAYS=30`・`EVENT_STUDY_SPAN=14`）、
  基準日は `time.time()` の JST の日。したがって「主な引数を変えて測る」は、データ量（倍率）と DB の状態（索引・統計）を変えることで代える
- 画面が読む表は `events`・`policy_state`・`errors`・`cost_daily` の 4 つ。インデックスは `db._INDEXES` の 8 本で、**`errors` には 1 本も無い**。
  `db.analyze` の MySQL 側も `_TABLES` の 3 表だけで、`errors` を含まない
- ANALYZE が走るのは (a) `/ingest` の保存後にプロセス内で 1 時間に 1 回（起動後の初回は必ず）、(b) `/import` の最後。どちらも `PRAGMA analysis_limit=400`

## 仮説（実行前に立てたもの）

1. 窓で絞るクエリ（`/`・`/assets`）は、総量ではなく直近 7〜14 日の行数に比例する。1 年分溜まっても、密度が同じなら速さは変わらない
2. `/` は最も重く、ANALYZE では縮まない（`docs/decisions/server.md` の記述）
3. `/effect` のコンテキスト分布は準拠者 1 人ごとに 2 本ずつクエリを出す（200 人で約 360 本）。5 列の被覆インデックスが無いと 1 本ごとに全表走査になり、分単位になる
4. `/policy` の `latest_values`（ROW_NUMBER）は `key_name = ? AND day >= ?` だが、インデックスは `(key_name, prev_value, user_email)` で `day` を持たない。
   **キーの全履歴（1 年分）を読むので、窓ではなく総量に比例して遅くなる。**しかも 1 画面で同じ形のクエリを 6 本出す
5. `errors` は索引が無いので `error_summary` は全表走査。平常の件数では問題にならないが、総量に比例する
6. ANALYZE が無いと、`skill_name`・`tool_name` を先頭列に持つ索引を誤って選び、`/assets` が遅くなる（`docs/knowledge/measurements.md` の既知の事実）

## 合成データ（1 倍）の設計と根拠

| 項目 | 値 | 根拠 |
| --- | --- | --- |
| 利用者 | 200 名、1〜2 台（2 割が 2 台） | UC の想定。端末数は推定 |
| 期間 | 今日（JST）で終わる 365 日 | UC の想定 |
| 活動日 | 平日 75%・週末 10%。1 割は途中から導入、5% は 20〜60 日前に停止 | 推定。停止は `/policy` の古い端末の表示を出すため |
| 1 人 1 活動日のイベント | 平均 80 件 × 利用者ごとの重み（対数正規 σ=0.8、平均 1）× 一様 0.5〜1.5 | UC の例「数十〜数百」の中ほど。偏りは実 CSV の「上位 5 名でコストの 35〜37%」に寄せた |
| セッション | 25 イベントに 1 本（最大 20）。開始ごとに `SessionStart` 1 件と policy 行 2 件（`policy.SET` の 2 キー） | プラグインの `session_start.py` の振る舞い |
| hook の内訳 | PostToolUse 70・UserPromptSubmit 12・Stop 10・PostToolUseFailure 3・PreCompact 1・UserPromptExpansion 1 | 推定。ツール呼出が大半 |
| `errors` | 0.1% のイベントに 1 件 | 推定（平常時） |
| `cost_daily` | 活動した利用者・日ごとに 2 行（モデル 2 種）、今日の 3 日前まで | 実 CSV の構造（`docs/knowledge/measurements.md`：当日に取れるのは 3 日前まで） |
| 準拠 | 1 割は `prev_value="80"`（非準拠）、ほかは初回だけ NULL で以後 `"60"` | `/policy`・`/effect` に行が出るように |

投入の経路（直接投入が契約どおりであることの担保）:

- `events`・`policy_state`・`errors` は、NDJSON を組み立てて **`ccgov.ingestion.ndjson.ingest`（`/ingest` の本体）** に渡した。HTTP と認証だけを省いた形で、
  列の選択・`coerce`・`day` の計算は本番と同じコードを通る
- `cost_daily` は CSV を書き出して **`csv_import.import_all`（`/import` の本体）** で取り込んだ
- 表とインデックスは `contract.ddl()` と `db.init()`（本番の起動時と同じ関数）で作った
- 加えて `typecheck.py` で、全行の列の並び・型宣言・記憶型（`typeof`）を契約と突き合わせ、Docker では実 HTTP の `/ingest` で入れた行と直接投入の行の記憶型を比べた

## 手順

一時スクリプト（このフォルダ）:

- `gen.py <DB> <倍率> [--recent-days N --recent-mult M]`: 上の設計で DB を作る
- `measure.py <DB> <出力 JSON>`: 実アプリ（`create_app`）を Flask の `test_client` で呼び、4 画面を描画まで計る。`db.connect` を差し替えてクエリごとの時間を記録し、
  実際に発行された SQL と引数で EXPLAIN QUERY PLAN を取る。DB の状態を 3 通りに変える
  （`analyzed` = 索引あり + `db.analyze`、`no_stat` = 索引あり + `sqlite_stat1` を削除、`no_index` = `ix_*` を DROP + 統計なし）。1 リクエストが上限秒を超えたら打ち切る
- `typecheck.py`: 契約との突き合わせ（上記）
- `docker_run.py`: `e2e/_server.py` の `DockerServer` で本番に近い形のサーバを立て、1 倍の DB を差し替えて HTTP で 4 画面を計る。`/ingest` を 2 回送り（初回は ANALYZE が走る）、
  前後で画面を計る。コンテナ内の SQLite で同じ SQL の EXPLAIN を取り、ホストとの違いを出す
- `run_host.sh`: heavy.lock を取り（`trap` で必ず外す）、倍率 0.5・1・2 と「1 倍 + 直近 35 日だけ 5 倍」を順に作って測り、消す

```bash
L=<product>/cc-governance-bmsd/.local/e2e-load-testing/uc-76-screen-perf   # 測定用の venv（server/requirements.txt）と DB を置く
tmp/e2e-load-testing/uc-76-screen-perf/run_host.sh $L
tmp/e2e-load-testing/uc-76-screen-perf/run_docker.sh $L   # heavy.lock を取り、1 倍の DB を本番の状態（索引 + analyze）に戻して、型検査・Docker（CC_E2E_RUN=b-uc76）・errors の嵐を続けて行う
```

- `storm.py <DB> <日数> <1 日の行数>`: 壊れた版が全 hook で失敗し続けた状況を模し、直近 7 日に `errors` を 1 日 10 万行（計 70 万行）足す（`ndjson.ingest` を通す）
- `measure.py` の打ち切りは**1 リクエスト（1 接続）あたり**の上限秒である（1 本のクエリごとではない）

### 判定のゲートを確かめたこと（緑を鵜呑みにしない）

- 画面の数字が空でないこと: 概況の「直近 7 日のイベント件数」を独立の SQL で数え、その値（`60,945` など）が HTML に描画されていることを全倍率・全状態で確かめた（全件 True）
- EXPLAIN の検出器: 同じ判定関数が、`no_index` では 15 本前後の `SCAN <表>` を拾い、`analyzed` では `SCAN errors` だけを拾った（両向きに動く）
- `typecheck.py`: 契約どおりの DB で ok。非数値の文字列を `is_interrupt`（INTEGER）と `cost`（DOUBLE）に入れた行と、`day` が NULL の行を足すと 3 件とも検出した。
  **ただし `ts` に `'123'` を入れた行は検出できなかった**（SQLite の型アフィニティが INTEGER 列の数字文字列を黙って整数に変えるため。検査の死角）
- 生成の行数: 生成ロジックだけを別に回して数えた行数（1 倍 3,131,721 行・2 倍 6,226,482 行・1 倍 + 直近 5 倍 4,389,821 行）が、`ingest` の保存件数と 1 行の違いもなく一致し、破棄は 0 件

## 結果

**判定: 1 年分・200 名（313 万行・1.49 GB）で、4 画面はホストで 0.1〜1.8 s、Docker（本番に近い形）で 0.1〜1.5 s。索引 + ANALYZE の状態で全表走査は `errors` の 1 本だけ。
遅くなる経路は 3 つ見つかった: (1) 直近の密度に比例して `/` が伸びる（直近 5 倍で 3.5〜5 s）、(2) `errors` の嵐で `/` が 6.9 s、(3) 5 列の索引が無いと `/effect` が 2 分を超える。**

### 測定条件

- ホスト: macOS（8 コア・8 GiB）・Python 3.13.2・**SQLite 3.51.0**・Flask の `test_client`（waitress を通さない）。DB ファイルは OS のキャッシュに載った状態（生成直後）
- Docker: Colima（2 CPU・3 GiB）・`python:3.9-slim`（**Python 3.9.25・SQLite 3.46.1**）・entry.sh + waitress + BASE_PATH。HTTP で測った
- 並行: **他トラックの作業で load average が 6.6〜12.1 と高かった**（1 倍の測定時 10.73、2 倍 7.92、1 倍 + 直近 5 倍 6.61、Docker 8.9〜9.6、嵐 8.09）。0.5 倍の測定時だけ UC46 のコンテナ 2 つが動いていた。
  同じ実行計画のまま中央値が 2 倍揺れた例がある（「想定外」）。**数字は 1 桁の精度で読むこと**
- 各画面 5 回（Docker の ingest 後と嵐は 3 回）。表は中央値（括弧は最小値）、単位は秒
- **SQLite の数字は本番（AIP・MySQL の可能性）の性能を表さない。**相対比較と壊れ方の確認にだけ使う

### 1 倍の Docker（本番に近い形・HTTP）

| 時点 | `/` | `/policy` | `/effect` | `/assets` |
| --- | --- | --- | --- | --- |
| DB を差し替えて再起動した直後（5 回） | 1.23, 1.48, 0.61, 0.80, 0.54 | 0.30〜0.35 | 0.87（初回）, 0.13〜0.30 | 0.10〜0.12 |

- `docker cp` で 1.49 GB の DB を入れるのに 26 s、再起動（`db.init` が既存の索引を確かめるだけ）に 3 s
- **再起動後の初回の `/ingest`（5,000 行）は 3.34 s、2 回目は 0.28 s。**初回は `_analyze_if_due` が 1.49 GB の DB に ANALYZE をかける分である。端末の送信の上限（`_sender.py` の `timeout_sec=60`）には遠い
- コンテナ内の SQLite 3.46.1 の実行計画は、ホスト（3.51.0）と 1 本を除いて同じだった。違いは概況の突合率のクエリで、3.51.0 だけが `CREATE BLOOM FILTER` を使う（索引の選び方は同じ）

### 直接投入が契約どおりか

- ホストの 1 倍の DB 全体（約 313 万行）: 列の並び・型宣言が `contract.ddl()` と一致し、記憶型は VARCHAR → text/null、INTEGER・BIGINT → integer/null、DOUBLE → real/null だけ。`event_id`・`ts`・`day` に NULL なし（`typecheck.py` が ok）
- Docker で実 HTTP の `/ingest` から入れた 10,000 行と、直接投入の約 293 万行を分けて集計しても、全列で上の許容の範囲に収まった（例: `ts` は両群とも integer のみ、`context_tokens` は integer/null）

### 実行計画（EXPLAIN QUERY PLAN）

索引 + ANALYZE の状態で、全表走査（`SCAN <表>` で索引を使わないもの）は **`errors`（`error_summary`）の 1 本だけ**。`errors` には索引が 1 本も無い。

索引は使っているが、窓で絞れていないものがある（仮説 4）:

- `/policy` の `latest_values`（1 画面で 5 回）と、`/`・`/policy` の `plugin_version_distribution` は `SEARCH policy_state USING INDEX ix_policy_state_key_name_prev_value_user_email (key_name=?)`。
  **`day >= ?` は索引で絞れず、そのキーの全履歴（1 倍で約 10 万行）を読んでから捨てる**。`plugin_version_distribution` は `/` で 2 番目に重い（1 倍 0.55 s・2 倍 1.03 s）
- `/policy` の `stale_terminals`・`not_introduced` は `SCAN policy_state USING INDEX ix_policy_state_user_email_ts`（索引の全走査）

ANALYZE の有無で計画が変わったのは `/assets` のスキル別の 1 本だけ（統計ありで `ix_events_skill_name_...` を skip-scan、なしで `ix_events_day_hook_event_context_tokens`）。
その 1 本は 0.010 s → 0.039 s（1 倍）だが、画面全体では差が揺れに埋もれた。**`/` の計画は ANALYZE の有無で 1 本も変わらなかった。**

### 仮説の答え合わせ

| # | 仮説 | 結果 |
| --- | --- | --- |
| 1 | 窓で絞るクエリは直近の行数に比例 | **ほぼそのとおり。**概況の健全性のクエリは直近の密度で決まり、1 倍 + 直近 5 倍（総量は 1.4 倍）で約 2〜5 倍に伸びた。総量ではなく直近の密度で決まる |
| 2 | `/` が最も重く、ANALYZE で縮まない | **そのとおり。**全倍率で最も重く、計画も ANALYZE で変わらない。時間の約半分が健全性のクエリ（`COUNT(DISTINCT CASE ...)` 10 個を直近と前の 2 回） |
| 3 | 索引が無いと `/effect` が分単位 | **そのとおり。**1 倍で 120 s の上限に達し、362 本中 298 本しか終わらなかった（1 本 0.4 s）。完走すれば 150 s 前後（推測）。索引ありでは 362 本で計 0.04 s |
| 4 | `/policy` の最新値が総量に比例 | **計画はそのとおり**（`day` で絞れない）。時間は 1 倍で 5 本計 0.31 s、2 倍で 0.52 s と小さい。policy の行が 1 年で 20 万行と少ないため、今の規模では問題にならない |
| 5 | `errors` は全表走査 | **そのとおり。平常（2,932 行）では無害だが、嵐（直近 7 日に 70 万行）で `/` が 6.9 s**、うち `error_summary` が 5.7 s。70 万行のうち 99.6% が直近 7 日の中にあるため、`day` の索引を足しても読む行は減らない（推測。DB を消した後に試そうとして失敗し、実測していない）。重さは窓関数 2 本の並べ替えと見る |
| 6 | ANALYZE が無いと `/assets` が遅い | **計画は変わったが、画面の差は小さい**（1 倍 0.14 vs 0.17 s）。既知の「約 2 倍遅い」は別の分布のデータでの話で、ここではスキルの行が少なく効かない |

### 伸び方（索引 + ANALYZE、最小値）

| データ | 直近 7 日の events | `/` | `/assets` |
| --- | ---: | ---: | ---: |
| 0.5 倍 | 30,917 | 0.56 | 0.07 |
| 1 倍 | 60,945 | 1.38（統計なしで 0.73） | 0.12 |
| 2 倍 | 116,383 | 2.21 | 0.27 |
| 1 倍 + 直近 5 倍 | 296,593 | 3.52 | 0.71 |

直近の行数に対してほぼ線形か、それより緩い（`/` は直近 10 倍で約 6 倍、`/assets` は約 10 倍）。**線形を超えて悪化する兆しは見えなかった**が、揺れが大きく細かい係数は言えない。
`/policy`・`/effect` はほとんど伸びない（`/effect` の 2 倍の中央値 0.97 は揺れ。最小値 0.37）。

## 想定外だったこと

- **同じ実行計画のまま、1 倍の `/` の中央値が「索引 + ANALYZE」1.82 s・「統計なし」0.94 s と 2 倍違った。**計画は同一なので ANALYZE の効果ではなく、並行の負荷（load average 10 前後）による揺れと見る。
  2 倍の `/policy`（中央値 3.04 s、SQL の合計は 0.80 s）も同じで、SQL の外側の時間が膨らんだ。**この Mac で並行作業中に測った数字は 2 倍の揺れを含む**
- `typecheck.py` の死角: SQLite は INTEGER 列に入れた数字文字列（`'123'`）を黙って整数にするので、記憶型の検査では拾えない。直接投入の検証は、記憶型だけでなく「本番と同じ `coerce` を通したこと」で担保する必要がある（今回は `ndjson.ingest` を通した）
- 生成の行数を見比べたとき、`cat *.gen.json` の並び（名前順）を実行順と取り違え、2 倍が 1.4 倍しか無いと誤読しかけた。生成ロジックの単独の集計で否定した（実害なし）
- `errors` に `day` の索引を足す比較は、先に DB を消してしまい測れなかった（スクリプトが `DB_DSN` 未設定で失敗し、続く削除だけが走った）

## 課題と改善案

### サーバ（`server/`。コードは変えていない。提案のみ）

1. **`errors` を `db._TABLES` に入れ、`error_summary` の形を見直す。**今は索引が無く、MySQL の `ANALYZE TABLE` の対象からも外れている。
