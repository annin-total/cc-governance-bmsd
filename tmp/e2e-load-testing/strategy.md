# 実機検証（負荷テスト）の戦略書

このフォルダは検証の作業場である。ほかのファイルから参照しない（PR 本文と報告書を除く）。
機微な情報（API キー・マスク済みの実 CSV・実メールアドレス）は `.local/e2e-load-testing/uc-<番号>-<タイトル>/` に置き、ここには置かない。

## 1. 目的

- 実物の Claude Code・プラグイン・集計サーバを使い、**E2E が見ていない経路**（更新・撤回・競合・障害からの回復・規模）を、やや過剰に叩く
- 結果を**今後に活かせる形**で残す: `e2e/` の追加・修正案、`docs/guide/e2e.md` の修正案、e2e スキルの拡張案、`docs/knowledge/` に足す外界の事実
- コードは使い捨ての前提で変えてよい。ただし片付けやすく進め、片付けたものと残したものを報告する

## 2. この取り組みへの意見

**意義はある。ただし「負荷」より「E2E の死角」を主にするべきだと考える。**

- 意義がある理由
  - ユースケースの評価で、E2E は**空の settings.json への新規導入**から始まるため、実運用で最も多い「前の値が入った端末の更新」「撤回」「壊れた設定」をほとんど判定していないと分かった
  - 本番の送信先を埋めると E2E の大半が落ちる見込み（No.50）など、初回リリースで表に出る穴が既に見つかっている。実物で確かめる価値が高い
  - hook の実際の入力、同時起動時の挙動、spool の上限のような**外界の事実**は、実物でしか取れない。`docs/knowledge/` に残せば長く効く
- 注意点
  - **この Mac の数字は本番の性能を表さない。**Colima は 2 CPU・3 GiB で、本番は AIP（Python 3.9・ポート 5000）。性能の数字は「相対比較」と「壊れ方の確認」にだけ使う
  - **組み合わせの網羅は E2E に向かない。**設定のマージの組み合わせ（型・既存値・ONCE の記録の有無）は、実物で代表の経路を 1〜2 本通し、網羅は `tests/` に移すほうが安く確実。報告書でそう提案する
  - 過剰なテストは、残す価値の判定を誤ると `e2e/` を太らせる。**E2E に昇格させる候補は「無言で壊れる・リリースを止める」ものに限る**
- やめるべきもの: 本番の環境・実利用者のデータ・Windows・Bedrock が要るもの（「5. 対象外」）。この環境で無理に模すと、偽の安心を生む

**件数**: 選んだのは **22 件**（似たものは 1 件に束ねた）。15 件では更新・撤回・障害回復の要所が漏れる。一方、30 件を超えると、1 件あたりの検証が浅くなる。

## 3. 前提（この環境）

- macOS・8 コア・8 GiB。Docker は Colima（2 CPU・3 GiB）。`claude` 2.1.283
- 認証: `product/cc-governance-bmsd/.env.local` の `ANTHROPIC_API_KEY`（値を表示・記録しない。実行時に環境変数で渡す）。`~/.config/cc-e2e/oauth-token` も使える
- マスク済みの実 CSV: `cc-governance/data/`（アーカイブ。読むだけ。コピーは `.local/` へ）
- ブランチ `e2e-load-testing`（PR #63 の上）

## 4. 並行と安全の設計

### 並行の制約（確認済み）

- **Docker のラベルの衝突**: `e2e/conftest.py` は、開始時にラベル `cc-e2e=1` の資源があると「片付け漏れ」として失敗する。**同じ Mac で 2 つの E2E がサーバを同時に使うと、互いを止める**
  - 対処（手順 0 で行う）: ラベルを実行ごとに変えられるようにする小さな変更を、このブランチに入れる（例: 環境変数 `CC_E2E_LABEL`）。これ自体を改善案として報告する
- **worktree には submodule が無い**: 作ったら `git submodule update --init` を行う（しないと契約の同期テストが落ちる）
- **マシンの資源**: 実セッションを大量に並列で起動する負荷は 1 トラックに限り、その間はほかのトラックが Docker を重く使わないよう、進捗記録で合図する

### セッションとトラック

| トラック | 担当 | 主な資源 | worktree（`bmsd-governance/work/wt-<トラック>`） |
| --- | --- | --- | --- |
| 監督（このセッション） | 戦略・進捗・報告書・統合・PR。作業はサブエージェントに委任 | — | 使わない（`e2e-load-testing` の作業コピー） |
| A 端末の状態 | 設定の配布・お知らせ・ステータスライン・導入と撤去 | 認証（`-p`）。Docker はほぼ不要 | `wt-a`（ブランチ `e2e-load-testing-a`） |
| B 送信とサーバ | 送信・再送・spool・受信負荷・画面性能・CSV・列の追加 | Docker（重い） | `wt-b` |
| C 収集と上流の事実 | hook の実入力・サブエージェント・非漏洩・処理時間・版の混在 | 認証（多め）。非漏洩に Docker | `wt-c` |

- **起動済みの 3 セッションに A・B・C を 1 つずつ渡す。**渡すのは、`product/` の外に置くハンドオフ文書（`bmsd-governance/work/e2e-load-testing/handoff-<トラック>.md`）のパスである
- 各セッションも監督役で、UC ごとにサブエージェントへ委任する（コンテキストの圧迫を防ぐ）
- 各トラックは自分の worktree で作業し、`tmp/e2e-load-testing/uc-*/` にコミットして push する。最後に監督が `e2e-load-testing` に統合する（UC のフォルダが別々なので衝突しない）
- 全体の進捗は `tmp/e2e-load-testing/progress.md`。各トラックは自分の行だけを更新する

### 安全の約束（全トラック共通）

- 本物の `~/.claude` を書き換えない。隔離は `CLAUDE_CONFIG_DIR` だけで行う（`HOME` は差し替えない）
- 送信先はローカルのサーバだけにする。本番の受信先・配布リポジトリには触れない（push しない）
- 認証の値を表示・記録しない。ログに出たら、そのログをコミットしない
- 資源には自トラックのラベルを付け、UC ごとに片付ける。残したものは `uc-*/notes.md` に書く
- 同種の失敗が 3 回続いたら、そのトラックを止めて監督に報告する

### 対象外にしたもの（理由）

- **この環境では不可能**: Windows（9・28・59）、Bedrock（81）、AIP へのデプロイ（73）、社内のプロキシ・証明書（49）、配布リポジトリの staging・自動更新の実配信（51・54）、IDE 拡張（25）
- **対話でしか見えない表示**（20・22・23・26・17）: Claude は対話の起動を代行できない（自動モードで拒否された）。必要ならあなたへの手順書にする
- **本番のデータが要る調査**（70 の一部・82・83・84）: 手元に本番のデータが無い
- **ほかの手段が向いている**: 集計ロジック・効果測定・依存の更新・MySQL（66・67・74・75）はサーバの `tests` の領分。旧版の Claude Code での回帰（61）は版を選んで入れる手間に比べて得るものが少ない
- **ほかの UC で足りる・既存の E2E で見ている**: 2・3・5・8・10・15・16・18・21・27・29・34・40・53・58・63・64・65・78・79・80・86

## 6. 進め方

0. **準備（監督）**: 進捗記録を作る。Docker のラベルを実行ごとに変えられるようにする（小さな変更。テストで確かめる）。ハンドオフ文書を 3 つ書く
1. **トラックの開始（あなた）**: 起動済みの 3 セッションに、ハンドオフ文書のパスを 1 つずつ渡す
2. **各トラック**: UC ごとに `tmp/e2e-load-testing/uc-<番号>-<タイトル>/` を作り、`notes.md`（目的・手順・結果・課題・片付け）と一時スクリプトを置く。1 UC を終えるごとにコミットして push し、`progress.md` の自分の行を更新する
3. **統合（監督）**: 各トラックのブランチを `e2e-load-testing` にマージし、報告書 `tmp/e2e-load-testing/report.md` を書く（結果・課題・改善案を `e2e/`・`e2e.md`・スキル・knowledge に分けて）
4. **PR**: `e2e-load-testing` から PR を作る（向き先はあなたに確かめる）。worktree を片付け、片付けたものと残したものを報告する

### 費用と時間の見込み（推定）

- API 費用: 実セッションを合計 300〜600 回起動する見込みで、**10〜40 USD**。同時起動（UC 14）と監査（UC 38）が大半を占める
- 時間: 1 トラック 3〜6 時間。3 並行で**半日から 1 日**

## 7. e2e スキルの拡張の方向（nice-to-have。報告書で提案する）

- `references/` に「負荷・回復」「更新の経路」の枝を置き、ユースケースに応じてワークフローを分ける
- 既存のテストで足りないときは、一時スクリプトを `.local/<作業名>/` に書いてよいことを、手順として明示する（今回の UC で使った雛形を元にする）
