# トラック B（送信とサーバ）の要約

測定条件: macOS 8 コア・8 GiB、Colima 2 CPU・3 GiB、claude 2.1.283。ほかのトラックと並行して測ったため、load average は 5〜21 と高い。
性能の数字は、相対比較と壊れ方の確認にだけ使える（本番は AIP）。詳細は各 `uc-*/notes.md` にある。

## UC ごとの結果

| UC | 結果 |
| --- | --- |
| 50 本番の送信先 | 12 件が落ち、7 件が通った。落ちた 12 件は、すべて `_market._check_ingest_url` が publish の段階で止めたもの。外への送信は無かった。通った 7 件は配る config を使っていない。このため、送信先が空のまま配っても E2E は全件緑になる |
| 46 停止からの回復 | 次の 4 経路で、取りこぼしと重複はどちらも 0 だった: 停止中に 150 セッション分を積む、送信の途中で kill する、送信先を変える、トークンを直す。ただし 401 と 404 は「届いた」扱いになり、error 行が送信回数の二乗で増えた（k=40 で 820 行） |
| 47 spool の上限 | 上限は 5 MB と 7 日の 2 つ。破棄は mtime の古い順にファイル単位で行い、どこにも記録が残らない。前段が本文を読まずに 413 を返すと、送信が最大 7 日詰まる。config.json が無い版では queue が際限なく増える |
| 77 一斉起動 | 140 同時でも 5xx と取りこぼしは 0（p95 は 3.5 秒以下）。実セッションの 20 並列では SessionStart hook が 5 秒で打ち切られ、SessionStart の行が無言で失われた |
| 76 画面の性能 | 1 年分・200 名（313 万行）で、4 画面とも 0.1〜1.8 秒。errors の嵐を模すと概況が 6.9 秒になった。errors には索引が無く、ANALYZE の対象からも漏れている |
| 39 長い値・特殊文字 | SQLite では巻き込みは無かった。MySQL が utf8mb4 以外だと、絵文字 1 字でリクエスト全体が 500 になる。深い入れ子でも RecursionError で 500 になる |
| 68 CSV の取り込み | 件数・合計・再取り込みは正しい。冪等キーが day のため、同じ日を含む別ファイルがその日を丸ごと置き換え、無言でデータが失われる。書式の変化のいくつかは、成功と表示されたまま NULL になる |
| 32 列の追加 | 文書の手順どおりなら値が届く。同期忘れ・型の誤った ALTER・版のずれは、サーバが動き続けたまま無言でずれる。`server.md` の「同期忘れを検出する」は誤り |

## 最も重要な発見 3 つ

1. **送信の失敗が端末でもサーバでも見えない**（UC50・46・47）
   - DNS や接続の失敗、spool の上限による破棄は、どこにも記録されない
   - 401 と 404 は「届いた」扱いになり、error 行を二乗で積んだうえで、本物のイベントを上限の外へ押し出す
   - 送信先を誤ったまま配っても、E2E は全件緑になる
2. **サーバ側で、データの無言の喪失とずれが起きる**（UC68・32・39）
   - CSV の日単位の置き換えで、その日のデータが失われる
   - 契約の同期忘れと型の誤りは、起動時の検査を通ってしまう
   - MySQL の文字コードが utf8mb4 以外だと、同じリクエストの正常な行も巻き込んで失われる
3. **高負荷の端末で SessionStart が落ちる**（UC77）
   - SessionStart hook が 5 秒の上限で打ち切られ、行が無言で失われる
   - E2E は hook の outcome を判定していない

## 片付け

- 片付けたもの:
  - Docker のうち、ラベル `cc-e2e` の資源（コンテナ・イメージ・ネットワーク）
  - `$TMPDIR/cc-e2e-*`
  - UC で起動したプロセス
  - `heavy.lock`
  - UC32 の作業コピー
- 確認: `plugin/`・`server/`・`e2e/` は無変更。コードの差分は UC フォルダの diff だけにある
- 残したもの: 実行ログを `.local/e2e-load-testing/uc-*/`（git 管理外）に残した
- 利用者の判断待ち: ホストの空きが 13 GiB から 5.3 GiB に減った
  - 原因は、Colima のデータディスクが空きを返していないことと、Docker のビルドキャッシュ（約 1 GB）と推定している
  - Docker はほかのトラックと共有しているため、`colima ssh -- sudo fstrim -a` も `docker builder prune` も実行していない
