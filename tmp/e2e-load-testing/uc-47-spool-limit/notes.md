# UC47 spool の上限と長期オフライン（No.47・No.42）

## 目的

端末の spool（`CLAUDE_PLUGIN_DATA/spool/*.jsonl`）の上限での破棄を、実物の hook・送信プロセス・集計サーバ（Docker）で確かめる。

1. 上限を超える量を積んだとき、どれがどの順で捨てられるか。破棄が記録されるか
2. 単独で上限を超える 1 ファイルを 1 回は送るか。巨大な本文へのサーバの応答と、その後の扱い
3. 長期オフライン（mtime を過去にずらす）からの復帰で、何が届き何が捨てられるか
4. No.42: 送信先が空の版で hook を動かすと何が起きるか。送信先を入れた版に上げたとき、積まれた分が届くか
5. hook の処理時間が spool の大きさで劣化しないか

## 仮説（実装を読んで立てたもの）

- 上限は 2 つだけ: 合計 `spool_max_bytes`（5 MB）と `spool_max_days`（7 日）。**件数の上限は無い。**`queue.jsonl` は上限の対象外（送信プロセスの `rotate` で spool に移ってから数える）
- 破棄（`_spool.prune`）は送信の**後**に走る。日数超えを先に消し、残りを **mtime の古い順**に合計が上限以下になるまで消す（ファイル単位。行単位では切らない）。
  一方、送る順は**ファイル名（epoch）の昇順**。両者の基準が違う
- 破棄は **error 行にもログにも残らない**（`prune` は何も記録しない）
- 「上限超えの 1 ファイルも 1 回は送る」は**サーバに届くときだけ**成り立つ。接続できないと、送信は 1 ファイル目で打ち切られ、その直後の `prune` で上限超えのファイルは一度も送られずに消える
- サーバには本文の上限（`MAX_CONTENT_LENGTH`）が無く、waitress の既定（1 GiB）まで受けるので、ローカルでは 413 は出ない。413 を返す前段（プロキシ等）があると、`HTTP 413` の error 行が積まれ、5 MB 超のファイルは直後の `prune` で消え、5 MB 以下のファイルは 7 日間毎回 413 を繰り返す
- 長期オフラインで**端末自体が止まっていた**（送信プロセスが一度も走らない）なら、復帰後の最初の送信で 7 日超のファイルも送られてから破棄される（送信が先）。
  **端末は動いていてサーバに届かなかった**なら、途中の送信プロセスの `prune` で 7 日超は消えており、届かない
- 送信先が空の版: hook は行を積み、送信プロセスは起動して退避と破棄だけを行い、POST しない。送信先を入れた版に上げた後の最初の送信で、上限内に残った分がすべて届く
- hook（`collect.py`）の処理時間は spool の大きさに依らない（hook は `queue.jsonl` への追記と `sent_at` の stat だけ。spool の走査は切り離した送信プロセスで行う）。送信プロセスの時間はファイル数に比例する

## 手順

一時スクリプトはこのフォルダ（`harness.py`・`run.py`・`timing.py`）。worktree のルートで:

```bash
CC_E2E_RUN=b-uc47 .venv/bin/python tmp/e2e-load-testing/uc-47-spool-limit/run.py      # 1〜4（Docker を使う）
.venv/bin/python tmp/e2e-load-testing/uc-47-spool-limit/timing.py                      # 5（Docker を使わない）
```

- `wt-b/plugin/` は書き換えない。`$TMPDIR/cc-e2e-b-uc47-*/` にコピーし、そちらの `config.json` を場面ごとに書き換える
- 状態の置き場は `CLAUDE_PLUGIN_DATA` で一時ディレクトリに向ける。`CC_GOVERNANCE_USER_EMAIL` を与えて git を読ませない。本物の `~/.claude` には触れない
- hook は `python3 <コピー>/hooks/collect.py Stop` を直接起動する。送信プロセスは `python3 <コピー>/hooks/_sender.py` を同期で起動する（hook からの起動は切り離されて待てないため）。4 だけは hook から送信プロセスを起動させる
- spool のファイルは人工的に作る。名前は実装と同じ `<epoch>-<uuid4hex>.jsonl`、行は契約の形の event 行（`session_id` に場面とファイル番号を入れ、到達を数える印にする）。大きさを揃えるため契約外のキー `uc47_pad` を足す（サーバは黙って捨てる）
- サーバは `e2e/_server.py` の `DockerServer`（本番に近い形・SQLite）。到達は DB の `events` を `session_id` ごとに数えて、残ったファイル・消えたファイルと突き合わせる
- 413 は Docker のサーバでは起こせないので、ローカルの小さなスタブ（全要求に 413 を返す `http.server`）で送信プロセスの振る舞いだけを見る
- 接続できない送信先は、閉じた 127.0.0.1 のポート

## 負荷の掛け方

- 容量: 1 MB × 8 ファイル（合計 8 MB）、単独 12 MB・50 MB のファイル
- 日数: 0〜13 日前の 14 ファイル
- 件数: 小さなファイル 0・1,000・10,000・30,000 個（合計は 5 MB 未満）で hook と送信プロセスの時間を測る
- 最大のデータは 50 MB 程度。数百 MB に届かないので `heavy.lock` は取らない

## 結果

測定条件: macOS（Apple M2・8 コア・8 GiB）。サーバは Colima（2 CPU・3 GiB）上の `e2e/_server.py` と同じ形（`python:3.9-slim` + entry.sh + waitress 3.0.2 + BASE_PATH、SQLite）。
hook と送信プロセスはホストの `python3`（pyenv 3.13.2。5 だけ Apple の 3.9.6 も）。時間は 1〜10 回の測定で、相対値としてだけ使う。
ほかのトラックの E2E が同じ Mac で並行して動いていた（時間の揺れの原因になりうる）。

**判定: 仮説はすべて実物で成り立った。**ただし、上限での破棄が何も記録されないこと、413 を返す前段があると無言で詰まる場合があることなど、運用で気づけない穴が確かめられた。

### 1. 容量の上限での破棄（送信先は閉じたポート → 後から Docker のサーバ）

1,048,762 バイトのファイル 9 個（`f0`〜`f7` は mtime が 0.8〜0.1 日前、`fx` は**名前の epoch が最新で mtime が最古**の 0.9 日前）と、hook が積んだ `queue.jsonl` の 1 行（`q`）。

| 段 | 結果 |
| --- | --- |
| 送信プロセス 1 回（接続できない） | `queue.jsonl` は spool に退避された。`fx`・`f0`〜`f3` の 5 個が消え、`f4`〜`f7`・`q` が残った（合計 4.2 MB） |
| 消す順 | **mtime の古い順**（名前が最新の `fx` が最初に消えた）。ファイル単位で、合計が 5 MB 以下になった時点で止まる（消しすぎも無い） |
| 記録 | **error 行は 0 件。**破棄はどこにも記録されない（接続失敗も記録されない。UC50 と同じ） |
| 送信先を Docker に向けて送信プロセス 1 回 | 残った 5 個の全行（2,123 行 × 4 + 1 行）が届き、消えた 5 個は 0 行。spool は空になった |

### 2. 単独で上限を超える 1 ファイル

| 場面 | 結果 |
| --- | --- |
| サーバに届く・12 MB（25,267 行）＋ 0.1 MB | 1 回の送信プロセスで両方届いた。送信プロセス 2.0 秒。応答は 2xx（413 は出ない）。spool は空 |
| サーバに届く・50 MB（105,068 行） | 全行届いた。送信プロセス 7.8 秒（`timeout_sec` 60 秒に対して）。spool は空 |
| 接続できない・12 MB | **一度も送られずに消えた**（送信が 1 ファイル目で打ち切られ、直後の `prune` が上限超えのファイルを消す）。error 行 0 件 |
| スタブが本文を読んでから 413（12 MB が古く、2 MB が新しい） | 1 回目: 2 本とも POST され、`send`/`HTTP 413` の error 行が 2 行。12 MB は直後の `prune` で消え、2 MB は残った。2・3 回目: 2 MB と error 行のファイルを毎回送り直し、毎回 413・error 行が増えた（スタブは全要求に 413 を返すので、error 行も届かない） |
| スタブが本文を読まずに 413 を返して閉じる（前段のプロキシの模擬） | 1 回目: 12 MB の送信が接続の切断で失敗し、**error 行 0 件**。打ち切られ、`prune` で 12 MB が消えた。2・3 回目: 2 MB も同様に毎回無言で失敗し、その後ろのファイルは送られない（先頭で詰まる） |

サーバ（waitress の既定の本文上限 1 GiB、アプリに `MAX_CONTENT_LENGTH` 無し）は 50 MB でも 2xx で受けた。`errors` テーブルにも何も入らなかった。

### 3. 長期オフライン（mtime を 0.5〜13.5 日前にずらした 50 KB × 14 個、7 日の境界の前後 2 分に 1 個ずつ）

| 場面 | 結果 |
| --- | --- |
| 端末自体が止まっていた（送信プロセスが一度も走っていない）→ 復帰後の最初の送信プロセスでサーバに届く | **16 個すべて届いた**（7 日超の 8 個も）。送信が `prune` より先に走るため |
| 端末は動いていてサーバに届かなかった（送信プロセスを接続できない送信先で 1 回）→ 復帰 | 7 日超（`d07`〜`d13`・境界の 2 分後）が消え、7 日以内（`d00`〜`d06`・境界の 2 分前）の 8 個だけが届いた。error 行 0 件 |

日数の判定はファイルの mtime（最後に追記した時刻。`rename` で変わらない）で行い、行の `ts` は見ない。サーバは古い `ts` の行もそのまま保存した。

### 4. No.42 送信先が空の版（`ingest_url: ""`）→ 送信先を入れた版

同じ `CLAUDE_PLUGIN_DATA` で、`PostToolUse` × 3 と `Stop` を 1 期間として 5 期間。期間ごとに `sent_at` を消し、`Stop` の hook が送信プロセスを切り離して起動するようにした。前もって 10 日前の 50 KB と 1 日前の 6 MB のファイルを置いた。

| 段 | 結果 |
| --- | --- |
| 送信先が空の間の hook | 常に exit 0・出力なし。行は積まれ、送信プロセスが起動し、`queue.jsonl` を spool に退避した（期間ごとに 1 ファイル） |
| 送信先が空の間の送信プロセス | POST しない（サーバの DB に `s4-` の行は 0 件）。**破棄は行う**: 10 日前のファイル（日数）と 6 MB のファイル（容量）が 1 期間目で消えた。error 行 0 件 |
| 送信先を入れた版に上げた後の最初の `Stop` | 5 期間の全行（各 4 行）と新しい 1 行が届き、spool は空になった。消えた 2 ファイルは届かない |
| （補足）`config.json` が無い版 | 送信プロセスは起動するが、何もせずに終わる（`_load_config` が None）。**`queue.jsonl` が退避も破棄もされず増え続けた**（3 期間で 2 → 4 → 6 行）。壊れた `config.json` も同じ経路（コードからの推定。実行は無い版だけ） |

つまり「送信先を空にした版」で止めている間に失われるのは、**7 日より前の分と、合計 5 MB を超えた古い分**。再開後に届くのは、再開時点で 7 日以内かつ新しい方から 5 MB 以内の分だけ。

### 5. 処理時間（ミリ秒。中央値 [最小〜最大]、hook は 10 回、`Stop_due` は 5 回、送信プロセスは 3 回）

spool は約 150 バイトのファイルを N 個（合計は 5 MB 未満）。送信先は閉じたポート（送信プロセスは 1 ファイル目で打ち切り、`prune` は全ファイルを stat する）。

| python3 | spool のファイル数 | `PostToolUse` | `Stop`（送信しない） | `Stop`（送信プロセスを起動） | 送信プロセス（同期） |
| --- | --- | --- | --- | --- | --- |
| pyenv 3.13.2（実体を直接） | 0 | 62 [60〜72] | 65 | 125 | 129 |
| 〃 | 1,000 | 61 | 62 | 145 | 158 |
| 〃 | 10,000 | 73 | 73 | 135 | 435 |
| 〃 | 30,000 | 90 [78〜135] | 85 | 153 | 1,297 [1,154〜2,250] |
| Apple 3.9.6（`/usr/bin/python3`） | 0 | 101 | 114 | 150 | 140 |
| 〃 | 30,000 | 110 | 99 | 155 | 774 |
| pyenv の shim（`python3`） | 0〜30,000 | 474〜705（最大 1,393） | 457〜760 | 584〜846 | 615〜1,629 |

- **hook の時間は spool の大きさでほぼ変わらない**（Apple 3.9 では差が無い。pyenv 3.13 の 30,000 個で +28 ms は、並行する負荷による揺れか、ディレクトリの大きさの影響かを切り分けていない）。`queue.jsonl` が 50 MB でも `PostToolUse` は 74 ms（3.13）・95 ms（3.9）
- **送信プロセスの時間はファイル数にほぼ比例する**（3.13 で 30,000 個 1.3 秒）。切り離して動くので hook は待たない
- **`python3` が pyenv の shim だと、hook 1 回が 0.5〜0.7 秒（最大 1.4 秒）かかる。**spool の影響より 1 桁大きい。hook の timeout 5 秒には届かないが、ツール 1 回ごとに払う

### 判定がゲートしていることの確認

- `run.py` の `selftest()`: 容量の判定（古い順の接頭辞・上限以下・消しすぎ）と日数の判定に、わざと壊した結果（新しい順に消した・消し足りない・消しすぎ・全部残した・全部消した）を与え、食い違いを返すことを確かめる（実行のたびに先に走る）
- 実装を壊した版での確認: プラグインのコピーの `_spool.prune` を (a) 新しい順に消す (b) 日数の上限を 2 倍にする、に書き換えて同じ場面を流し、判定がそれぞれ「古い順の接頭辞でない」「8 個の扱いが日数の規則と違う」で**落ちた**
- 到達の判定は、消えたファイルの印が DB に 0 行、残ったファイルの印がファイルの行数と一致、の両向きで見た

## 想定外だったこと

- **前段が本文を読まずに 413 で切ると、端末は何も記録せず、そのファイルで毎回打ち切られる**（`_post_file` は `OSError` を「届かなかった」として扱い、error 行を積まない）。
  5 MB 以下のファイルなら 7 日間、その後ろの新しいファイルも一緒に止まる（送信は名前の古い順で、先頭の失敗で打ち切るため）。AIP の前段に本文の上限があるかは確かめていない（推測。本番の環境が要る）
- 送信先が空のときに error 行もログも出ないので、止めている間に失われた量を管理者は知る手段が無い
- `config.json` が無い・壊れた版では、上限が効かず `queue.jsonl` が増え続ける（コードのコメント「送信先が空でも退避と破棄は行う。行わないと queue.jsonl が上限なしに増える」の意図が、設定を読めない場合には守られていない）
- 送る順（名前）と消す順（mtime）の基準が違う。今の実装では名前の epoch と mtime はほぼ同じ時刻になるので実害は見つけていない
- pyenv の shim の起動の遅さ（hook 1 回 0.5 秒超）。利用者の `python3` が shim の端末は多いと思われる（推測）

## 課題と改善案

### 端末側の修正案（本物に入れるべきか: 設計判断として提案）

1. **破棄を記録する（P1 寄り）**: `_spool.prune` が消したファイル数（と行数）を返し、`_sender.run` が `append_error("prune", "age"|"size", None)` のような固定値の error 行を積む。
   件数を載せる列は契約に無いので、まずは「消したことがある」だけでも概況の失敗の表に出る。No.42 で止めていた間の損失、長期オフラインの損失が管理画面で見える。
   `tests/plugin/client/test_sender.py` に「上限超えで消したら error 行が 1 行積まれる」を足し、記録を外すと落ちることを確かめる
2. **接続の切断・タイムアウトも区別して記録する**: 今は `URLError`（SSL 以外）と `OSError` を無言にしている。UC50 の「接続失敗は無言」と同じ根。
   少なくとも「本文を送っている途中の切断（`BrokenPipeError`・`ConnectionResetError`）」は前段の拒否の疑いがあるので、例外クラス名で error 行にする（毎回積むと増えるので、同じ段・同じ種類は `sent_at` の周期に 1 行で足りる）
3. **大きなファイルを分けて送る**: 1 ファイルを N 行（例: 1 MB）ごとの POST に分ける。前段の本文上限と `timeout_sec` の両方に効く。
   分けるなら、途中まで届いたファイルの扱い（届いた行を消して書き直すか、サーバの重複排除に任せるか）を決める必要がある（UC46 の重複の結果と合わせて判断）
4. **`config.json` が読めないときも `rotate` と `prune` を既定値で行う**（`_DEFAULT_CONFIG` の上限を使い、POST だけしない）。`tests/` に「config.json が無くても 7 日超のファイルが消える」を足す
5. 名前と mtime の基準を揃える（どちらかに統一。実害は見つけていないので優先度は低い）

### サーバ側

- `MAX_CONTENT_LENGTH` を設ける案（UC39 の改善案 5）は、端末が上限超えのファイルを分けて送らない限り、**単独で大きいファイルの行を失わせる**。
  入れるなら端末の分割（端末側 3）を先に入れる。上限の値は端末の 1 リクエストの最大より大きくする

### `e2e/` の追加・修正

- E2E に昇格させる候補は 1 本だけ: 「送信先が空の版で積み → 送信先を入れた版に上げ → 積んだ分が届く」（No.42）。hook を直接起動すれば認証も実セッションも要らず、共有の `server` fixture で十数秒以内に終わる見込み（hook 21 回の起動が主。この UC では個別に計っていない）。
  上限の破棄と日数は `tests/`（`test_spool.py`・`test_sender.py`）が境界値を見ており、E2E で繰り返す価値は低い
- `e2e/` の部品として、`harness.py` の `Box`（プラグインのコピー + `CLAUDE_PLUGIN_DATA` + hook・送信プロセスの直接起動）に当たるものがあると、実セッションなしで端末側の経路を安く通せる。今の `_root.py` は `claude` の起動が前提

### `docs/guide/e2e.md` の修正

- 「実物でも確かめられない限界」に書く: spool の上限（容量・日数）での破棄は E2E では見ない（`tests/` が見る）。破棄は記録されないので、実物でも「消えたこと」はファイルの有無でしか分からない
- hook の時間を測るときは、`python3` が何に解決されるか（pyenv の shim か）を条件に書く。shim だと 1 回 0.5 秒上乗せされる

### e2e スキルの拡張

- 「端末の状態を直接作る」枝: spool のファイルを人工的に作る（名前 `<epoch>-<uuid4hex>.jsonl`・mtime を `os.utime` でずらす）、送信プロセスを同期で起動する、印（`session_id`）で到達を数える、の雛形としてこのフォルダの `harness.py`・`run.py` を示す
- 前段の拒否を模すスタブ（本文を読んで 413／読まずに切る）の 2 種を雛形にする。両者で端末の記録が変わる

### `docs/knowledge/` に足す外界の事実（実測）

- waitress 3.0.2 + Flask（`MAX_CONTENT_LENGTH` 無し）は 50 MB の NDJSON 本文を 2xx で受けた（Colima 2 CPU・3 GiB・SQLite で 10 万行を約 8 秒）
- Python の `urllib` は、サーバが本文を読まずに応答して接続を閉じると、`HTTPError`（413）ではなく接続の切断（`OSError` 派生）を受け取ることがある（Python 3.13.2・12 MB と 2 MB の本文で再現。ローカルのスタブでの結果で、実際のプロキシの振る舞いは未確認）
